写对话用大白话是对的, 但**进项目写代码注释时不能切换模式**。我之前在 LP 脚本里加的注释:

```
# 外部源 (External source, 真·从基地外部进入物流网络的物品):
# 1. 协议核心 (sp_hub) 的 protocolHubOutputs — 显式声明的外部输入
# 2. 出货口 (unloader) 拉的物品中, "没有任何 recipe 能产" 的那些 —
#    代表游戏走默认区域物流从外部矿点自动送入 (源石矿/铁矿等)
#
# 关键修正 (2026-05-13): 之前把所有 unloader 都当外部源是错的。
# 出货口/装货口本质是 "协议网络的取出/存入端", 是基地内部 routing,
# ...
```

用户原话: "你注释的很不好, 我发现你很不会注释或者说一进去项目就不会说人话了, 这个时候加注释反而更奇怪了"

**Why:** 大段+多括号+英中混注+年代戳+论文摘要式 "关键修正:..." 在代码里读起来碍眼,
像论文片段被塞进了代码块。对话里我能说人话, 但碰到代码就启动了"工程化严谨"模板,
两种语气割裂, 注释反而比没注释更扰乱阅读。这种长注释属于 commit message / PR
description, 不属于代码本体。

**How to apply:**
- 默认**不写**注释。代码意图能从命名+结构看出来就不解释。
- 只在 "未来读者会卡住的 why" 写一句, 用对话里同样的人话语气 — 例如:
  - `# 只有矿石走区域物流外部送, 其他物品都是内部循环` ← 短, 人话
  - 不写 `# 关键修正 (日期): 之前 X, 是因为 Y, 这次改 Z, 原理是...` ← 学术段
- 不要在注释里塞日期戳 `(2026-05-13)`, git blame 已经记了
- 不要中英括号互注 `routing (路由)` `external source (外部源)` — 选一种语言一致写
- 不要写多段+多级标号注释, 那是文档不是注释
- 不要在注释里 "解释自己为什么这么改" — 那是 commit message 的活
- 写完看一眼: 这段注释如果删了, 后来人会不会卡? 不卡就删
- 跟 [[lazy-mode]] 同源 — 心智成本要低; 大块注释 = 多余心智成本
