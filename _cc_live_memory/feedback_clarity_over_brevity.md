**沟通规则: 清晰 > 简短**.

**Why**: 2026-05-16 D step 2 trial 完成后做汇报 + 列选择, 第一版用了术语
("hint" "UNKNOWN" "FEASIBLE" "master.solve" "candidate" "ghost rect" 等)
但只解释了**字面意思**, 没展开**为什么这样设计**. 用户直接说"听不懂, 还
是不够人话, 或者说还是用术语省略了很多逻辑".

第二版重写: 把每个术语展开成**场景描述** + **为什么这样选** + **如果选了
会发生啥**. 用户说"这次说的就很详细而且最重要的是很清晰了, 清晰在我们这
个项目里是最重要的".

**How to apply**:
- 这个项目用户偏好 verbose + 场景化讲解 > 紧凑 bullet list. 跟 CLAUDE.md
  里"用大白话" 一致但更深一层 — 不只是中文表达, 是**把背景逻辑展开**.
- 列选择/方案的时候, 每条都写: **怎么做** (具体动作) + **为什么会有用**
  (内部机制) + **代价** + **风险**. 不能只 label 一个方案名让用户猜.
- 出现新术语第一次用一定要展开. 第二次可以缩写. "UNKNOWN" 第一次要解释
  成"求解器在限定时间内既没说'能塞下'也没说'不可能', 没结论" 而不是
  默认用户记得.
- 用 比喻/类比 帮直觉理解. 例如 hint = "别人告诉你答案在第 42 页, 但你
  还是要自己走完推理链验证".
- 表格里数字旁边补一句"这是啥"
- 不要"按 priority 分类" 然后用代号 (A/B/C/D), 除非每条都展开过具体内容
- 紧凑型回复 (≤200 词) 只适合**纯技术问题** (具体 commit / 数字 / 命令).
  涉及决策/选择/方向时**永远展开**.

**反例 (don't do)**:
- "5/5 candidates UNKNOWN, master.solve 解不动" — 没解释 UNKNOWN 是啥,
  没解释为啥 master 解不动是问题
- "A. 加 master_seconds; B. hard constraint" — 没展开机制和代价
- "选 hint 注入还是 hard constraint?" — 没解释两者差别

**正例 (do)**:
- "UNKNOWN 是求解器既没说'能'也没说'不可能', 它还得回头再花时间收掉"
- "把 hint 升级成硬约束 = 强制 master 按 blueprint 摆 225 个, 它只需要
  解剩下 41 个 + 凑空矩形. 搜索空间断崖式下降. 但破坏'全局最优'证明"

**反思**: 之前 memory 里 [[directly-state-core-finding]] 说"第
一句给结论" 是正确的, 但跟这条不冲突 — 结论先讲, **然后展开**. 不是
"结论 + 列代号" 让用户问"那 A 到底是啥".
