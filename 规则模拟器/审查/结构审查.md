# 规则模拟器结构审查

范围：`规则模拟器/src/` 全部 13 个文件、`tests/legal_base.rs`、`Cargo.toml`。只看三条做法要求：不吞没想到的情况、状态只存规范量、回放专用项用类型和模块隔开。另外看有没有多余的层。逐步行为对不对不在本审查范围内。没有改代码，也没有提交。

## 结论

三条要求大体做到了。全库没有 `unwrap_or`、`unwrap_or_default`、`Default`、`unwrap()`。缺省值只在「表里没有这一行或这个子键」时给出，最后还核对每张表是否剩下域外键。状态表示和 Lean 的 `各格合规矩` 一一对得上。两样回放专用的东西（`waiting`、`ReplayRule`/`OldRule`）都是 `oracle` 模块的私有项，正式入口 `LegalBase` 拿不到它们。

真正的隐患有三处，按严重程度排：

1. 正式入口把「组没有级别」悄悄当成「不入表」。在合法基地上这种情况不该出现，出现了也不报错（发现 1）。
2. release 构建没开溢出检查。验收跑的是 release，不变量一旦被破坏，减法会静默回绕（发现 2）。
3. 输出行里对象键的先后依赖 serde_json 没开 `preserve_order`。我在草稿目录里开了这个特性重编，黄金输出逐字节变了，程序自己的「期望」核对却仍然通过（发现 3，已实测）。

其余是小的结构改进。

## 写得好的地方（后续修改请保留）

- **缺省值只给不存在的行。** `snapshot.rs` 的 `row`/`part`（48–59 行）只在键不存在时给缺省值；值写错了照样报错。246–264 行最后统一检查十二张表有没有剩下没认领的键。这样「找不到就跳过」的口子被堵住了：给错种类的单位写开关，或者给箱子写 `["存货",0]`，都会报错。
- **解码后反向编码核对。** `json.rs` 的 `decode`（9–15 行）解码后再编码回去，和原值比较。多余字段、类型被悄悄转换这类问题都会被拦下。
- **`Kind` 的四个方法都穷举了全部变体，没有通配分支。** 它们是 `model.rs` 79–116 行的 `ports`、`stock_slots`、`transport`、`outlets`。新增种类时编译器会逐处提醒。
- **状态的形状。**
  - 运输格是 `Option<Load{item, stopped, from}>`（`state.rs` 61–65 行、`Body::Transport` 95–98 行），正是要求里举的那种写法。
  - 制造缓存是 `Batch::{Idle, Running(&Recipe, Nat), Finished(Stack)}`（71–75 行），和 Lean `物品格的规矩.lean` 的 `各格合规矩` 逐条对应：制造中时缓存恰为配方用量，空闲时缓存为空或恰为一批产物。缓存里的货因此没有另存一份。
  - `Filter::{Open, Item(..)}`（6–27 行）从类型上排除了「没设放行物品却设了上限」。
  - 开关只存在于 `Machine` 和 `BoxState` 里，不是一张独立的表。
  - `BoxState` 里仓储模式和冷却是两个独立字段。黄金里确实有 `{"仓储模式":true,"冷却还剩":38}`，所以这样存不会拼出非法组合。
- **不变量写成断言，不会默默继续。** 例如 `Gate::received` 的 `assert!(count < limit)`（`state.rs` 52 行），`Machine::start` 断言至多一条配方合用（192–195 行）。
- **段内操作先校验后改动。** `action.rs` 55–183 行：`Switch` 先整列核对再改（98–104 行），`Offline` 先重建判定表再替换。失败时状态不动，`tests/legal_base.rs` 有这条回归测试。
- **隔离做得对。**
  - `Parameters`（`model.rs` 247–253 行）不含「输入判定都没货时」字段。
  - `LegalBase` 固定传 `step::Twice`（`lib.rs` 43 行）。
  - `waiting`、`ReplayRule`、`OldRule`、`Selection` 都是 `oracle.rs` 的私有项。
  - Lean 解码器的怪癖（单键构造子 `tag`、离线历史里的 `offline_kind`）只放在 `oracle/input.rs`。正式入口收的是已经类型化的 `Event`/`Action`。
- **两处看着像吞掉、其实对得上的地方。**
  - `Nat::at_most` 在 `index()` 为 `None` 时取上界（`nat.rs` 64–69 行）。`Nat` 只存十进制数字，`None` 只可能是超出 `usize`，所以取上界就是正确的 `min`。
  - `move_one` 找不到通道位置就不写进货下标（`movement.rs` 176–178 行），对应 Lean `物品格.lean` 157 行的 `if L.算进货 c then … else s.进货上次`。

## 发现

### 1. 正式入口把「组没有级别」悄悄丢掉（吞掉没想到的情况）

- **位置**：`lib.rs` 30 行 `Tables::build(h, |_, _| None)`；`topology.rs` 240–243 行（`rank` 走不到终点时调 `missing`）、245–271 行（`level` 里的各个 `?`）、299–302 行（`filter_map` 丢掉没有级别的组）。
- **问题**：Lean 里「无级别的组不入表」是回放要用的语义，所以 `Tables::build` 照做。但在合法基地上它不该发生：
  - `走得通` 保证每个连着通道的运输单位都有运输带，`rank` 永远走不到 `missing`。
  - `命题.lean` 的 `末端元件有终点`、`同组次序相同` 两条（前提都是端口数合）保证元件组的次序都存在且相等。
  正式入口传 `|_, _| None`，又对 `level` 返回 `None` 不作任何检查。如果 `legal()` 的实现有漏洞，或者以后改拓扑时引入错误，某个组就会从判定表里消失：它的通道永远不动货，程序也不报错。求解器拿这个当规则模拟器时，只会看到产量偏低。
- **改法**：让 `Tables::build` 额外返回被丢掉的组（或者每条非带内通道是否都进了 `elements`/`facilities`），由调用方决定怎么处理。`LegalBase::tables` 遇到非空就返回 `Err`，回放入口照旧接受。`LegalBase` 的 `missing` 改成 `|_, e| unreachable!("合法基地上 {e} 必有运输带")`，把「这里不该走到」写进代码。

### 2. release 构建没开溢出检查，不变量破了会静默回绕（吞掉没想到的情况）

- **位置**：`Cargo.toml` 没有 `[profile.release]`。可能下溢的地方有：
  - `state.rs` 151 行 `*count -= n`
  - `movement.rs` 123 行 `self.warehouse[..] -= 1`
  - `step.rs` 135 行 `80000 - *stored`
  - `action.rs` 152 行 `80000 - *stored`
- **问题**：这些减法都靠不变量保证不下溢，比如取货前已经核过有货、仓库不超过 80000。`验收/common.py` 14 行和交付报告的命令都用 `--release`，而 release 默认关闭溢出检查。不变量一旦被破坏，`usize` 会回绕成巨大的数并继续运行，正好是「越界时取余」那一类。debug 下会 panic，所以单测发现不了这个差别。
- **改法**：在 `Cargo.toml` 加 `[profile.release] overflow-checks = true`。这一版不求速度，代价可以接受。也可以把这几处改成 `checked_sub(..).expect("…")`，不过加配置项最省事、最全。

### 3. 输出的对象键先后依赖 serde_json 的特性开关，程序内的期望核对也看不出来（吞掉没想到的情况，已实测）

- **位置**：
  - `snapshot.rs` 302 行准入口对象按 `放行, 累计上限, 每5tick上限, 累计已收, 名额, 拍` 写出。
  - 345 行 `json!([r, t])` 把 `Recipe` 按声明顺序 `单位, 原料, 产物, 时长` 转成对象。
  - 368–372 行 `Map` 收集顶层对象。
  - `oracle.rs` 131 行用 `Value` 相等核对期望。
- **问题**：规格书要求键按 UTF-8 字典序输出。现在靠 serde_json 默认的 `BTreeMap` 碰巧排好了序。只要依赖图里任何一个包打开 serde_json 的 `preserve_order`，`Map` 就变成按插入顺序，所有对象都按写入顺序输出。这个包以后要被求解器依赖，Cargo 的特性合并会让这件事随时可能发生。
- **实测**：把 `src/`、`Cargo.toml` 复制到草稿目录，只给 serde_json 加上 `preserve_order` 后重编。`准入口周期.json` 的 332 行输出里有 323 行和原构建不同，`缓存格.json` 的 177 行里有 174 行不同。两份都以 0 退出，因为 `oracle.rs` 131 行的 `Value` 比较不看键序，段内的「期望」核对照样通过。只有 `验收/golden.py` 的逐字节比较能发现。
- **改法**：
  - 输出时不依赖 `Map` 的实现：快照的对象一律按键的字典序插入，例如准入口写成 `名额, 拍, 放行, 每5tick上限, 累计上限, 累计已收`；配方对象不走 `json!(r)`，改为按 `产物, 原料, 单位, 时长` 显式构造。这样两种 `Map` 输出相同。
  - 或者在输出前把整行规范化成字节，期望也比较字节。
  - 加一条单测：断言一行带准入口和制造中的快照序列化后，各对象的键严格递增。

### 4. 回放的「每步判两次」走的不是正式入口那份代码（回放专用项没隔开）

- **位置**：`oracle.rs` 16–19 行 `ReplayRule::Current`、42–64 行 `impl MergerRule for ReplayRule`、143–146 行；`lib.rs` 40–44 行；`step.rs` 13–22 行 `Twice`。
- **问题**：`ReplayRule` 把现行规则和四种旧说法放在同一个运行时枚举里，`Current` 分支再委托给 `Twice.accepts`。后果是黄金和随机对拍跑的「每步判两次」，实际是 `step::<ReplayRule>`：每次判定都多算一个 `Selection.first`，再走一层 `match self`。正式入口跑的是 `step::<Twice>`，这个单态化版本只有 `tests/legal_base.rs` 的三项测试覆盖。现行规则在回放里也带着旧说法的分支，这是本该删掉的那种运行时开关。
- **改法**：`oracle` 读到 `每步判两次` 时直接用 `Twice`，其余四种用 `OldRule` 自己实现 `MergerRule`（Decision 为 `Selection`）。走步处写成 `match rule { Current => step(&Twice), Old(r) => step(&r) }`。`ReplayRule::accepts` 里的 `Current` 分支随之删掉，回放的现行规则和正式入口就是同一份单态化代码，对拍的覆盖也就落在正式路径上。

### 5. 段首装状态时先按「是否运输单位」分开，再用通配分支兜底（吞掉没想到的情况，轻）

- **位置**：`snapshot.rs` 165–181 行（`kind.transport()` 分支里 `_ => Err("未处理的运输种类")`）、183–230 行（`k if k.stock_slots() > 0` 守卫加 `_ => Err("未处理的非运输种类")`）。
- **问题**：这两处虽然会报错，但把「新增一种单位」从编译期的穷举检查推迟到了运行期，而且只在输入里真有这种单位时才报。`Kind` 的方法都是穷举写法，这里不一致。Lean 的 `各格合规矩` 本身就是对种类的一次穷举匹配。
- **改法**：改成对 `kind` 的一次穷举 `match`，17 个变体按 `传送带|汇流器|桥接器格`、`分流器`、`物品准入口`、`协议储存箱`、`协议核心|仓库取货口`、九个机种分组写全，删掉两个通配分支。

### 6. 协议核心和仓库取货口共用一种设施，`destination` 只好另外传种类（状态能拼出非法组合，轻）

- **位置**：`state.rs` 92 行 `WarehousePorts(Vec<Option<Item>>)`；`movement.rs` 50 行（签名里的 `k: Kind`）、81–83 行、149 行；`action.rs` 107–116 行。
- **问题**：
  - 同一个单位是核心还是取货口，一半信息在 `Body`，另一半要回头查 `layout.kinds`。`move_one` 和 `Put` 都得先查一次种类再传进来。
  - `Vec` 的长度应该是 6 或 1，现在只靠构造时保证。如果有人构造出长度为 1 的协议核心，类型系统拦不住。
- **改法**：拆成 `Facility::Core([Option<Item>; 6])` 和 `Facility::Pickup(Option<Item>)`。`destination(u, x)` 就不再需要 `k`，`Put` 的前置条件可以直接看 `body` 是不是 `Box`/`Machine`。快照和 `Target` 各多一个分支，`destination` 的签名和两处调用变简单，长度不变量也写进了类型。收益不大，可以留到下一次动这块时一起做。

### 7. 正式参数的计数策略是不具名二元组（别的，轻）

- **位置**：`model.rs` 251–252 行 `on_change: (Counter, Counter)`、`on_offline: (Counter, Counter)`；用法见 `tests/legal_base.rs` 9–10 行。
- **问题**：这是求解器要直接填的公开类型。哪一项管 `累计已收`、哪一项管 `名额`，只能去看格式事实。两项类型相同，写反了编译器也不会提醒。
- **改法**：改成 `struct CounterPolicy { count: Counter, quotas: Counter }`。回放入口照旧从二元数组解码，在 `oracle.rs` 121–122 行转换一下即可。

### 8. 两处靠枚举声明顺序决定输出顺序，没有核对（别的，轻）

- **位置**：`model.rs` 35–55 行 `ITEMS` 和 `Item` 的声明各写了一遍；`model.rs` 185–191 行 `Slot` 派生 `Ord`。
- **问题**：
  - `仓库` 表的段首键序核对用 `Item` 派生的 `Ord`，输出顺序却按 `ITEMS` 数组走，`warehouse[x as usize]` 又用判别值当下标。三者现在一致。将来只要改了其中一份，输入接受的顺序就会和输出顺序不一样，而且不会报错。
  - `Slot` 的 `Grid < Stock < Output < Cache` 正好满足格式事实要求的「存货、取货、缓存」顺序，代码里没有注释说明这是有意的。
- **改法**：加一条 `const` 断言或单测，检查 `ITEMS[i] as usize == i` 且 `ITEMS` 严格递增；在 `Slot` 声明处注明变体顺序就是规范格位顺序，不能调换。

### 9. 布局里同一组单位存了两份（多余，轻）

- **位置**：`topology.rs` 6–10 行 `kinds: BTreeMap<Id, Kind>` 和 `built: Vec<Id>`。
- **问题**：Lean 只有一张按建成先后排的 `单位表`。这里的两份由 `apply` 的 `Build`/`Remove` 分支同步维护（37–45、61–64 行），以后有人只改其中一份就会不一致。这是布局，不是走步状态，所以风险低。
- **改法**：存成一个 `Vec<(Id, Kind)>`，另写一个查种类的方法；这一版不求速度，线性查找也行。或者保留现状，但给 `Layout` 加一个 `debug_assert`，检查 `built` 和 `kinds` 的键集合相同。

## 看过、认为不必改的

- **`Tables::build` 的 `missing` 闭包和 `step::MergerRule` 两个钩子。** 它们是用类型隔离回放项的最小写法。删掉就得把 `待接箱的次序` 或旧说法写回核心模块，复杂度只是挪了地方。
- **`Simulation` 的字段对 crate 内公开，两个入口各自每次传 `Self::tables`。** 两处都是私有包装，不会混用。改成类型参数只是把同样的东西挪进泛型。
- **`movement.rs` 118、142 行、`action.rs` 143 行的通配分支都 panic 或报错，不放行。** `Collect` 把不能收的格合并成一条错误，符合 Lean 的前置条件。
- **`Nat` 用十进制字符串表示。** 这是为了在任意大的读数上和 Lean 一致，属于有意的取舍，不是多余的层。
- **`json.rs` 的手写数字和代理对处理只在 `json::parse` 里用到**（调用方只有 `oracle.rs` 163 行）。正式入口收的是 `Value`，走不到这段。以后可以挪进 `oracle` 模块，让核心不带文本格式的怪癖，但这不影响三条要求。
