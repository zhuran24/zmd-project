# 派证明的说明

这份是交给被派来证明的模型读的：任务书里给出它的路径，再写上分给它的命题、文件名和可以当假设用的命题。

## 这是什么

`/home/zhuran24/zmd-research-fresh/规则模型/` 是一个 Lean 4 工程（Lean v4.35.0，经 elan 装在 `~/.elan`，不依赖 Mathlib）。它把一款游戏里传送带、分流器、汇流器、制造单位这些东西每一步怎么运转的规则写成了一个状态机。规则原文是上一级目录的《明日方舟：终末地》游戏规则.txt，工程的做法写在 `规则模型/README.md`。标识符都是中文，写在 «» 里。

`Endfield/命题.lean` 列出了要证的命题，每条是一个 `def «名» : Prop := …`，文件开头讲了这些命题是怎么来的。你的任务是证其中指定的一条或几条。同一时间可能还有别的模型各证各的，每个只写自己的那一个文件。派任务的一方下面叫「主会话」。

## 文件

- 定义所在的文件，按依赖先后：`Endfield/` 下的 `计量与基础.lean`、`配方.lean`、`判定与轮询.lean`、`单位.lean`、`通道与移动.lean`、`拓扑与级别.lean`、`框架.lean`、`物品格.lean`、`判定.lean`、`走步不改历史.lean`、`作用.lean`、`合法基地.lean`、`物品格的规矩.lean`；格子层（单位的位置、朝向、端口，从位置算出建成、接通、拆除这些事）在 `Endfield/格子/` 下的 `几何与端口.lean`、`场地与建造.lean`、`供电与操作.lean`；最后是 `命题.lean`。
- `Endfield/证明/基础.lean`：几条共用的引理，都已证完，直接拿来用：时刻 t+1 的布局是时刻 t 的布局上发生一件事；每种事对单位的种类、通道表、出、进的影响；合规的历史上每一刻的布局都整齐；`最近一次变成` 给出的是怎样的一刻；端口数合时一个单位的通道不多于端口。
- `Endfield/证明/` 下别的文件是已经证完的别的命题，可以读来参考写法，但不要 import 它们。
- 你只新建、修改任务里指定给你的那一个文件。别的文件都不要改，包括 `命题.lean`、`基础.lean`（除非任务指定的就是它）、`Endfield.lean`、`lakefile.toml`。

## 你的文件要长什么样

- 开头只写一行 `import Endfield.«证明».«基础»`（它已经带进了全部定义和 `命题.lean`）。
- 主定理放在 `namespace Endfield.«证明»` 里，名字和类型在任务里给出，形如 `theorem «某命题» : «命题».«某命题» := by …`。任务里若列了「可以当假设用的命题」，把它们写成主定理的显式参数，例如 `theorem «甲» (h乙 : «命题».«乙») : «命题».«甲»`；主会话最后会用别人证出的定理把这些参数填上。任务里没列的假设不要加。
- 不许出现 `sorry`、`admit`、`axiom`、`native_decide`、`unsafe`、`partial`、`opaque`、`implemented_by`。`decide`、`omega`、`simp`、`grind` 这些策略都可以用。
- 辅助引理一律写成 `private theorem`／`private def`。工程有个核对脚本，要求每条非 private 的声明前有文档注释 `/-- … -/`，注释第一行以「据：」加规则文件里的名词（用顿号隔开）开头；private 的不查。主定理前的注释，第一行照抄 `命题.lean` 里那条命题注释的第一行，空一行以后用一两句中文说这条定理的意思。
- 文件开头在 import 之后写一段 `/-! … -/`：证的是哪条命题，证明的思路（几句话）。

## 怎么编译

```
export PATH="$HOME/.elan/bin:$PATH"
cd /home/zhuran24/zmd-research-fresh/规则模型
lake env lean Endfield/证明/<你的文件>.lean
```

没有任何输出就是通过。只用这条命令检查你自己的文件。不要运行 `lake build`：它会去编译别人写到一半的文件，还会和别人抢同一个构建目录。

Lean 自带库的源码在 `~/.elan/toolchains/leanprover--lean4---v4.35.0/src/lean/`，找现成的引理（`List.Perm`、`List.mergeSort`、`List.Pairwise`、`List.find?` 之类）可以在那里 grep。试验用的临时文件放在 `/tmp` 下你自己新建的目录里，不要放进工程。

## 命题不成立怎么办

新立的命题只在一些具体布局上用 `#eval` 试算过，没有证明过；陈述本身可能有错，或者少一条前提。证的过程中若发现命题不成立，或者缺一条前提就证不出：不要改 `命题.lean`，也不要改证一条弱一些的。找出具体反例（最好是一段能 `#eval` 的 Lean 代码，放进回报），或者写明卡在哪一步、缺的是哪条前提，然后停下。这个工程要找的就是规则没写清的地方，发现一处本身就是要的结果。

## 回报

最后的回复用中文，只写这几样，不用写过程：

1. 结果：证完／没证完／命题有问题；
2. 文件路径，主定理的完整签名（含用到的假设）；
3. 最后一次 `lake env lean` 的输出（通过时写「无输出」）；
4. 没证完的：卡在哪一步。命题有问题的：反例或缺的前提；
5. 主会话该知道的别的事（定义里可疑的地方、规则没写清的地方）。没有就不写这一项。
