## 一、 工程概况与当前规则基线

`/home/zhuran24/zmd-research-fresh/规则模型/` 是《明日方舟：终末地》游戏规则的 Lean 4 状态机工程（版本 `v4.35.0`，经 `elan` 装在 `~/.elan`，不依赖 Mathlib，中文标识符统一写在 `«…»` 内；工程整体设计与架构见 `规则模型/README.md`）。规则原文位于上一级目录的 `../《明日方舟：终末地》游戏规则.txt`。

- **注意走步顺序的现行代码口径**：涉及走步的证明一律以 `Endfield/判定.lean` 中的 `«一步于»` 为准——现行模型每步按规则正文「判定顺序」原六条的 **2、3、4、5、1、6** 执行，状态依次经过整理、元件移动判定、非运输单位移动判定、结束制造判定、开始制造判定、计时（两段移动中遍历到通往汇流器且起点不是分流器的通道时由 `«汇流器收»` 现算；按规则采用的 `每步判两次` 取值，元件移动阶段读取整理后的状态，非运输单位移动阶段读取元件移动结束后的状态；证明中能否使用这一取值以该命题的前提为准），而规则正文第 1 条目前尚未同步改字。
- **命题与证明现状**：`Endfield/命题.lean` 保存各条命题的陈述（形如 `def «名» : Prop := …`），该文件开头解释了为什么有些地方要证明结果不看先后或选择时不会并列；文件中还陈述了物品格规矩保持性、历史合规、格子层与里层同步等命题以及两条顶层命题。已有证明由 `Endfield/证明/总.lean` 汇总（命题清单与证明状态用 `python3 查证明.py` 查看）。受派席位只按任务书处理分给自己的指定命题；同一时间可能有其他席位并行写别的文件，每个席位只负责自己的那一个文件。

## 三、 证明文件写法要求

1. **首行导入与模块注释**：
   - 新建普通证明文件的第一行只写 `import Endfield.«证明».«基础»`（它已传递带入全部定义与 `Endfield/命题.lean`）；修订已有文件时保留该文件正在使用的模块导入（例如 `Endfield/证明/基础.lean` 首行导入 `Endfield.«命题»`，部分格子层证明导入 `格子重接` 或 `格子同步`）。
   - 在 `import` 之后写一段 `/-! … -/` 模块注释，用几句话交代本文件所证的命题和证明思路。
2. **主定理签名与假设参数**：
   - 主定理放在 `namespace Endfield.«证明»` 里，**名字和任务书指定的完整签名照写**：任务书列为「可当假设用的命题」全部保留为主定理的显式参数（即使证明体未用到其中某一条，也不要删去，以便主会话在 `Endfield/证明/总.lean` 中按统一签名传参）；任务书未列出的假设严禁私自添加。
   - **特别留意 Lean 标识符语法与首行注释**：Lean 不允许裸汉字出现在未加双角引号 `«` 和 `»` 的标识符中（例如写成 `(h乙 : …)` 会报语法错）；假设参数可写作 `hB`、`hstep`、`h2` 等，若名字含汉字则把整个名字写在 `«…»` 里（如 `«h乙»`，注意不是中文书名号 `《》`）。主定理前的文档注释第一行必须原样照抄 `Endfield/命题.lean` 中对应命题注释的第一行（不要在首行后额外添括号提示，否则 `查名词.py` 会把括号内容也当作规则名词切分报错），空一行后再用一两句中文说明定理含义：
     ```lean
     /-- 据：判定顺序、制造

     用一两句中文简述这条定理的含义。 -/
     theorem «某命题» (h2 : «命题».«乙») : «命题».«某命题» := by
       …
     ```
3. **辅助引理与文档注释检查**：
   - 普通派发证明中新写的辅助引理和辅助定义一律写成 `private theorem`／`private def`（修订已有文件时，保留其他模块已经引用的公开声明）。
   - 工程的 `查名词.py` 对 `Endfield/证明/` 下的 `private` 声明免查文档注释；主定理按上例原样照抄对应命题注释的第一行，其他由脚本检查的非 `private` 声明前也必须写 `/-- … -/` 文档注释（首行按 `查名词.py` 开头列出的七种格式选用）。
4. **禁用逃生口**：严禁出现 `sorry`、`admit`、`axiom`、`native_decide`、`unsafe`、`partial`、`opaque`、`implemented_by`。常规证明策略（`decide`、`omega`、`simp`、`grind` 等）均可正常使用。

## 四、 单文件编译检查

只用下面这条命令检查你负责的单个文件（**不要运行 `lake build`**，以免去编译别人尚未写完的文件，或与其他席位同时争抢同一个构建目录）：

```bash
export PATH="$HOME/.elan/bin:$PATH"
cd /home/zhuran24/zmd-research-fresh/规则模型
lake env lean Endfield/证明/<你的文件>.lean
```

没有任何输出且退出码为 0 即代表通过。查找与 `List.Perm`、`List.mergeSort`、`List.Pairwise`、`List.find?` 有关的标准库引理，可在 `~/.elan/toolchains/leanprover--lean4---v4.35.0/src/lean/` 下检索。试验用的临时草稿放在 `/tmp` 下你自己新建的子目录里，不要放进工程目录。

## 五、 命题不成立或缺前提时怎么办

新立的命题往往只在一些具体布局上用 `#eval` 试算过，尚未经过证明检验，陈述本身可能有错或少写了前提。如果在证明途中发现命题不成立，或者缺一条前提就证不出：
- **不要改 `Endfield/命题.lean`，也不要擅自改证一条更弱的命题**；
- 找出一个具体反例即可停手回报（最好是一段能用 `#eval` 跑出来的 Lean 代码，放进回报），或者写明卡在哪一步、具体缺哪条前提。这个工程要找的就是规则没写清的地方，发现一处本身就是要的结果。

## 六、 回报格式

最后的回复用中文，只写下面这几项，不用贴长篇试错过程：

1. **结果**：证完 ／ 没证完 ／ 命题有问题；
2. **文件与签名**：文件路径，以及主定理的完整签名（含用到的假设参数）；
3. **编译输出**：回报最后一次运行 `lake env lean` 的退出码和实际输出（确实没有任何输出时写「无输出」）；
4. **卡点或反例**（没证完或命题有问题时填）：没证完写卡在哪一步；命题有问题写具体反例或缺的前提；
5. **主会话该知道的别的事**（模型定义里可疑的地方、规则文件没写清的地方）：即使定理已经顺利证完，只要在证明时发现了这类问题也请写上；没有就不写这一项。
