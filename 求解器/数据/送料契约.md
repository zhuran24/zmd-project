# 送料契约

日期：2026-09-19。状态：第四轮目录全字段回源门禁已实现；feeding-v2 增加逐记录计划满速标记；候选 B 尚无几何或运行认证。

## 使用与证据范围

`候选B/contract.json` 是完整输入。`正式静态目录.json` 从三份正式文件转录完整原文、单位、配方、任务与约束，Rust 编译时内置；输入文件无权覆盖规则、端口容量、机型下限或成品目标。目录自身的 `version`、`transcribed_at`、`source_root`、`sources[].path/sha256/lines` 给出共享版本与三份正式来源；候选资产的额外指纹在 `候选B/来源清单.json`。规则依据仅为仓库根的《明日方舟：终末地》游戏规则、求解任务、求解约束；会议材料用于识别候选资产与未决义务。

在仓库根运行：

```bash
python -B 求解器/数据/工具/formal_catalog.py
CARGO_HOME="$PWD/求解器/.cargo-home" cargo test --locked --manifest-path 求解器/Cargo.toml
CARGO_HOME="$PWD/求解器/.cargo-home" cargo run --locked --manifest-path 求解器/Cargo.toml -p topology -- 求解器/数据/候选B/contract.json > 求解器/数据/候选B/校验报告.md
```

命令的依赖缓存、构建产物和报告均在求解器内。程序标准输出为 Markdown 报告；退出码 `0` 表示可检查项通过，`1` 表示至少一项检查失败，`2` 表示加载或命令行错误（以上为接口编码，非游戏数值）。未知项不改变退出码，故成功退出不能用于运行验收。

当前 CLI 同时运行候选 B 的交接数字回归，其他候选须另立回归入口；此程序不是通用布局认证器。

检查器对每条正式约束列出未覆盖部分，同时对可计算的投影给出逐项结果。同一条约束可以既有通过的计数投影，又有不能静态检的运行部分；这不是对完整条文同时给相反结论。例如研磨进料的端口计数可检，真实到货时序不可检。报告结论均以输入计划成立为条件。不会把计划满速当成实际满速，不证明可嵌入性、调试可达性、活性或全部可达循环态达标。

## 数值与空值约定

契约中的结构化物理数值使用 `Quantity = {"value":"分子/分母或整数", "category":"类别"}`，分母严格为正。运算使用任意精度整数构成的有理数，拒绝 JSON 浮点值与小数字符串；无需容差。类别枚举为「条文直引／算术推论／候选／启发式／实测」。标识符、版本号、哈希、命令退出码中的数字是编码，不是物理数值。

- 条文直引：正式文件明写的配方用量、耗时、容量、目标等；正式已采纳约束中的数字也属于此类。
- 算术推论：据正式数字运算所得值。若以候选为前提，结论仍须带该前提，不会升级为真实布局事实。
- 候选：待实现的计划、计数选择、速率、来源指派。本候选的速率窗口与平均批间隔也标为候选，即使换算精确。
- 启发式：估算或搜索偏好，不作必要性证据；本输入没有此类值。
- 实测：测得的量，不能仅凭类别升级为全称证书。本输入没有此类值。

`null` 表示尚未给出或不适用，含义由字段定义；不等于数值零。待验和待求是状态，不是失败判定。缺少必需的可空字段仍是加载错误。

## 逻辑送料记录表 logical_feeds

每条逻辑送料记录表示两个相邻非运输端点之间、尚待布线的送料需求。相邻指中途不得经过另一非运输单位；路径中的运输单位数量及几何均未知。每条专用路径在源端对应非运输→运输的一条实体通道，在目标端对应运输→非运输的一条实体通道。运输单位之间的实体通道数 E 未知；制造缓存内部通道另行建模。据：通道、缓存格、端口对接、运输端口收支。

| 字段 | 说明 |
|---|---|
| id | 逻辑送料记录唯一 id，使用 LF 前缀加原 C 编号的数字部分（如原 C109 → LF109）；同源同目标平行边不能合并 |
| source / target | 分别引用机器 id、来源变量 id 或核心 id；矿石来源仅作 source，核心仅作 target |
| source_recipe / target_recipe | 相应机器的计划配方 id；来源和核心处为 null |
| source_port / target_port | 稳定逻辑端口身份。`:out:`／`:in:` 后的序号是转换分配的标签，不是边上坐标或接通顺序 |
| item | 正式物品名称 |
| planned_rate | Quantity，件/tick；正值，代表计划平均通过量 |
| planned_full_speed | 必需布尔值；等于 planned_rate 与目录端口速率上限的比较结果；属于候选计划的算术标记，不是运行证书 |
| proven_actual_rate | 必需可空 Quantity；本步全部 null。当前校验器拒绝非空，因为尚无证书格式及证书验证程序 |
| via | 对象，bridge／splitter／merger／gate 仅对应桥接器／分流器／汇流器／准入口这四类运输单位；值为 null、true 或 false |

`via` 中某值为 null 表示该路径尚未落实该类运输元件，不等于没经过；全局 `planned_absent` 是明确的计划限制，它与 null 的局部几何占位同时存在。已填 true 不得违反全局排除。桥接器是否使用尚未知，不能写成零个桥接器。

同一对逻辑端口可以用多条记录表示不同物品或配方时段，端口负荷须合计后不超过容量。当前专用模型禁止同一端口连向不同端点，也禁止多个不同来源端点共用目标端口；需要那种结构时须换成含运输网络的新契约。S、R 按不同的端点端口计数，不能简单按记录行数计算一般混线表。

## 三种边与储存箱分段

| 对象 | 字段名／id 前缀 | 依据与用途 |
|---|---|---|
| 逻辑送料记录 | `logical_feeds`／`LF` | 契约的计划需求，非规则单位或规则通道；编号编码，无物理含义 |
| 端口相遇形成的实体通道 | `physical_channels`／`PC` | 规则 L16；至少一端是运输单位，实体布局可导出；不存进本版 contract.json |
| 制造缓存内部通道 | `buffer_channels`／`BC` | 规则 L18；存货格→缓存、缓存→取货格，不经端口；不存进本版 contract.json，不计 S/R/E |

表中三种字段名是交接命名约定；其中 PC、BC 留给布局／内核格式，不表示本契约已经提供这些实体。Rust 类型为 `LogicalFeed`，旧顶层 `channels` 与旧 C 前缀不被 feeding-v2 接受。原 CSV 的 `channels.csv` 和 C id 是来源标识，保持源文件原样。

协议储存箱属于仓储单位，是非运输单位；`via` 中禁止 `storage` 字段，连 `null` 或 `false` 也拒绝，防止旧格式被静默接受。`planned_absent` 中的 `storage` 仍表示本候选明确排除箱体，它不把箱体分类成运输单位。据：协议储存箱、运输单位、仓储单位。

若送料需经过箱体 X，应表示为两段：`A:out:a → X:in:i` 与 `X:out:o → B:in:b`，分别使用不同 LF id；X 必须有独立单位身份，两段中的箱端配方为 null。相对于无箱的 A→B，新增 X 的存货和取货接口，S、R 各增加 1；因此这两段独占路径共计 S=2、R=2（算术推论，前提：端口互异且均有正通过量）。多物品、多配方记录复用同一接口时，只按端点和端口二元组去重计数，不能按行数累加。据：端口对接、运输端口收支。

箱体无线传输入库不是端口通道：若物品仅在箱内传输入库，不虚构 X→仓库 的 LF/PC，也不为无线传输增加 S 或 R。此时须在带箱格式中另表无线交付与箱体守恒；本版没有该格式。不能将入箱与箱体普通端口外送视为同一条直达送料。箱体汇合、分配、传输开关及进出不等率也不能用布尔占位表达。据：传输、入库途径、协议储存箱。

当前加载器只有制造单位、矿石来源和核心端点，故带箱实例仍超出 feeding-v2 支持范围，校验报失败。`feed_interface_counts` 对已经分段的记录提供计数投影；测试中的合成箱端点只验证分段和去重算术，不是带箱候选的验收。完整带箱格式须同时增加仓储单位表、配方为空的端点规则、箱体收支、无线交付、运输结构和认证接口，不能只添加一条 `via.storage=true`。

|---|---|

| identity.side | 仓库取货口指定后为「左边界」或「下边界」；协议核心及待求变量为 null |
| identity.index | Quantity；边界端口序号或核心取货端口序号，待求为 null |

## 扇出表 fanouts

| 字段 | 说明 |
|---|---|
| machine / recipe / item | 源机器、该机唯一计划配方、产物；当前形状分类只实现单配方机器 |
| ports | Quantity，已用取货端口数 |
| planned_port_rate | Quantity，每端口计划件/tick |
| planned_mean_batch_interval | Quantity，计划平均批间隔 tick/批，与机器配方计划一致 |
| batch_size | Quantity，每批产物件数，据：配方 |
| planned_shape | 「满速扇出定则型／轮询均分型／两者都不落」 |
| certification | 独立状态栏，本步一律「待验」 |

分类算法先看所有取货端口是否计划满速；否则看平均批间隔是否为一 tick、相邻两批产物件数之和是否不大于端口数；其余归「两者都不落」（这些判别数字为算法定义或配方算术，**只作计划形状分类**）。多配方扇出的形状认证本版不支持，不能猜定逐批顺序。

「满速扇出定则」标记为候选，未审，仅保留形状名称，不用于正式检查通过判据。正式「轮询均分」还要求真实组时刻、同级性、可达路径、首格排空与首态等；形状符合不代表这些前件已证。M068 的计划平均批间隔是 2 tick（候选），不证明实际恒定间隔。候选「轮询均分（松）」未用于任何验证。

## 检查计算

逐机、逐配方、逐物品核对：输入通道速率之和＝批次率×配方用量，输出通道速率之和＝批次率×配方产量。全局逐物品核产出＋矿石出库＝制造消耗＋成品入库；同时单独核两种成品目标 3/5、11/20 件/tick（条文直引），防止内部配平但低产的计划被接受。

端口容量按相同端口的所有记录求和；每侧已用端口身份数不大于机型容量。机型下限、通道下限及条件式条款先计算台数前件再检查结论，满载部分只检查计划负荷。矿耗按单位矿耗反算并与计划外部流比较。植物回路按回路守恒检查，不把调试初始库存当持续来源。其余具体投影与运行缺口在生成报告中逐条列出。

正式静态目录含全部正式配方，包括候选原脚本未使用的「蓝铁粉末→蓝铁块」配方；原脚本的配方子集不成为规则全集。目录中的配方数值逐项带类别，约束条文文本中的数字整体按条文直引解释。

## 共享单位目录

[正式静态目录.json](正式静态目录.json) 的 schema 为 `static-catalog-v2`，是单位属性、配方 id 与配方值的共享输入。18 类单位涵盖制造、核心、运输、仓储、供电；`recipes[].kind` 和契约 `machines[].kind` 均引用 `units[].id`，值为正式中文名称，属于数据编码而非代码标识符。规格和内核引用同一 id，不再另建单位常量表。

每个单位条目含 dimensions（宽、高）、area、ports（存取数、layouts 的边及格位置）、inventory（角色、格数、容量与未定说明）、power_required、powered_functions 和 basis。制造单位还含 static_lower_bounds 的台数及两侧通道下限；数字来自正式机型下限、通道下限，不是设计选择。`static_checks` 保存静态判据使用的正式数值与据，`task` 保存完整目标、十条任务条件及两成品速率，Rust 从目录读取这些阈值。候选 B 回归数字、分类算法及归一化算术仍在代码中，不能与正式阈值混同。转换器只读目录并调用统一的 `formal_catalog.py` 门禁。门禁分别核对三份原文的全部字节指纹与完整行文本，以及从原文重建的约束上下文、任务、静态阈值、全部配方和单位字段；任一层不符即拒绝。原文快照一致不能替代结构化字段一致。门禁不写回目录，不自动批准规则变化。

端口表采用零起点编码坐标：x 向东、y 向北，width 沿 x、height 沿 y；南北边从西向东编号，东西边从南向北编号。layouts 是规范朝向的可选端口型，结合四向旋转表示允许方向；不是建造顺序、接通顺序或独立选项参数。桥接器两轴方向还须由先接端决定，不能凭目录任选。核心格位 1/4/7 对应条文第 2/5/8 格，输入 1…7 对应第 2…8 格（算术换码）。

`inventory` 中的 null 不能统一解释：核心格数不限，缓存可容纳的物品数量／种类不限，桥接器容量未定；制造输入格上限 50 和不限制物品种类已定，但容量计数域及混装语义未定。`inventory_rules` 保留单位内同种跨格唯一性，协议储存箱、缓存格和桥接器是明文例外；桥两轴可同时存放同种物品，各自受容量、滞留和端口额度约束。仓库取货口只引用核心仓库格、不复制格容量；供电桩没有物品格或端口。供电桩中心 12×12 的精确覆盖格集合留给规格参数轴。目录不裁定这些未定语义；依据见各条目的 basis 与 note。


## 目录版本、单位设定与数字类别

`schema=static-catalog-v2` 保持原单位几何接口；`version=2026-09-19-contract-r3` 标识目录数据内容版本；第四轮更新校验工具与说明，目录数据字节未变。任何目录消费者可先执行 `python 求解器/数据/工具/formal_catalog.py` 回源核验；不必运行候选转换器。Rust 的 cargo 一致性测试把编译时内置的目录字节经标准输入交给同一回源入口，并运行全字段变异回归；无需调用候选转换器。CLI 的目录版本行只报告版本，不单独证明回源通过，验收须连同前述门禁和 cargo 测试执行。目录的 sources 相对 source_root 定位三份正式文件，lines 保留空行和分节；文件字节指纹另外保留终止换行等信息。编译后的 Rust 报告列出内置版本；正式文件变化须重新审核目录并重新构建。

`constraints[].section/text/basis/source_line/basis_line/obligation` 保留完整条目上下文。不得依赖的四个量显式带 `obligation=目标须对其每种取值都达成`。`task.conditions` 是规范转录，不表示所有条件已经实现为运行检查。规则逐行与判据落点见[规则覆盖表](规则覆盖表.md)。

准入口 `settings` 含可选放行物品、设身份后可单独设的累计与窗口上限（1–5000、1–5，条文直引）、窗口 5 tick（条文直引）及首件起算和走完后下一件重起规则。储存箱 `transfer` 含 5 tick 冷却、按单位一次判定及未定冷却粒度；所有需电单位的 `switches` 引用其功能并标设定可改。据：物品准入口、传输、判定、开关、设定。阻断恢复及冷却粒度等未定项仍交规格轴，不擅定。

制造与箱体的两侧端口数由边长和一口一格推出，类别为算术推论；核心明写的 14/6、来源域上限 23 为条文直引。校验器按字段角色核 Quantity.category：机型容量与面积跟目录，计划速率与间隔为候选，目标及配方批量为条文直引；合法枚举但错标同样失败。契约类别检查不能单独证明证据真实性；目录门禁另从正式条文投影生成预期 Quantity，比较 value 与 category，并严格检查对象键集合、类型、数组长度、唯一 id、空值和未定状态。

## 目录门禁的字段范围

- 配方：全部 18 条的 id、kind、投入／产出物品集合和逐项批量、耗时及所有数字类别；包括候选 B 未使用的“精炼-蓝铁粉末”。
- 单位：全部 18 类的身份、族类、尺寸、面积、端口数及每个端口型的边／位置／角色／轴、物品格及容量状态、供电需求与功能、下限、准入口设定、箱体传输、开关、供电覆盖宽高／中心／未定状态，以及依据和说明。值从正式条文提取或按明确编码重建，不从待核目录或候选表反求预期。单位投影实现见 [formal_units.py](工具/formal_units.py)。
- 数字类别：直引量、面积乘积和零起点换码分别保留类别；合法枚举中的错标也拒绝。端口朝向、id、中文说明和未定状态采用当前目录编码约定，格式调整须显式同步比较器，不被静默忽略。

字段依据和变异证据见[第四轮门禁验证](修订验证/r4/门禁验证.md)。门禁核验静态转录及编码一致性，不构成执行语义、供电边界读法或候选运行认证。

## 计划满速与运输下界

每条 LF 保留 `planned_full_speed`，校验器重算并报告。候选 B 的 315 条记录中，300 条计划平均速率恰为 1 件/tick（其中矿石来源 52、非矿石 248；均为候选数据的算术计数）。若未来认证真实逐 tick 满速，且实现遵守无分流、无汇流的计划，这些路径到下一个非运输端点的沿途物品格须逐 tick 恰进出一件，不能与其它流共用该格；桥接器另一轴不被满速独占条款排除，且可同时承载同种物品；仍须服从各轴容量、滞留及按单位调度规则。仅平均计划值不完成这一运行证明。据：满速独占、运输单位、物品格、桥接器。

在候选排除分流与汇流、接口正流量及身份检查通过的前提下，运输端口收支给出 `T+b≥max(S,R)+E=315+E≥315`（算术推论；E≥0）。箱体过站的无箱投影给出 `T+b≥⌈305.65⌉=306`（算术推论），前者更强。实际 T、b、E 仍未知。S=R 是当前专用端口双射结构的恒等式，只列作冗余一致性检查，不能说由它独立验过分流／汇流配置。

物料流量按制造单位或矿石来源首次发出的速率计量；箱体普通端口中转不算新增物料。它不同于箱体过站的 Q（每次出箱各计一次），也不同于按端口去重的 S/R。当前带箱输入仍被拒绝；分段负例仅验证这些计量边界，完整带箱支持还须实现箱体守恒与无线交付。
