## 二、发现

### C2-r2-L3-1（次要）via 三栏为 null 即算「受限模型排除分流、汇流、准入口」，与本线自己的字段语义冲突

**位置**：`crates/topology/src/lib.rs:529-535`（检查「契约/运输占位」）、`lib.rs:422-428`（「契约/受限模型」）；`数据/送料契约.md:88`；`数据/候选B/contract.json` 全部 315 条记录的 `via` 四栏均为 `null`。

**事实**：代码判据是 `[splitter, merger, gate].iter().all(|v| v.is_none() || *v == Some(false))`，即 `null` 与 `false` 同样通过，而该行的说明文字写的是「受限模型排除分流、汇流、准入口」。同一交付的 `送料契约.md:88` 却写「`via` 中某值为 null 表示该路径尚未落实该类运输元件，**不等于没经过**」。两句放在一起，逐记录层面没有任何数据确认过这三类元件不在路径上；「排除」只来自顶层 `planned_absent` 这一条输入文件里的声明，而契约本身把运输层写成「运输实现待求」「路径中的运输单位数量及几何均未知」（`送料契约.md:75`、`contract.json` 的 `model` 字段）。

**影响范围**：以 D=M=B=0 为前提的四行「能检且通过」——`矿石分流与专机/计数`（lib.rs:879-883）、`箱体接口/已知计数投影`（968-975，η=5 用了 M=0）、`运输端口收支/可知投影`（963-967，R−S=0 用了 D=M=0）、`成品汇入/通道下限/入库途径`（949-959，K≥6 用了 B=C=0）。本席逐条验算过：即便 D、M、B 实际大于 0，这四行的判据仍是充分或更强的（η 随 M 增大而变小、−2M≤R−S≤2D 比 R=S 松、K+3B+2C≥6 比 K≥6 松、N矿≤52+2D矿+2B矿 与 D矿+3B矿+C矿≥52 在 C矿=52 时恒成立），所以**没有产生错误的通过结论**；问题只在于文档口径自相矛盾，且检查项的说明文字宣称了数据没有承载的事情。

**据**：规则「通道」「分流器」「汇流器」「物品准入口」「协议储存箱」；求解约束「运输端口收支」「箱体接口」「矿石分流与专机」「成品汇入」。要么在 `送料契约.md` 明写「在 `planned_absent` 排除某类时，该类的 `via` 栏 null 必须读作 false」，要么让校验器对被排除的三类要求显式 `false`。

### C2-r2-L3-2（次要）「矿系不入库」的检查丢了「种植机恰 32 台」这个前件，对种植机多于 32 台的合法契约会误报不通过

**位置**：`crates/topology/src/lib.rs:934-941`。

**条文**（求解约束·矿系不入库）：「……协议核心的存货通道、以及有供电状态且传输开着的协议储存箱，**只输送成品或植物系物品**；**种植机恰 32 台时**植物系物品也不入库，进入仓库的只有成品。」条文分两层：无条件层允许成品**或植物系物品**进核心，只有在种植机恰 32 台时才收紧为「只有成品」。

**代码**：无条件要求所有目标为核心的记录物品都在 `["高容谷地电池","精选荞愈胶囊"]` 内。候选 B 的种植机恰 32 台，故本次结论正确；但对一个种植机 >32 台、按条文合法地让荞花或砂叶入库的契约，本行会报「能检且不通过」，属于把条文的条件式当成无条件式。对照：同一文件里 `研磨进料`、`封装进料`、`满载配置` 都正确地写了 `counts(kind) != low || …` 的前件保护，唯独此处没有。

### C2-r2-L3-3（次要）两行判据与它们自称核过的量不是同一个量：`dedicated.len()` 被当成 C矿，但它不含「专机」条件

**位置**：`crates/topology/src/lib.rs:853-872`（`dedicated` 与 `ore_valid` 的构造）、`879-883`（矿石分流与专机/计数）、`976-980`（箱体过站/已知流量投影）。

**事实**：`dedicated` 对**每一条**矿石记录都插入其目标机器，与该机器是否满足「只做该矿石配方、每 tick 一批、没有别的存货通道」（即 `ore_valid`）无关。`矿石分流与专机/计数` 的判据是 `private && dedicated.len()==52`，说明文字却写「原矿接收专机 **C矿=N矿=52**」；`箱体过站/已知流量投影` 的判据是 `dedicated.len() >= 52`，说明文字写「核 **Q≥52−C矿**」。求解约束·矿石分流与专机把 C矿 定义为「其中**只做该矿石配方且每 tick 一批**的专机台数」。因此当一份契约有 52 台不同的原矿接收机但其中若干不是专机时，这两行会以「能检且通过」的身份宣称 C矿=52，而这是假的（同一次运行里 `矿线专机/计划` 会不通过，所以整体退出码仍是 1，但这两行本身是错误的通过）。

**改法提示**：把 `ore_valid` 并进这两行的判据，或把说明文字改成只宣称「52 条矿石记录指向 52 台互异的接收机」。

### C2-r2-L3-4（次要）「不能静态检」的理由文字按条目名硬编码，内含未经计算的数据相关断言

**位置**：`crates/topology/src/lib.rs:1071-1092` 的 `match name` 表；另见 `lib.rs:833-838` 灌装混线的 else 分支文字。

**事实**：`"混做清空"` 一行写死「**本候选无混做**」，`"灌装混线"` 一行写死「**本计划前提不触发**」，`"矿石分流与专机"` 一行写死「无分流无箱的专用计划与专机批次率已核」。这些是对输入数据的断言，但代码从不计算它们，字符串与任何契约内容无关。本席核过候选 B 确实没有多配方机器（219 台全部单配方）且灌装机三台都是 4 条存货通道（count_in=3≠2），所以当前文字为真；但第一轮任务书已经写明「217 台混做支的独立候选是后续异源双做的另一半」，届时把校验器指向那个契约，报告仍会原样打出「本候选无混做」，成为一句假陈述。`灌装混线/结构` 的 else 文字「并非恰两台至少四输入」同理：台数不等于 3 时前件不触发的真正原因是台数，而不是这句话。

**据**：求解约束「混做清空」「灌装混线」的前件都带机器配置条件；报告是交付物，其中的事实陈述应当由代码算出而不是写死。

### C2-r2-L3-5（次要）条文阈值仍硬编码在 Rust 里，目录只存条文文本，没有结构化字段也没有一致性测试

**位置**：`crates/topology/src/lib.rs:906-926`（物料流量 19 个阈值）、`886-897`（单位矿耗 20/30/40 与 34/18）、`687-700` 与 `924-925`（成品目标 3/5、11/20）、`413-421`（出库上限每边 23）、`963-967`（S≥312、R≥307）、`968-975`（S+R≥624）、`840-852`/`874-878`（矿石来源 52）、`949-959`（K≥6、核心存货 ≥2）。

**事实**：第二轮任务书 §3.B.1 要求把目录做成「规格、契约、Rust 三方唯一真源」并加「硬编码值与目录逐项相等」的一致性测试。目录侧只做到了**机型**常量（端口数、面积、台数与通道下限、核心容量）——这部分确实改成从目录读并有 `legacy_machine_constants_equal_catalog` 与 `catalog_unit_properties_match_formal_reference_values` 两个回归测试。上列的条文阈值则仍是 Rust 字面量：目录里只有 `constraints[].text` 的整段中文，没有任何结构化字段，也没有任何断言把这些字面量与条文对上。`convert_candidate_b.py:43-44` 的两个 `assert` 只保证「目录的配方/约束文本与正式文件一致」，一旦 `求解约束.txt` 的数字改动，转换器会拦住目录不同步，但 Rust 里的 19 个流量阈值、624、312/307 等不会被任何测试发现，报告会出现「条文更新了、判据还是旧数」的静默不一致。

同时 `数据/送料契约.md:155` 写「Rust 编译时内置目录，运行检查从目录取机型与核心容量；**旧硬编码仅留在一致性测试作为回归对照**」，容易被读成运行检查里已经没有硬编码；实际上运行检查里至少还有上列八处条文数字。建议要么给目录加 `constraints[].values` 之类的结构化字段并加测试，要么把这句话的辖域明确限制在机型常量上。

### C2-r2-L3-6（次要）转换器从 `fanout.json` 读入 IEEE 浮点并经 `str()` 转有理数，与契约「拒绝浮点」的口径不一致

**位置**：`数据/工具/convert_candidate_b.py:128`：`'planned_mean_batch_interval': quantity(str(row['批间隔tick']))`。

**事实**：`送料契约.md:24` 写「运算使用任意精度整数构成的有理数，**拒绝 JSON 浮点值与小数字符串**；无需容差」，Rust 加载器也确实拒绝（`zero_denominator_and_missing_fields_fail_loading` 的 `float` 分支）。但转换器的输入 `/home/zhuran24/文档/会议2全套/会议目录/seat-opus-4/fanout.json` 里 `批间隔tick` 是 JSON 浮点（本席核过：33 条全是 `float`，值为 1.0 或 2.0），转换器用 `Fraction(str(float))` 把它十进制化。本次 33 个值都可精确表示，`扇出/计划分类` 又会把它与机器侧用整数算出的 `Fraction(20, 批次每20tick)` 比对，所以**没有产生数值误差**；但同一管道里其余数字（`件每20tick`、`k`、`每端口速率`、`每批件数`）都走 CSV 字符串或整数，唯独这一项依赖浮点的十进制表示，和契约自述的口径不一致。改法：直接用机器侧的 `Fraction(20, 批次每20tick)`，或把源值按精确分数重建并断言两者相等。
