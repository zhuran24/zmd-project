### C2-r3-L3-1（重要）报告抬头声称「比较阈值为条文直引」，但多处实际比较阈值是算术推论或候选数字

**位置**：`crates/topology/src/lib.rs:306`（`Report::markdown` 抬头，原样出现在交付物 `数据/候选B/校验报告.md:5`）。被该句错误覆盖的判据至少有：`lib.rs:643`（`busy <= 1`）、`lib.rs:738`（`load == 1`）、`lib.rs:963-967`（`s == rr`）、`lib.rs:968-975`（`s + rr >= 624`）、`lib.rs:949-959`（`core_in >= 6`）、`lib.rs:1038-1039`（`2×batch_size ≤ ports`）、`lib.rs:1067`（候选 B 交接件数 219／3325／315／31／5／5／4／6／38／30／2／1）。

**抬头原文**：「报告中的观测计数和计算值均为算术推论（以候选数据为条件）；**比较阈值为条文直引**。计划数字仍属候选。」

**为什么不成立**，逐项对回条文与本交付自己的类别定义（`数据/送料契约.md:26-28`：条文直引＝正式文件明写的数字；算术推论＝据正式数字运算所得值；候选＝待实现的计划、计数选择）：

### C2-r3-L3-2（次要）`Quantity.category` 只做枚举白名单，任何判据都不读它——「每个数字标类别」在校验器一侧没有语义约束力

**位置**：`crates/topology/src/lib.rs:31-53`（`Quantity` 的 `Deserialize`）。全文搜索 `category`，运行代码里只有第 34、42、45、51 行，全部在反序列化里；`validate` 的 4630 条判据没有一处读取 `category`。

**事实**：加载器只检查 `category` 落在「条文直引／算术推论／候选／启发式／实测」五个词里，不检查它与该数字的实际来源是否相符。于是契约里把一个条文直引的数标成算术推论（或反过来把一个候选数标成条文直引）不会被任何检查、任何 `cargo test` 发现。这不是假设：同一轮「字段覆盖」视角存活的发现 C2-r2-L1-5 指出 `contract.json` 的 `source_domain.left/bottom` 把 23 标成「算术推论」，而约束「出库上限」原文明写「仓库取货口每边至多 **23** 个」、「边带排布」原文明写「左、下两边各 **23** 个仓库取货口」——按本交付自己的定义（`送料契约.md:26`「正式已采纳约束中的数字也属于此类」）应为条文直引。这条错标能一路通过 22 项测试和 4573 项检查，正说明类别栏目前没有守卫。

**影响**：第一轮任务书 §3.B.1 把「每个数字标类别」列为契约的交付要求；现在这个要求只落到「格式里有这个字段」，没有落到「标对」。后续候选（217 台混做支）转换时，类别栏的可信度不会比现在更高，而下游正是靠它判断哪些数字可以直接引用。

**据**：第一轮任务书 §3.B.1「每个数字标类别：条文直引／算术推论／候选／启发式／实测」；求解约束「出库上限」「边带排布」；`数据/送料契约.md:26-30`。

### C2-r3-L3-3（次要）`运输端口收支/可知投影` 里的 `S == R` 在端口身份检查通过时恒真，不构成对设计的任何约束，却列在「能检且通过」

**位置**：`crates/topology/src/lib.rs:963-967`（判据 `s >= 312 && rr >= 307 && s == rr`），与 `lib.rs:359-363`（`feed_interface_counts`）、`lib.rs:501-516`（`port_links` / `reverse_links`）。

**条文**（求解约束·运输端口收支）：「……则 S ≥312，R ≥307，T+b+2M ≥ S+E，T+b+2D ≥ R+E，**−2M ≤ R−S ≤ 2D**」。代码以 D=M=0 推出 R=S 并报「能检且通过」，detail 写「D=M=0 的计划满足 R−S=0」。

**事实**：`port_links` 把每个用到的源端口映成唯一的目标端口，`reverse_links` 把每个用到的目标端口映回唯一的源端口，二者冲突即 `契约/端口身份` 不通过。因此只要 `契约/端口身份` 全部通过，「用到的源端口集」与「用到的目标端口集」之间就是一个双射，`feed_interface_counts` 的两个基数**必然相等**。也就是说 `s == rr` 这一合取项在任何能通过前面检查的契约上都为真，永远不可能单独失败；探针 P1（把 6 条成品记录并到同一核心端口）里它之所以报错，也是因为 `契约/端口身份` 同时报错。

**影响**：不产生错误结论（S=R 在受限模型下确实成立），但报告把一条由**契约格式**强制成立的等式列为「能检且通过」的条文投影，读者会以为候选 B 的分流／汇流配置经过了检验。真正被检验的只有 `s >= 312`、`rr >= 307` 两项。detail 或判据应说明这一点，或把该项归入格式不变量而不是条文投影。

**据**：求解约束「运输端口收支」原文；`数据/送料契约.md:90`「当前专用模型禁止同一端口连向不同端点，也禁止多个不同来源端点共用目标端口」。

### C2-r3-L3-4（次要）`物料流量` 用的 `throughput` 对储存箱分段记录会重复计数，与同文件 `feed_interface_counts` 的去重口径不一致

**位置**：`crates/topology/src/lib.rs:660-671`（`throughput` 逐记录累加 `planned_rate`）与 `lib.rs:906-933`（`物料流量/{item}` 用 `qmap(&throughput, item) >= min`）；对照 `lib.rs:357-363` 的文档注释「按非运输端点的不同端口计 S、R；**输入必须已在每个储存箱处切段**」与 `tests/validation.rs:204-228` 的分段测试。

**事实**：本契约自己规定（`数据/送料契约.md:104`）「若送料需经过箱体 X，应表示为两段：`A:out:a → X:in:i` 与 `X:out:o → B:in:b`，分别使用不同 LF id」。在这种表示下，同一件物品会出现在两条逻辑送料记录里，`throughput[item]` 变成实际流量的两倍，而 `物料流量/{item}` 是 `>=` 比较——一个实际只有 17 件/tick 蓝铁粉末、但经一个储存箱中转的计划，会被判成「34 ≥ 34，能检且通过」。`feed_interface_counts` 已经按 (端点, 端口) 去重处理了分段，`throughput`（以及 `external`、`delivered`）没有对应处理。

**当前不可触发**：`planned_absent` 必须恰含 `storage`（`lib.rs:422-428`），加载器拒绝 `via.storage` 的任何取值（`legacy_channels_and_storage_shortcut_are_rejected`），且 `契约/送料引用` 只认「制造单位／矿石来源／核心」三种端点，带箱契约根本装不进来。所以候选 B 的 `物料流量` 19 行结论是对的。

**为什么仍要记**：两处口径不一致是**有方向**的——去重的那一处有测试守着并写进了契约说明，不去重的那一处既没有测试也没有登记。`送料契约.md:108` 已经把「完整带箱格式」列为下一步要加的东西；到那一步时，`物料流量` 会安静地给出错误的「能检且通过」，而不是像 `via.storage` 那样 fail-closed。

**据**：求解约束「物料流量」原文（每 tick 至少需…合计 305.65 件）；规则「协议储存箱」「传输」；`数据/送料契约.md:104`、`:108`；`lib.rs:357-358` 自己的注释。

### C2-r3-L3-5（次要）报告抬头说内置的是《游戏规则》《求解任务》《求解约束》三者的静态目录，但目录里没有任何来自《求解任务》的内容

**位置**：`crates/topology/src/lib.rs:306`（抬头第一句，出现在 `数据/候选B/校验报告.md:5`）；`数据/正式静态目录.json`（顶层键只有 `recipes`、`constraints`、`schema`、`conventions`、`units`）；两个成品目标写在 `lib.rs:687-690` 的 Rust 字面量 `ratio(3,5)`、`ratio(11,20)` 里。

**事实**：抬头写「检查依据为内置《游戏规则》《求解任务》《求解约束》静态目录」。目录里 `constraints` 是《求解约束》56 条的逐字文本（本席核过，差异 0），`recipes`／`units` 是《游戏规则》的转录，`basis` 字段引的全部是《游戏规则》的名词或《求解约束》的条目名（本席遍历全部 `basis`，无一条引《求解任务》）。《求解任务》唯一进入运行判据的内容是两个成品速率 0.6／0.55，它们不是目录字段而是 Rust 字面量；任务条件（仓库物品、外部过程、零干预运行、循环态、建造方式、调试期、操作精度、离线、判定次序、仓库取货口位置）在目录里没有对应物。

**影响**：与 C2-r2-L3-5（存活）同一方向但不同对象——那一条说的是条文阈值没有回到目录，这一条说的是**报告对自己依据范围的描述**不准确。读者据此会以为《求解任务》已经被结构化成共享真源，从而不再去核 `lib.rs` 里的 3/5、11/20 是否与任务一致。

**据**：求解任务「目标」节与「任务条件」十条；`数据/正式静态目录.json` 的实际键集与 `basis` 取值；`crates/topology/src/lib.rs:687-690`。

## 三、结论

代码自第 2 轮起未被修改，本席按「校验器正确性」视角重跑并独立复算后，同样**没有发现会让实现做错的缺陷**：22 项测试与 4573 项通过、0 项不通过、57 项不能静态检的结论可逐字节复现，判据与《求解约束》条文逐条对得上，全程有理数无浮点，目录对正式文件逐字一致。

本轮新增五条发现：一条重要（报告抬头把算术推论与候选数字统一说成条文直引，违反本项目的数字分类纪律，会误导 A、C 两线），四条次要（类别栏无语义守卫、S=R 是格式恒真项、`throughput` 在带箱格式下会重复计数、抬头对内置目录范围的描述不准）。同时提醒：第 2 轮存活的 C2-r2-L3-2 … L3-6 五条因本轮未起草而**全部仍未处理**，不应因为本轮报告「0 项不通过」而认为它们已闭环。
