## 3. C3-r4-L1-01 的独立否证

**结论：`refuted=false`，未能否证。** 三个主反例都与指定规则或数字类别约定相矛盾，且本席独立重编译重现了全部漏检。

### 3.1 回源判错依据

- [游戏规则](../../../《明日方舟：终末地》游戏规则.txt) L89 明写“1 蓝铁粉末 → 1 蓝铁块，1 tick”。[目录](../正式静态目录.json) L124–140 的 `精炼-蓝铁粉末` 是这条配方，故耗时改为 2 直接违背原文；候选暂未使用这条配方不改变其正式性。
- 游戏规则 L76 明写供电桩“以自己中心为原点12x12的范围”。目录 L3484–3495 单独存储 `coverage.width/height`，其宽度不是 2×2 的单位占地宽度。将覆盖宽度改为 13 不属于边界接触判据的读法差异。
- 游戏规则 L41 直接给出核心存货端口“共 14 个”。首轮任务书 §3.B.1 要求每个数字标类别；契约 L24–30 定义类别，L171 又明确“核心明写的 14/6……为条文直引”。目录 L2388–2395 原值正确，将该 `category` 改为“候选”违反既定类别含义。这里判错根据是正式明写的数字加任务／契约的分类定义，不是声称游戏规则自身含有 JSON 类别字段。

第二轮任务书 §3.B.1 要求目录作为规格、契约、Rust 三方唯一真源，并加逐项一致性测试。契约 L165 明示任一消费者可直接执行 `formal_catalog.py`，不必运行候选转换器。因此不能把仅在另一入口执行的检查当作该入口已经完成的检查。

### 3.2 代码覆盖与反例逐项对应

`formal_catalog.py` L104 的投影仅有 `constraints`、`task`、`static_checks`。L108–111 比较正式来源快照及这三个投影；L114–125 补查准入口和储存箱；L126–131 补查跨格规则，并只对制造、储存箱、桥接器的端口数检查算术类别。这里没有配方表比较，没有供电覆盖尺寸比较，也没有核心端口类别比较。

Rust `validation.rs` L425–443 固定比较单位尺寸、面积、端口计数和库存数量／容量的 `value`，没有比较供电 `coverage` 或这些值的类别。L447–468 与 L478–565 核端口布局，不能核覆盖尺寸。L470–474 的配方循环只核 `kind` 指向制造单位。L741–756 的回源测试运行上述 Python 文件，没有调用转换器。

本席三个单字段复跑均得到 `verify=accepted`、29 项 Rust 测试通过，且均重新编译。原始日志分别见[未用配方](否证-r4-2-证据/unused_recipe_duration-cargo-test.stdout)、[供电覆盖](否证-r4-2-证据/power_coverage-cargo-test.stdout)、[核心类别](否证-r4-2-证据/core_port_category-cargo-test.stdout)。这三个反例足以支持“存在未覆盖的配方、单位属性及类别”，不需要推断所有字段均漏检。

### 3.3 尝试采用的反证为何不足

1. **原目录当前正确**：本席独立配方回源和单位原值核对确认这一点。发现也明确限定为校验覆盖缺口，正确的当前数据不能证明错误目录必被拒绝。
2. **转换器已有完整配方比较**：`convert_candidate_b.py` L24–41 确实从原文解析全部配方，且本席配方前段对耗时变异明确拒绝。它能保护该转换入口，但 `verify` 与 Cargo 没有执行这条断言；供电宽度、核心类别变异连这个前段也接受。因此该保护不足以否证发现的入口范围。
3. **SHA-256 与完整源文本已核**：实验保留全部 `sources`。验证被保存的原文没有漂移，不等于验证另外存储的结构化字段正确；反例正是二者不一致仍通过。
4. **契约已声明不做几何、类别不证明证据真实性**：这些限定排除了运行／几何认证，不豁免已明写的 12×12 转录一致性，也不能使将明写的 14 标成候选成为正确分类。这里没有要求 CLI 验证真实供电布局。

本条“重要”所依据的共享输入完整性风险成立；没有证据将其否掉。无需据此认定当前候选配平错误或提高严重度。

## 4. C3-r4-L3-1 的独立否证

### 4.1 回源与实际消费

游戏规则 L92 明写“2 蓝铁粉末 ＋ 1 砂叶粉末 → 1 致密蓝铁粉末，1 tick”；目录 L144–164 的 `研磨-致密蓝铁` 对应该条。将耗时改为 `1/2` 直接违反已写数值，不需要假定未定调度语义。规则 L76 同样直接排除供电覆盖宽度 13。

第二轮任务书 §3.B.1 与契约 L154–165 将配方和单位目录交给其他消费者共享。`formal_catalog.py` L104–132 没有这两类数值比较；Rust 测试 L425–474 及 L741–756 也没有补齐。Rust `lib.rs` L164–169 读取配方耗时，L229–230 内置共享目录；L754 将 `planned_batch_rate × duration` 加入负荷，L795–799 只判断负荷不超过 1。这能检候选相对目录的负荷，不能独立证明目录耗时对回原文。

本席[耗时变异测试](否证-r4-2-证据/used_recipe_duration-cargo-test.stdout)为 29 通过、0 失败；[编译日志](否证-r4-2-证据/used_recipe_duration-cargo-test.stderr)确认重新编译。CLI 退出 0，见[变异报告](否证-r4-2-证据/used_recipe_duration-cli.stdout)。其 `制造能力/M120` 从原版“各配方批次率×耗时之和 **1** ≤1”变为“各配方批次率×耗时之和 **1/2** ≤1”，仍列在通过项中；报告分组仍是 4925／0／59。该变化排除了仅运行旧二进制、没有消费变异值的解释。

供电宽度变异独立重编译后同样为 29 项通过、CLI 退出 0，见[测试](否证-r4-2-证据/power_coverage-cargo-test.stdout)与[CLI 报告](否证-r4-2-证据/power_coverage-cli.stdout)。Rust `UnitSpec`（L191–197）甚至没有 `coverage` 字段；固定 JSON 测试也未补核。这说明共享目录核验漏检，不说明 CLI 已认证过错误的几何覆盖。

### 4.2 对可能否证理由的裁定

完整转换器配方断言的存在是有效的局部保护，本席也确认它拒绝 `1/2` 反例。但该条指称的独立回源、Cargo 和既有候选重验三条路径都不运行该断言，故无法据此把本条判成已经覆盖。

“配方变快仍满足机器上限”解释了候选负荷检查为何通过，不能证明规则允许变快。发现指向的正是缺少原文一致性守卫，并未声称在正确规则下该候选被证明不合法。

供电的 `positive_area`／`closed_touch` 决定边界相交语义，目录 `coverage.width` 存的是条文明写的范围宽度。第三轮主席对最严读法的裁定不允许把 12 换成 13，故不能借该未定项否证尺寸反例。

本条与上一条共享部分根因，但其已用配方反例及 CLI 数值影响已单独验证；不以重复为理由撤销任一发现。
