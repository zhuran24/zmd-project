# 内核第3轮复核：规格保真

日期：2026-09-20。审查对象为第五轮实现及规格第8轮的当前文件。结论：有4条发现，其中3条阻断、1条重要；生产键的字段编码本身未发现与§6.2不同，检查点准入和周期结果验收仍有缺口。

游戏行为依据为仓库根《明日方舟：终末地》游戏规则.txt、求解任务.txt、求解约束.txt。五份任务书及第五轮§2、第三轮§2所列裁定用于确定本次工程验收口径。实施对照为规格第8轮的受限转移定义、内核输入、内核输出及schema、受限模型声明、配置和对内核的修改请求。受限读法的实现一致性不替代其一般规则相容性证明。

本报告针对当前文件内容；开工原始字节指纹见[r3-规格保真-证据/开工指纹.json](r3-规格保真-证据/开工指纹.json)。复现脚本及结果均在该证据目录，未复制源码仓、target或依赖缓存。编译使用工作区共享`求解器/target`。具体检验包括：新生成的检查点正负例、窗口到期负例、独立验收负例、两矿容量对照、切支恢复、桥双通路、研磨制造、真实环带周期，以及现有周期/运行记录的字段和台账核算。

完整复现入口（仓库根执行）：


## 2. 发现

### KR-r3-L1-01：已闭包检查点的参数冲突被派生器覆盖

- 严重性：阻断。
- 位置：`求解器/crates/kernel/src/seed.rs:9–36、58–61`；`engine.rs:404–418`；规格`内核输入.md §6.4（357–363行）`。
- 结论：`canonicalize_seed`在辨别种子阶段之前重建`parameter_values`，使参数缺失或冲突的`after_closure`检查点被改写为可续跑输入。

正式规则L29–32使游标和授权具有运行历史；任务L14固定同刻判定先后。工程裁定KQ-07落实为输入§6.4第360行：“after_closure检查点保留原已执行游标、参数、台账、活动事件身份与时间锚点……缺失或冲突即拒收”。转移§1也要求完整且自洽的排序数据。允许新调度起点派生，不等于允许为旧检查点替换参数后沿用原历史。

`seed.rs:12–33`无条件从顶层`Parameters`生成种子当前值；集合缺失时还补全轴名。直到`derive_context`才在第60行遇到`after_closure`直接返回。`Engine::validate_seed`的当前参数一致性检查只看覆盖后的数据，故无法发现原始冲突。

复现采用粉碎机实际运行在t=1的检查点。完整对照经`seed`前后StateSeed逐字段相同，直接续跑首项t=2。负例只将顶层`warehouse.external_supply`从原显式历史改为`sufficient`，检查点仍保留原参数。结果：

| 操作 | 结果 |
|---|---|
| 对冲突输入直接`run` | 退出2，`invalid_input`，当前值/生命周期与参数向量不符 |
| 对相同冲突输入`seed` | 退出0，输出`kernel-input-v3`，检查点参数被换成`sufficient` |
| 执行派生后的输入 | 退出0，`completed`，后续出矿按新模式补回 |
| 将检查点`parameter_values`直接改为[]后`seed` | 退出0，99轴被补回 |

证据：[冲突输入](r3-规格保真-证据/checkpoint-parameter-drift-input.json)、[直接运行拒收](r3-规格保真-证据/checkpoint-parameter-drift-run.json)、[错误接受的派生输入](r3-规格保真-证据/checkpoint-parameter-drift-seed.json)、[派生后运行](r3-规格保真-证据/checkpoint-parameter-drift-after-seed-run.json)、[缺失参数派生](r3-规格保真-证据/checkpoint-parameter-missing-seed.json)。

修订边界：先辨别阶段；after_closure校验原参数/记忆并保留，冲突拒收；before_boundary的新起轮派生另行处理。此发现不要求由库存反演历史，也不反对明确新建另一个参数点。

### KR-r3-L1-02：到期窗口被当作合法after_closure待办延后一刻执行

- 严重性：阻断。
- 位置：`求解器/crates/kernel/src/engine.rs:764–765`；`transition.rs:480–510、676–687`；规格`受限转移定义.md §2.1、§3.4`及`内核输入.md §5.2、§6.3`。
- 结论：窗口日程校验对after_closure仍允许`deadline==t`，从而接受边界维护未完成的“已闭包”种子，并在t+1才消费已到期事件。

规则L64：“该5 tick从它收下的第一件物品起算、走完后由下一件物品重新起算”。任务书3§2.2已排除窗口耗尽永久锁闭/全盘停表。转移§2.1第23行要求本刻边界一次收集全部已过5tick的窗口并清除窗口原因；输入§5.2第280行明定after_closure的边界及闭包均已完成。因此在after_closure锚点，仍待办的窗口deadline必须严格晚于当前t；before_boundary允许deadline==t是不同情况。

代码只拒绝`deadline != expected || deadline < self.t`，没有按phase区分等号。分流器实际t=5检查点中的两个窗口原为start=1/deadline=6。负例将两者同时改为start=0/deadline=5，保留计数1、window_exhausted及断边。输入通过`seed`及`run`，在t=6日志中实际执行`W|5|probe_gate_a`和`W|5|probe_gate_b`，比规定维护边界晚一刻。

这不是预计制造deadline可因暂停滞后的情况：受限转移§2.1区分制造工作量与窗口墙钟；输出§2第35行仍要求窗口按5tick真实截止核验。对生成的同一记录执行`verify-record`，现有独立事件检查明确拒绝：“执行的操作/目标/时刻与待事件登记不符”。

证据：[实际检查点对照](r3-规格保真-证据/gate-checkpoint-control-input.json)、[非法到期检查点](r3-规格保真-证据/gate-expired-after-closure-input.json)、[派生器错误接受](r3-规格保真-证据/gate-expired-after-closure-seed.json)、[延迟执行记录](r3-规格保真-证据/gate-expired-after-closure-record.json)、[独立验收拒绝](r3-规格保真-证据/gate-expired-record-verification.json)。

修订边界：窗口日程与阶段联合校验，after_closure拒收`deadline<=t`；不能为了修复而重新执行t或清空检查点旧账。制造预计截止与暂停语义应继续保持现行区别。

### KR-r3-L1-03：周期验收跳过了全记录事件身份和时序独立检查

- 严重性：阻断。
- 位置：`求解器/crates/kernel/src/cycle.rs:602–675`；对照`output.rs:518–526`、`event_identity.rs:175–247`；规格`内核输出.md §2、§5.3.1`。
- 结论：`verify_cycle`以同实现重算一致代替强制的全前缀事件验收，可接受其内嵌记录已被`verify-record`判非法的周期结果。

输出§2第35行明确：“跨集合唯一性必须由语义验收器独立核，不能仅靠重算相等”；§5.3.1要求重建完整记录并核逐笔守恒和事件唯一性。规则L64窗口期限也是此处的时序判据。周期起点独立重跑只覆盖(a,b]，不能替代从seed到a的合法前缀。

`verify_cycle`当前核输入文件与内嵌输入相同，调用`run_cycle`并比较整个JSON，然后重跑周期段；没有调用`validate_event_identity`或`verify_record`。相同实现产生相同错误前缀时，前一次比较仍为真；错误发生在周期前时，后一次周期重跑也无法发现。

最小复现为核心加一个隔离准入口，库存为空、无PC、显式sufficient。t=5的after_closure条件种子保留start=0/deadline=5的待窗口事件；这是有意非法的准入测试，不能作为可达性见证。结果如下：

| 检查 | 实测结果 |
|---|---|
| `cycle --max-ticks 3` | 退出0，`counterexample`，生产部分周期P=1、区间(6,7] |
| 前缀t=6 | 实际执行过期事件`W\|5\|gate` |
| 对完整结果`verify-cycle` | 退出0，`input_checked`、`cycle_replayed=true` |
| 将内嵌run_record原样取出后`verify-record` | 退出2，`invalid_input`，窗口执行时刻与待办登记不符 |

证据：[最小非法输入](r3-规格保真-证据/tiny-expired-after-closure-input.json)、[被接受的周期结果](r3-规格保真-证据/tiny-expired-cycle.json)、[周期验收通过](r3-规格保真-证据/tiny-expired-cycle-verification.json)、[原样内嵌记录](r3-规格保真-证据/tiny-expired-embedded-record.json)、[记录验收拒绝](r3-规格保真-证据/tiny-expired-embedded-record-verification.json)。

本发现与02分别成立：02是装载器遗漏阶段不变量；03是证书验收器没有执行规格明确要求的独立检查。修掉这个输入漏洞仍不能以“同实现重算”替代全局注册/消费和时序核验。周期验收应先核包括搜索前缀在内的内嵌v3记录，再执行现有周期起点重跑。

### KR-r3-L1-04：sufficient种子派生缺少两矿正库存准入

- 严重性：重要。
- 位置：`求解器/crates/kernel/src/seed.rs:34–41`；`engine.rs:275–781`；`interfaces.rs:171–229`；对照`transition.rs:523–545`、`cycle.rs:143–153`。
- 结论：`kernel seed`能成功导出源矿库存为零的sufficient输入，违反输入§5.4的种子前提，直到后续运行才拒收。

任务L7要求两矿“持续可得且足够覆盖任意数量的消耗”；本版输入§5.4第305行将其编码为“sufficient要求种子两矿各有正数、唯一且≤80000的库存格”。空格的历史身份不产生物品（输入§4/§6；转移§4.1）。

复现从现有生产循环环带输入出发，保持`sufficient`，只把StateSeed的源矿格改为`item=null、quantity=0、empty_identity=specified(源矿)`；任务初始六满格条件保持。`seed`退出0，输出可识别的`kernel-input-v3`；对该输出`run --ticks 1`才因`warehouse.external_supply`返回invalid_input。代码在仓库结构校验中只核0/item/身份一致性，正矿检查位于后续boundary与生产域检查，未纳入seed成功条件。

证据：[缺矿输入](r3-规格保真-证据/zero-ore-sufficient-input.json)、[错误接受的派生输入](r3-规格保真-证据/zero-ore-sufficient-seed.json)、[后续拒收](r3-规格保真-证据/zero-ore-runtime-rejection.json)。有限执行最终停止而未伪造矿石，因此此条定为重要；不能将派生成功作为满足输入§6自洽要求的证明。
