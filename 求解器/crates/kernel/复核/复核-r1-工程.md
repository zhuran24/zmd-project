## 2. 发现清单

### KR-r1-L3-01：非对象快照绕过 Stop 错误通路

- **id**：`KR-r1-L3-01`
- **where**：`/home/zhuran24/zmd-research-fresh/求解器/crates/kernel/src/input.rs:208–214`
- **claim**：`layout.snapshots` 的成员未经对象校验即写入 `base`，非法布尔成员会触发 panic，无法返回带位置的 Stop 或停止记录。
- **evidence**：《内核输入》§2 规定 snapshots[] 每项为对象；《受限转移定义》§1 要求错误返回 invalid(field, reason)。将原粉碎机样例的 snapshots 改为 [false]，release CLI 实测退出101，stderr 为 `cannot access key "base" in JSON boolean`，指定的输出记录未生成，见 `r1-工程-evidence/input-probes.json` 的 snapshot-bool。
- **severity**：重要。

调用链在 `Input::parse` 中先只检查外层是数组，随后 `s["base"] = ...` 对 bool 进行可变对象索引；这次 panic 发生在 `Geometry::build` 以及其 `Result` 返回之前。`main` 的 `execute()` 错误分支只能接收 `Err(Stop)`，不能把 panic 转成 `stopped_record`。因此外层虽然最终也是非零退出，却丢失了规格要求的错误类别、字段位置和结构化停止记录；嵌入执行器调用库入口也会遭遇解栈。

最小复现文件为 [snapshot-bool-input.json](r1-工程-evidence/snapshot-bool-input.json)。除将目录与轴表引用改成绝对路径以便放置副本外，机制变异只有该数组。它不是合法布局的转移反例，故不升级为阻断级；缺陷在非法输入的错误通路。应先核对象类型与快照字段，再组装共用 base，错误通过 Stop 传播，并增加真实 CLI 的非对象成员负例。

### KR-r1-L3-02：非法准入口物品类型被执行为阻断条件

- **id**：`KR-r1-L3-02`
- **where**：`/home/zhuran24/zmd-research-fresh/求解器/crates/kernel/src/input.rs:500–525`；`/home/zhuran24/zmd-research-fresh/求解器/crates/kernel/src/polling.rs:337–360`

- **evidence**：《内核输入》§4 明定 item 为物品名或 null，规则 L64 的设定对象为某一种物品；将分流器样例 probe_gate_a.item 改为7，执行2刻返回0/completed，并将该门标为 identity_mismatch、total_received=0，见 `r1-工程-evidence/input-probes.json` 的 gate-numeric-item。

`fields` 只核键集合；当前设置读取代码检查单位类型、重复记录、两类限额及 item 是否为 null，没有核 item 的 JSON 类型。`validate_tree` 也不对普通整数报错，因为表示索引允许整数。后续 `maintain_identity` 直接比较 `Value(7)` 与物品字符串，它们必不相等，于是删除入边并锁存身份原因。本应在装载阶段拒收的字段被解释成实际的游戏守卫。

证据输入为 [gate-numeric-item-input.json](r1-工程-evidence/gate-numeric-item-input.json)，输出为 [gate-numeric-item-record.json](r1-工程-evidence/gate-numeric-item-record.json)。仅第一门身份变异；同次运行第二门正常收到1件并因窗口耗尽断边。此处不是要求内核发明新物品允许域，只要求落实已定义的类型边界。输出 schema 通过不能弥补这个输入缺口。应在写入 `gate_settings` 前使用类型化记录或显式检查，非法类型返回 `invalid_input`。该问题只证明非法输入被误接受，未据此宣称任何合法物品名输入的轨迹错误，列重要级。

- **id**：`KR-r1-L3-03`
- **where**：`/home/zhuran24/zmd-research-fresh/求解器/crates/kernel/src/interfaces.rs:227–249`

## 4. 复杂度与资源成本

令 C 为实际 PC 数，S 为全部本地槽位数，W 为已声明仓库格数，T 为模板数，R 为该时刻扫描轮数。

1. `move_channel` 每次访问调用 `refresh`，后者重新扫描全部 C 条实际边并求 `physical`；`source` 为找一个单位的格，会过滤整份 inv 键；`target` 的单位同种查找也会扫完整 inventory。即使不算阻尼，具有 C 个移动模板的一轮已有可达的 `O(C²·S)` 扫描形态，而不是仅 `O(C)`。核心收货还反复遍历 W 个仓库格。见 engine.rs 的 source/target/physical 与 polling.rs 的 refresh。
2. 每模板前 `maintain_identity` 又遍历全部实际边；图变化时 `group_levels` 按全部单位侧逐条检查 active 集合，约为单位侧数乘 C。阻尼沿路径前进时每一步扫描 active 找后继，路径长度 L 时为 `O(L·C)`，并会在反复 refresh 中重复求值。无缓存的重复成本比单说“O(n²)”更具体。
3. 闭包 seen 保存每轮完整动态投影的序列化字节，约为 R 乘投影大小；它在每个时刻重新创建。`allocated` 与 `executed` 则在每次访问登记两个 BTreeSet 身份，跨时刻不清理。即使 `--no-output`，运行 t 个时刻的历史身份空间也随 `t·R·T` 增长，查找还随集合长度带对数成本；关闭日志不等于常量空间。
4. full_state_each_instant 在 `rows` 累计全部完整快照；checkpoint_delta 累计事件、检查点和差分，当前状态数组有变化时仍整体替换。两格式都不是边算边写的流式记录器，CLI 最后还要生成完整 pretty JSON 字符串。

这些成本可从代码循环直接定位。任务书4 §4.8 不设性能指标，README 已披露重复扫描和大布局未验收；没有凭一个小样例把它们另列为不合规格的 finding。进入参数枚举执行器之前，建议给单位/角色格、单位侧邻边建立索引，并对物理可动集合及阻尼作有依据的失效更新；事件身份的压缩还须保持《内核输入》§3.1/《内核输出》§2 的全局唯一性，不能简单清空登记表。
