### KR-r3-L3-01：装载前使用未验证结构导致panic

- **severity：阻断。**
- **where：**`/home/zhuran24/zmd-research-fresh/求解器/crates/kernel/src/engine.rs:170`；`/home/zhuran24/zmd-research-fresh/求解器/crates/kernel/src/seed.rs:24`。
- **claim：**普通装载和种子派生都在验证输入结构前建立索引或改写JSON，畸形StateSeed会使CLI以101退出且不生成约定的错误结果。
- **evidence：**任务书4§4.2、§5要求显式Stop及错误不吞；受限转移§1要求invalid/unsupported等返回，内核输入§2.3要求先校验槽位身份再建寻址字典。`Engine::construct`先执行`slot.split(':')`并访问`parts[1]`，随后才在`validate_seed`核格集合；`canonicalize_seed`第24行先修改`state["semantic_context"]["parameter_values"]`，第31行才调用解析验证。

从合法粉碎机输入仅将第一项inventory.slot改为`bad`，release公开`run`在engine.rs:170报`index out of bounds: the len is 1 but the index is 1`，退出101、stdout为空、没有结果文件。相同来源的有效对照退出0；改为`bad:input:0`则正常返回invalid_input/退出2。另仅将`initial_state.nonwarehouse.value`改为布尔true，公开`seed`在第24行的JSON可变索引中报`cannot access key "semantic_context" in JSON boolean`，同样退出101且无结果。两者均不是受限模型的正常停止。

证据：[CLI探针汇总](r3-工程证据/CLI探针汇总.json)、[可重复脚本](r3-工程证据/cli_probes.py)。应在建立格索引及修改种子前完成对应结构/身份校验，使用带位置的Result返回；两个公开入口都需覆盖，不能仅捕获其中一个panic。

### KR-r3-L3-02：循环装载把资源未决归为stopped

- **severity：重要。**
- **where：**`/home/zhuran24/zmd-research-fresh/求解器/crates/kernel/src/cycle.rs:685`，由`src/main.rs:175`调用。
- **claim：**`load_stopped_cycle`将装载阶段的inconclusive错误改报为stopped，导致同一整数资源不足在run与cycle的顶层状态中分类不一致。
- **evidence：**受限转移§1区分inconclusive(resource)，内核输出§1将inconclusive定义为资源不足，§5.1、§5.3要求资源未决与unsupported/unresolved停止分开。第685行的status分支只有`invalid_input`和其余一律`stopped`；同一行却把原inconclusive的stop.kind保存为`resource`。

以生产循环环带为基础，仅将非空运输格`a:transport:0`的entered_at设为可表示的i64最小值。当前时间减该值超出i64，`compute_physical`正确返回`inconclusive(resource.integer)`。公开run的顶层status为inconclusive；公开cycle却给`status=stopped, stop.kind=resource, stop.axis=resource.integer`，两者都退出2。这会使按顶层status统计、保留和重试未决点的执行器漏分类。没有据此声称代码产生了假周期。

证据：[同源CLI对照](r3-工程证据/CLI探针汇总.json)、[循环结果](r3-工程证据/cycle-load-age-overflow-result.json)。装载外壳应保留inconclusive分类；运行中和键归一阶段的现有资源分支不能代替这个入口的回归。

## 2. 缓存读集及失效条件

依据正式规则的物品格、滞留、轮询、两种优先级、阻尼、物品准入口和协议储存箱，结合受限转移§2–§4，缓存必须保持同一次计算的源选择、目标选择、可动性及排序结果。以下结论限定于完整装载后、布局/设定/参数固定的运行段。

`physical_cache`缓存的是PC的`(Option<Route>, reason)`。读集为：现存边；两端单位/端口/桥轴；源格物种、非空状态和entered_at；目标格物种/数量/容量、本单位其它普通格的同种占位；仓库物种/数量/历史身份、标签、匿名空格序O及端口指派；门身份设定和阻断原因；当前时刻与两端端口预算；执行模式的D.2守卫。它不读轮询游标和current_level。

级排序分两部分：静态键`level_keys=(最大阻尼,最早接通时刻)`读取级成员、当前图、沿途机型/桥轴、局部分叉表和接通时刻；最高可动级另外读取该级全部成员的physical结果及显式level_order。级内授权仍现场读取next_channel和接通环，不缓存授权。

| 会改变结果的变化 | 写入及失效路径 | 审查结论 |
|---|---|---|
| 普通格入货、减量、清空、物种改变、新entered_at | engine.rs:1014、1048的remove/put先invalidate_slot；cache.rs:15按整个单位的全部几何入/出PC失效，并标脏这些PC两端的侧 | 完备覆盖同单位跨格影响；桥的另一轴也包括在内 |
| 制造输入归集、旧批出缓存、换种导致普通格占位改变 | transition.rs:7经remove/put修改普通格；出缓存前逐项核同种与容量 | 源/目标选择缓存随普通格更新失效；不只处理首物种 |
| 仅buffer内容、phase、remaining改变 | boundary完成改buffer；制造模板现场读取progress/buffer | physical不读buffer或phase；随后影响普通格时走上述失效。直接clear buffer不构成遗漏 |
| 仓库数量、历史身份、匿名格赋种、新标签或O变化 | warehouse.rs:179的commit_deposit统一invalidate_unit("@warehouse")；仓库remove经invalidate_slot | dependencies覆盖全部有仓库指派的口及核心端PC，不只失效当前物种的一口 |
| sufficient出矿，源仓库存量保持、端口预算变为1 | 成功PC先put目标，再写两口usage；目标失效包含这条PC和双方侧 | 本几何一个端口至多一条PC，因此不必为未变化的其它矿口库存额外失效；失效后到预算提交之间没有physical查询 |
| 普通成功PC消耗端口预算 | put/remove或核心commit先失效，随后usage写入；门图刷新在其后 | 没有把提交前结果再次填回缓存的间隙 |
| 箱体无线成功清空全部格，并向仓库入库 | warehouse.rs:180失效仓库PC，279再失效箱体PC，281才逐格清空 | 两端依赖都覆盖；拒收/空箱的冷却变化不被physical读取 |
| 新tick令年龄增长，预算清零，制造/冷却推进，显式补矿 | transition.rs:668先全失效并清级键，再boundary，最后refresh | 每刻重新计算相关守卫；显式补矿另经commit失效 |
| 成品生产代表归零及历史身份转换 | transition.rs:668全失效后，在684调用represent_products；尚未进行physical计算 | 私有代表化当前调用点安全，不能据此将它移到缓存填充之后而不加失效 |
| 门身份不符、累计或窗口耗尽导致删边；窗口到期恢复 | polling.rs:379重建实际图，经354重建记忆；全失效、清level_keys、重建级成员再refresh | 覆盖远处路径改变阻尼、可用出支集变化及级出现/消失；不限于邻接PC |
| 失败尝试或成功后游标前移、current_level变化 | polling.rs::advance直接改游标；grant现场读取；physical无反向依赖 | 不需因纯游标变化失效physical；改变可动集合的事务已标脏侧 |
| 开关、供电、端口指派、布局/桥方向、接通序、分叉表、级仲裁、输入格序或容量参数变化 | 当前运行段固定；调试、离线、重建等在check_external_stops先停止；更换参数重新解析/构造Engine | 不属于当前运行中的漏失效证明；未来支持这些写操作必须重建dependencies、slot_groups、arbitration_rank及相应缓存 |

补充核对：cache.rs::cached_physical只缓存成功返回的计算结果，错误由`?`传播。polling.rs:173在dirty为空的提前返回之前仍做生产域矿候选预检，不能用缓存命中跳过该动态停止条件。级键也在每tick清空，比只在图变化时失效更保守。缓存开关切换会清physical并标脏全部侧；相同固定图下残留的静态键不改变结果。

失效充分性可按每次原子事务归纳：构造时为空；事务不写上述读集则旧结果仍有效；写读集的事务依表失效覆盖全部受影响PC及两端侧，图事务覆盖全部级与路径；失效期间不穿插其它模板。因此在当前支持域，下一次physical/refresh/grant读取到的是与直接计算相同的值。这个论证不授权调用方绕过接口直接修改Engine公开字段后继续复用派生索引。

独立[缓存探针](r3-工程证据/cache_probe.rs)对24个样例共544个时刻，逐字段比较直接计算、启用缓存、内存解析并反转单位/PC/BC/inventory数组的三个执行结果，全部相同，见[结果](r3-工程证据/缓存扩展差分.json)。现有round5_cache_differential另涵盖三份规模fixture。有限差分是上述读写审查的补充，不是所有参数点的穷尽证明。

## 3. 确定性、数值及三处工程修复

确定迭代序：状态寻址、依赖、图、排序键和查重使用BTreeMap/BTreeSet；语义顺序使用显式template_order、connection.tie、level_order、recipe_order、slot_order和轮询members，不能用库存排列代替。仓库新物种的UTF-8规范顺序只在规格允许的无可观察标签竞争分支使用。未发现HashMap/HashSet迭代影响输出。

数值与unsafe：生产源码未发现f32/f64计算或unsafe代码，lib.rs使用`forbid(unsafe_code)`。StrictValue拒绝文件中的浮点和重复键，内存解析另经validate_tree拒绝浮点。时刻/数量用整数，率用i128交叉乘法及精确有理约分；时差溢出本体返回resource.integer。性能脚本中的小数是纳秒换算的测量统计，不参与转移。不能把这些检查表述为任意无界整数运算均已支持；装载资源状态遗漏见KR-r3-L3-02。

三处潜伏修复的核验结果：

1. **max_sweeps已接入。**main.rs:66–73解析正整数，run及cycle都传入实际引擎；扫描上限在transition.rs:694执行。环带`--max-sweeps 1`使run退出2、completed_ticks=0、统计inconclusive=1；改1000则两刻完成。cycle的一轮预算亦给resource.sweeps/inconclusive，未将预算当闭包。两刻预算不足以找到20刻周期时仍报resource.ticks，不能把它当修复失败。
2. **基目录接口已实现。**input.rs:306的parse_with_base以虚拟memory-input.json定位引用，不读取该输入文件；24个样例在该文件实际不存在时解析并与文件入口结果相同。seed导出的绝对目录/轴表引用在复核目录再次run四刻通过。需要文件指纹的交付记录仍要求输入持久化，未要求取消依赖文件验证。
3. **inventory规范排序已实现。**engine.rs:79在装载时按slot排序，索引由排序后的数组建立；反转库存表示没有改变完整tick。成员接通环等有语义顺序的数组没有被该排序误改。畸形标签的验证时序另见KR-r3-L3-01。

制造潜伏项一并确认：remaining归零决定完成，预计pending截止只作身份审计；completed输出守卫遍历全部缓存和取货格内容，核单种、容量及所有输入格的同种冲突。现有暂停完成测试是受控内部试验，不充作固定开关运行段中已触发transfer.resume_event的证据。
