## 2. 发现与完整论证

### KR-r5-L2-01：生产域装载先读矿容量，D.2守卫执行过晚

**严重度：重要。** `check --cycle-domain`及循环搜索在D.2检查之前，以普通有限仓库模式重算物理可动集合和轮询当前级，违反D.2先于矿容量/physical/级排序读取的顺序要求。

依据是受限转移§6.1 D.2及内核输出§5.1.1、§5.3第3步：现存PC的源候选为矿、目标为核心时，必须在目标容量及其它物理/权限筛选之前停止；包括最终满仓拒收的尝试。这里不反对读取正库存合法性，也不要求放过伪造的轮询种子；问题是域外候选已存在时仍先计算矿容量能否接收。

实际调用链：

1. `src/main.rs:208`先调用`Engine::new`，209才调用`domain_report("static")`。`src/cycle.rs:594–602`同样先new，596才打开`production_abstraction`。
2. `src/engine.rs:311`把该标志初始化为false；350在返回前执行`rebuild_memory()`。
3. `src/polling.rs:349–360`重建分级后调用refresh；168的D.2检查以`production_abstraction`为前件，此时跳过；217继续调用physical。
4. `src/engine.rs:1048`的局部D.2保护同样因false跳过，1060随后调用target；核心目标进入`plan_deposit`。`src/warehouse.rs:158–166`读取仓库原矿数量，比较`old + 1`与80000，影响`current_level`。

复现由[probe.py](r5-规格保真与工程-证据/probe.py)构造。复用现有`core_inbound.json`的几何，在`belt:transport:0`放入已滞留1刻的1件源矿，并显式设置sufficient。分别用79999、80000源矿库存派生合法种子，两者普通check均通过，静态域检查最终也都能报D.2 fail；但在到达该报告前，核心input侧的当前级分别被算成`L|core|input|other`和null，见[ore-dependent-memory.json](r5-规格保真与工程-证据/ore-dependent-memory.json)。两份合法输入、调用和输出均保留。

进一步只改79999种子的矿量为80000、不更新轮询记忆，`check --cycle-domain`先报`invalid_input @ poll_memory`，五项D均变成unresolved/not_checked，见[ore-capacity-changed-domain.log](r5-规格保真与工程-证据/ore-capacity-changed-domain.log)。此交叉试样的轮询记忆确实已不符合普通有限状态校验，**不作为合法循环输入反例**；它仅展示容量依赖的校验发生在D.2之前。两份分别派生的合法种子及明确调用链才是本发现的主证据。

影响：新静态入口和生产装载尚未满足“先检查回矿候选、再读物理容量”的工程契约；D.2诊断还可能被后续容量依赖校验抢先覆盖。本席没有据此找到误发的周期证书。运行推进后的refresh和有资格transfer守卫位置正确，已有回归也通过，不能用它们覆盖构造阶段。

修订方向：分离结构/库存合法性检查与容量依赖的级/权限重建，让生产域构造在第一次physical求值前具备D.2保护；静态命令保留五项报告，并保持普通finite_concrete的真实容量语义。

### KR-r5-L2-02：合法相对路径记录在批验和恢复入口被拒收

**严重度：重要。** 仅将已核记录的来源和producer路径改为契约允许的相对路径，同一材料能通过verify-cycle，却被verify-record、verify-batch和记录checkpoint入口拒收。

内核输出§1的fingerprints允许绝对路径或相对记录文件的路径；§5.1第112–116行明确各路径按所属文件目录解析；§5.3第1–2步要求引用式材料整链验收。任务书6 K4要求批量入口核全部v3记录与证书，K1要求检查点分段续跑。合法的路径表示变化不改变轨迹及固定三元组。

代码有两处同一根因：`src/main.rs:138–149`的verify-record把input指纹路径直接传给`Input::load`，相对调用cwd而非记录目录；即使cwd碰巧正确，`src/output.rs:566–568`仍将含相对fingerprints/producer.path的原记录与生成器输出的绝对路径对象直接比较。checkpoint的记录分支在181正确拼接了输入路径，却在182进入同一个未规范路径的比较器。`tests/verify_all.py:43–54`对completed记录调用此入口，已由证书核过的completed记录也会再次失败。

复现有完整绝对路径对照与合法相对路径材料包：

| 材料及命令 | 结果 |
|---|---|
| 原始`referenced-7.record.json` → verify-record、checkpoint | 均退出0 |
| 只相对化fingerprints[].path和producer.path的`relative.record.json` | schema通过；轨迹、参数、库存及所有来源sha256不变 |
| 对应引用式证书 → verify-cycle | 退出0，前缀与P刻均重跑通过 |
| 同一相对记录 → verify-record，cwd=求解器 | 退出2，按错误基目录找不到来源 |
| 同一相对记录 → verify-record，cwd=记录目录 | 退出2，`交付记录与完整重算逐字段不同` |
| 同一相对记录 → checkpoint | 退出2，同一比较错误 |
| [relative-package](r5-规格保真与工程-证据/relative-package/certificate.json)含该记录及能验过的证书 → verify-batch | 退出2，失败于记录独立验收 |

构造时仅重新计算被引用记录**自身**因路径文本变化而改变的sha256；未更新任何来源文件摘要，未改轨迹。verify-cycle成功是因为`src/cycle_io.rs:173–191`已经按记录目录规范producer和fingerprints，再与重算结果比较；它与其它入口的行为不一致。

证据：[extra_probe.py](r5-规格保真与工程-证据/extra_probe.py)、[extra-results.json](r5-规格保真与工程-证据/extra-results.json)、[relative-record-verify-local.log](r5-规格保真与工程-证据/relative-record-verify-local.log)、[relative-package-batch.log](r5-规格保真与工程-证据/relative-package-batch.log)、[extra-schema-results.json](r5-规格保真与工程-证据/extra-schema-results.json)。

影响：按引用式契约组织的合法材料包不能可靠进入统一批验或从记录导出检查点。修订应共享带基目录的记录装载/验收入口，在内存中规范路径，同时先核原始字节sha256；不能靠改写被审文件或放宽事件/状态比较解决。

### KR-r5-L2-03：诊断外壳被checkpoint当作可恢复材料而panic

**严重度：重要。** checkpoint把verify-cycle的“诊断已复现”成功返回当成存在可恢复输入，随后解引用合法的null，退出101。

内核输出§5.1.2明确允许装载前失败对象的replay_input_ref、last_state、cycle全为null；§5.3第1步允许在复现相同装载停止后核诊断，但这不表示存在运行状态或周期。受限转移§1要求无法形成后继时返回具位置的停止。checkpoint可以拒绝这种对象，但必须判明没有可恢复状态。

直接使用被审交付的`evidence/round6/cli/overflow.json`，没有篡改：verify-cycle退出0且返回`diagnostic_replayed=true, cycle_replayed=false`；紧接着执行checkpoint，`src/main.rs:164`忽略这一区分，168对`artifact["replay_input_ref"]["path"].as_str()`调用unwrap，触发`called Option::unwrap() on a None value`。退出101，无结构化错误输出，也没有生成检查点。

复现命令（在求解器目录）：

```bash
target/release/kernel verify-cycle crates/kernel/evidence/round6/cli/overflow.json --config 规格/内核配置-v1.json
target/release/kernel checkpoint crates/kernel/evidence/round6/cli/overflow.json --config 规格/内核配置-v1.json --out crates/kernel/复核/r5-规格保真与工程-证据/invalid-checkpoint.json
```

原始日志：[load-shell-verify.log](r5-规格保真与工程-证据/load-shell-verify.log)、[load-shell-checkpoint.log](r5-规格保真与工程-证据/load-shell-checkpoint.log)。修订应在取source/state之前检查已装载引用及末态是否存在，诊断外壳返回带checkpoint位置的明确拒收，不能从不存在的状态推导续跑输入。

## 4. D.1–D.5、put及摘要碰撞专项

| 义务 | 实现核对 | 结论 |
|---|---|---|
| D.1 固定上下文、整数/global、sufficient及未来事件 | Input/Engine装载及cycle.rs:150–198；固定图/设定/参数不在搜索中改写；未来历史及预占运行身份检查 | 未发现新增不一致 |
| D.2 唯一正矿、原子补回、候选回矿与全箱回矿 | cycle.rs:199–231、278–299；polling.rs:168、warehouse.rs:259–269；矿候选检查只依赖活动边和源物种，传输在容量计划前检查 | 运行路径通过；构造阶段未前置，见01。矿正数/合法范围校验与容量守卫区别对待 |
| D.3 成品格不可指派、O为空、规范新格标签 | cycle.rs:232–262；Engine先核指派格存在；retain_history及新格绑定身份保持O不扩张 | 未发现新增不一致 |
| D.4 全部静态装载义务及未来无终点请求 | cycle.rs:264依赖完整Engine装载；报告声明未来动态请求仍停止、可达性未证 | 未把pass解释为种子可达或未来全准入 |
| D.5 结构界B | cycle.rs:121–143、265–272；全部几何核心入PC加300×有电且传输开启箱数，严格小于80000 | 算式和失败边界一致；没有以实测低流量替换结构界 |

`Engine::put`位于engine.rs:1143–1191：先确认本地格身份和正入量，普通格逐项核物种，单次count先核容量，再核合计，之后才失效缓存和写库存。错误是带slot位置的Stop::invalid；buffer依据正式规则L18允许多物种、无限容量，其caps来自目录。第六轮两项回归分别核错物种/超容拒收后的完整状态不变，以及临时双产物配方在缓存共存、普通取货格整批拒收；正式目录字节未变。

seen为`BTreeMap<String, Vec<usize>>`，没有每刻完整键或状态（cycle.rs:606）。完整State仅保留种子、当前/末态和间隔检查点；before_boundary不入seen，after_closure锚点位置0可入。恢复选择`checkpoints.range(..=position).next_back()`，按相同参数推进到候选；第一次before_boundary位置计数与step_compact的first处理对应。摘要同桶逐个候选恢复后比较完整键，只有`candidate == key`才发周期；不相等则保留所有旧位置并追加当前位置（639–667）。恢复不足返回resource.replay，不当键相等。

独立重跑的强制所有键碰撞测试通过，间隔7时完整结果等于正常搜索；故障注入replay_limit=0得到inconclusive且无cycle。本席另用公开CLI把检查点间隔设为1及7，两份无记录结果完全相等，见[interval-comparison.json](r5-规格保真与工程-证据/interval-comparison.json)。搜索间隔与记录checkpoint_interval独立，两者都要求正整数；碰撞消歧未发现不一致。
