## 2. KR-r5-L2-01：生产域装载的 D.2 守卫顺序

**裁定：未能否证，`refuted=false`。** 生产入口确实在检查 D.2 前，用有限仓库容量算过物理可动集合及当前级。最终能报告 D.2 失败，不满足规格要求的“容量读取前”停止。

### 2.1 原文与实际调用链

受限转移 §6.1 D.2 要求：每次准备计算 physical 集合、级排序或授权前，检查全部现存 PC 的源候选；源候选为两矿之一、目标为核心存货端口时，在目标容量及其它物理/权限筛选前停止。即使年龄、端口预算或权限不满足，也不能跳过候选。输出 §5.1.1 第 126 行和 §5.3 第 3 项重复了先后要求；KQ-08 亦明确满仓拒收候选在内。

源码调用链如下，各处均已回源读取：

1. `src/main.rs:208–209` 的 `check --cycle-domain` 先 `Engine::new(input)`，后 `domain_report("static")`；`src/cycle.rs:594–602` 的搜索先 new，596 才设 `production_abstraction=true`，600 起报告和检查域。
2. `src/engine.rs:311` 在构造中把模式置为 false；350 执行 `rebuild_memory()`。`src/polling.rs:349–360` 重建级后调用 `refresh()`。
3. `src/polling.rs:168–170` 仅在模式为 true 时调用 `check_production_candidates()`，此时跳过；217 继续调用 `physical()`。构造阶段 `cache_enabled=false`，没有用旧缓存规避这次求值。
4. `src/engine.rs:1048–1060` 的局部矿候选守卫也被 false 跳过，随后 `target()` 的核心分支（969–973）进入 `plan_deposit()`；`src/warehouse.rs:158–166` 读取矿仓数量并比较完整入量与 80000。

### 2.2 独立运行

从既有 `tests/fixtures/core_inbound.json` 复用几何，在 `belt:transport:0` 放 1 件源矿，`entered_at=-1`、当前时刻 0，显式指定 sufficient。对 79999、80000 两个矿量分别派生自洽种子。两份种子均通过 **真实 `Input::load(..., false)` 和 `Engine::new`**，不是仅通过结构检查。

独立 Rust 探针源码嵌在 `reproduce.py::probe_constructor`，由标准输入交给 rustc，二进制只写入 `求解器/target/r5_seat1_constructor_probe`；没有修改内核或插桩。探针在 `Engine::new` 返回后、调用 `domain_report` 前取出公开的模式和记忆。结果见 [constructor-observation.log](否证-r5-1-证据/constructor-observation.log) 与 [ore-results.json](否证-r5-1-证据/ore-results.json)：

| 源矿量 | Engine::new | 返回时生产抽象开关 | 核心 input 当前级 | 随后的 D.2 报告 | 普通 run 首刻源矿入库 |
|---|---|---|---|---|---|
| 79999 | 成功 | false | `L\|core\|input\|other` | fail | 1 件 |
| 80000 | 成功 | false | null | fail | 0 件 |

两份输入的 `check --cycle-domain` 最终均退出 2、D.2=fail；`cycle --max-ticks 1 --no-record` 均停止且没有周期。普通 run 的一件入库/容量拒收对照符合有限仓库语义，进一步确认两份输入不是伪造的普通运行状态。证据分别为 `ore-79999-*`、`ore-80000-*` 文件。

### 2.3 否证尝试与边界

- **“构造只是普通种子校验”不足以否证。** 输入 §6.3 的确要求核当前级，普通 run 也应保留真实容量。本发现不反对库存数值范围、身份或种子完整性校验；它指出生产入口复用的构造过程已经计算了规格要求在 D.2 后才允许计算的矿目标容量。输出契约没有给构造阶段豁免，可以先核必要结构并排除当前矿候选，再进入依赖容量的重建。
- **“最终都拒收，没有误发证书”不足以否证顺序问题。** 本席确实没有得到误发周期，这限定了影响范围，却不能使已经发生的提前读取满足“先于”要求。
- **现有测试未覆盖这一顺序。** 独立重跑 `round5_ore_return_candidate_stops_before_capacity_or_age`、两项 `round6_static_*` 均通过，见 [旧 D.2 测试日志](否证-r5-1-证据/existing-d2-test.log)、[静态测试日志](否证-r5-1-证据/existing-static-tests.log)。前者先成功构造再断言 production_domain/search 停止；后两项核报告及后续动态停止，没有断言构造前置顺序。它们与本席观察可以同时成立。

本裁定不使用“只改矿量、不更新轮询记忆”的交叉输入作为合法反例，也不要求 D.2 之前禁止读取矿量以检查正库存或容量合法范围。

## 3. KR-r5-L2-02：相对路径记录的入口不一致

**裁定：未能否证，`refuted=false`。** 同一已核运行记录只改合法路径表示，能通过引用式周期验收，却被独立记录验收、批量验收和记录 checkpoint 拒收。

### 3.1 契约与源码

输出 §1 的 fingerprints 明许绝对路径或相对记录文件的路径；§5.1 的引用说明规定证书引用相对证书目录、目标 JSON 自身的路径相对目标文件目录，明确排除调用 cwd 作为基准。§5.3 要求按所属文件目录解析后核完整来源链。

`src/main.rs:138–148` 的 verify-record 把 input 指纹中的字符串直接交给 `Input::load`，未以记录父目录拼接。`src/output.rs:565–568` 又直接比较原记录与重新生成的整份绝对路径记录。记录 checkpoint 在 `main.rs:181` 拼接输入路径正确，但182起仍进入这个未规范路径的比较器。`tests/verify_all.py:43–54` 对 completed 记录调用 verify-record，已被证书核过的 completed 记录也不例外。

相比之下，`src/cycle_io.rs:173–191` 已规范被引记录 producer 路径和 fingerprints；其 `canonical_fingerprints` 同时读取真实源并核原始字节 SHA-256。这说明路径解析已有正确覆盖，但仅在周期验收入口，不能覆盖其它三个入口。

### 3.2 独立材料与实测

本席用当前内核从 `数据/样例/生产循环环带.json` 重新生成 [绝对路径证书](否证-r5-1-证据/absolute-package/certificate.json) 和记录（21 个完成时刻，周期 P=20）。随后仅把记录的 fingerprints[].path 和 producer.path 改为相对其新目录的表示，形成 [相对路径材料包](否证-r5-1-证据/relative-package/certificate.json)。仅更新证书对该记录原始字节的摘要与对应引用路径，没有更新任何来源文件 SHA-256。

[relative-equality.json](否证-r5-1-证据/relative-equality.json) 记录独立检查：把相对路径按记录目录恢复为规范绝对路径后，两份记录整个 JSON 对象相等；轨迹、参数、库存和来源摘要均不变，且每个来源摘要都重新读取文件核过。两种记录、两种证书均通过当前 schema，见 [schema-results.json](否证-r5-1-证据/schema-results.json)。

| 同一材料的入口 | 绝对路径包退出码 | 相对路径包退出码 | 相对包结果 |
|---|---:|---:|---|
| verify-cycle，cwd=求解器 | 0 | 0 | 前缀与 P 刻重跑通过 |
| verify-record，cwd=求解器 | 0 | 2 | 输入相对调用 cwd，找不到文件 |
| verify-record，cwd=记录目录 | 0 | 2 | 已能找到输入，但原记录与绝对路径重算对象不同 |
| 记录 checkpoint，cwd=求解器 | 0 | 2 | 同一整对象比较错误 |
| verify-batch，cwd=求解器 | 0 | 2 | 证书已核；completed 记录再次进入 verify-record 后失败 |

原始日志为 `absolute-*`、`relative-*`；关键证据见 [相对周期验收](否证-r5-1-证据/relative-verify-cycle.log)、[本地 cwd 记录验收](否证-r5-1-证据/relative-verify-record-local.log)、[记录恢复](否证-r5-1-证据/relative-checkpoint.log)、[批量验收](否证-r5-1-证据/relative-batch.log)。

### 3.3 否证尝试与边界

“相对路径找不到文件只是运行位置不对”被本地 cwd 对照排除；本地 cwd 仍失败于对象比较。“移动后来源失效或记录被改坏”被来源原字节核验、规范化后整对象相等及 verify-cycle 成功排除。“cycle 已覆盖记录，所以 batch 会跳过”与 verify_all.py 的 completed 分支及实际批验失败不符。

保持运行状态、事件和 JSON 类型严格比较是必要的；本发现只要求按照契约解释路径，不主张放宽实际轨迹比较，也不授权改写既有记录的来源摘要。

## 4. KR-r5-L2-03：装载失败外壳的 checkpoint panic

**裁定：未能否证，`refuted=false`。** 原始合法诊断外壳可通过诊断复现，但 checkpoint 将该成功返回误用为存在恢复输入，实际对 null 解引用。

### 4.1 原文与代码

输出 §5.1.2 允许、并在装载前失败分支要求 `replay_input_ref/run_record_ref/last_state/cycle/level=null`、`completed_ticks=0`；schema 的 CycleResult 对 `replay_input_ref=null` 分支作相同约束。§5.3 第1项允许复现同一装载停止后核诊断，未声称存在游戏转移或周期。输入 §6.4 的恢复则要求真实完整状态。

`src/cycle_io.rs:140–141` 明确返回 `diagnostic_replayed=true`、`cycle_replayed=false` 的成功对象。`src/main.rs:164` 只使用 `?` 接受成功，没有判断是否存在恢复上下文；168 对 `artifact["replay_input_ref"]["path"].as_str()` 直接 unwrap。合法 null 因而落入 panic。

### 4.2 独立运行与否证尝试

直接使用未改动的 `crates/kernel/evidence/round6/cli/overflow.json`；SHA-256 为 `5dafe7e264eef6ad796ec580d5e15162dddf244edffe665301d97adb74f55179`。当前 schema 接受该文件，记录状态为 `inconclusive`、停止轴 `resource.integer`、原因“时差溢出”，恢复引用和末态均为 null。

- [load-shell-verify.log](否证-r5-1-证据/load-shell-verify.log)：verify-cycle 退出 0；返回 `diagnostic_replayed=true`、`cycle_replayed=false`。
- [load-shell-checkpoint.log](否证-r5-1-证据/load-shell-checkpoint.log)：checkpoint 退出 **101**，标准错误定位 `crates/kernel/src/main.rs:168:77`，报 `called Option::unwrap() on a None value`；标准输出为空，没有生成检查点。
- [load-shell-state.json](否证-r5-1-证据/load-shell-state.json)：保留输入摘要、合法 null 分支及目标文件不存在的检查结果。

“该外壳格式非法”被 schema 和实际诊断复现排除。“诊断核验成功意味着有可恢复状态”与规格、返回字段及 null 内容相矛盾。checkpoint 可以明确拒绝无恢复状态材料，但当前行为是未处理的程序 panic，不能以本来就不可恢复否证这一发现。绝对路径完整记录的 checkpoint 同时通过（§3），故并非本机所有恢复调用都失效。
