## KR-r1-L1-01

**结论：`refuted=false`。未能否证；缺矿前提失效后仍正常完成的行为已复现。**

原文：《求解任务》L7 要求两矿“持续可得且足够覆盖任意数量的消耗”；《受限转移定义》§2.1（L23）明确限制空历史：当前库存足以覆盖整段消耗，且不违持续可得。《受限模型声明》§2（L100）同样要求容量内、持续充分的输入历史。这是被测环境的前提，不是达标率守卫。

代码：`interfaces.rs:169–221` 校验 through、补给物种/数量/时间及 runtime 引用，`:262–265` 只核外部过程名称；`transition.rs:267–278` 仅以 `t > through` 停止，`:451–506` 只执行已列补给。`engine.rs:737–752、864–870` 在仓库空格时返回无源候选，按普通 `source_empty` 处理，没有持续充分性失败的停止分支。

独立复跑既有 `r1-规格保真-证据/ore-shortage-input.json`：任务初始锚点六种仍各80000，当前条件种子源矿为1，补给为空且 through=3。新产物[ore-l1-record.json](否证-r1-1-证据/ore-l1-record.json)退出0/completed，t=0…3 仓库源矿均为0。唯一出库发生于 t=0；t=1 该件入粉碎机缓存后，进料带已空，矿口及进料带存货口的本刻额度均未用，却无法补入第二件。正常原输入在相同时间段出库4件，完成2批；负例仅出库1件、完成1批。

已检验的反驳：① through=3 只能证明没有越出声明的时间段，不能证明物料供应；②“实际只消耗1件，所以1件足够”忽略缺矿已经削减了后续尝试，且不满足独立的持续可得要求；③这不是仅在最后边界恰好用尽的争议，t=1 后还有被测时段和可补货机会；④条件种子未证可达不免除该段环境前提。上述反驳均不能消除此发现。

## KR-r1-L1-02

**结论：`refuted=false`。未能否证；当前轨迹明确逆于输入的同刻执行先后。**

原文：《内核输入》§3.1（L88–90）规定统一事件域、occurs_before 的执行先后，以及所有来源偏序取交集、冲突拒收。《受限转移定义》§2.1 要求按输入显式序回放补矿。规则L25、任务L14提供同刻顺序语义的来源，但本条的直接错误是工程历史接口不相容。

代码：`input.rs:84–134` 只在 timeline.relations 自身建图验环；`interfaces.rs:189–221` 只核补给数组时间非递减，不把数组先后并入关系；`transition.rs:464–505` 按补给数组顺序执行。KQ-01 披露了同刻采用数组序的临时编码，并未授权覆盖统一关系。

本席重读输入：种子仓库源矿为79990；补给数组为 `[supply_a,supply_b]`，两个事件均在 t=1 补1源矿；关系明确 `supply_b occurs_before supply_a`。容量有余不是拒收来源。[supply-order-record.json](否证-r1-1-证据/supply-order-record.json)仍退出0/completed，实际补给事件序为 `supply_a,supply_b`，Rust 重算也接受。

已检验的反驳：两次同种加法的终态可交换，不能使相反的事件历史合法；本输出契约明确保留事件和顺序。KQ-01 的字段形状待定，也不能否定早已写明的关系交集义务。

## KR-r1-L1-03

**结论：`refuted=false`。未能否证；恢复路径漏核历史身份，Rust 自身重算重复了该错误。**

原文：《内核输入》§3.1（L88）规定共用 ID 只能引用同一实例、历史登记不能被新实例复用；§6 的 pending 引用与 trigger 仍在统一域。《内核输出》§2（L33）、§3（L47）要求拒绝历史别名及同 ID 的操作/目标/触发改变，明确不能仅靠重算相等。规则L25、L35区分判定与制造完成，ID本身属于工程编码。

代码：`engine.rs:136–142` 将 timeline ID 和 pending ID 汇入集合，碰撞被合并；`:159` 的 executed 初始为空；`:236–256` 只约束特定 runtime 前缀；`:626–670` 检查 pending 自身唯一、进度及期限，没有检查同名历史事件的 kind/time。到期经 `transition.rs:371–403` 消费原 pending ID。`allocate`/`precheck_new_event` 能拒绝新分配碰撞，但该恢复事件不再走新分配；`execute` 只核已分配和本次已执行集合。

负例与合法 after_closure 对照的唯一内容差别，是 pending ID 改成 `build_0`（另见输入差异证据）。历史中它是 t=-13 的 build；新记录却在 t=2 用它表示 crusher 的 manufacture_complete。[historical-alias-record.json](否证-r1-1-证据/historical-alias-record.json) completed，公开 `Input::load`、`Engine::new`、`verify_record` 均成功。原 `runtime_record.validate_event_identity` 独立拒绝：`待事件与输入历史身份冲突: build_0`；未改名对照通过。

已检验的反驳：新事件生成器有冲突检查是真的，但没有覆盖恢复日程这一入口；pending 中合法 runtime 引用允许共享名字，也不意味着允许与一个已建造历史事件共享身份。`output.rs:365–394` 的整份重算相等不能代替契约要求的独立身份核验。

## KR-r1-L1-04

**结论：`refuted=false`。未能否证；确认的是错误离线引用漏拒收，不是正确离线事件漏停。**

原文：《内核输入》§3.1（L88）要求事件引用同域且由相应记录拥有；§3.3（L106）明确 selected_events[].event 指 offline。《受限转移定义》§1 排除运行段内离线后效；配置 offline.events 遇离线即停。正式来源为任务L13，不能把 runtime 注册当成同一次离线的合法类型。

代码：`interfaces.rs:267–274` 只核 offline/product_withdrawal 子对象键，没有逐条核 selected_events 引用。`transition.rs:279–319` 遍历 timeline.kind，并直接跳过 runtime；它没有反向核拥有离线记录的事件必须为 offline。

本席直接比较两输入，唯一差异为 `/timeline/events/27/kind`。误指 runtime 的[offline-wrong-kind-record.json](否证-r1-1-证据/offline-wrong-kind-record.json)退出0/completed、运行4刻；改回 offline 的[offline-control-record.json](否证-r1-1-证据/offline-control-record.json)退出2，在 t=1 以 `offline.events @ review_offline` 停止，只保留 t=0。坏引用还通过 Rust 自身重算。

已检验的反驳：合法离线确有停止实现，与坏输入漏检是两件事。否证该发现需要已有引用检查实际拒绝负例；只指向正常停止分支不能做到。离线一例足以支持本条核心，不据此宣称所有调试和拿取形状都已逐种复现。

## KR-r1-L1-05

**结论：`refuted=false`。未能否证；查询无关的表项确实被公开装载和执行接受。**

原文：《内核输入》§5.3（L295）规定 fork_unit 必须沿该查询方向实际遇到，明确禁止无关分流器、断边或非出支入表。规则L27的阻尼是实际所经元件，分叉只数其中一支；“有这个分流器”不等于“本查询会遇到它”。

代码：`input.rs:657–688` 只核查询边存在、fork_unit 为分流器、选中边从该单位出发，以及键唯一；没有核 query→fork 的路径相关性。`polling.rs:140–160` 在实际求值遇多支时核对应选择，只能保护被遇到的查询，不会筛除表中永远无关的项。

本席重跑 `unrelated-fork-input.json`，公开 Input、Engine 及两刻运行均成功，新记录为[unrelated-fork-record.json](否证-r1-1-证据/unrelated-fork-record.json)。表项把 `PC|probe_left:west:0|probe_gate_a:south:0` 绑定到主支 `splitter`，选 `PC|splitter:north:0|north_box:south:0`。

**证据描述校正：** 原复核报告说该查询从 probe_gate_a 去 probe_merger，这与本次实际 PC 表不符。当前 probe_gate_a 没有出边；probe_left 的另一条出口才直接接 probe_merger。独立按 PC 方向展开，本查询只到 probe_gate_a 即无后继，仍确定不经过主 splitter。该文字细节有误，不推翻“所填 splitter 无关却被接受”的核心发现。

已检验的反驳：表项可能未改变这段库存，但契约禁止这类输入，不能因未使用便当作已合法校验；也不能将未定义的备用表项解释擅自补入规格。是否必须对单级请求阻尼的 KQ-04 不会解除表项相关性义务。

## KR-r1-L1-06

## KR-r1-L2-03

**结论：`refuted=false`。未能否证；未进入 completed 输出处理却给出了该轴的实际执行证据。**

原文：《内核输出》§1（L18）定义 exercised 为实际执行，要求本次逐轴证据；L56 说明不要求区分所有读法，但仍要实际触发。《受限转移定义》§4.2 第1步仅在 completed 才处理整批输出及保留；规则L18、L13约束整批和容量。

代码：`output.rs:220、234` 只要存在任一 manufacture/success，便把全部 manufacturing.* 标为 exercised。`transition.rs:12–50` 的输出/受阻处理则严格位于 completed 分支；归集开工来自后续 idle/intake 分支，不等同于它。

新复跑[manufacturing-prefix-record.json](否证-r1-1-证据/manufacturing-prefix-record.json)只有 t=0、1；三个制造单位先全 idle，末刻只有 crusher 变 working，其余仍 idle。无 manufacture_complete；唯一制造成功 `J|1|0|11`，内部账仅 `BC|crusher:input:0|crusher:buffer:0`。记录却把 manufacturing.output_blocked 标 exercised 并引用此 ID。

已检验的反驳：评估 `phase == completed` 为假，不是执行了整批受阻机制；该分支主体在本次根本没进入。即便“已定”轴无需再次证明规则，也必须如实报告本段是否执行，记录自身的 other_values 亦写未执行结构仍未验证。其他单元测试能覆盖输出冲突，不能成为这份两刻记录的事件证据。

## KR-r1-L3-01

**结论：`refuted=false`。未能否证；对象类型未核验即可变索引，panic 已由新构建实测。**

原文：《内核输入》§2（L43）规定 snapshots[] 每项为对象；《受限转移定义》§1（L7）规定错误返回 invalid(field, reason) 等带信息结果；《内核输出》§1允许装载失败时以 null 字段保留停止位置。

代码：`input.rs:208–214` 只确认外层是数组，复制成员后立即 `s["base"] = ...`；false 不支持该可变对象索引，早于 Geometry::build 的 Result 返回。`value.rs:281–315` 通用封套遍历不拒绝普通布尔值；`main.rs` 的 Err(Stop) 分支不会捕获此 panic。

既有复核报告记录了 release 失败；本席从原源码新构建的 debug CLI 独立复跑同一输入，退出101，stderr 包含 `cannot access key "base" in JSON boolean`，指定 `snapshot-bool-record.json` 未生成。输入与粉碎机原样例除两个绝对路径引用外，仅 snapshots 改为 `[false]`，见输入差异文件。

已检验的反驳：非零退出不能替代规格规定的结构化、带字段位置的停止；这不是一个已被合理拒收的 invalid_input。发现针对非法输入错误通路，不声称合法快照运行受损。

## KR-r1-L3-02

**结论：`refuted=false`。未能否证；非法物品类型被当成了实际身份守卫。**

原文：《内核输入》§4（L117）要求 gates[].item 为物品名或 null；规则L64设定的是某一种物品。整数7是 JSON 数值而非物品名，也没有转换成物品名的接口规定。

代码：`input.rs:500–525` 核字段、单位类型、重复、限额，以及 item 非 null，没有核 item 为字符串。`value.rs:281–315` 允许普通整数；`polling.rs:342–360` 将 Value(7) 与货物字符串直接比较，失败便记 identity_mismatch 并断边。`engine.rs:875–877` 的物理检查也采用同样比较。

本席确认机械变异仅 `/settings/gates/0/item`（另两项为路径重定位）。[gate-numeric-record.json](否证-r1-1-证据/gate-numeric-record.json)两刻退出0/completed；probe_gate_a 被记 identity_mismatch、total_received=0。原物品名对照正常完成；同一负例中的另一门正常收件。这确认不是“数值类型在更早入口已拒收”。

已检验的反驳：设置键集合和 Quantity 限额检查存在，但不涵盖 item 的类型；把所有“不等于7”的物品都阻断，仍不是合法物品身份设定。该发现不对所有字符串物品名的允许域作额外裁定。

## KR-r1-L3-03

**结论：`refuted=false`。未能否证；当前种子的唯一性校验不能覆盖任务初仓表的重复标签。**

本席比较原样例：唯一实质变异为 `/initial_state/warehouse/slots/1/slot` 改成第一行 warehouse_0；六种满额保留，当前运行种子完全不变。[initial-duplicate-slot-record.json](否证-r1-1-证据/initial-duplicate-slot-record.json)两刻退出0/completed，公开装载及 Engine 构造、Rust 重算均接受。

已检验的反驳：本条没有要求不同时刻库存相等，也没有要求先证明种子可达。问题是输入自报的同一锚点表内两个物种共享同一标签，与已经明确的唯一性规定直接冲突；不能把未用于当前寻址的历史字段视为不必校验。

## KR-r1-L3-04
