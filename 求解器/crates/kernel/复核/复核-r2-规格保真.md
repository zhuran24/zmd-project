## 1. 判据、范围与结论

判据为三份正式文件、[受限转移定义](../../../规格/受限转移定义.md)、[受限模型声明](../../../规格/受限模型声明.md)、[内核配置](../../../规格/内核配置-v1.json)，以及所引用的运行语义、内核输入、内核输出及其schema。四份任务书已按指定次序读取；任务书3 §0的分工延期不取消本轮任务。候选约束、参考执行器、旧复核报告和实现席自述均不作为裁定规则的依据。

本报告覆盖指定的源文件、测试文件、README、修订记录、两份历史验证文档、第1轮修订证据、四份内核运行记录及全部KQ暂取处理；另外追读直接参与转移的`polling.rs`、配置、目录和状态/数值定义。机器可读发现见[findings JSON](findings-r2-规格保真.json)。

## 2. 发现及完整论证

### KR-r2-L1-01：同刻历史关系可以与实际边界顺序相反

- **where：** `/home/zhuran24/zmd-research-fresh/求解器/crates/kernel/src/input.rs:174–213`、`src/transition.rs:377–423`、`src/event_identity.rs:118–149`。
- **claim：** 统一历史未与固定边界阶段取交集，冲突的同刻先后关系仍可产出completed记录。
- **severity：** 阻断（结果会错）。

**规格依据。** 内核输入§3.1定义`occurs_before`为“执行发生在前，时刻不大于”，并要求“所有来源的偏序……取交集，冲突拒收”。受限转移§2.1明确先办工作量耗足的制造完成，“然后按输入显式顺序回放该时刻的两矿补给”，最后窗口维护。配置`time.instant_order=chronological_phases`和`time.manufacture_events=completion_before_closure`将该顺序固定。因此同刻的“补矿先于制造完成”与本版配置交集为空，应拒收或在执行前明确停止，不能忽略关系后声称完成。

**代码。** `timeline`现已把补矿数组内部次序加入有向图，但图中没有加入制造完成→外部补给等由profile产生的边。关系检查对同刻`occurs_before`只核`x<=y`以及显式图无环。`boundary`始终先执行完成，再调用`ore_supply`。独立事件身份检查核id、操作、目标和时刻，不检查`timeline.relations`相对于实际执行序。

**复现。** [phase-control输入](复核-r2-规格保真-证据/phase-control-input.json)使用粉碎机原布局，给恰一批在制原料、remaining=1及t=1的`completion_probe`待事件，并给同刻补1源矿的`supply_probe`；参数与种子当前参数同步。t=0已出库1件，因此t=1补1件不超80000。有效对照给`completion_probe occurs_before supply_probe`。反例[phase-conflict输入](复核-r2-规格保真-证据/phase-conflict-input.json)仅将这条关系反向。

两者均由公开CLI返回0、`status=completed`，t=1实际事件前缀都为：

```json
["completion_probe", "supply_probe"]
```

反例输入却要求相反顺序。[反例记录](复核-r2-规格保真-证据/phase-conflict-record.json)还通过`output::verify_record`，结果为`{"verify":{"Ok":null}}`；完整重算重复了同一遗漏。具体命令、返回码和对照见[探针结果](复核-r2-规格保真-证据/探针结果.json)。这是运行记录与自身保存的历史矛盾，不要求证明合成在制种子可由真实调试到达。

**处置边界。** 应联合核输入关系与profile规定的边界/模板次序；初态已登记的待事件即可在装载时核此反例，新产生实例则需在实例化或执行时核。不能为了接收本反例而把完成移到补矿之后，那会违反本版阶段选值。旧补矿数组反序测试应保留，并补本对照及反例。

### KR-r2-L1-02：图变化后生成自身无法重载的固定分支后态

- **where：** `/home/zhuran24/zmd-research-fresh/求解器/crates/kernel/src/polling.rs:140–163`、`src/input.rs:865–889`、`src/transition.rs:265、676–705`。
- **claim：** 固定分支失活后内核继续产出completed后态，而该后态连同原参数无法重新装载，执行与恢复的支持域不闭合。
- **severity：** 重要（会漏覆盖或误导后续）。

**规格依据。** 受限转移§1接受完整`after_closure`状态并定义`step_tick`；§3.4要求按完整新图重算受影响级及阻尼，§5.3要求缺定义/不支持时返回明确停止位置。内核输入§5.3要求choices表项属于当前所选路径、禁止断边表项，并定义`fixed_for_run`为“整段固定表”；§6要求恢复数据和接通/轮询关系一致。配置未授权内核改写固定分支表。

**不依赖歧义的结论。** “原分叉退化成唯一出边后，是否仍调用旧分支绑定”在现行文字下仍需澄清；本报告不据此直接裁定哪条真实游戏路径必须采用。确定缺陷是：运行入口接受并生成的完整后态，在同一profile、同一固定表下被装载入口拒绝。这是本轮可复验的恢复覆盖损失，即便选择表只在真实分叉处使用，也不能让运行与恢复各用一套有效性条件。

**复现布局与前态。** [branch-cut输入](复核-r2-规格保真-证据/branch-cut-input.json)是独立合成布局：非运输源箱的两条取货PC分别直连`merge_a`和`merge_b`，形成两个活跃取货级。第一路经`merge_a→fork`，固定选择`fork→gate→sink_a`，另有`fork→sink_b`；第二路经`merge_b→sink_c`。第一路阻尼为3，第二路为1。源箱有5源矿；分流器已有1源矿、entered_at=-1。gate同种放行、累计限额1。种子给出相容的当前级和指针，显式模板序先访问所选`fork→gate`，全部几何、历史和种子经公开装载入口通过。

**实际行为。** t=0首事件`J|0|0|0`成功把分流器的1件送入gate，累计用尽，切断的恰是固定表中所选出支。内核没有停止：阻尼函数在只剩一条活跃出边时直接走`outgoing[0]`，第一路阻尼由3变成2；随后仍完成源箱到两汇流器的移动，CLI返回0、`completed`，记录也通过`verify_record`。

将这一个闭包后态原样替换到同一输入的`initial_state.nonwarehouse.value`，保持全部参数不变，公开`Input::parse(...).and_then(Engine::new)`返回：

```text
invalid_input input @ damping.branch.choices: 所选出支不在查询的当前图中
```

这里尚未调用`run_record`，所以与KQ-02的输出起点冲突无关。对照[branch-retained输入](复核-r2-规格保真-证据/branch-retained-input.json)只取消累计限额：同一路阻尼保持3，闭包后态重新装载成功。原始库结果分别为[断边结果](复核-r2-规格保真-证据/branch-cut-library.json)和[保留分支结果](复核-r2-规格保真-证据/branch-retained-library.json)。

**处置边界。** 规格线应明确固定表在图变化后的调用/保存规则；实现线须使连续执行、参数有效性和重载一致。若原绑定失活属于未支持域，应在首次触及停止而不交付这种completed后态；若允许退化唯一通路，应正式说明休眠表项如何保存并使重载同样接受。不能靠恢复时删除或改写固定表来声称原参数续跑成功。本项不将“阻尼由3变2”单独计作已证明的游戏结果错误。

### KR-r2-L1-03：未被任何记录拥有的时间线事件被静默跳过

- **where：** `/home/zhuran24/zmd-research-fresh/求解器/crates/kernel/src/input.rs:39–80`、`src/interfaces.rs:326–381`、`src/transition.rs:301–317`。
- **claim：** 全局事件仅核正向引用，孤立runtime或connection_close事件可进入运行区间并被静默忽略。
- **severity：** 重要（会漏覆盖或误导后续）。

**规格依据。** 内核输入§3.1对全局事件要求“每项必须由相应记录拥有”，runtime须由种子日程/移动记录等具名记录引用；§3.2规定connection_close必须进入`timeline.connection_events`并给channel、cause和几何快照。受限转移§1只允许已明确给出的两矿外部过程，缺必需数据为invalid，未支持事件须停止。输出§1–§2又要求完整保留并实际执行所声称覆盖的历史，不能以记录文件中存在该行代替办理。

**代码与复现。** `timeline`检查id唯一、kind和关系；`check_action_references`检查“动作行→全局事件”方向，却不反向核“每个全局事件→拥有记录”。`check_external_stops`显式跳过所有runtime，connection_close落入`_ => continue`。在未改其它字段的粉碎机样例中，仅向timeline加入t=1的`unowned_probe`，分别取kind=runtime与connection_close，均无相应拥有记录。

两项探针均返回0、`completed`并通过`verify_record`。`input_history.timeline.events`保留该事件，实际ticks事件中完全没有它；运行与原样例相同。见[runtime输入](复核-r2-规格保真-证据/unowned-runtime-input.json)、[close输入](复核-r2-规格保真-证据/unowned-connection_close-input.json)及同目录各自`-record.json`。

**处置边界。** 建立按kind核拥有记录的反向索引；保留合法runtime恢复、运行中注册及补矿工程接口的拥有关系。裸connection_close缺必要描述，宜直接invalid；描述齐全但本版未实现的结构后效则明确unsupported。不应推测这个未知事件的物理后效，也不应忽略后返回completed。本项与01不同：没有添加任何先后冲突，仅检验全局历史是否完整。
