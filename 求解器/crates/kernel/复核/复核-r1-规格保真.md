## 2. 发现

### KR-r1-L1-01：不足以保持矿石持续可得的历史仍被完成运行

- **severity：阻断（结果会错）。**
- **where：** `/home/zhuran24/zmd-research-fresh/求解器/crates/kernel/src/interfaces.rs:169`、`:262`；`src/transition.rs:267`、`:451`；`src/engine.rs:737`、`:869`。
- **claim：** 内核只核补矿历史的覆盖终点、事件形状及容量，没有核持续充分性，矿源已断供时仍把所请求轨迹标为 `completed`。
- **evidence：** 正式任务 L7：“仓库中的源矿与蓝铁矿持续可得且足够覆盖任意数量的消耗”；受限转移 §2.1：“空历史只有在当前库存足够覆盖整个被测段消耗且未违持续可得时才可作该段见证”；受限模型声明 §2 的 `warehouse.external_supply` 同样要求“容量内且持续充分”。

代码在 `interfaces.rs:184–221` 只检查 `through`、事件次序、物种、正数量及同刻 runtime 引用；`:262–265` 只比较 `environment.ore_supply` 字符串。`check_external_stops` 对补矿只检查 `t > through`，`ore_supply` 只执行列出的事件。仓库取空后，`source` 返回 `None`，`physical` 将它作为普通 `source_empty`，没有把外部前提失效与合法物流阻塞分开。

[ore-shortage-input.json](r1-规格保真-证据/ore-shortage-input.json)保留任务初始锚点的六物种各 80000，只把显式运行种子的源矿改成 1；其它库存、现图、轮询记忆和全部参数保持相容，补矿事件为空且 `through=3`。这是校验外部历史的条件种子，不声称该种子可达。

[实际输出](r1-规格保真-证据/ore-shortage-record.json)返回退出码 0、`status=completed`，执行 t=0…3。t=0 取走唯一源矿，此后仓库源矿始终为 0；t=1 的后续扫描中送料带已腾空、相应新时刻端口额度可用，矿源仍因无货停供。这不是仓库满、下游拒收或端口限额导致的合法阻塞，而是输入宣称的外部过程不成立。后续循环搜索若接受这种记录，会把供给不足当作布局行为。

**修复验收条件：** 在具体有限段内机械核查显式补给能维持持续可得；触及时停止并定位 `warehouse.external_supply`，不能补造事件或自动灌满，也不能将坏环境继续当合法坏轨迹。

### KR-r1-L1-02：同刻补给的数组序可以违反统一历史关系

- **severity：阻断（结果会错）。**
- **where：** `/home/zhuran24/zmd-research-fresh/求解器/crates/kernel/src/input.rs:84`；`src/interfaces.rs:189`；`src/transition.rs:464`。
- **claim：** 补矿数组序与 `timeline.relations` 的同刻执行先后相矛盾时，装载器没有拒收，执行器按数组输出相反的事件序列。
- **evidence：** 内核输入 §3.1：“所有来源的偏序……及原因/后效关系取交集，冲突拒收”；`occurs_before` 表示执行发生在前。受限转移 §2.1 要求按输入显式顺序回放补矿，§1 禁止把容器次序暗当语义优先序。

`timeline` 单独核关系中的数值时间及关系图无环，却没有把补矿数组引入同一偏序。`check_input_axes` 只要求补给时间非递减；`ore_supply` 直接遍历数组。KQ-01 自定数组作为同刻补给顺序后，也必须与已定义的统一时间线相容，不能覆盖它。

[supply-order-conflict-input.json](r1-规格保真-证据/supply-order-conflict-input.json)给两次 t=1 的合法正量源矿补给，数组是 `[supply_a,supply_b]`，另明确给 `supply_b occurs_before supply_a`。当前种子源矿为 79990，容量不是冲突来源。两份先后约束的交集为空，本应 `invalid_input`。

[实际输出](r1-规格保真-证据/supply-order-conflict-record.json)却为 `completed`，t=1 前两个事件依次是 `supply_a`、`supply_b`。本例两次同种增量可交换，不会使最终数量不同；错误已经体现在不可能满足输入的事件历史上，不能凭终态计数恰巧相同接受该输入。

**修复验收条件：** 把补给显式序与统一关系一起校验，矛盾负例拒收；相容的显式序原样执行。不以另一处参考实现同样未检查为依据。

### KR-r1-L1-03：待完成事件可冒用历史建造身份，并通过自身重算验收

- **severity：重要（会误导后续）。**
- **where：** `/home/zhuran24/zmd-research-fresh/求解器/crates/kernel/src/engine.rs:136`、`:236`、`:626`；`src/transition.rs:371`；`src/output.rs:365`。
- **claim：** 种子 pending 事件与 timeline 的身份、类型、时刻没有联合核验，已有建造事件 ID 能被再次用作制造完成事件并通过 `verify_record`。
- **evidence：** 内核输入 §3.1 规定全输入唯一事件域、共用同一事件只能引用同一实例；§6 规定 pending 引用全局 runtime 等相应事件。内核输出 §2 明令拒绝历史别名、同 ID 的操作/目标/触发改变，§3 要求全记录事件身份独立校验，不能仅靠重算相等。

`Engine::new` 用 `timeline.ids ∪ pending.ids` 建 BTreeSet，交集碰撞被静默合并。`validate_seed:236–256` 只处理特定 runtime 前缀，`:626–670` 核 pending 自身唯一性、目标及进度，却不核同名历史登记。到期时直接消费 pending ID；`executed` 初始为空，未阻止把已建造事件再次执行。`verify_record` 只是重算后与记录比较，因此会重复同一错误。

[pending-historical-alias-input.json](r1-规格保真-证据/pending-historical-alias-input.json)使用真实 t=1 闭包状态，在不改工作量或缓存的情况下，将唯一待完成事件的 ID 从 `C|2|crusher` 改为 `build_0`。timeline 中 `build_0` 明确是 t=-13 的 `build`。

[实际记录](r1-规格保真-证据/pending-historical-alias-record.json)在 t=2 输出 `{event:build_0, operation:manufacture_complete, target:crusher}`，状态为 `completed`。本次源码探针进一步得到 `historical_alias_self_verify=Ok(())`。独立事件身份校验器拒绝它，错误为 `待事件与输入历史身份冲突: build_0`；未改名的 after_closure 对照则通过。见 [独立事件身份结果](r1-规格保真-证据/event-identity-independent.json)。

**修复验收条件：** 恢复装载与输出验收都联合核注册表、已执行集合和 pending；共享 ID 只准引用同一未办实例。增加正向恢复、历史别名和已办再待办负例；不能靠重新生成相同坏记录通过。

### KR-r1-L1-04：外部动作记录的事件引用未检查，停止域可被错误类型绕过

- **severity：重要（会漏校验或误导后续）。**
- **where：** `/home/zhuran24/zmd-research-fresh/求解器/crates/kernel/src/interfaces.rs:267`；`src/input.rs:145`、`:39`；`src/transition.rs:279`。
- **claim：** 离线、拿取和调试记录未按所属接口核全局事件引用，离线记录误指 runtime 时既不拒收也不停止而被当作没有离线执行。
- **evidence：** 内核输入 §3.1 要求每项事件由相应记录拥有、各引用同域；§3.3 明确 `environment.offline.selected_events[].event` 指 offline；§6.1、§6.2 分别约束调试和拿取引用；受限模型声明 §2 的 `offline.events` 为“出现任何离线/上线事件”即停，受限转移 §1 的运行段不执行离线后效。

`interfaces.rs:267–274` 只核 environment 子对象的顶层键，没有遍历 selected_events。`debug_operations` 也只以顶层字段和通用 Decision 封套出现，没有按 §6.1 核所属事件。执行停止检查只遍历 timeline.kind，runtime 会被跳过。因此错误引用并非得到一个带出处的失败，而是整条动作记录不参与执行。

[offline-wrong-kind-input.json](r1-规格保真-证据/offline-wrong-kind-input.json)把一项完整离线后效记录的 event 指向同刻 t=1 的 runtime 事件 `review_offline`。这故意违反事件类型契约，正确结果应是装载拒收，不是执行离线后效。实际 [记录](r1-规格保真-证据/offline-wrong-kind-record.json)为 `completed`，运行 4 时刻。只将该事件 kind 改回 offline 的 [对照](r1-规格保真-证据/offline-control-record.json)在 t=1 返回 `unsupported offline.events`，保留一刻前缀。

这证明的是**坏输入引用漏检**，不是声称合法、正确登记的 offline 会漏停。正确登记的离线和玩家事件的外层停止实现存在；它不能代替引用合法性校验。对其它动作表也应使用同一拥有关系检查，不能靠用户填写两个地方永远一致。

**修复验收条件：** 对动作表逐条核引用存在性、kind、拥有关系及同一事件不重复登记；错误类型/悬空引用为 invalid，合法且进入运行区间的未实现动作携相应轴停止。

### KR-r1-L1-05：阻尼分支表接受与查询路径无关的分流器

- **severity：重要（会漏校验或误导后续）。**
- **where：** `/home/zhuran24/zmd-research-fresh/求解器/crates/kernel/src/input.rs:657`。
- **claim：** `damping.branch.choices` 只核节点及出边存在，没有核分流器属于该 channel 的实际查询路径，接受规格明确禁止的无关分叉表项。
- **evidence：** 内核输入 §5.3：“fork_unit 是沿其搜索方向实际遇到的分流器……禁止把任一无关分流器、断边或非出支塞入表”；受限转移 §1 要求完整相容的排序及选择数据，受限模型声明 `damping.branch` 指向该接口。

`input.rs:666–686` 检查 channel 存在、fork_unit 类型为分流器、outgoing_channel 源单位等于 fork_unit、键不重复。没有从 channel 检查所选路径或表项与现图的关联。

本次 [源码探针](r1-规格保真-证据/review_probes.rs)在分流器样例中给以下表项：查询 `PC|probe_left:west:0|probe_gate_a:south:0`，fork_unit=`splitter`，选 `PC|splitter:north:0|north_box:south:0`。探针支路从 probe_gate_a 去 probe_merger，不经过主三路的 splitter；它与所填分叉无关。其余字段保持一致，经过公开 `Input::load` 和 `Engine::new` 后仍为 `Ok`。可读回输入见 [unrelated-fork-input.json](r1-规格保真-证据/unrelated-fork-input.json)，日志为 `unrelated_fork accepted=true`。

本发现不声称多余表项已改变本条有限轨迹的库存；问题是执行器把不符合其已声明输入语义的选择向量作为已核输入保存，后续参数遍历/覆盖将失去可信定义域。

**修复验收条件：** 按实际查询方向核表项的相关性、所选路径和当前出支；图变更时对需要求值的选择重新核。若允许备用表项，须先由规格明确其辖域，不能静默扩大当前接口。

### KR-r1-L1-06：仓库接收域两轴只有赋值，没有规定的逐边界报告

- **severity：重要（会漏覆盖或误导后续）。**
- **where：** `/home/zhuran24/zmd-research-fresh/求解器/crates/kernel/src/config.rs:120`、`:267`；`src/transition.rs:672`；`src/output.rs:327`。
- **claim：** `warehouse.acceptance=capacity_and_path` 和 `warehouse.acceptance_quantifier=per_instant` 未实现所要求的两成品接收域报告。
- **evidence：** 受限模型声明 §2 的前一轴要求“分别记录两成品容量许可及存在物理入库途径”，后一轴要求“在每个观察边界报告接收域”；内核配置同名两轴的 meaning 保留这两项职责。正式目标的接收条件与全称认证虽然尚未验收，当前 profile 的逐时刻报告义务已经选定。

两轴只在枚举和配置一致性检查中出现；库没有计算两成品接收域的函数。`summary` 三个分支分别输出样例投影或非空库存/完成批次/入库补给计数；`run_record` 同样不增加接收域。四份实际输出也只有参数值和 `coverage_status=not_exercised`，没有每观察边界的容量许可及途径结果。

保存完整库存使将来可以补算其中的容量部分，但不等于已经“分别记录”；一个 `not_exercised` 标签也不能把当前配置要求每刻执行的职责变成可不执行。这里不要求开始完整目标认证，也不要求把接收谓词用于物品移动守卫。

**修复验收条件：** 在每个输出观察边界分别给两成品的容量许可、物理入库途径及所选组合接收域；如接口确实尚不能定义，显式登记为实现缺口并由规格线解决，不能声称 99 轴执行含义全部实现。

- **severity：重要（会误导后续）。**

- **evidence：** 受限转移 §1 明确 `step_tick` 从已闭包 t 到 t+1；内核输出 §2 同时要求“首项起于 start_state.environment.time”，§2.1 又称 start_state 是“首次边界前完整种子”。

## 5. KQ-01–KQ-05 暂取处理的意见

| 疑问 | 意见与理由 |
|---|---|
| **KQ-01 非空补矿编码** | **字段形状可作为明确披露的临时工程编码，当前实现仍须补相容性检查。** event/time/item/quantity 不改变补矿物理机制，关联同刻 runtime 合理；但不得以接口缺字段为由忽略已经正式定义的持续充分性、全局拥有关系和先后交集。01、02、04是独立于该编码选择的现行义务。正式接口纳入前不能将此形状宣称为规格已唯一规定。 |
| **KQ-02 after_closure 首时刻** | **同意从 t+1 推進，不同意把当前格式称为已满足输出契约。** 转移§1的语义明确，重放t会错；输出§2/§2.1需要正式统一。发现07按接口债务登记，不能靠实现席自行改现行规格消除。 |
| **KQ-03 新标签冲突** | **当前拒收合理。** 转移§4.3明确“标签冲突且未给替代标签报invalid”；既有输入没有替代接口，不应自行追加后缀或改已有指派。全输入一致更名是工程身份更名，可作为调用方准备过程；它不是运行中偷偷换标签的授权。此入口尚缺完整覆盖但没有产生错误后继，本轮不另计缺陷。 |
| **KQ-04 单取货级是否求阻尼** | **按需计算有条件合理，保留规格澄清。** 正式规则的阻尼用于级间比较，停止轴又以“请求求阻尼”为前件；仅一级时跳过不会改变最高级。代码实际用 `s.levels.len()>1`，且只算含可动成员的级，并非“只有一个可动级就跳过”。规格§3.4“重算所有受影响级、排序及阻尼”的字面较宽，应明确是否允许惰性求值。直接请求无终点仍会停；不能把单级轨迹通过当作一般阻尼定义。另一个“原固定分支断开而剩唯一活路”的问题见§6，不由本KQ自动授权。 |
| **KQ-05 身份批维护日志** | **在现行封闭 operation 枚举下，当前不冒名的处理合理，但事件审计能力有限。** `maintain_identity` 确实不是判定；完整后态和确定重算可以核后效，不能虚报成move/窗口到期/玩家动作。当前未把身份维护随意标成独立事件覆盖是合适的。若需要定位每次非判定维护及其因果，应由输出契约补独立 operation；现有两个参考样例没有身份不符，不构成这项日志义务已获证。 |

## 6. 保留未决、未列为确定缺陷的观察

**固定分支遇断边后只剩一路。** `polling.rs:140–163` 在活跃出边数大于1时查固定表；只有一条时直接走唯一出边。本次人工删边探针得到：同一已选分支消失且仍余两条时返回 `unresolved damping.branch`，再删一条后返回 `Ok(1)`。另一个完整合法几何与种子的动态探针通过两门身份不符批删边，得到既定北路消失、唯一东路存活；同一查询阻尼由2变成 `Ok(3)`。见 [dynamic 输入](r1-规格保真-证据/fixed-branch-dynamic-input.json)、[t=0 后态](r1-规格保真-证据/fixed-branch-dynamic-tick.json)及源码日志。

输入§5.3一方面说 fixed_for_run 是整段固定表，另一方面说未遇分叉的查询不需要表项；未明确“原先的分叉因现图只余一路是否不再受原绑定约束”。若固定的是分流器处的原分支身份，现实现就漏停并换路；若仅在当前真实分叉时调用选择表，退化唯一边可能成立。本轮不擅自裁定，故没有把该观察计为阻断发现。规格线应明示此调用前件，并决定所选分支失活时是否返回 `damping.branch`/`damping.no_terminal`。发现05只依赖明确的“无关分流器禁止入表”，不依赖此歧义。

**有限正确性边界。** 现有证据未证明本组合对轮询均分、密集结点等的全部前件相容性，也未实现其它时间域、一般调试/离线后效、初态可达性、全参数或全部可达循环。这些已由现行规格明确保留，不作为本轮新增缺陷。缺陷01不属于合法坏布局轨迹，而属于输入外部前提本身失效；缺陷06也只要求当前profile的接收域报告，不要求完整目标认证。
