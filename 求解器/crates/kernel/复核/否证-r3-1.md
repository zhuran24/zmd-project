## 2. 逐条否证判定

### 2.1 KR-r3-L1-01：检查点参数被派生器覆盖

**判定：未能否证，refuted=false。**

输入§6.4的原文要求after_closure保留原已执行“游标、参数、台账、活动事件身份与时间锚点”，并规定“缺失或冲突即拒收”；KQ-07答复同样要求保留并校验。规则L29–32的轮询历史和任务L14固定次序说明参数与历史不能任意混接。此处直接的工程义务已明文，不依赖额外假设。

回源[seed.rs](../src/seed.rs):9–36看到`canonicalize_seed`先从顶层参数生成`current`，在第24行无条件替换StateSeed的`parameter_values`，随后才解析并构造引擎。第58–61行对after_closure的提前返回位于上述替换之后。[engine.rs](../src/engine.rs):404–418确有一致性检查，但它看到的是被覆盖后的镜像，不能核原始冲突。

本席先从粉碎机输入实际运行4刻，取t=1的完整后态；合法检查点经seed前后逐字段相等。随后分别清空检查点参数表，或仅将顶层`warehouse.external_supply`改为sufficient而保留检查点原显式历史模式。两例直接run均退出2/invalid_input，原因均为`parameter_values`当前值/生命周期不符；两例seed均退出0、输出99轴，且对派生结果run均退出0/completed。

关键材料：[缺失输入](否证-r3-1-证据/crusher-missing-input.json)、[冲突输入](否证-r3-1-证据/crusher-supply-conflict-input.json)、[直接拒收](否证-r3-1-证据/crusher-supply-conflict-direct.json)、[覆盖后的种子](否证-r3-1-证据/crusher-supply-conflict-seed.json)、[成功续跑](否证-r3-1-证据/crusher-supply-conflict-resumed.json)、[对照比较](否证-r3-1-证据/checks.json)。

可反驳方向是“派生本来允许同步参数”。输入§6.4确实允许before_boundary作为新调度起点派生，但对after_closure明确作了相反限定；本例没有把阶段改为新起点。因此该许可不能否证发现。合法检查点保留正确也不能覆盖冲突输入。

### 2.2 KR-r3-L1-02：窗口截止等于当前时刻仍被当作已闭包待办

**判定：未能否证，refuted=false。**

规则L64规定窗口从首件起走满5 tick，之后由下一件重新起算；任务书3§2.2排除窗口耗尽永久阻断及全盘停表。受限转移§2.1要求边界一次维护全部已过5 tick的窗口；输入§5.2定义after_closure为“边界及闭包均已完成”。所以该阶段仍存在的窗口待办应满足deadline>t；before_boundary允许deadline=t是另一个情况。

回源engine.rs:764只拒绝`deadline != expected || deadline < self.t`，没有按phase处理等号。transition.rs:480–510在下一边界按`deadline<=t`消费待办，而after_closure的首次step先推进到t+1。制造预计deadline因暂停可滞后是另一个机制；窗口在输出§2仍按真实5 tick截止核验。

本席重新跑分流器到t=5，保留完整检查点，仅将两个已开窗口的start由1改0、截止由6改5、事件身份同步为`W|5|probe_gate_a/b`。seed和run均退出0；run第一刻t=6才执行两个W|5事件。对同一运行记录执行verify-record退出2，报“执行的操作/目标/时刻与待事件登记不符”。见[异常种子](否证-r3-1-证据/gate-expired-input.json)、[实际运行](否证-r3-1-证据/gate-expired-run.json)、[验收拒绝](否证-r3-1-证据/gate-expired-verification.json)。

补核尝试排除“等号始终非法”的过强结论：隔离门同一t=5、start=0、deadline=5，在空台账下仅将phase改成before_boundary。它在t=5完成维护，run和verify-record均成功，见[合法等号对照](否证-r3-1-证据/tiny-before-boundary.json)及[验证](否证-r3-1-证据/tiny-before-boundary-verification.json)。因此问题准确限定为已闭包锚点的准入遗漏，不能通过一概禁止边界前等号来表述。

### 2.3 KR-r3-L1-03：周期验收缺全前缀独立事件检查

**判定：未能否证，refuted=false。**

输出§2要求窗口按真实截止核，跨集合事件唯一性“必须由语义验收器独立核，不能仅靠重算相等”；§5.3.1要求重建完整记录、核守恒及事件唯一性，§4还明确循环结果内含可独立验收的v3记录。故周期段回放不是搜索前缀合法性的替代品。

回源[cycle.rs](../src/cycle.rs):602–675，`verify_cycle`核来源相等、调用同一`run_cycle`比较整份JSON，再从周期起点重跑P次。它没有调用`validate_event_identity`或`verify_record`。相反，[output.rs](../src/output.rs):518–526会在重算前调用[event_identity.rs](../src/event_identity.rs):175–247的独立检查；其中窗口触发时刻与实际tick必须一致。Engine装载时对空ticks调用身份检查，只覆盖起点，不能检查后续非法消费。

本席复用既有最小隔离门的布局输入，但重新执行到t=5，再自行构造start=0/deadline=5的异常after_closure待办。cycle在t=6的前缀错误消费W|5|gate，随后发现(6,7]的P=1生产部分低产周期。`verify-cycle`退出0、`cycle_replayed=true`；原样取出其run_record，`verify-record`退出2，明确因W|5|gate时序不符拒收。

材料：[输入](否证-r3-1-证据/tiny-expired-input.json)、[完整周期结果](否证-r3-1-证据/tiny-expired-cycle.json)、[周期验收通过](否证-r3-1-证据/tiny-expired-cycle-verification.json)、[原样内嵌记录](否证-r3-1-证据/tiny-embedded-record.json)、[记录验收失败](否证-r3-1-证据/tiny-embedded-verification.json)。

可反驳方向是“完整JSON已重算相等，周期段也合法”。实测恰说明错误前缀由同实现稳定重现，且错误落在周期段之前，两项比较仍能通过。因此不能否证。此项与2.2相关但不同：2.2是准入校验，2.3是规格要求的独立验收缺失。本例不证明一般循环算法错误，也不把条件负例冒充任务可达状态。

### 2.4 KR-r3-L1-04：sufficient派生缺少两矿正库存检查

**判定：未能否证，refuted=false。**

任务L7要求两矿持续可得；输入§5.4把本版sufficient的准入明确写成“两矿各有正数、唯一且≤80000的库存格”，转移§2.1要求每次出矿原子补回。输入§6.3也说明历史身份不计库存。该条件是种子准入义务，不只是出现出矿事务时的守卫。

回源seed.rs:34–41从`Engine::new_derived`成功后立即导出状态；engine.rs:275–781核通用仓库/身份等，但没有两矿正库存条件。transition.rs:523–545的检查位于执行边界；cycle.rs:143–153另在生产域准入核正矿，均未成为seed成功的前提。

本席以生产循环环带为正对照：真实cycle及verify-cycle均成功。变异只把StateSeed源矿改为空格、数量0、保留源矿历史身份；顶层任务初始六满格和sufficient参数未改。seed仍退出0生成kernel-input-v3；导出结果run一刻退出2/invalid_input，原因是源矿无库存。见[缺矿输入](否证-r3-1-证据/zero-ore-input.json)、[派生成功](否证-r3-1-证据/zero-ore-seed.json)、[运行拒收](否证-r3-1-证据/zero-ore-run.json)。

“运行时最终拒收”限制了后果，却不能使违反种子准入的成功导出变得合规。这里的必然拒收限定为尝试推进至少一个tick的该输入，未声称零tick空请求也触发边界检查；也未声称代码已经凭空造矿或产出假达标证书。

### 2.6 KR-r3-L2-02：历史传输相位免除了类型和值域检查

**判定：未能否证，refuted=false。**

规则L36规定5 tick冷却，约束·传输相位要求覆盖合法相位；输入§1.1规定Time/Quantity表示，§5.4要求未支持值明确停止。当前受限模型声明和配置的transfer.phase具体为“每箱输入整数剩余0…5”。半tick属于本版未覆盖而非因此被正式规则排除；字符串not-a-Time连Time格式都不满足。

回源interfaces.rs:119–158只查explicit_residuals外壳、箱身份、slot及冷却条数，并在非after_closure时比较历史remaining与当前冷却；对after_closure没有独立Time解码/范围检查。engine.rs:615之后确实校验当前`progress.cooldowns`，但它不等于历史参数本身。参数镜像一致性也只是相等关系，不能使两个相等的非法对象合法。

已检验最有力的反驳：检查点历史初相位确实可以不同于当前冷却。合法对照的north_box/east_box初相位0而当前冷却5，仍正常续跑，见[补核对照](否证-r3-1-证据/supplement-results.json)。发现并未要求两者相等，只要求历史值也满足本版声明的类型和域。因此不能否证；P=20的物理投影重复本身没有被此例推翻，错误在被接受和认证的参数域。

### 2.7 KR-r3-L2-03：桥搬运不能替代先接定向运行覆盖

**判定：未能否证，refuted=false。**

规则L63把端口类型确定归于“先接上的那一端所接的单位”；这是定向的历史后效。输出§1将exercised定义为实际执行，将input_checked定义为输入/结构检查；任务书5 K6要求实际运行覆盖，做不到则逐条解释缺口。输入§2.2、§3.2允许核定既有方向的历史一致性，不等于运行期间又发生一次定向。

回源output.rs:265–267把`connection.bridge_first_contact`与bridge.*放在同一成功move筛选条件，只要搬运涉及桥就exercised。audit_round5.py:140–146直接汇总这些标签，missing由是否出现exercised决定，没有对先接后效的独立谓词。input.rs:562–610确实计算最早接触、检查桥方向与非桥邻端互补；这证明有结构核验，不能否认它。但该代码只核输入中已resolved方向的正确性，没有本次运行中的pending→resolved状态转移。

本席新跑桥样例0…29并通过verify-record；输入两轴均已resolved，四个接通事件在-5、-4、-3、-2。先接轴标exercised并引用32条事件，全部是成功move，首项`J|0|0|0`只是south_box→bridge。两轴分别进8/出8、两成品无线各入库8件均得到实测确认，但这些是定向后的物流。见[完整覆盖抽查](否证-r3-1-证据/bridge-coverage.json)及[运行记录](否证-r3-1-证据/bridge-control.json)。

为检验“其它样例其实补了该轴”，本席还读取聚合审计中声称覆盖先接的全部10份记录及其输入；全部引用证据仍只有move。各份输入的桥均已resolved，明细与来源哈希在[补核结果](否证-r3-1-证据/supplement-results.json)。聚合`required_unexercised`仍只列transfer.resume_event。因此发现的遗漏不被另一条真实先接记录抵消。

本结论不要求两种先接读法的区分实验，也不否定桥方向结构校验已实现；它要求按既有五态口径报告“输入核验”和运行覆盖缺口。没有找到文件已逐条承认该缺口的依据。

### 2.8 KR-r3-L3-01：畸形槽位及StateSeed触发panic

任务书4§4.2及§5要求显式Stop和错误不吞；受限转移§1规定invalid/unsupported/unresolved/inconclusive返回；输入§2.3要求身份先校验再建寻址字典。畸形输入当然不应运行成功，但这不授权CLI跳过错误结果契约。

engine.rs:168–170将slot以冒号分割后直接取`parts[1]`，而slot全集校验在后续validate_seed；seed.rs:24在解析StateSeed前使用可变JSON索引改写字段。这两条路径分别在普通装载与seed入口，不能由另一入口有检查来覆盖。

以本席已成功运行的粉碎机输入为同源对照：inventory首个slot改为bad，公开run退出101，stderr指向engine.rs:170索引越界，stdout为空、指定结果文件不存在；改为bad:input:0则正常退出2并写invalid_input结果。另把nonwarehouse.value改为true，seed退出101，stderr为`cannot access key "semantic_context" in JSON boolean`，stdout空、无结果文件。见[bad槽日志](否证-r3-1-证据/bad-slot.log)、[非法单位标签对照](否证-r3-1-证据/bad-unit.json)、[布尔种子日志](否证-r3-1-证据/boolean-seed.log)。

panic有stderr且非零退出，所以“被吞”不应理解为完全无错误信号；可成立的准确内容是没有按约定返回带位置的Stop/错误结果，公开CLI异常崩溃。原发现已明确描述这一点，措辞收窄不构成对其实质的否证。

### 2.9 KR-r3-L3-02：循环装载资源错误被归为stopped

**判定：未能否证，refuted=false。**

受限转移§1独立定义`inconclusive(resource)`；输出§1把inconclusive定义为资源不足，§5.1/§5.3区分资源未决与unsupported/unresolved技术停止。资源界限不是游戏行为规则，本项依据是该明确输出契约。

回源main.rs:175在cycle装载错误时调用`load_stopped_cycle`；cycle.rs:685的顶层status只有invalid_input与其余stopped两个分支，但stop.kind又专门把inconclusive映射为resource。因此原始资源语义仍在内层，却从顶层分类丢失。

本席从合法环带仅将a:transport:0的entered_at改为i64最小值。该值可表示，t减entered_at超出i64；同一输入run退出2/status=inconclusive，报resource.integer时差溢出；cycle退出2/status=stopped、stop.kind=resource、axis=resource.integer。见[同源输入](否证-r3-1-证据/overflow-input.json)、[run结果](否证-r3-1-证据/overflow-run.json)、[cycle结果](否证-r3-1-证据/overflow-cycle.json)。

可反驳方向是“stop中保留resource已经足够”。这仅说明信息没有全部丢失，不能满足顶层状态的契约；读取status的统计/重试方仍会误分组。有限整数溢出是否另应扩大数值域不影响当前Stop已被明确分类为inconclusive。没有产生假周期这一事实也不能否证装载分类缺陷。
