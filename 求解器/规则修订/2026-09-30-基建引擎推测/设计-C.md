# 设计推测 C：从 bug 反推实现

日期 2026-09-30。角度：把每个怪现象当成实现留下的指纹，反推能同时产生全部已知现象、写起来最省事的那份代码，再拿它回答三个未定问题。
状态：完成。只做了静态阅读和网络检索，没有做游戏实验。

读法：【证据】写出处（E 编号指同目录 `证据.md`，其余写文件:行或网址）；【推测】是我的推理，写出理由；【估算】是数值换算，写出假设。"规则 L27"指 `《明日方舟：终末地》游戏规则.txt` 第 27 行。社区页面路径省略公共前缀 `参考资料/天师府学院及赤石科学院成果公开文档/`。

## 结论

1. 【证据】开发商说过：离线时服务器也在算工厂；一台 32 核 64G 的服务器算复杂工厂能同时带 3000 人，优化后 4000 人，每人每秒工厂核心运算约 1 毫秒；离线运算分级，几天不上线就改用更精简的频率估算（第一节出处）。成本压力是真的，离线降档是开发商自己承认的。
2. 【推测】全部"放置顺序"类现象，指向同一个省事的写法：计算先后不是每步从布局算出来的，而是几张"接通时追加到表尾、断开时删掉"的登记表，有改动时再按层数分一次桶。先后因此是建造历史的函数，不是布局的函数。
3. 【推测】分流器的各种特殊待遇（不进汇流器的轮询、作末端时不按机器合并、第一次从第二条通道开始）可以归到一个数据结构：只有分流器有多个固定出口，凡是按"它唯一的下游"登记的代码都把它漏掉了。这不是社区说的"漏调用了一个辅助函数"，是结构性的，所以也不会被单独修掉。
4. 【推测】下线时工厂多半不常驻内存，而是分批"载入—补算—存档—卸载"；每批开头从存档重建登记表。一批约 5 分钟（约 305 秒）：旧版下线传送带约每 5 分钟卡一下、三个"11.8 次/小时"的丢失（1 小时 ÷ 11.8 ≈ 305 秒）都是这个周期。离线后优先级改回去、依赖相位的装置失效、准入口下线降速，都出自这个批边界。
5. 对三个未定问题的预测（第五节）：同轴相邻桥接器满载不掉速（把握约八成）；分流器几支通同一台机器时按近的那支数（七成）；机器、协议储存箱、仓库口不被汇流器的其他上游带动（六成），储液罐、暗管出口会（六成）；仓库与协议核心的"随机"是固定遍历次序在缺货时露出来（五成）；准入口阻断不改变先后（八五成）；下线会把同层先后和末端序重置成按存档次序的标准次序（六成）。
6. 对"一张布局长期稳定达标"：只有由层数决定的先后和平均流量靠得住；同层先后、末端序、轮询相位随时可能在批边界被换掉，达标要对这些次序都成立，而且中途换次序后还要能回到达标状态；满载的准入口要留余量。

## 一、开发商给出的约束，和由此算出的成本

【证据】腾讯新闻 2026-01-22《终末地上线，对话鹰角CEO&CTO：阵痛、反思、向上走》，CTO 顾煜的回答（https://news.qq.com/rain/a/20260122A03N6Q00 ，搜狐转载 https://m.sohu.com/a/978873252_204824 ）。要点转述如下：
- 工厂在玩家离线时也在运算，服务器要不停做校验运算。
- 一台 32Core 64G 的服务器算复杂工厂时，同时只能算 3000 个玩家；每个玩家在线运算的服务器工厂节点平均 2000 个以上。
- 靠内存复用和管理优化、事件聚合、Tick 分级、GC 优化、PGO 优化，稳定人数提到 4000，单人每秒工厂核心运算时间约 1 毫秒。
- 离线运算分级：玩家活跃期用最高的运算频率；几天没上线就用相对精简的频率估算，依此类推。

【证据】社区归纳出计算粒度 1/4 秒、客户端能看到的变化每 1 秒一次（E1）；半速管道里一秒内两次位移只看得到一次，操作也要等到整秒才生效（E3）。

【估算】（假设：1 毫秒指一个玩家一秒游戏时间的工厂步进，2000 个节点，每秒 4 步）
- 每秒 8000 次节点更新用 1 毫秒，每次约 125 纳秒，这正是逐节点、逐步硬算的量级，不需要什么事件驱动的物品模拟。
- 4000 人 × 1 毫秒 = 每秒 4 核·秒，只占 32 核的八分之一。所以卡住人数的不是步进本身的 CPU，而是内存（64G ÷ 4000 ≈ 每人 16MB）、网络同步和其余逻辑。
- 由此，离线玩家最该省的是常驻内存和网络，而不是步进。最便宜的办法是不常驻：隔一段时间载入、把这段时间补算完、存档、卸载。补算一秒游戏时间仍是约 1 毫秒，但内存只在补算的那零点几秒里占用。
- 规模感：若 100 万玩家的工厂全部常驻满频，需要约 250 台这样的服务器；降档的收益主要来自不常驻，以及几天不上线改为估算后连补算都省掉。

【推测】"GC 优化、PGO 优化"说明服务器跑在带垃圾回收的托管运行时上，最可能是 C#/.NET，与 Unity 客户端同一种语言。这让"同一份工厂代码客户端、服务器各跑一份"变得便宜：客户端算来显示（所以每秒同步一次也不卡顿），服务器算来作数并校验。

## 二、如果我来设计：框架，以及游戏在哪几处选了最省事的写法

本节是【推测】：既是我会怎么做，也是对游戏实际做法的推断；引用处另标出处。

**作数与防作弊。** 基建产出直接换成装备和地区货币，客户端算的不能作数。所以服务器权威：客户端只上传操作（建、拆、移动、设定），操作排在两步之间生效（规则 L25；E3 的"操作滞后到整秒"）。服务器每秒下发一次状态或校验值，客户端在两次同步之间自己推演画面。

**确定性与数值策划。** 两端要逐位算出同样结果，就不能用浮点和并行乱序：定步长 1/4 秒，位置用整数（传送带每步 1/8 格，管道每步 1/2 格，E1、E6），同一步里按一张固定的表逐个判定。数值策划要的是"直线满速正好 30/min、配方正好 2 秒一批"，这在固定表下能严格成立（按我们规则跑的纯链全部满速，`求解器/规则修订/2026-09-30-迟滞/核对-模拟2.md:15`）；只在少数怪拓扑里掉一点，策划可以接受。

**每步做什么。** 元件按表判定（下游在前，满带上的空位同一步就传到上游，E78）→ 设备收发 → 结束到时的制造 → 开始能开始的制造（导论:276-278）。下游在前是必须的：反过来排，每件物品每过一个元件都要晚一步。

**先后表怎么来。** 这是指纹最多的地方。
- 每步重新从布局算拓扑序太贵，所以只在接通、断开时维护，有改动才重建。
- 最省开发量的维护法：一个元件第一次有了送货通道，就追加到"判定表"表尾；一个机器第一次有了非分流器上游，或一个元件成了死路，就追加到"起点表"表尾；断开时删掉。重建时按起点表的次序一组组从下游往上游做 BFS 编层数，已编的不改；最后按层数分桶，桶内保持判定表次序。
- 结果：同层先后＝"第一条送货通道接通"的先后（导论:184 的"先有下游连接的先算"），末端序＝起点表次序（导论:116）。两者都记着建造历史，布局相同、建法不同就跑出不同结果。
- 如果是我，会多写几行：同层按实体坐标或编号排，把轮询指针存档。游戏没这样做；而上线后再改会改变所有玩家现有蓝图的行为，所以我预测它不会被当成 bug 修。

**分流器。** 传送带、汇流器、准入口都只有一个下游，代码里自然有一个"唯一下游"字段；分流器有三个固定出口，这个字段为空。凡是按"谁以我为唯一下游"登记的地方（汇流器和机器的收货轮询名单、起点表按机器合并）都会漏掉分流器。分流器只能自己往外送：从指针的下一条开始试，指针初值 0，所以第一次从第二条通道开始（E26 的"231"）。机器出货是另一个模块写的"最久未成功的先试"，初值全是"从未成功"、按接通先后排，所以是"123"（E27）。两套轮询写法不同，本身就说明物流和设备是两拨人写的。

**下线。** 按第一节的成本结论，下线后工厂不常驻：每批载入、用同样的 1/4 秒步长补算一段、存档、卸载；几天不上线改用估算。载入时要重建先后表，而存档里没有"每条通道何时接通"，最省事的是按存档次序把所有单位重新接一遍。于是历史造成的同层先后和末端序被抹成按存档次序的标准次序；没存档的轮询指针、准入口窗口余量、格内相位在每批开头回到初值或被取整。

**仓库。** 仓库是一个地区共用的库存，主基地和子基地都往里存取，协议储存箱还会无线写入。我会把它做成独立模块，在物流之后单独处理，按一个字典的遍历次序服务所有存货口、取货口和协议核心端口；协议储存箱每 10 秒批量写一次（E83），这就是"事件聚合"：把高频的小写入攒成低频的大写入，降低共享库存上的争用。

## 三、反推出的代码

【推测】下面是能同时产生第六节里"解释了"那些现象的最短写法。行尾注释写它留下的指纹。

```
# —— 登记：只在接通、断开时改 ——
x.out        # 唯一下游；分流器、有两个去向的桥轴为空
x.outs/x.ins # 全部送货/收货通道，按接通先后
r.feeders    # 以 r 为 out 的元件，按接通先后          → 分流器永远不在里面（E28、E29）
tick_list    # 第一条送货通道接通时追加                → 同层先后（E16）
sink_list    # 起点键，第一次出现时追加                → 末端序（E12—E15）

on_link(a, b):                       # a 的取货端口碰上 b 的存货端口
    if a.outs 为空: tick_list.append(a); sink_list.remove(a)   # 不再是死路
    a.outs.append(b); b.ins.append(a)
    if a.out == b: b.feeders.append(a)
    if a 的 outs 里没有元件: add_key(a.out or a)                # 键是它送往的机器；分流器 out 为空，键是它自己 → 不合并（E13）
    else: 撤下 a 的末端身份                                      # 分流器另有元件下游就不是末端（导论:114）
    dirty = True
on_place(e):  若 e 是元件且没有送货通道: add_key(e)            # 死路先放就排前（E5）
add_key(k):   若 k 不在 sink_list: 追加                        # 已在即"合并"
on_unlink:    反向删除；某键不再有末端元件就移出 sink_list     # 逐个重放不移出、同时重放才移到表尾（E14）

# —— 重建：dirty 时做 ——
rebuild():
    for k in sink_list:                                         # 一组组数，数过的不改（E13）
        BFS：起点是 k 的末端元件，层 1；沿 ins 往上游，未编号的层数加 1
             途经机器 d 时把这条出口追加到 d.ports                   # 机器出口按层数从小到大排
    剩下未编号的元件（没有出口的环）：按 tick_list 次序各自再起一次 BFS   # 预测，社区未解（E80）
    schedule = 按层数分桶，桶内保持 tick_list 次序

# —— 每步 ——
step():
    for x in schedule: fire(x)
    for d in 机器: 出货回合(d)            # 全部机器在全部元件之后 → 满箱晚一步（E10）、过路带先走（E31）
    机器：结束到时的制造，开始能开始的制造
    仓库模块：按字典遍历次序服务存货口、取货口、协议核心端口；协议储存箱每 40 步批量写入
fire(x):                               # 单出口元件
    advance_once(x)                    # 本步第一次被碰到才挪 → 每步只动一次（E93）
    if 头件到端: send(x, x.out)          # 桥轴没有固定 out，去向由物品来路定，不回送
send(x, r):
    advance_once(r)                    # "使动"：只让下游内部挪，不让它往外送 → 下游满时晚一步（E4、E11）
    if x 是分流器 or r 只有一个存货端口: return r.accept(x.head)   # 多入口的汇流器、机器、桥轴按名单收
    if r 本步已收过: return False
    for f in r.feeders，从 r.ptr 的下一条起:          # 谁先来触发都由 r 选（E28 非分流器之间轮询）
        advance_once(f); if f 头件到端 and r.accept(f.head): r.ptr = f; return f is x
fire(分流器):  从 ptr 下一条起试 outs；ptr 初值 0      # 第一次从第二条开始（E26）
出货回合(d):   d.ports 分级：接汇流器的各自一级，其余合一级、层数取最大；按级试，
              同级按"最久未成功的先试"，初值按接通先后       # 123（E27）；分级见下

# —— 存档与载入 ——
save():  存各单位与内容；不存 tick_list、sink_list、接通时刻（多半也不存 ptr）
load():  按存档次序逐个 on_place、on_link；rebuild()     # 下线后先后变成标准次序（E64、E65）
```

三处我拿不准，或找不到更省事的写法：
- 机器出口的分级（接汇流器的各自一级、其余合一级）我找不到让它自然冒出来的写法，多半是显式写的；jnk 也说这里"目的性太强"（伪代码:69）。出口按层数排则是 BFS 途经机器时顺手追加的自然结果。这部分就是规则 L33。
- 机器放在全部元件之后是最省事的写法（两个循环），它让满载过路带总在机器之前补上汇流器（`页面/附录 常见的优先级结构设计.md:13`）。社区的写法是机器排在它最后一个非汇流器下游之后（导论:86）；若那样，机器可能先于出口汇流器出货，汇流器要下一步才被补上，每件多等一步，即"4 件卡 1 秒"，这或许就是 E8（汇流器紧贴协议储存箱出口、最后放置时可触发）。E8 能用来分辨两种写法，我没推出它的 1312 周期。
- 汇流器不在自己回合向上游要货。若要，它在层数小时总先把非分流器上游的货收进来，分流器永远抢不到，与"分流器先算者优先"（E28）冲突。

社区模型来源：jnk 伪代码（`附件/新建 文本文档.txt`）、元件计算输出论断（`页面/终末地物流bug分析导论.md:26,70`）、工厂计算输出论断（同文:86）。

| 工厂作为汇流器上游时被其他上游带动输出（导论:86-88，C5） | 对制造单位、协议储存箱、仓库取货口、反应池不同意：收货名单只收元件，它们在全部元件之后才出货，所以满载过路带总先走（附录:13）。储液罐、暗管出口同意：`页面/优先输入_输出_汇入理论.md:25` 把它们和管道、汇流器列为同一轮询组，推测它们实现成元件式节点 | 分歧（分两类） |
| BFS 结束后统一输出工厂（伪代码:67）；接汇流器的出口单独处理（伪代码:69） | 同意统一在全部元件之后；同意汇流器出口的处理多半是显式写的 | 一致 |
| 取货口、协议核心随机表现优先或轮询（导论:270） | 不是随机：仓库模块按固定遍历次序服务各口，货够时人人拿到（像轮询），缺货时排前的独占（像优先）；删掉重放、下线重载会改变遍历次序 | 分歧 |
| 11.8/h 常数与离线降速无关，已弃（E73） | 我认为弃早了：约 305 秒一次的批边界是共同触发，几个子系统各有自己的存档缺陷，所以修复日期不同（E74）正是预期 | 分歧 |

## 五、未定问题：预测、把握和实验

### 5.1 同一轴上相邻两个桥接器（`求解器/内核维护/2026-09-30-步进规则同步/终审.md:73-91`）

**预测：满载直线不掉速，仍是 1。把握约八成。**
- 【推测】收货名单在我的写法里是"以 r 为唯一下游的元件"。下桥 B2 有两条送货通道（回上桥 B1、往下），唯一下游为空，和分流器一样不在 B1 的名单里，所以 B2 判定时不会带动 B1 上方的带段。换成动态写法（问上游"手里的货是给我的吗"）结论也一样：B2 手里的货来自 B1，不能回送。
- 【推测】层数从下游一次 BFS 数上来，先到 B2 再到 B1，有访问标记，不会绕回自己。
- 【证据】本地社区资料里没有"两桥相邻掉到 8/9"的实测（证据.md:778）。【推测】横穿两条相邻平行线要用两座相邻桥，是极常见的摆法，而社区对 1/4 秒级的卡顿（4n 卡 1s、8n/(8n+1)）很敏感；若真掉速，很难没人记下。唯一沾边的是"两个管道桥都会降速，延长后不降"（`页面/水管传输规则研究.md:236-250`，E41），没说两桥是否相邻，当事人归因于相位。
- 对我们的条文：问题出在 L31 把结构上的上游都算进"一起判定"、L28 允许数层数时绕回。若游戏不掉速，L31 可改为只算"送货通道只通向这个单位的"元件，这与分流器不参加是同一个理由。
- 实验：仓库取货口（库存充足）→ 3 格带 → 两座相邻桥接器（直线穿过同一轴）→ 3 格带 → 仓库存货口；旁边一条不带桥的同样线路作对照，两条线运不同物品，同时开始，10 分钟后比仓库增量。满速各 300；8/9 约 267。"先放桥后放带"和"先放带后放桥"各做一次。也可直接看桥后的带：掉速时会出现每 4 件错开半格的"4n 卡 1s"外观。
- 附带可分两种写法：让 B2 往下直接接汇流器，汇流器另一边接满载带。静态写法下 B2 像分流器（先判定的一方独占），动态写法下两边轮流。

### 5.2 不补的设定.txt 的四条

**分流器几支通到同一台机器时按哪支数：按近的那支。把握七成。**
- 【推测】同一台机器是一个起点键，它的非分流器末端在同一次 BFS 里一起从层 1 出发，最先到达分流器的就是最短的那支。只有某支途经的元件已被更早的起点组编过号，才会按那个号，但那已是"通到不同机器"的情形。分流器直接贴着机器的那一支不算（分流器不在机器的收货名单里），分流器靠另一支被数到。
- 实验：研磨机的两个存货端口分别由分流器的两支供蓝铁粉末，短支 1 段带（1 个元件），长支"带—桥接器—带"（3 个元件）；砂叶粉末另走一条限速 6/min 的线，使蓝铁粉末只消耗 12/min，两支都堵满。按"短支先接通"和"长支先接通"各建一次，再各同时重放研磨机一次。预测四种情况下长支第一段带都出现迟滞（物品有的对齐箭头、有的错半格，导论:100），因为按短支数时分流器比长支首元件先判定（核对-模拟2.md:24 的推导）。若某种建法不卡，说明游戏会按长支数。

**机器是否被汇流器的其他上游带动：制造单位、协议储存箱、仓库取货口、反应池不会（六成）；储液罐、暗管出口会（六成）。**
- 【推测】收货名单只收元件，机器在全部元件之后才出货（第三节）；储液罐、暗管出口被社区列进与管道、汇流器同一轮询组（`页面/优先输入_输出_汇入理论.md:25`），推测它们实现成元件式节点。两种社区说法（导论:84-88；附录:13）说的是两类单位，并不矛盾。
- 实验：存满矿的协议储存箱出口紧贴汇流器，汇流器另一边接满载过路带，下游进仓库存货口，数 10 分钟。带动说预测两边轮流、过路带上游开始堵；我的预测过路带 300、箱子 0。再把过路带换成半载：两说都预测箱子补空当。对照组把箱子换成储液罐、带换成水管，预测两边轮流。

**协议核心与仓库存取货口的特殊表现：来自独立的仓库模块，按固定遍历次序服务、没有轮询指针。把握五成。**
- 【推测】存货侧先到先收，仓库装得下时看不出（E36）。取货侧货够时每个口都满速，看着像轮询；缺货时次序在前的口拿走全部，看着像优先（E37、E69）。次序初值大致是建造次序；删掉重放可能插到别处（字典复用空位）；下线重载后回到按存档次序（E35 的"下线多半修正，有时反而引出"）。它们在物流之后才出货，所以紧贴出口的汇流器上过路带总先走（导论:270）。
- 实验：两个仓库取货口 A、B 取同一种物品，让仓库里这种物品保持近乎为零（只从一个存货口进 10/min），A、B 下游都通畅，数 10 分钟 A、B 各拿多少。预测一方几乎全拿，而不是各半。再拆掉占优的那个口重建，看是否翻转；再下线 30 分钟，看是否翻回。

**物品准入口阻断是否改变计算先后：不改变。把握八五成。**
- 【推测】阻断是运行状态（收货时答"不收"），不是接通或断开。若阻断就重建先后表，每个限速准入口每 10 秒要触发一次重建，既贵又没用处，没有理由这样写。
- 实验：分流器—汇流器直连的优先汇入结构（E28），用放置顺序定好谁独占；在独占那一路分流器的上游插一个计数准入口，让它用完累计额度阻断 1 分钟，再调高额度放开。预测独占关系不变。对照：把这个准入口拆掉重建（真的断开再接通），预测可能改变。

### 5.3 下线期间与上线后

**预测（整体把握六成）：**
- 计算先后：下线后每批补算开头从存档重建先后表；上线切回满频时再重建一次，此后到下一次编辑或重载都不变。【推测】重建按存档次序，存档次序多半是实体编号：移动不换编号（E101 移动的反应池带着物料，说明移动的是同一个单位），删掉重建换新编号。所以"移动重放"调出的优先级下线后会改回去（E65），"删掉重建"调出的会保留。
- 轮询状态：指针多半不存档（五成），每批开头回到初值。长期份额几乎不变，每批最多偏一件；依赖精确相位的装置（时钟、整流、准入口同步，E66）会失效。
- 各单位里的物品：数量守恒（三月修复后，E74）；格内相位在批边界可能被对齐。满载单位在批边界会丢一点吞吐。【估算】E63 的产线在 8—12 小时里积出约 50—100 件，折每小时 4—13 件；按每小时 11.8 批算，每批少 0.35—1.1 件，相当于 30/min 下每批停 0.7—2 秒，与三月记载的"约每 5 分钟一次、总时长低于 4 秒"（E59）同一量级。
- 几天不上线：【证据】开发商说改用精简频率估算（第一节）。【推测】估算大概是平均产率乘时长，上线时把内部状态设成某个标准状态；这期间 1/4 秒级的效应（迟滞限速）可能不体现。

**对"一张布局长期稳定达标"意味着：**
1. 只有层数决定的先后和平均流量可靠。同层先后、末端序、轮询相位都要按"随时会被换"对待；规则 L27、L28 写"无法确定"正对应这一点。
2. 我们的证明默认次序定下后不变，游戏里下线时每批都可能换一次。所以还需要：从任一可达状态、换成任一允许的次序后，仍会回到达标。E77 的多稳态和 E67 的溢流器就是这类风险。
3. 零余量的要求下，别让准入口正好卡在额度上，给批边界的损失留缓冲。

**实验：**
- 次序重置：两个分流器同层直连一个汇流器，先放汇流器，再放 S1、S2（各自上游另有满载供给），确认 S1 独占。复制三组：甲不动；乙把 S1 删掉重建；丙把 S1 用移动挪开再挪回。乙、丙此时应变为 S2 独占。下线 30 分钟再上线：预测甲、乙不变，丙回到 S1 独占。若三组都不变，说明存档保存了接通历史；若三组变成同一种，说明是按坐标重建。
- 批边界损失：三条线运不同物品，末端都进仓库存货口，读仓库增量：甲是满载 30/min 过一个只设放行物品的准入口，乙是满载过额度 5（每 10 秒 5 件，即 30/min）的准入口，丙同乙但上游只供 25/min。在线挂机 1 小时、下线 1、2、4 小时各测一次。预测甲、乙下线时少、丙不少，少的件数随下线时长线性增加，约每小时 4—13 件。社区的修法正是把经过准入口的流量降下来（`页面/1.5智能最大毛产.md:364`），与"只有满载单位丢"相符。
- 指针存档：一个分流器三路各进一个不供电的空协议储存箱（不供电就不无线传输），上游 30/min，下线 20 分钟，每箱约 200 件、未超容量。指针存档时三箱相差不超过 1；每批重置时第二条接通的那路多出至多"批数"件（约 4 件）。先在线挂 20 分钟做对照。
- 多天估算：n=3 的迟滞限速器（24/25，导论:164）接仓库存货口，在线测 1 小时的速率，再离线 3 天，看平均速率是 24/25 还是 1。
