EnKAD 终末地基建模拟器调研
日期：2026-09-30
状态：公开网页与公开构建代码的静态核查完成；未运行模拟器，未取得原始仿真内核源码。
对象：https://beta.enka.network/endfield/aic/ 。正式版 https://enkad.enka.network/ 用于核对产品介绍与教程。以下“当前实现”指此次读取的 beta 构建，不把旧更新记录直接当作当前实现。

一、结论

EnKAD 不是只用配方比例算产量的计算器。作者在 2026-03-25 宣布放弃难以处理分流、汇流和反压的静态求解，改用逐步运行工厂的 emulator。目前 beta 的公开 JavaScript 把设备、传送带、水管、仓库等打包为物流图，交给 WebAssembly 内核运行，再显示物品、缓冲、堵塞、产率和时间线。

它距离“完美模拟”有一项可以从公开代码直接指出的缺口：供电覆盖状态没有传入这条生产仿真路径。移除仅提供覆盖的电力塔，会改变前端的 powered 显示，却不会因此改变内核收到的物流图或设备 disabled 字段；内核不能据此停止那台机器。这个判断来自数据流静态核查，不是运行实测。

另一个重要差异是公开仿真 tick 为 0.5 秒，传送带画面接收每格四个离散位置的状态；社区导论的最小步为 0.25 秒、每格八个位置。这说明不能把 EnKAD 的一个 tick 当作社区的一个 tick。内核是否另有不可见的半步处理，公开文本看不出，因此不能仅凭这个差异就断言它一定没有迟滞输出。

社区评价它“可以在一定程度上模拟优先输出现象，但是无法模拟复杂限流器”。此次没有找到官方原始源码仓库或开源许可证；决定详细轮询、层级、使动和迟滞行为的部分在 WASM 中。不能把“有分流器、有优先级标记、有堵塞状态”升级成“已实现社区十三项特性”。它适合作布局、配方、产量和一般堵塞的辅助检查，不适合作复杂限流器或亚秒时序的最终验收依据。

三、它是什么

1. 作者与形式
【作者说明】正式名称是“EnKAD - Arknights: Endfield Factory Planner”，自称 Endfield AIC blueprint editor：在浏览器规划工厂并计算产能，可从空白方案或现成蓝图开始。产品属于 Enka.Network；公开个人页把 Algoinde 标作“Head of Enka.Network”，正式版教程署名 Algoinde。可确认 Algoinde 与产品的主要关联，不能据此列出完整开发团队或认定全部代码都由一人写成。[S1—S3]

它是网页编辑器兼生产仿真工具，不是面向算法研究者的独立开源库。公开菜单包含新建、我的方案、最近方案、收藏、设置、更新记录、帮助；可分享方案和导入游戏蓝图。教程面向工厂游戏新手，讲配方、传送带供料、仓库、合流和空间规划。目标用户首先是搭建、检查、分享产线的玩家。[S1—S3、S4]

2. 语言与公开程度
【构建代码】前端使用 Svelte/SvelteKit，交付为 JavaScript；生产内核为 aic.DXY4r1Ur.wasm。调用器中有 zig、Zigler、zigler 等名称，提示内核很可能使用 Zig，但没有原始源码或编译说明，不能把这个语言判断列为已核实事实。[S5]

【未确认】官网未给出源码仓库或开源许可证。查询 Algoinde 的公开仓库、GitHub 的 EnKAD 名称和作者名下 endfield 仓库，未找到对应工程。Algoinde/BlewPrints 虽是 Svelte 工程，其 README 明确是 Blue Prince Wiki，不是 EnKAD。准确结论是“未找到原始源码及开源许可”，不是“已证明作者从未公开源码”。公开 JavaScript 仍可核查部分数据流；可下载的 WASM 二进制不等于原始源码公开。[S9]

3. 更新日期与规模
【作者说明】首页仍显示“Last update version: 1.2 (April 17, 2026)”，正式版另提供“Try the beta version; supports 1.5”。然而 beta 内置更新记录最新已标完成条目为 2026-08-08。因此首页的 4 月文字不能作为项目停更日期。[S1、S4]

【公开响应头】当前 WASM 资源的 Last-Modified 是 2026-09-27 12:37:35 GMT。这是资源发布/文件修改时间的线索，不是可核验的开发提交时间。[S10]

【构建代码】默认工作区构造尺寸为 70×70；有 Valley IV 等区域预设、固体与液体物流、协议储存箱、反应池以及新设备数据。仿真提供整个工厂、单设备和选区边界的产率，并能回看捕获的时间线。它的范围已经是整张布局，而不是只模拟一个分流单元。未得到原始代码量、用户数量、可靠运行的设备数量上限或性能测试数据。[S4—S6]

四、仿真怎么做

4.1 从静态求解改成动态运行

【作者说明】更新记录的三条关键说明如下。[S4，On 更新记录数组，约字符 31,000—39,000]

2026-03-15：“The splitters/convergers and backpressure logic killed me”，当时只有 somewhat working solver。
2026-03-25：“The production solver is now an emulator.” 作者称静态求解工厂产量在数学上很难处理，“You fix one thing, another one breaks”，于是改成运行工厂，模拟约 5—25 分钟的游戏经过时间，收敛早则提早停止；当时称已移入 Web Worker。
2026-04-20：“Full solve toggle”。作者解释当时为性能只分析运行末段的一部分；全程平均虽不精确，却有助于找出堵塞来源。

这几条说明既证明它确实转向动态仿真，也记录了作者遇到的困难和统计取舍。但不能把当时的 Web Worker、5—25 分钟或 Full solve 开关原样当作当前 beta 路径。

【构建代码】当前可见路径是 captureRunChunked → wasm_capture_begin → 多次 wasm_capture_step → wasm_capture_finish。在 JavaScript 里按帧时间预算批量推进内核，再以 requestAnimationFrame 让出执行时间；本次所见这条调用链没有 Worker 转发。内核还支持 wasm_run、wasm_seek、传输事件、产率、堵塞/空闲区间和测试结果查询。[S5，captureRunChunked，约字符 580,000；Uo.capture，约 587,000]

4.2 时间单位、运行上限与统计

【构建代码/作者界面说明】Uo.MS_PER_TICK = 500；设置描述是“1x is realtime: one tick every 0.5s”。产率转为每分钟时乘 120，与每秒两个公开 tick 相符。公开推进参数和回放时间轴使用整数 tick；不是纯静态流量公式，也没有证据表明对外采用事件时间跳跃式调度。[S5，MS_PER_TICK，约 585,000；pathRates，约 595,000；S7，playbackSpeed，约 5,200]

当前默认 solveMaxTicks 为 7200，传给内核的 ceiling 默认相当于 60 分钟；参数允许的上限 86400 相当于 12 小时。这是运行上限，不是每次必定运行这么久。内核返回 Insufficient / Approximate / Converged 等统计状态；收敛判据的内部实现看不到。[S5、S7]

【静态推导】若没有更细的内部步骤，0.25 秒后才出现的空位不属于这个公开时间格点，无法逐事件复现社区“一步晚 0.25 秒”的现象。要复现，必须有内核半步等更细状态，或以另外的等效处理保存相关作用；公开文本不能确认有无这种处理。因此这里只记时间口径不同，不据此给迟滞功能判“没实现”。

统计稳定也不是规则正确的证书：Converged 至多说明内核按自身模型得到某种稳定产率，不能证明该模型与游戏的全部规则一致。作者旧记录里的末段统计取舍与当前内核统计方法是否完全相同，同样未确认。

4.3 图、传送带与物品状态

【构建代码】So.build 从编辑器格网追踪实际物流连接。So.pack 生成：
- nodes：设备 id、disabled、recipes、mode、value、counter、item；
- edgenodes：传送带/水管路径 id 与 length；
- edges：from、to、BELT/PIPE 类型、固定物品、输入口/输出口编号；
- depot、环境关系、按 tick 标注的 events 与 tests。

物流桥的两轴分别生成节点；不会把交叉桥两轴混成一个共享单元。设备端口编号被保留，但它们的详细轮询逻辑在内核中。[S5，So.build，约 568,252；So.pack，约 572,000]

【构建代码】内核给前端的路径状态包括 itemIds、stuck、headTick。传送带绘制以 n >> 2 选格、n & 3 选格内位置，即每格四个离散索引位置；水管绘制另走一条路径。smoothItems 设置只是对画面平滑插值；不能把平滑动画理解成内核用连续小数坐标仿真。[S5 的 getPathItems；S8 的 Ce.#n，约 26,100；S7 的 smoothItems]

这个接口不能证明传送带每格可堆四件物品，也不能证明内核完全没有更细临时状态；能证明的是对外返回及绘制使用这套离散状态，而非社区每格八个最小位置的同一接口。

4.4 分流、汇流、工厂端口与协议储存箱

【构建代码】设备库包含分流器、汇流器、协议储存箱；图传入连接与端口编号，内核返回 lastInIndex、inputSlots、outputSlots、oneBuffer 等设备状态，以及 MARK_PRIORITY / MARK_TIE / MARK_SPLITTER 等端口标记。可见它有缓冲、路由与优先级相关处理，不是把所有端口都当成无状态的均分流量。[S5]

【社区评价】有“一定程度”的工厂优先输出支持。[C1，59—61 行]

【未确认】上述字段不能确定 231、123 的轮询顺序，失败是否跳过，是否使用“最久未输出”的工厂轮询，也不能确定协议储存箱是否先收后送、满箱空位晚一步传播。没有公开核心算法可据以补全这些结论。

4.5 物品准入口与复杂限流器

【作者旧说明】2026-05-05 更新记录称 control ports 从类似桥接器改成能按指定物品过滤，同时说“There's no item counting”，当时作者认为计数不太有用。[S4]

【当前构建代码】这条旧说明已不足以描述当前 beta。当前准入口界面同时有速率和计数控件，读取运行中 getCounter，并把 state.value、state.counter 送入 WASM。界面另明确提示：“In-game you can only select increments of 6/m. Arbitrary rates are an EnKAD convenience.” 即非游戏档位的速率是主动提供的规划便利。[S6，conditioner 控件，约字符 46,100—47,600；S5 的 Building.State 和 So.pack]

因此能确认当前有过滤、限速/计数配置与计数状态接口；不能再称当前 beta 完全不支持计数。限速计时、停开后的恢复、计数清零及多个控件交互的内核正确性仍未确认。

【社区评价】“无法模拟复杂限流器”。友情链接没有列出具体失败布局或测试版本，也没有把问题归因于单个物品准入口缺少设置。按社区其他文章语境，复杂限流器还可以依赖环路、优先级、阻塞、物品相位或迟滞；不能把这句评价改写成“根因就是没有计数准入口”。[C1—C3]

4.6 水管与供电

【构建代码/作者说明】固体与水管分层，图的边有 BELT/PIPE 区分，液体/气体设备也有不同数据。2026-08-08 更新称泵只取液体、气罐只存气体、液罐只存液体。可确认不是把水管完全当固体带子换皮；但一根管道禁止同时存在两种液体，以及水管迟滞的精确实现，公开文本看不出。[S4—S5、S8]

【构建代码】电力塔等覆盖范围在前端合并为格子集合，再设置机器 powered；渲染会据此显示未供电。然而 So.build 不因 powered 排除物流连接，So.pack 给设备的 disabled 来自 state.disabled，不来自 powered；图没有传入电源覆盖坐标或供电关系。packEnvs 处理的范围设备是 EnvGenWithActivator，不是电力塔。[S5，覆盖计算约 537,400—538,550；So.build/pack；Q.env；S8 的 unpowered 显示]

【静态推导】保留同一组机器、配方、物流连接和手动启停状态，只删除一座没有物流口、只提供覆盖的电力塔：前端 powered 可从真变假；nodes、edgenodes、edges、depot、envs、events、tests 不因此改变。内核获得相同输入，不可能仅因这次供电覆盖消失而停机。因此在当前公开生产路径中，“设备是否被电力塔覆盖”不是生产的有效停机条件。此缺口可以确定；真实供电总量不足、燃料不足后的停电和恢复时序则没有足够公开证据可核。

七、局限、原因和能下到哪一级结论

1. 作者明确说过的困难或取舍
- 静态求解阶段难以同时处理分流、汇流、反压；修正一个问题会破坏另一个。作者为此改成动态运行。这是他实际开发经历的公开说明，不是“游戏所有规则不可计算”的证明。[S4，2026-03-15、03-25]
- 为性能曾只分析模拟末段，全程平均只是另一种诊断口径。该条证明做过统计取舍，不能证明他主动省略了某个物流机制；也不能证明当前 beta 仍原样采用旧统计器。[S4，2026-04-20]
- 配方自动传播时，作者说不确信覆盖所有情况；反应池修复时用了“as (I think) they did ingame”。前者是工具功能局限，后者显示相关实现包含作者对游戏的推测，不是官方底层代码直译。[S4，2026-04-15、04-26]
- 允许非游戏档位的准入口速率，界面明确称其为 convenience。这是主动扩展规划功能；用这些档位得到的布局并不自动成为游戏可搭建布局。[S6]

2. 可以确认的当前缺口
供电覆盖与生产停机没有连通，属于模型未接入这一规则的缺口。作者没有在已读公开说明中解释为什么这样处理，因此不擅自给它安上“为了速度”的动机。

3. 游戏机制尚未摸清
社区底层模型标有残缺、猜想及未完成研究，尤其特殊工厂和无下游环。即使模拟器完整照着这份导论实现，也仍需要用游戏实验验证剩余机制。EnKAD 是否已用其他研究补齐，未确认；不能拿社区未解项目直接断言它也未实现。[C3]

4. 依赖建造历史的隐藏状态
社区把末端序、同层连接先后、蓝图保存/放置次序列为影响结果的状态；几何相同未必行为相同。当前 EnKAD 图保留端口、路径和数组顺序，但看不到独立的真实连接时间与末端序记录。它可能重建一部分顺序，是否等同实际游戏历史未确认。此问题属于完美复现必须处理的输入信息问题，不是已经定位的内核 bug。[C3，116—120、184、367—371 行；S5]

5. 社区评价的边界
“无法模拟复杂限流器”是有明确出处的评价，不是本次复现出的反例。友情链接没有给具体错误布局、版本或失败项；且当前 beta 已出现旧更新记录没有的计数界面。因此不能从这句话推断每一种复杂限流器均失败，更不能指定一个未经核查的唯一根因。

综合看，EnKAD 展示的是：一般动态仿真可以做好大量常规布局工作，但“能跑出产量”与“把隐藏顺序、细粒度时序、特殊设备和供电全部复现”是不同的完成标准。这里可以证明它至少没有把供电覆盖接入生产路径；其他十三项应逐项验证，而不是用 emulator 的名称或收敛标记代替验收。
