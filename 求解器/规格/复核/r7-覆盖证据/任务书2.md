## 2. 主席已定的事（核过）

- **T13 不是选择点，是正式文件笔误，已改**：`求解约束.txt` 的「回路守恒」逐 tick 式原写「基地内（含缓存格）」，仓库在基地内，入库不改变基地内总数，该式在字面读法下只要入库非零就恒假；相邻的「回路存量」用的正是「仓库外」。已改为「仓库外（含缓存格）」。选择点清单里的 T13 整条删除，把它的处理记进修订记录。
- **T7 的端口到格映射定为分配读法**：规则 L15「存货/取货端口：把物品存进/取出本单位物品格的端口」、L16「运输单位的存货端口/取货端口与其他单位的取货端口/存货端口相遇」、L17「存货/取货物品格…只与该单位的存货/取货端口和缓存格相连」是同一句式，斜线按位置对应；L15、L16 的非分配读法各自与条文自身矛盾（存货端口取出物品；存货端口与存货端口相遇成通道），L17 没有理由单独反例化。T7 里其余各项（存货格混装甲乙、容量计数域、开闸论域、开闸完备度、多配方锁定时点、大机选格）仍未定，须拆成正交轴。
- **T6 拆两轴**：传输的判定粒度按单位一次（规则 L25「一个单位的一次尝试制造或尝试传输」、L36「自身所有物品格内的所有物品」），已定；冷却粒度（按箱一个 5 tick 冷却还是六格各一个）未定。
- **第一块砖的布局本轮不做**：它属于试点步。本轮写内核输入格式，内核测试用合成小布局。
- **受限模型声明的性质**：它写的是「第一版内核实现哪一组读法」，是工程分期，不是对规则的裁定。每条选的读法必须在被条文排除后剩下的集合里，写明覆盖损失和其它取值何时补；任何一条都要能被参数轴替换。

### B. 契约修订与真正的复核（codex 修订 → opus 三视角复核 → codex 两席否证 → codex 修订，至多 2 轮）

2. 按完整性批评 §4.1 改 `via.storage` 口径：协议储存箱是仓储单位不是运输单位，经过它的逻辑路径要切成两段分别计 S、R；契约说明与 contract.json 同步。

### C. 内核输入格式规格（codex 起草 → opus 三视角复核 → codex 两席否证 → codex 修订，至多 2 轮）

新文件 `求解器/规格/内核输入.md`：
1. 布局：每个单位实例的类型（用单位目录 id）、占格、朝向、端口位置由类型与朝向推出、供电桩；协议核心与仓库取货口的仓库格指派。
2. 建造史：逐个建成的时刻序（蓝图：传送带在其余单位之后，其余次序不定→参数）；接通时刻由此推出；离线事件的表示（接通先后重取）。
3. 设定：开关初值、准入口设定（放行物品、累计上限、每 5 tick 上限）、核心 6 取货端口与 46 个仓库取货口的物品格指派、储存箱与传输开关。
4. 参数向量：按运行语义 §3 的三类生命周期与 A 线的参数轴表逐项列字段。
5. 初态与调试操作：引用 T11、T12，表示成「初态 ＋ 有限的调试操作序列（不精确到 tick）」。
6. 与送料契约的对接：逻辑送料记录里的机器 id 与布局实例 id 的映射字段。
7. 三个合成小布局样例（JSON 或 TOML，放 `求解器/数据/样例/`）：桥接器双通路、分流器三路轮询、一台混做粉碎机接两台下游；样例只要求合法（占格不重叠、端口相遇成通道），不要求达标，作为内核测试输入。
复核视角：覆盖（任何合法布局都能表示吗，规则里有没有输入格式表达不了的设定或事件）、可导出性（每个字段对应哪条规则，有没有擅自加的自由度或擅自砍的自由度）、一致性（与运行语义的 State/Parameters、单位目录 id、送料契约的映射是否一致，样例能否按格式解析且合法）。
