## 1. K-r1-L3-01（重要）`semantic_context` 的运行部分在输入格式里没有落点

`运行语义.md` 第 23 行把完整状态定义为七组：`State = (layout, settings, inventory, progress, logistics, environment, semantic_context)`；第 33 行给 `semantic_context` 的内容是「判定排序规则与固定性辖域（T2）；制造端口到格映射……；其他参数当前值、生命周期、**未决事件日程**；**tick 内已发生移动的记录**」，并注明「记录用于核对端口速率与原子判定」（据：判定、判定次序、约束·端口速率）。

`内核输入.md` 第 7 行声明「状态对接 [运行语义](运行语义.md) §2」，§6 第 219–228 行把非仓库初态定义为 `StateSeed={inventory,progress,logistics,environment}`。逐组对照：`layout`→§2、`settings`→§4、`inventory`/`progress`/`logistics`/`environment`→StateSeed，六组有落点；`semantic_context` 中属于参数的部分落到 §5 的三个生命周期对象，但**「未决事件日程」与「tick 内已发生移动的记录」两项在全文没有任何字段**（全文检索 `semantic_context`、「已发生移动」、「未决事件日程」在 `内核输入.md` 均无命中）。

这不是可以推给「派生量」的项：约束·端口速率是「每个端口每 tick 至多通过 1 个物品」，要在一个时刻内串行地逐个判定（规则 L25）并仍然守住这条上限，就必须知道本时刻该端口已经成功过几次；`受限模型声明.md` 第 19 行也明写时刻结束的重复判据「须含指针、级内记忆、阻断、额度和**本刻端口额度**」。同时 `time.instant_end`（T1）未定，所以也不能用「初态总落在时刻边界、该记录必为空」来免掉这个字段——§6.1 与 §8 恰恰强调调试结束的准确时刻不可指定。

后果：按本格式播种或续跑一个非时刻边界的状态时，端口额度与待判定事件无法表示，执行器要么补默认（＝给未定量取值），要么拒收全部此类初态；而 §9 的自查写的是「T11/T12 初态及不精确操作各有落点」，会让后续误以为状态对接已完成。§6 末尾「需要新历史的机制须先升级 StateSeed」是通用兜底，没有点名这一项，也没有登记覆盖损失。

## 2. K-r1-L3-02（重要）桥接器的「待定方向」无法表示，`port_layout` 强制取定值

`运行语义.md` 第 27 行把 `layout` 组的内容写成「……端口；建成状态与建造次序；**桥接器每对端口的已定/待定方向**」——待定是状态的一种合法取值。规则 L63 也只说「端口类型由先接上的那一端所接的单位决定」：某一对平行边始终没有相邻端口时，这对边的类型没有任何条文把它定下来。

`内核输入.md` 第 51 行要求每个实例给 `units[].port_layout`＝目录 `ports.layouts` 的整数索引，桥接器的四个 layout 每个都同时钉死两条轴的存取方向（目录 `桥接器.ports.layouts` 复算确认：4 个 layout 形如「竖轴南进北出／北进南出」×「横轴西进东出／东进西出」）。格式里没有「该轴方向待定」的编码，也没有把 `port_layout` 写成 Decision。只接一轴的桥接器是合法布局（例如只做南北过桥、东西两侧无邻居），此时输入必须为未定的横轴断言一个方向。§2 第 51 行自己说这个值「仅为预期导出结果……须通过 §3 先接历史核验」，而未接通的轴根本没有可核验的先接历史；最小检查器对这种布局报 `unsupported: 未接桥轴方向无法在此子集核验`，等于这类合法布局既不能如实表示、也不能被检查。

这既与 `运行语义.md` 的状态定义冲突，也踩到「未定不是取值的来源」。可行的修法（供起草人参考，不是裁定）：把桥接器的轴向改成两条轴各一个 Decision（`unresolved`／`derived`，derived 指向先接事件），`port_layout` 对桥接器只作为导出结果的冗余校验位或直接取消。

## 3. K-r1-L3-03（重要）`warehouse_slots` 放进 `settings`，与两边的「设定」定义都冲突

`运行语义.md` 第 28 行把 `settings` 组写成恰三类：「各需电功能开关；核心六个取货端口、每个仓库取货口的仓库物品格指派；准入口身份及两类限额是否设定和数值」，性质栏是「**明文可设定项**；可随时更改，但调试后禁止玩家修改」（据：设定、开关、协议核心、仓库取货口、物品准入口、零干预运行）。`内核输入.md` 第 30 行的顶层表也把 `settings` 描述为「§4 的**明确可设定项**；据：设定、开关、准入口、核心、仓库取货口」。

但 §4 第 92 行的 `settings={switches,gates,warehouse_slots,warehouse_assignments}` 多出了 `warehouse_slots`，第 98 行给它的据是「规则 L13–14、L41」：L13 是物品格通则、L14 是仓库的定义、L41 里「可自行设定」的宾语是「每个取货端口各连接仓库的某一物品格」，也就是 `warehouse_assignments`。三条据没有一条授权玩家设定某个仓库格放哪种物品；规则 L22 的「设定」清单里也没有它。按规则，仓库格的物品身份是库存的结果（L13：一格只放一种，核心内同种只占一格），属于 `运行语义.md` 的 `inventory`／`environment`（「仓库库存」）而不是 `settings`。

后果有两处具体的：其一，`settings` 整体被任务 L8「零干预运行」冻结，把仓库格身份当设定会让实现把「哪些物品能有仓库格」当成整场不可变的玩家输入；其二，`warehouse_assignments` 是真设定，它引用的 slot 必须是已命名的 `warehouse_slots`，于是「把某取货端口指到一个当前为空、却已预先绑定物种的仓库格」成了格式的常规用法（三个样例都给 0 件的成品格绑定了物种），而空格是否保留物种身份在制造侧正是未定轴 `manufacturing.empty_slot_identity`（T7），仓库侧同样没有条文裁定。§4 自己又写「不宣称完整游戏物品域已证有限」，与把这张表当静态设定表相矛盾。

## 4. K-r1-L3-04（次要）§7 对 `ORE*`／`CORE` 逻辑端口的映射与 `source_map` 重叠，且没有一致性与完整性要求

复核实际契约数据（`候选B/contract.json`，219 机器 ／ 315 条 LF ／ 52 个来源）：逻辑端口串除了 `M000:out:1` 这类，还有 `ORE000:out:1`（52 条矿源 LF 的 source_port）与 `CORE:in:1…14`（成品入库 LF 的 target_port）。

`内核输入.md` 第 249 行的 `port_map` 只举「把 `M:out:n` / `M:in:n` **等**逻辑端口映到对应实例规范口，角色、端点须匹配」；第 247 行的 `source_map` 另有 `{source,port}`，把 `sources[].id` 直接绑到实际的核心／仓库取货口 output 端口；第 250 行的 `feed_map` 又要求「路径的首尾口对应 port_map」。于是一条矿源 LF 的首口同时受 `source_map`（按 ORE 变量）和 `port_map`（按 `ORE000:out:1`）两张表约束，而 §7 没有写这两者必须相等，也没有写 `ORE*:out:*` 到底该不该进 `port_map`。另外 `machine_map` 明写「完整绑定覆盖全部机器且单射」，`source_map` 只写「逐个互异」，没有对 52 个来源的完整性要求，`core_map` 与 `CORE:in:n` 的端点归属也只能靠「端点须匹配」一句含糊承接。

这不影响本次交付（`contract_binding` 全为 null、最小检查器明确拒收非空绑定），但后续写加载器时两张表可能给出互相矛盾的物理端口而无规则可判。建议在 §7 明写：`ORE*`／`CORE` 前缀的逻辑端口其端点分别由 `source_map`／`core_map` 决定，`port_map` 对它们的取值必须与之相等（或禁止重复登记）；并给 `source_map` 写完整性要求。

## 5. K-r1-L3-05（次要）§8 的「最小子集」清单与检查器实际拒收的条件不符，拒收信息也不按 §8 的 `unsupported` 纪律

§8 第 279 行写「对超出子集者明确报 unsupported，不判物理非法」，并列出最小子集的附加要求：仓库格绑定目录已知物品、全部开关为显式布尔、建成时间为互异符号、桥每轴有唯一非桥先接端、`profile_id=null`。实测（对样例的内存副本调用 `check_examples.py` 的 `check()`，不改样例文件）：

| 输入 | 文档怎么说 | 程序行为 |
|---|---|---|
| `construction.selected_order=null` | §3 第 80 行明写「selected_order 为 null 或每实例恰出现一次的 id 数组」 | 拒收，信息「建造见证必须每单位恰一次」，无 `unsupported:` 前缀，§8 也没登记这条限制 |
| `time_relations` 追加一条可从见证推出的真关系（`build_0 < build_2`） | §3 第 82 行「`time_relations` **包括** `{before,after,relation,basis}`」，按任务书 §4「枚举默认是包括」应可为超集 | 拒收，信息「符号时刻关系须与见证次序相符」（`check_examples.py:228,234` 要求恰为相邻链），无前缀，§8 未登记 |
| 仓库格 `item=null` | §4 第 98 行明写允许 null；§8 已登记子集要求 | 拒收，信息「仓库格 id 重复或未知物品」，无前缀且措辞像非法而非超出子集 |
| `anchor`／任一开放轴给 `specified` | §8 未逐项登记 | 拒收且带 `unsupported:` 前缀 ✓ |

也就是说 `unsupported` 前缀纪律只落实了一半，两条限制（`selected_order` 非空、`time_relations` 恰为相邻链）文档里完全没有。后果是后续拿一份合法且信息更全的输入来跑，会得到读起来像「布局非法」的失败。

## 6. K-r1-L3-06（次要）样例检查器把 `候选约束.txt` 钉进只读指纹，非正式来源一变就使交付自检失败

`check_examples.py:55–61` 的 `SOURCE_HASHES` 除三份正式文件外还钉了 `候选约束.txt` 的 SHA-256，`:430–431` 用 `require(fingerprints == SOURCE_HASHES, ...)` 把它作为硬失败条件。但 `内核输入.md` §1 列的来源只有三份正式文件与共享目录，全文没有一处依赖候选文件的内容；候选约束按纪律「不是正式约束」，且是仍在增长的工作文件（现 862 行）。

后果：任何人往 `候选约束.txt` 追加一条候选，`python -B 求解器/数据/样例/check_examples.py --self-test` 就会以「正式/候选文件指纹与读取快照不同，须人工重新核对」退出 1，而三个样例、目录、轴表都没有变。把非依赖、非正式的文件写进失败条件，会让这条复现命令很快变成假红。建议要么把候选文件的指纹挪到报告的「记录」栏而不进 `require`，要么删掉。

## 7. 本席明确核过而**不**作为发现的几点

- §5.1 把已定轴编成英文值（`retain_whole_batch`、`actual_inbound` 等）：轴表对应行确为中文单值，§5.1 已声明是编码而非新增候选，检查器逐值比对，成立。
- 样例把 80000／0 标 `条文直引` 而 §6 又说「满额由核心容量与同种单格推出」：口径上更像算术推论，但 `送料契约.md` 的类别定义把「正式文件明写的……容量」归入条文直引，两读都能自洽，不足以成为发现。
- 桥接器的 `(port_layout, rotation)` 对同一物理构型存在 4 重别名（轴标签互换），使同一布局可有不同 PC id：仅影响 id 的规范性，不影响任何检查结论与同轴判定，按次要以下处理，不单列。
- `检查结果.json` 的 `axis_alignment: "全部字段名、已定值和生命周期逐项检查"`：程序确实逐项检查了**样例**三个生命周期对象的分组；文档 §5 表的生命周期列未被程序比对，但本席手工复算 87 行全部相符，故不列为发现。
