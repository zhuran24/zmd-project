日期：2026-09-19。席位：Claude 源，视角「覆盖」。被复核对象：`求解器/规格/内核输入.md`（`kernel-input-v1` 草案）与 `求解器/数据/样例/` 下三个样例、`check_examples.py`、`generate_examples.py`、`检查结果.json`。

## 一、样例合法性：独立复算

不复用 `check_examples.py`，另写一份只依规则条文与共享目录的复算脚本（草稿在本席 scratchpad，逻辑如下），重算占格、端口世界坐标与法向、以及「相遇」集合：

- 占格：按目录 `dimensions` 取规范 `(w,h)`，局部格 `(u,v)` 按 r0/r90/r180/r270 分别取 `(u,v)`、`(h−1−v,u)`、`(w−1−u,h−1−v)`、`(v,w−1−u)`，再加 `origin`。
- 端口：规范格 south=`(p,0)`、north=`(p,h−1)`、west=`(0,p)`、east=`(w−1,p)`，格与外法向一起按同一旋转换码（法向按 `(x,y)→(−y,x)` 逆时针）。
- 相遇：两端口占相邻格、法向相反、面对同一条格边，一端 output、另一端 input，且至少一端 `family=transport`（据：规则 L16；约束·端口对接）。

复算结果：

| 样例 | 越界 | 占格重叠 | 占格数 | 独立导出 PC | 文件申报 PC | 一致 |
|---|---|---|---|---|---|---|
| 桥接器双通路.json | 无 | 无 | 122 | 4 | 4 | 是 |
| 分流器三路轮询.json | 无 | 无 | 128 | 4 | 4 | 是 |
| 混做粉碎机两下游.json | 无 | 无 | 149 | 9 | 9 | 是 |

另外逐对检查「法向相对但未成通道」的邻接，三个样例都没有出现同类端口（出对出、进对进）面对面，也没有两个非运输端口面对面。即：没有被漏登记的相遇，也没有伪造的通道。缓存内部通道按目录 `inventory` 的 input/output 计数逐条导出，得 0、0、8，与文件一致（粉碎机 1+1、研磨机 2+1 两台）。

朝向与端口边的逐项核对：

- 仓库取货口（`分流器三路轮询`）：`bottom_source` r0 置于 `origin.y=0`，3×1 的 south 长边贴下边界、取货端口在 `(4,0)` 朝北向内；`left_source` r270 置于 `origin.x=0`，换码后占 `x=0, y=3…5`，端口在 `(0,4)` 朝东向内。两者都落在任务 L15 允许的左／下边界，r90（右边界）与 r180（上边界）被正确排除。
- 桥接器（`桥接器双通路`）：`port_layout=0`（south=存货、north=取货、west=存货、east=取货）。按建造见证 core→south_box→bridge→north_box→west_box→east_box，各通道接通时刻取两端较晚建成者（规则 L28）：竖轴 south 侧 = rank 2、north 侧 = rank 3，横轴 west 侧 = rank 4、east 侧 = rank 5。两轴先接端分别是 `south_box:north:2`（取货口）与 `west_box:north:2`（取货口），按规则 L63「端口类型由先接上的那一端所接的单位决定」，桥的 south、west 必须是存货端口——与 `port_layout=0` 一致，且两轴先接均无平局、邻端非桥接器。
- 传送带（`混做粉碎机两下游`）：`belt_b0` r0+layout1 = 南进东出；`belt_b1` r270+layout2 换码后 = 西进北出；其余 r0+layout0 = 南进北出。逐段与申报路径的首尾端口一致，桥接器无、不涉跨轴。蓝图次序核对：非传送带 5 个在前、7 条传送带在后，符合规则 L9。

结论：**三个样例在「占格不重叠、端口相遇成通道、朝向与端口边一致」三项上合法**，本轮在样例几何上没有发现。

补记（不是发现，供后续注意）：三个样例都不满足达标侧的构型约束（供电下限 P ≥10、取货口配置 46 口、成品汇入等），`混做粉碎机两下游` 的粉碎机没有任何上游存货通道，因而永远不会真的制造。这与任务书 §3.C.7「样例只要求合法，不要求达标」一致，草稿 §8 也已写明，不构成问题。

## 三、发现

### K-r1-L1-1（重要）调试期重建造成的「重新接通」在格式里无处落，且被接通先后的派生式漏掉

**位置**：`求解器/规格/内核输入.md` §3（`construction` 段：「`moments` 为 `{event,unit,time}` 数组；event 唯一……selected_order 非空时 moments 同序、同实例集合」；「selected_order 为 null 或每实例恰出现一次的 id 数组」）、§5.1（「connection.order 的 derived.value=`construction_then_offline_events`」）、§6.1（`debug_operations[].action` 含 `rebuild`）。

**说的是什么**：格式一边把 `rebuild` 列为合法的调试动作，一边把接通次序定义成只由「建造史 + 离线事件」派生的量，而建造史每个实例只允许一个建成事件、一个建成时刻。规则 L10 明说重建会让「它的通道重新接通」；规则 L28 说接通时刻就是两端较晚建造者的建造时刻；规则 L29 的轮询、L31/L32 的两种分级都按接通先后定序。于是一次调试期重建会产生一批新的接通时刻和新的接通先后，而格式里：

- `construction.moments` 放不下第二个建成事件（每实例恰一个，且检查器要求 `len(moments)==len(order)`、`moments` 与 `selected_order` 同序同实例集合）；
- `connection.order` 的派生式 `construction_then_offline_events` 没有重建这一段，按此式实现会算出重建前的接通次序；
- `debug_operations[].effects` 是 Decision，草稿只说「引用相关轴及合法后效」，没有给新接通次序的编码（对照离线段是有 `new_connection_order` 的具体编码的）。

顺带的同源缺口：`rebuild` 的 payload 只有 `{unit}`，没有新占格／新朝向，也没有与之配对的「只拆不建」动作，所以「拆 A、拆 B、再按选定次序建回」这一类调试程序没有表示。

**条文据**：规则 L10「重建：拆除一个单位后再建造它，它的通道重新接通」；L28「接通：通道形成的那一刻，即它两端的单位中较晚建造的那个的建造时刻」；L29「这些通道按接通先后轮流取得尝试移动的权限」；L31「一级的阻尼取其中最大的、接通时刻取其中最早的……接通早的级别高」；L32「各级按其中最早接通的通道排序」；任务 L11「调试期：布局的全部工作可以不用完全依赖蓝图，同样可以由玩家来做部分操作」。

**为什么是重要而不是阻断**：约束「不得依赖的量·接通先后」已经要求目标对任意接通先后都达成，所以重建不会给全称认证域加新取值，认证的可靠性不因此破；破的是「表示一条具体的调试见证」的能力——而 `求解约束.txt` 的「来源定序」「取货分级」「种子起动」都要靠具体的调试与接通安排来落地。另外 §6.1 已写「重建／既成旋转及其他非设定动作的适用域与后效仍待 T11」，作了对冲；但 §5.1 的派生式是肯定句，检查器还硬要求这个字符串（`check_examples.py` 第 305–308 行），两处不一致。

### K-r1-L1-2（重要）桥接器方向被钉成每实例静态必填字段，离线重排后的方向没有编码，且方向一变 PC id 全失效

**位置**：`内核输入.md` §2 表 `units[].port_layout` 行；§3 桥接器段；§5 `offline.direction_effect` 行；§3 `environment.offline` 段（`new_connection_order` 用 PC id 的有序分组）。

**说的是什么**：`port_layout` 必填且单值，把桥接器每一轴的存／取角色钉成整场静态属性。但规则 L63 说这个角色不是设定，而是「由先接上的那一端所接的单位决定」；任务 L13 说离线后任意两条通道的接通先后可能改变。若离线把某轴两端的先后换过来，该轴的角色就要按新的先接端重定——格式里没有任何有定义的字段能承载「离线后这一轴改成另一向」：`selected_events[].effects` 是 Decision，草稿只说它「引用 §5 的接续轴」，没给编码；`offline.direction_effect` 轴本身也只是记录这个读法待审，不是表示手段。

更硬的一层后果：端口 id 是 `<unit>:<canonical_side>:<position>`，角色挂在 layout 上；桥接器一翻向，原来的 `bridge:west:0`（存货）就变成取货，`PC|<source_port>|<target_port>` 的整条 id 跟着变。于是 §3 要求「`new_connection_order` ……必须覆盖当时全部存在边」的那个 PC id 集合，在允许翻向的读法下会指向一批不再存在的 id；`scenario.expected_paths`、§7 的 `feed_map[].paths` 同理。也就是说，这不只是少一个字段，而是离线段的现有编码在翻向发生时自身不封闭。

**条文据**：规则 L63「桥接器：……每对中一边是存货端口、对边是取货端口，端口类型由先接上的那一端所接的单位决定」；L28 接通定义；任务 L13「离线：离线后任意两条通道的接通先后可能改变」；`求解约束.txt`「不得依赖的量·接通先后：任意两条通道之间的接通先后　据：蓝图、离线」。草稿自身 §5「`offline.direction_effect` ……open：保留桥接器历史定向／新先接序的后效待审」已承认这一读法未被排除，按「未定不是取值的来源」，格式不该先替它选「整场静态」。

**严重度**：重要——格式把一个未定量实质地固定成了静态属性，后续实现与认证都会沿用这一隐含假设；但草稿把它标成「预期导出结果，不能作为设定」并要求过先接历史核验，最小检查器也只收「每轴有唯一非桥先接端」的子集，所以不至于当场算错。

### K-r1-L1-3（重要）仓库物品格的「哪格装哪种」被放进 settings 并钉成静态，条文没有这个设定授权，物品无格可落时也没有规定

**位置**：`内核输入.md` §1.2 顶层表 `settings` 行（「§4 的明确可设定项」）、§4 表 `warehouse_slots[]` 行；三个样例 `settings.warehouse_slots`（各登记 19 个物品格）。

**说的是什么**：规则里「可自行设定」的只有端口到物品格的那条连线（L41「每个取货端口各连接仓库的某一物品格（可自行设定）」、L73 同句式），没有任何条文把「仓库的某一物品格装哪种物品」列为设定项。草稿把 `warehouse_slots[].id→item` 放在 `settings` 下、并且是静态单值，等于凭空多给了一个设定自由度（L22「设定：可自行设定的项目都可以随时任意更改」的论域并不含它）。

同一处还留了一个实现没法定的洞：物品格的种类归属在运行中是会动的——某格清空后是否保留身份、新种物品进仓库时落到哪个 `item=null` 的格，格式里既没有字段也没有轴（§5 给制造格留了 `manufacturing.empty_slot_identity` 与 `manufacturing.input_slot_selection`，仓库侧的 `warehouse.*` 八条轴里没有对应项）。规则 L41 明说核心「物品格数量不限」，所以「格不够」不是理由，但「落哪一格」确实无条文可依，应登记为选择点而不是当成输入里的设定。

**条文据**：规则 L41「协议核心：……物品格数量不限、每格上限 80000……每个取货端口各连接仓库的某一物品格（可自行设定）」；L13「物品格：……只能够放置一种物品的格子，当物品格超过一个时一个单位内一种物品也只能放在一个物品格内（协议储存箱和缓存格除外）」；L14「仓库：协议核心中的所有物品格的集合」；L22 设定的论域；L73 仓库取货口同句式。

**严重度**：重要——多给的自由度会被当成可搜索维度而误导后续；缺的那一条会让实现在「新物品入库」时无据可依（`求解约束.txt`「矿系不入库」只在恰 32 台种植机时才把入库收窄到成品，其余配置下植物系物品是可以入库的，所以这不是一个空情形）。

### K-r1-L1-4（次要）端口 id 与 PC id 非规范化：同一物理布局有多组等价编码，id 随编码而变

**位置**：`内核输入.md` §2.1（「稳定端口 id 为 `<unit>:<canonical_side>:<position>`，用规范边命名，旋转后 id 不改」）、§2.2（「本版 id 的确定编码是 `PC|<source_port>|<target_port>`」）。

**说的是什么**：id 用「规范边」命名，只保证在给定 `(port_layout, rotation)` 下稳定，不保证同一物理配置只有一种编码。目录里至少两类单位有 180° 对称的角色分布，因而有多编码：桥接器 r0+layout0 与 r180+layout3 是同一个物理配置（南进北出、西进东出），但前者该物理南口叫 `bridge:south:0`、后者叫 `bridge:north:0`；协议核心 r0 与 r180 的物理端口集合相同而 id 映射不同；供电桩四向全等价。于是同一张布局可以写成不同的 JSON，派生出不同的 PC id 集合。草稿把 PC id 当成跨文件的指称锚（`scenario.expected_paths`、离线 `new_connection_order`、§7 `feed_map[].paths` 都按 PC id 引用），却没有给规范化规则（例如「同一物理配置取字典序最小的 (layout, rotation)」）。

**条文据**：规则 L63（桥接器两轴独立定向，只有 4 种物理配置）、L41（核心存货边成对、取货边成对，位置集合各自对称）、L76（供电桩无端口）；目录 `正式静态目录.json` 中桥接器 4 个 layout、核心 1 个 layout 与四向旋转。

**严重度**：次要——不影响单份输入的合法性判定，也不影响三个样例（样例里没有出现等价重编码）；但会让跨输入的比较、去重与缓存不可靠，且与 §2.1 自称的「稳定 id」有出入。
