## 2. 逐项否证

### 2.1 K3-r3-L1-01：逐时刻排序的有限表

**结论：`refuted=false`；未能否证。**

**回源。** 规则 L25 规定“同一时刻的多个判定逐个进行，先后无法确定”；任务 L14 只规定“同一时刻多个判定的先后固定”。约束 L3、L10 要求目标对判定先后的每种取值达成。第二轮任务书 §3.A.3 明确保留“每个时刻各一份固定次序、时刻间不必相同”；第三轮 §3.C 要求能给新产生判定实例定序的编码。现行选择点清单 T2、运行语义 L101 也区分 `global` 与预先给定的 `order_at(t)`。

**反例的规则核验。** 覆盖报告给的 A、B 两箱分别占 `(10…12,10…12)`、`(16…18,10…12)`，桩占 `(13…14,10…11)`，核心占 `(50…58,50…58)`。本席独立按整数矩形复算：均在 70×70 内、互不重叠；桩中心 `(14,11)` 的 12×12 范围为 `[8,20]×[5,17]`，两箱均有正面积交集。没有运输单位，规则 L16 不生成任何 PC。见[周期排序独立复算](否证-r3-1-证据/周期排序独立复算.json)。

选空箱、功能开启的具体初值和核心/桩/A/B 依次于 −20/−15/−10/−5 建成的历史。规则 L36 明说空格也尝试，采用每次尝试后冷却 5 的读法，A、B 在 0、5、10……共同到期。预先规定 `t=5k` 时偶数 k 按 A→B、奇数 k 按 B→A。所有同刻次序均固定，不发生同刻重抽；每箱冷却仍为 5，库存始终空、无移动、无端口消耗和轮询竞争。仓库六种满格条件可独立满足，矿石没有消耗；没有玩家定时操作。该合成见证不达产率目标，达标布局专用的机器数量等条件不能用于排除其物理合法性。这里未把某个初值或开关历史提升为规则默认。

**穷举现有入口。** 内核输入 L246、L248、L250 的 `event-order-v1`：`global` 必须全程同一模板序；`per_instant` 只收具体时刻的有限数组且缺时刻即停；`scan_round_then_template` 只排列同刻重复实例。任何有限表都遗漏某次未来共同到期；`Time.symbol` 没有奇偶量词或周期模式，`basis` 是依据而非函数。L250 自述“无限或符号函数需另增函数编码”，与发现相符。

**尝试的反驳不成立。** 受限模型已披露只选 global，故本发现不能表述成“本版有限样例无法执行”或“隐蔽默认”。但原发现针对通用编码缺口；公开登记损失不能让周期序列变成可输入值。两独立空箱交换次序虽不改变物理投影，也不构成现格式已经保存该排序的证据；文件没有给出可把一般逐时刻序全部归约为 global 的等价性证明。未找到能够排除该取值或已经实现相应编码的原文。

### 2.2 K3-r3-L1-02：闭包中途的阶段编码

**结论：`refuted=false`；未能否证。**

**回源。** 规则 L25 的判定逐个进行；任务 L8、L11–12 规定零干预、调试及不精确操作，没有把调试结束限定为完整扫描边界。第三轮 §3.C 要求 StateSeed 完整。内核输入 L286 更明确说“调试可能结束在 tick 中途，不能无证明清空这些记录”；L310 要求恢复状态与计时、预算等相容。受限转移定义 L7 要求中途种子带扫描位置、边界阶段和去重状态。

**实际断点复验。** 本席在原 `check_golden_trace.run` 的循环入口只读观察，独立捕获 `J|2|0|1` 完成后的[物理投影](否证-r3-1-证据/闭包中途物理投影.json)：t=2、轮号 0、下一模板索引 2；`C|2|crusher` 已完成，crusher 为 completed、remaining=0；input 有源矿 1，buffer 有源石粉末 1，feed_belt 已空；`feed_belt:north:0` 与 `crusher:south:0` 的额度均已用 1；模板 11 的制造判定尚未发生。该观察没有把执行器尚未刷新到快照的 `semantic_context` 当成完整合法种子，取证明确保存的是动作之间的物理与控制位置。

**无法准确落字段。** L252 的 phase 仅 `before_boundary/after_closure`。前者不能正确说明完成边界已处理，后者不能正确说明本刻制造模板和后续扫描尚未处理。已有 round、next_template、端口账可保留部分信息，但没有第三种阶段的约定或去重解释。给两种 phase 填矛盾的游标、把未知字段塞进 Decision.value，均不等于符合正文的完整 StateSeed。

**尝试的反驳不成立。** 不精确操作禁止玩家保证命中特定断点，不会自行证明实际历史绝不出现该阶段；在没有玩家动作的前后区间改变调试结束标签，也不增加投料、改设定或重启制造。现 profile 的外部事件阶段和首版执行器支持域确实更窄，实测本身没有证明“改标签后的完整输入会被 profile_v1 接受”。然而发现问的是一般输入是否有这种中途状态的编码，现行 L252 正承认中途恢复尚缺阶段去重状态、报告 unsupported。受限转移定义的抽象要求也未补出具体第三阶段语法。不能用首版拒收来否证表示缺口；亦不把本次观察冒充全调试历史的可达性证明。

### 2.6 K3-r3-L3-01：运行状态 Decision 外壳漏验

**结论：`refuted=false`；未能否证。**

**回源。** 内核输入 L17 规定 unresolved 的 value=null、basis 为非空字符串数组，Decision 状态域只有 unresolved/specified/derived/not_applicable；第三轮 §3.C 要求 StateSeed 完整。规则 L25、任务 L14 使运行排序上下文具备实际语义，不能把未解状态默认为已解。相关拒收边界在内核输入 L310、L353 再次声明。

**实测与控制。** 五个变体均只改一个 Decision 外壳，原具体 value 保持不变。分别把 judgment_context.status 改 unresolved、tick_context.status 改 unresolved、withdrawal_memory.status 改 unknown、删 tick_context.basis、删 connection_order.basis。五例全部通过 checker.check，随后各执行四个时刻。同时对同一损坏 Decision 单独调用现有 `checker.decision`，五例全部被正确拒绝，分别报“未解/不适用不能偷填值”“Decision 状态非法”“Decision: 字段缺失或未知”。见核验结果 `decision_mutations` 及对应的输入反例副本。

**代码定位。** `runtime_example.py:177` 只核 connection_order 的 status/value 而漏 basis；L180、L185、L187 只核 withdrawal_memory、judgment_context、tick_context 的 value。父对象的 `fields(...)` 只核当前层键集合，没有递归验证内层 Decision。check_examples 在进入 runtime 前检查参数和顶层初态 Decision，并未补这五个嵌套对象的外壳验证。

**尝试的反驳不成立。** 将这些变体解释为“运行数据值仍够用”不能否证格式违例；独立 Decision 校验已经给出同项目现有的拒收依据。全空、idle、t=0 的支持域也没有授权非法 status 或省略 basis。缺陷是遗漏调用已有校验，不是要求支持更多物理机制。

### 2.7 K3-r3-L3-02：当前可动级和空格仲裁硬编码

**结论：`refuted=false`；未能否证。**

**回源。** 规则 L15、L73 使取货口读取所指仓库格；L30 只在能移动通道的最高级轮询。内核输入 L118 明文“空格没有物品可取，历史身份不生成物品”，L308 要求初态 current_level 按物理守卫算；L284 要求空格序覆盖已声明无身份空仓库格。受限转移定义 L37 把“源选择器有1件货”列为 physical 的必要条件，L65 要求完整无身份空格序。

**独立反例。** 在任务初始仓库与 StateSeed 当前仓库同时加入 `empty_extra`，item=null、quantity=0、empty_identity=specified/null 且 basis 非空；只将 ore_source 指派改至此格。六类初满仓库、几何、历史、96 轴与全空非仓库状态均保留。没有违反“指空格必须已解身份”的主席裁定，也没有据身份生成物品。

于是源口对应 PC 的 physical=false，ore_source 输出侧与 feed_belt 输入侧的 current_level 均应为 null；空格仲裁序应含 empty_extra。保留原两个非空 current_level 和空仲裁表时，原检查器却通过，参考执行完成四个时刻且制造 0 批。只修 current_level、只补空格序、两者同时修正，三例分别以轮询记忆不符、级仲裁/空格选择不完整、轮询记忆不符拒绝。见[错误派生状态](否证-r3-1-证据/输入反例-空源错误派生状态.json)及核验结果 `empty_source_wrong_derived/empty_source_corrections`。

**代码定位与反驳。** `make_poll_memory:76` 用实例名 ore_source/feed_belt 设两个可动级，不读实际指派库存；`validate_runtime:176` 把它当期望；L183 无条件要求空格序为 []。执行器 `refresh:67–72` 才按实际 physical 重算，不能倒推装载时已验证一致性。声称只支持固定样例也不足：现检查器确实接受改指派后的错误种子，且正文列的子集没有把仓库来源格永久锁死。实现可以拒绝超支持域，但不能把互相矛盾的种子报为完整运行输入通过。

### 2.8 K3-r3-L3-03：制造超容量和摘要失配漏检

**结论：`refuted=false`；未能否证。**

**回源。** 规则 L17 的制造存货/取货格上限为 50，缓存的无限例外不适用于 `crusher:input:0`。内核输出 L27 明确要求 summary/state 一致，L37 要求验证实际事件后效。第三轮 §3.C 的实际轨迹义务适用于被交付记录本身。

**独立复验。** 在正常重新生成记录中，只把 t=2 的 crusher:input:0 写入 999 件源矿，原 17 项回归通过；另一次只把该刻 summary.warehouse_ore 写为 12345，仍 17 项通过；最后按原发现合并两处破坏，也 17 项通过。对应完整副本为[制造格999件](否证-r3-1-证据/输出反例-制造格999件.json)、[摘要失配](否证-r3-1-证据/输出反例-摘要失配.json)、[合并反例](否证-r3-1-证据/输出反例-制造格及摘要.json)。真实重算该刻仓库源矿量为 79997；原闭包后 input 格为空，不能与 999 件混同。

**尝试的反驳不成立。** schema 的 Quantity 只核字符串、数字类别等结构，没有单位槽位容量或 summary 的跨字段约束；记录仍能通过类型检查。输入经过容量检查或另一次 run 产生合法状态，也不能证明磁盘 output 的状态正确。代码 L131–153 的断链与 L2-01 同源，但本条的容量域、变体和不一致摘要已分别核验，不以重复发现为由省略或标 true。该结论是验收缺口，不指控原始记录本来已有 999 件。

### 2.9 K3-r3-L3-04：参数投影来源哈希失配
