```bash
python -B 求解器/规格/复核/内核输入/复核-r3-可导出性-证据/复核检查.py
```

完整结果见[复核结果.json](复核-r3-可导出性-证据/复核结果.json)。检查分为三种，证据能力不同：

1. 独立几何核算没有调用被审 `geometry` 函数，直接由目录尺寸、端口、旋转和正式通道条件重新导出占格及全部 PC。
2. 被审有限参考执行器在冻结输入上重跑，完整 `trace.ticks` 与原记录逐字段相等；这是复现一致性。另按手算期望独立核对成功事件、全部非空库存、仓库数量、制造进度、物料账和端口额度，这是针对这段前缀的独立核查，并非第二套一般内核。

## 五、发现

### K3-r3-L2-01：输出回归未验证被交付记录的语义关联

- **where**：`求解器/数据/样例/test_runtime_input.py:131–153`；`求解器/规格/内核输出.md:16–20、27–37`。
- **claim**：输出回归验证的是另行重算的摘要，而未将被读取记录的参数、完整状态和事件与输入及重算关联，错误运行记录仍可报告通过。
- **severity**：重要。
- **evidence**：规则 L59：“运输单位：一个物品格（上限1），桥接器例外”；规则 L23：“物品在运输单位的物品格中必须停留至少 1 tick”；规则 L25 要求逐个判定。第三轮 §3.C 要求输出保存“逐字段赋值……实际轨迹、验证范围”。内核输出 L27 要求“校验器必须核两者一致”，L37 要求分别验证输入关联及事件守卫/后效/时序。

代码 L131–134 只比较 `actual` 的摘要与黄金；L135 另读 `output`，随后只检查 schema、所列指纹、三项结构负例和若干输入配置值。没有比较 `output.trace.ticks` 与 `actual`，没有核 `output.parameter_assignment == data.parameters`，也没有重建输出 summary 与 state 的关系。

三个独立反例均使 17 项回归继续通过：

| 输出单点修改 | 应拒绝的理由 | 实测 |
|---|---|---|
| tick 0 的 feed_belt:transport:0 数量从 1 改成 2 | 直接违反运输容量 1，同时与 summary、一次出库账不符 | 通过 |
| 记录 `time.domain.value` 改成 `invented_domain` | 记录参数与真实输入、完整状态中的当前参数不相同，也不是本版选值 | 通过 |
| tick 3 的 events 改成空数组 | 库存变化和 tick_context 的成功事件引用没有对应实际事件 | 通过 |

反例、实际回归报告和日志在[反例目录](复核-r3-可导出性-证据/反例/)及[日志目录](复核-r3-可导出性-证据/日志/)。这不证明原轨迹错误：原轨迹已在本次逐字段重算相等。缺陷是回归入口会给错误证据盖“通过”结果，后续无法把该结果当作交付记录的语义验收。

修订方向：在支持的确定性有限子集内比较记录的完整轨迹、初态、参数、历史和验证区间与真实重算；同时核 summary/state、event 引用、端口预算及状态约束。未实现的关联检查须在验证结果中单列，不能用 schema 通过代替。

### K3-r3-L2-02：实际未触发轴与已触发选值没有分开记账

- **where**：`求解器/数据/样例/check_golden_trace.py:172–179`；`求解器/规格/内核输出.md:18–20`；`求解器/规格/内核输出.schema.json:130–155、192–228`。
- **claim**：运行记录的未覆盖清单仅复制配置的通用覆盖损失，没有登记该次轨迹中未触发的机制，无法直接区分填了值与实际验证了该值。
- **severity**：重要。
- **evidence**：第三轮 §3.C 要求运行记录包含“未覆盖轴、实际轨迹、验证范围”；本次复核要求回答“哪一格组合被证过、哪一格只是没跑到”。求解约束 L3 的量词是“目标须对其每种取值都达成”。内核输出 L18 明确要求“未覆盖该轴其它值、未触发、超出覆盖即停和待证明须分别写明”。

`uncovered_axes` 是遍历参数投影文件、排除“已定”后直接复制 `{axis,coverage_loss,disposition}`，没有读取轨迹的机制调用或结构前件。实际 84 行中，下面几项都标为“本版选值”：

| 轴 | 本次真实情况 | 记录 reason |
|---|---|---|
| time.domain | 0、1、2、3 整数时刻实际执行 | 非整数相位、建造/暂停时距 |
| transfer.cooldown_scope | 没有箱体，未触发任何传输或冷却 | 按格异相冷却 |
| polling.level_tie | 每侧至多一级，未触发级间平局仲裁 | 并列级联合轮询及其他仲裁 |
| damping.belt_component_rule | 有带路，但有限执行代码没有阻尼求值或多级取货比较 | geometric_components |

后三项的 reason 只说另一种读法未覆盖，没有说连所填本版值也没有在本次事件中接受相应验证。`validation_scope` 只有全局有限区间、黄金比对与非全称布尔标记，也未补这一层区分。字段能容纳中文 reason，故问题并非必须换数据结构才能解决，而是生成器没有按文档填出本次运行覆盖事实。

完整轨迹使人可以回查部分未触发原因，但这不能替代接口已经要求的显式未触发记录，也不能把 96 项填写自动提升为 96 项语义验证。修订方向是保留全赋值，同时逐项标注本次 exercised/not_exercised/unsupported/proof_pending 等等价状态，附相关事件或结构依据，并明确“整组赋值下的一段有限轨迹已核”所涵盖的性质。

### K3-r3-L2-03：覆盖清单的来源投影与实现依赖未被指纹封闭

- **where**：`求解器/数据/样例/check_golden_trace.py:7–8、172–177`；`求解器/数据/样例/kernel_profile_v1参数赋值.json:4–6`；`求解器/规格/内核输出.md:15`。
- **claim**：运行记录未校验或指纹绑定实际读取的参数投影及检查器依赖，使旧 profile 投影可以混入标注新规格指纹的已通过结果。
- **severity**：重要。
- **evidence**：第三轮 §3.C 要求保存逐字段赋值、目录与正式源指纹、未覆盖轴和验证范围。第二轮 §2 将受限声明定义为“第一版内核实现哪一组读法”，不能把不同声明混为一组。内核输出 L15 明确规定“指纹不匹配需重新核验，不允许刷新后沿用旧结论”。

`check_golden_trace.py` 实际读取 `kernel_profile_v1参数赋值.json` 来构造未覆盖清单，并导入 `check_examples.py` 承担输入、目录、几何和数值检查；但 fingerprints 不含这两个文件。更直接地，参数投影中的 `profile_source.sha256` 仍为：

```text

```
