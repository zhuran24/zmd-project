# 内核运行记录

日期：2026-09-19。状态：`kernel-output-v1` 有限轨迹 schema；具备可验证的参考输出，不包含全部可达循环证书格式。机器可读定义见[内核输出.schema.json](内核输出.schema.json)，本节规定其语义关联。来源为运行语义 §2–6、受限模型声明的记录义务、内核输入 v3；不新增游戏机制。

## 1. 顶层契约

所有字段必填，明确标为可空的字段也不可省略，未知键拒收。装载前失败而无法形成合法参数、历史、种子或验证范围时，parameter_assignment/input_history/trace/validation_scope可为null，并在open_items给停止位置；completed时这四项均必须非空，不能伪造未发生的状态。物理数字沿用 Quantity，时刻沿用有理 Time；schema 第一版只接有理轨迹，非有理事件输入输出为 unsupported，不用浮点近似替代。Decision 的 value 形状由轴/状态所属接口继续校验，单靠 JSON Schema 不证明它可执行。

| 字段 | 类型与语义 |
|---|---|
| schema、run_id | kernel-output-v1、唯一运行标识。 |
| profile_id | 必须等于输入与 parameter_assignment.profile_id，例如 kernel_profile_v1；不能仅凭此名字认定相同解释，仍核源指纹及逐字段值。 |
| producer | `{kind,path,claim}`；kind=kernel、bounded_reference_checker 或 manual_expected，明确产物由内核、有限重算还是手算产生。工具路径也入指纹。手算期望不能标成实际内核输出。 |
| status | completed（所请求有限前缀完成）、invalid_input、unsupported（实现不支持）、unresolved（规格或输入义务未解）、inconclusive（资源不足）。任何状态都不自动表示达标或全题无解。 |
| fingerprints[] | `{role,path,sha256}`；至少含 input、catalog、axis_registry、profile、三份 formal_source、实现 checker/kernel 对应 checker 角色，以及本记录使用的 semantics、schema；若比较黄金结果，另有 golden。哈希针对原始字节，path 绝对路径或相对记录文件；指纹不匹配需重新核验，不允许刷新后沿用旧结论。 |
| parameter_assignment | 原样保存完整 Parameters 的三个生命周期对象和轴表引用；字段集合严格等于被锁定轴表，禁止漏轴、重复轴或悄悄默认。输入历史产生的当前值也存入每个 StateSeed.semantic_context。 |
| input_history | `{timeline,construction,debug_operations,environment,reachability}`，完整保留输入的事件、关系、接通、建成、调试、离线、补矿、拿取历史/策略及初態可达性证据；结构分别按内核输入 §3、§6 校验，不以文件名代替内容。 |
| uncovered_axes[] | `{axis,reason,disposition}`。未覆盖该轴其它值、未触发、超出覆盖即停和待证明须分别写明；即使本轨迹未使用的轴也不从逐字段赋值中删除。空数组须有全覆盖证据，本有限 schema 不支持据此声称全称认证。 |
| trace | `{start_state,ticks,end_time,format}`，format=full_state_each_instant，每时刻记录完整状态。时间推进、同刻顺序及中止点均不得跳步冒充已运行。 |
| validation_scope | 有限区间 from/through、golden_match、conditional_witness 起点、已完成批次数；universal_parameters/all_reachable_cycles/target_certified 必须 false。后续认证需要新版本证据结构，不能将这些位自行改 true。 |
| open_items[] | 未完成义务、超范围和解释冲突；若 status 非 completed，必须注明首个停止事件与原因，允许只保留合法前缀。 |

原 91 轴全有值是本轮历史验收要求。当前共享表新增 5 轴后为 96 项，本例 96 项全填；该数字不是 schema 常量，字段集合由指纹锁定的轴表定义。据：第三轮任务书 §3.C、运行语义 §3；记录接口为工程编码。

## 2. 逐事件、逐时刻内容

`ticks[]={time,events,state,summary,closure}`；time 严格递增，state 为该时刻闭包后的完整 StateSeed，首项起于 start_state.environment.time。summary 只是可读投影，以完整状态为准，校验器必须核两者一致。每个 state 的参数、物品格、在制、轮询记忆、待事件、端口额度都保存，不用状态哈希代替内容。据：运行语义 §2；内核输入 §6。

`events[]={event,operation,target,outcome,detail?,basis}`。operation 分 move/internal_move/manufacture/transfer、非判定制造完成、时间推进、补矿、离线、玩家动作；判定与非判定不能互相冒名。event 是实际实例 id；判定扫描机会由 EventOrder 规则生成，no_request 只是未获授权的扫描观测，不是已经发生的判定，不能以观测数统计规则判定数。失败须记录原因和真实权限后效，成功有库存增减；具体成功物流和端口计量保存在 state.semantic_context.tick_context，同步核对 event 引用。据：规则 L18、L23–25、L29、L35–36；约束端口速率。

closure 给出压缩依据及扫描轮数。全状态重复指会影响后继的物理及调度状态相等；单调增长的诊断事件序号不得混入闭包判等。资源上限不能充当闭包证明；无法核验归约时返回 inconclusive/unresolved，不推进时间。zero-time 的失败循环也须保留被压缩前后相同的轮询状态。据：受限模型声明 time.instant_end、运行语义 §4。

`pending_events` 可有 manufacture_complete，表示工作量到期的非判定事件；输出事件登记表同时为这些运行时 id 提供统一引用域，恢复时并入原 timeline。输入不能事先穷举无限新事件，因此 EventOrder 与完成事件生成式提供运行中扩展注册；每个新实例 id 唯一且不重用。边界未完成的活动事件保留 waiting/ready，不会被“未列即空”抹去。

## 3. 验证与结果解释

必须分开验证：JSON Schema 的字段/类型；输入格式的引用、生命周期、值域和 StateSeed 完整性；事件的守卫、后效与时序；黄金期望比对。前三者某项未实现时须列出，不能仅凭 schema 通过说轨迹合法。哈希锁定来源不等于证明来源结论。

参考产物是[混做粉碎机两下游运行记录](../数据/样例/混做粉碎机两下游-运行记录.json)，producer 为 bounded_reference_checker。它由[独立有限重算](../数据/样例/check_golden_trace.py)读入运行样例生成，并与单独手填的[黄金摘要](../数据/样例/混做粉碎机两下游-黄金轨迹.json)比较。Rust 内核尚未在本轮实现；这个记录验证输入、手算和有限参考执行的接口，不改变 L=0，也不证明任何完整目标或“混做已达标”。

复现：在仓库根运行 `python -B 求解器/数据/样例/check_golden_trace.py`，再运行 `python -B 求解器/数据/样例/test_runtime_input.py`。报告只写在求解器内。完整机械结果与来源一致性见[本轮自查](内核输入修订验证-r3/自查报告.md)。
