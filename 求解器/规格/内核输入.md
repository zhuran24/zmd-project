### 1.1 数值、未知与证据

物理数值用 `Quantity={value:字符串,category:字符串}`，整数或有理数 `n/d`，分母为正，禁用浮点；类别沿用送料契约的条文直引、算术推论、候选、启发式、实测。位置、库存、限额和时长均适用。样例坐标是候选，派生占格和计数是以候选为前提的算术推论；工具通过数是实测，不是游戏运行实测。schema、索引、旋转码、id、哈希及事件序号是表示编码，不是物理数值。依据：送料契约“数值与空值约定”；规则 L4–5、配方、单位尺寸。

`Decision={status,value,basis}`：`status` 包括 `unresolved`（value=null）、`specified`（具体表示）、`derived`（依赖表达式）、`not_applicable`（value=null，basis 须说明结构前件）。basis 为非空依据字符串数组。未定与不适用不同；specified 也只表示填写，不表示已审合法。涉及机制的 specified 另须由执行器识别其语义版本并查验全规则依据；不能把任意字符串当可执行函数。据：任务书纪律、运行语义 §3、四件前置义务对照。

本版 JSON 的有限数组不宣称真实状态空间有限。时间使用 `Time={kind,value}`：`rational` 的 value 为 Quantity；`symbol` 的 value 为符号 id，符号的含义由带依据的时间关系定义；未完成解释时拒绝运行。任意非有理相位可先作为符号约束保存，当前检查器不求解该约束。这避免把时间偷偷限定为整数或有理格点。依据：规则 L23–25、L35–36；任务操作精度；运行语义 §3、T1/T6。

## 2. 布局、端口与三种边

`layout={base,id,anchor,units,physical_channels,buffer_channels,snapshots,post_debug}`。主对象是一个命名快照，不是无阶段的最终布局。`id` 为快照 id；`anchor={event,side}` 指 §3 全局事件及 `before/after` 的事件前/后状态。主快照和 snapshots 的 id 互异。`snapshots[]` 每项为 `{id,anchor,units,physical_channels,buffer_channels}`，共用 base；units 只列当时已建成且未拆除的单位，未出现的单位不占格、不供电、不成边。建造中未有核心的快照允许核心数为零，完整蓝图/最终快照必须恰一核心。据：蓝图、重建、通道、协议核心。

`construction.moments[].placement` 另存每个实例首次建成时的几何（§3），不从主快照倒推历史。旋转/重建操作引用前后快照。每个快照均须按本节重算占格、端口相遇、全部可能 PC、供电；相邻快照间的差异须由事件和合法后效解释，不能把快照当任意改几何的授权。`post_debug` 是 Decision：specified.value 为调试结束事件后的快照 id；derived.value 为 `{from_snapshot,through_event}`，要求逐事件推演到 debug_end；unresolved 表示终态未给。实际几何因不精确历史而有多个结果时，每个具体历史分别携快照，历史族由参数/策略量化，不可只检查其中一个。最大空矩形及达标几何验收只用这些调试终态，不能拿主快照替代。据：旋转、重建、任务目标、调试期、操作精度。

桥接器静态样例主快照锚在 `blueprint_complete` 后，post_debug 未解。运行样例给具体历史、同一几何的 debug_end 后快照及完整状态；首次 placement 不被运行状态覆盖。

### 2.1 占格及端口公式

目录规范宽高 `(w,h)`，局部格 `(u,v)` 的逆时针旋转：r0 为 `(u,v)`，r90 为 `(h−1−v,u)`，r180 为 `(w−1−u,h−1−v)`，r270 为 `(v,w−1−u)`，然后加 origin。旋转后宽高在 r90/r270 互换。单位占格是全部局部整数格的像，须在基地内（据：规则 L8）。旋转公式为方格算术（据：规则 L11）；完整蓝图与最终快照恰有一个核心（据：规则 L41）。任意两实例占格互不相交是达标布局的必要条件：允许重叠与不允许重叠两读法中，后者更严格，目标须对每种取值达成，故必须能在后者下建造。本格式的合成测试亦采用此必要条件作为测试子集，不宣称条文单独禁止一切重叠解释。据：约束“不得依赖的量”总则；第三轮任务书 §2.1 的最严读法推理。此推理只用于单调的合法性条件，不适用于分流比例、轮询或级序平局。

端口规范格：south 的 position p 在 `(p,0)`，north 在 `(p,h−1)`，west 在 `(0,p)`，east 在 `(w−1,p)`。格及向外法向一起旋转。桥接器的四个物理端口位置从目录全部 layouts 的位置并集取得，未定方向不删除端口；pending/unresolved 端口角色为空。稳定端口 id 为 `<unit>:<canonical_side>:<position>`，用规范边命名，旋转后 id 不改；position 是目录索引编码。布局不另输入世界端口坐标、端口数量或角色覆盖；据：规则 L12、单位端口条文、目录 conventions。

仓库取货口规范 south 长边在边界、north 朝内，因此 r0 时 origin.y=0；r270 时 origin.x=0；其余朝向不符合任务的左/下边界。此方向结论从长边贴边、取货朝内与旋转换码导出。达标任务所需左/下各 23 个属于约束“取货口配置”；不对合成小布局强加 46 个。格式能逐个表示全部 46 个并逐口指派，不以来源变量替代实际单位。依据：规则 L73；任务 L16；约束出库上限、取货口配置。

供电桩也是 units 中的实例。需电状态必须由桩中心、目录覆盖尺寸与 `power.cell_rule` 参数导出，不接受任意 `powered=true`。达标供电义务统一按 positive_area 计算；closed_touch 多覆盖的机器不抵该义务。运行守卫仍按所选 power.cell_rule 计算并另记，不能混淆。理由是 positive_area 的供电集合包含于 closed_touch，而目标须覆盖较严条件（第三轮任务书 §2.1；约束不得依赖的量）。覆盖边界未定时输出待定；不把“无计算结果”当停电，也不把肉眼靠近当认证。依据：规则 L19–20、L76；完整性批评 §1.4。

### 2.2 实体通道 PC

按T5已定规则表示相遇：两端端口占用相邻格、法向相反并面对同一条格边，一端output、另一端input，且至少一端family为transport，导出PC。`connection.port_meeting=shared_edge_opposite`归fixed/F；仅角点接触不成通道（主会话三审 §6 owner 09-21裁定；规则L12、L16）。几何相遇给可能边，建成与准入口当前阻断状态决定实际可用边；其它端口相遇值按已定轴冲突拒收。

记录为 `{id,source_port,target_port}`。本版 id 的确定编码是 `PC|<source_port>|<target_port>`。`connection_time` 不手填进 PC，由建成事件较晚者导出。没有运输端的制造机直接贴边不生成通道；无线传输也不是 PC。PC 的两个端口身份唯一决定该有向几何边；重建/恢复可以复用 PC id，但每次接通的事件实例另存于 timeline.connection_events（§3.2）。物理面对面关系可用稳定无向 `contact={ports:[p,q]}` 表示（两端按字符串排序，只作身份规范化，不定事件顺序）；任一轴状态为 unresolved，或 pending 且有面对面端口时，physical_channels 必须 null，由完整方向赋值族再导出，不能把未知边当不存在。pending 且轴两端均无面对面端口时可确知该轴没有 PC，其它已定轴照常导出；pending 却已有面对面端口则须核先接机制，不能静态判无边。据：通道、接通、重建、传输。

### 2.3 内部通道 BC 与槽位身份

槽位引用为 `<unit>:<role>:<index>`；role 取目录 inventory.role，index 为零起点编码；储存箱显示编号等于 index+1。核心仓库槽位由 §6 initial_state.warehouse.slots 的 slot 命名，新增运行槽位在 StateSeed.warehouse 中声明，数量不设有限上限。仓库标签须为非空字符串、在仓库表内唯一，并避开单位槽位保留语法 `[A-Za-z][A-Za-z0-9_]*:[a-z_]+:[0-9]+`，同时不得与任何 inventory 格同名；缓存格也属于该保留域。该义务适用于任务初值、每个 StateSeed、运行中新格及输出状态，先校验再建寻址字典。物品格标签是工程身份，可一致更名而不改变库存、指派或游戏行为；仓库只属于核心，制造 input→buffer 不得扣仓库（规则 L14、L17–18）。桥接器的 vertical/horizontal 是规范轴，随实例旋转，仍为两个独立格。内部 BC 只连制造 input→buffer 与 buffer→output；记录 `{id,source_slot,target_slot}`，id 为 `BC|<source_slot>|<target_slot>`，按目录格数逐条导出。据：规则 L13、L17–18、L63、L72。

BC 没有外部端口，不计 S/R/E，不套每端口每 tick 单件上限。大机每个输入格到缓存分别有结构引用，开闸谓词可联合读多个格；不能因存成两条边就认定闸门独立。`judgment.buffer_event_class` 和 `cascade.buffer` 另管判定及级联。桥接器内部沿各自同轴格通行，禁止在路径中跨轴；两格独立不等于轮询按轴独立。据：缓存格、轮询、存货优先级、桥接器；T2/T7/T14。

## 3. 统一时间线、建造与接通历史

### 3.1 事件及时间关系

`timeline={events,relations,connection_events}`。`events[]` 为 `{id,kind,time}`，id 是全输入唯一的非空字符串；kind 包括 build/debug_operation/offline/blueprint_complete/debug_end/unit_removed/unit_rebuilt/connection_open/connection_close/withdraw_product/runtime。`time` 为 §1.1 的 Time 或 null（当前未定位）。建成、调试、离线、拿取及后效子事件都从此集合引用；各对象的 event 字段没有自己的 id 命名空间。每项必须由相应记录拥有，阶段边界由 construction 或 environment 引用，runtime 由 StateSeed 的日程/移动记录引用。引用同一事件是共用同一实例，不能复制成另一个事件。重复策略的具体发生每次分配新 id。整数参考实现将 `I|`、`J|`、`C|`、`W|`分别保留给身份维护、运行扫描、制造完成、窗口到期；非 runtime 历史事件不得使用这四个前缀，装载时即拒绝。runtime 历史中的已登记实例可以被恢复日程引用，但不能被新生成实例复用；生成器以整个输入 timeline 为初始注册表，每次新建扫描或完成日程都先查冲突，完成日程在开工时分配 id，到期仅消费一次。此为编码约束，可一致更名，不限制合法建造先后。据：蓝图、判定、重建、调试期、离线、操作精度。

`relations[]` 为 `{before,after,relation,basis}`，两端均引全局事件；relation 包括 strict（真实时刻小于）、same_time（真实时刻相等，未定先后）、occurs_before（执行发生在前，时刻不大于）。同刻可用 same_time 加 occurs_before 表示交织；不允许严格先后自环、顺序环，或等时类内的 strict。所有来源的偏序、when.after/before、蓝图序、动作数组序及原因/后效关系取交集，冲突拒收；未比较的两项仍未定，不按 JSON 数组/id 排序。允许冗余的传递关系，不要求只写相邻链。据：判定、接通、操作精度。

玩家操作记录的真实 Time 是历史见证，不是可指定的执行时刻；策略只给不精确触发条件和次序，须覆盖允许的全部实际时刻。精确回放一条历史不证明玩家能强制实现它。`when={after,before,condition,timing}` 中 after/before 为全局事件 id 数组（空数组表示未限制），映成 occurs_before；condition 为 Decision，specified 值的谓词编码见 §6.2，timing 必须 imprecise。可以直接写“某次离线 → 某次改准入”或反向先后，也可把操作插在两个 build 之间；阶段授权另由 initialization.debug_actions/offline.events 审查。据：任务调试期、操作精度、离线。

`construction={mode,order_domain,selected_order,moments,complete_event}`，mode=blueprint_once，order_domain=all_rule_consistent_orders。selected_order 为 null 或全部首次建成实例各一次的见证数组，非传送带在传送带之前；不是玩家可指定的蓝图次序。`moments[]={event,unit,placement}`：event 指 build，unit 为稳定实例 id，placement 为 `{kind,origin,rotation,port_layout,occupied_cells}`，与 §2 换码一致；桥的 port_layout=null，先接方向由历史导出。每实例首次建成只出现一次，重建用下节字段。complete_event 指 blueprint_complete，须在全部首次建成之后，允许与最后一次建成同刻；已建子图在建造期间继续运行。selected_order=null 时由 relations 保存部分关系，不能默认 moments 的数组顺序。据：蓝图、接通、建造方式、移动。

### 3.2 接通事件、结构变化与桥方向

`timeline.connection_events[]={event,channel,action,cause,geometry_snapshot,construction_basis}`。event 指 connection_open/connection_close；原因事件先于其后效发生（occurs_before），首次/重建 open 还与较晚建成事件 same_time。action 为 open/close，与 kind 一致；channel 为 PC id，geometry_snapshot 指该边可重算的快照（close 用事件前几何，open 用事件后几何）；可引用其它时刻同几何的快照，但必须另由 placement/结构历史证明事件时两端存在且其几何相同，不能仅凭未来快照倒推，cause 指引起变化的全局事件。construction_basis 是 Decision；首次建成/重建开边时 specified.value=`{source_build,target_build,later_build}`，两端分别引用最近仍有效的 build/unit_rebuilt，later_build 必须是较晚一端，接通时间与其相同。一般恢复/旋转时该关系按 gate.reconnect_record/T11 接续轴审查，未审不能伪造新建成时刻。相同 PC 的再次 open 必须有新的 event；先 close 后 open 才是新通道生命段，不可覆盖旧记录。据：规则 L10、L16、L28–32、L64。

`rotate` 的 payload=`{before_snapshot,after_snapshot}`；新 origin、rotation 及完整相遇表均从后快照读取，前后差异须限于目标旋转及派生量，port_layout 必须相同，rotate自身的坐标变化由旋转定义核验；调试搬运或拆建另记相应动作及快照。`rebuild` 的 payload=`{remove_event,build_event,before_snapshot,removed_snapshot,after_snapshot}`，子事件分别指 unit_removed/unit_rebuilt，同一设计 unit 可反复重建，每次 id 都不同，拆除快照中目标缺席。操作开始、拆除、再建成按 occurs_before 关联，拆除到再建成的时间差不取默认；每次全部受影响 PC 的 close/open 均进入上述记录。传送带重建允许后快照选择另一 port_layout；首次建成也必须明确选择。12 个有序边对的相对转角分三类，每类四朝向；旋转保持相对转角，不能跨类（据：规则 L60、L11；算术推论）。调试经拆后再造选择另一形状的路径据规则 L10、任务 L12，零干预后禁止玩家改变据任务 L8；缺库存后效时工具停止回放；明确清理后再拆建的程序仍在调试权限内。两次建成之间固定属于本版生命周期选择，其它调试操作的后效待实现；[旧修改请求](内核输入-对参数轴的修改请求.md)保留为史料。库存去向、桥定向、轮询及准入后效引用相关轴，未解决时仅可保存约束，不能执行。据：重建、旋转、物品格、轮询、操作精度。

桥方向的验证必须注明采用的 `connection.bridge_first_contact`：物理邻接先接读法看最早面对面端口；有向通道形成先接读法还须给定向与成边的历史一致性证据，不能以联立有解代替可执行历史。两轴独立存状态，未接一轴保留 pending，未知一轴保留 unresolved。最小检查器仅在两种已登记读法的唯一非桥先接见证一致时给条件结构通过；若读法分歧、同刻平局或桥互依赖，报 unsupported，不把物理邻接读法强加给 unresolved 轴，也不声称覆盖未来未登记读法。据：桥接器、通道、接通；T5。

### 3.3 离线及接续

一次纯接通重排是零耗时环境关系，前后保持几何、设定、供电、已建桥定向、库存物种/数量/年龄、批次及剩余时长、箱冷却、准入口累计和当前窗、固定判定规则。正时长离线段另记物料与计时事件，按规则L20、L23、L35—36、L64推进。依据任务L14及任务6 PA-08。

重排后按规则L29、L31—32更新环序、级内最早接通、级排序和最高可移动级；保存指针的通道身份。精确可达排列族、并列关联和指针接续关系仍须提交证明（PC-04）；工具未实现时返回unsupported。扩大到全部候选指针成员的探索须声明充分方向，低产路径另核真实可达性。

## 4. 设定与仓库引用

`settings={anchor,switches,gates,warehouse_assignments}`。anchor 是全局事件前/后锚点，设定只在该快照时成立，其它时刻由合法操作推演；不冻结运行库存。

| 字段 | 类型与约束；依据 |
|---|---|
| `switches[]` | `{unit,function,enabled}`；function 必须在目录 powered_functions；enabled 是布尔或 Decision，每个需电功能恰有一条。制造与箱体 transfer 分开；无电仍可设开关，但不保证功能运行。据：规则 L19–22、L35–36 |
| `gates[]` | 每个物品准入口恰一条 `{unit,item,total_limit,window_limit}`；item 为物品名或 null（未设），限额为 Quantity 或 null（未设）；item 未设时不能预设限额；累计 1…5000、窗口 1…5，均整数条文直引界限。任务L12允许调试取消限制，具体动作后的计数/窗口状态须保存；当前回放支持范围见§6.1。据：规则 L64；T9 |
| `warehouse_assignments[]` | `{port,slot}`；核心全部六个取货端口及实际建成的每个仓库取货口都恰指一个 §6 声明的仓库 slot，多个端口允许共指同格；不能由此复制库存。指向 item=null 的格时，该格 empty_identity 必须为 specified（历史物种或 null）或可求值的 derived；unresolved/not_applicable 均拒收。此规则同时适用于初始指派、调试改指派和状态恢复；空格没有物品可取，历史身份不生成物品。据：规则 L13–14、L41、L73；第三轮任务书 §2.3 |

核心六口的契约序号以目录规范 output 端口的展平顺序从 1 编码，随旋转保持 id。左/下仓库口按距左下角由近到远从 1 编码；完整达标布局为每边 23 个。身份序号与具体物品格指派分离：source 变量绑定端口，端口设定才决定从哪格取货。未填指派不能默认为源矿。依据：送料契约“来源身份”；规则核心、仓库取货口；约束取货口配置。

配方不是设定字段。全部合法配方从目录按 kind 查询；scenario.recipe_intents 仅为测试覆盖意图，不能用它禁止同机匹配其他配方、要求逐批交替或强行把某物品分配到出口。结构测试中的 switch=true 是该锚点的候选设定，不表示规则规定开机初值。依据：规则 L18、L22、配方；T7/T11。

## 5. 参数向量及生命周期

`parameters={axis_registry,profile_id,fixed,offline_mutable,fixedness_unproven}`。axis_registry 为 `{path,sha256}`，path 相对输入文件，必须引用正式轴表；profile_id 是 null 或受限模型 id，null 表示没有选执行配置。其余三项为字段名到 Decision 的对象。轴名中的点是 JSON 键的一部分，去掉生命周期外壳、按点拆分即可无损还原运行语义 §3 的 time/judgment 等分组，不另造语义别名。依据：运行语义 §3；选择点参数轴 §1–2；工程序列化约定。

### 5.2 判定排序规则 EventOrder

`judgment.order_scope=fixed_run_order`、`judgment.order`均为F。事件身份、比较序和重复实例嵌入整场固定，含各时刻、失败重试和离线接续；依据任务L15、约束L10。`event-order-v1`的封闭对象为`{schema,scope,template_order,repeat_embedding,instant_overrides}`，其中scope=global、instant_overrides=[]；template_order恰覆盖全部几何可能PC的move、制造单位manufacture及箱transfer。BC按所选事件归类保留内部动作，完成事件仍为非判定事件（规则L18、L25、L35）。

`repeat_embedding=scan_round_then_template`使用固定模板序，实例按(instant,round,template_index)登记。新启用模板已越过时须在后续轮重新尝试；源货、目标空位、门原因或级变化都重新激活相关候选。该表示是工程日程，完整失败环到未来唤醒的出口按受限转移§5另证。

旧event-order-v2/v3的per_instant时间函数改序编码保留在历史记录中。当前游戏证书准入拒绝改变相对判定序的时间函数；扩大探索所得坏路径须还原同一固定规则，才可作真实反例。其它固定排序表示需新版本和重复实例保持证明。

运行上下文 `judgment_context` 的基础字段为 `{instant,phase,order_scope,round,next_template,ordered_events,next_event}`。phase 包括 before_boundary、in_boundary、in_closure、after_closure。round、next_template 是非负编码整数；ordered_events 是本轮已执行模板前缀，next_event 是下一已实例化机会的 id 或 null。整数 profile 的 id 为 `J|t|轮|索引`，标识位置，不替代所选排序。next_template 可等于模板数，表示末模板已执行但本轮闭包检验尚未执行；不能据此直接推进时间。非整数实现须使用可逆规范时刻标签，当前参考执行不支持。

before_boundary 表示本刻边界尚未执行；after_closure 表示边界及闭包均已完成。这两者无 continuation 字段。in_boundary 和 in_closure 则**必须**带 continuation，恢复位置由 phase、轮号、游标与下列记忆联合决定，不能通过清空端口账来模拟新时刻：

| 阶段 | continuation 编码和恢复语义 |
|---|---|
| in_boundary | `{schema:boundary-continuation-v1,queue,next_boundary,processed_events}`。queue 为本次边界全部已定序的 `{event,operation,target}` 记录（window_maintenance 对同刻多门是一笔不可分批事务，其内部不是恢复点），operation 包括 time_advance/manufacture_complete/ore_supply/window_maintenance；next_boundary 是待执行下标（允许等于队列长度），processed_events 恰为前缀 id。时钟/工作量推进也在队列中且只办一次；已处理后效必须体现在 StateSeed，未处理到期事件保留 pending_events。边界队列耗尽才进入扫描轮0。未解释的边界顺序不能伪造队列。 |
| in_closure | `{schema:closure-continuation-v1,boundary_done,boundary_events,seen_boundaries,round_changed,instant_events,completed_batches}`。boundary_done 在本整数配置恰为 manufacture_completions/external_history/window_maintenance 三阶段；boundary_events 列已经办完的非判定事件，禁止再次办理。instant_events 保存本刻至断点的全部真实事件/扫描观测；ordered_events 必须等于其中当前轮的 J 前缀，next_event 与 next_template 对齐。completed_batches 为审计累计数，不作物理守卫。 |

in_closure 的 seen_boundaries 保存本次闭包无物理变化段已见的完整调度投影，不只存哈希。当前无箱、无准入口、无仓库入库/身份改变、无外部切换的参考子集投影为 `[inventory,progress,poll_memory,port_usage_map]`，port_usage_map 为端口到已用整数件数；该子集E/O全程不变且在完整StateSeed中保留，故未重复纳入这个有前件的子集投影；每项都是实际整轮边界，不能由当前中途库存倒造。round_changed 标记本轮此前是否已有物理改变；轮末据它决定清除旧 seen 段后再判重复。分流器含箱体和门控的参考执行只支持整刻记录，直接拒绝其in_closure导出/续跑；它的实时闭包键另含warehouse、完整logistics及arbitration。若扩到仓库入库/身份改变、箱体、准入口或外部事件的中途续跑，必须按受限转移定义 §5.1 扩投影并增 continuation 版本；不能将本子集投影冒称全部机制的闭包记忆。

pending_events 保存尚未处理的完成事件等，tick_context 保存当前窗口全部成功移动、端口额度及内部穿越；三处事件 id 同域，边界已办事件不得又在 pending 中 ready，成功件数必须与物品格及端口账一致。in_boundary/in_closure 只允许原子事件之间的切点，不插入同一判定内部。调试结束在这种实际切点不代表玩家可以精确保证该结束位置。据：规则 L18、L25、L35；任务 L8、L12—13；约束端口速率。

[中途种子.json](内核输入修订验证-r4/中途种子.json)保存实际 `J|2|0|1` 后状态：第一批已完成、第二件矿已入 input、制造模板11未运行，round=0、next_template=2。表示回归执行 JSON 往返并逐字段对照该断点的完整重算，拒绝丢失边界/闭包记忆或清零端口账。第四轮Python参考入口当时只接受before_boundary全空种子，作为史料保留。当前Rust接受已完整校验的before_boundary条件种子及after_closure恢复状态，可含非空库存、正常intake/working/completed、箱冷却和门窗；in_boundary/in_closure直接续跑仍为unsupported，程序全部可达后态的认证另证。能保存/校验与已经实现通用恢复是两项不同结论。

### 5.3 阻尼分支 DampingBranch

`damping.branch` 的 specified.value=`{schema,fixedness,choices,evaluations,on_missing}`，schema=`damping-branch-v2`，fixedness=`by_available_set`，evaluations=[]，on_missing=`unresolved`。choices[] 恰为 `{fork_unit,available_channels,outgoing_channel}`。fork_unit 必须是分流器；available_channels 是其几何可能出支的一个非空子集，按PC id排序作集合编码；所选outgoing_channel必须属于该集合。键(fork_unit,available_channels)唯一；本版要求对每个可能被阻尼查询触达的分流器列全体非空子集（含单成员集），不会因运行中断边才临时补策略。不能把缺表项当随机选择或默取首支。（据：规则L27阻尼、L64准入口；表为工程受限读法）

求值时只以**现存图的出边**构造可用集合，不以货物、端口额度、physical或对端授权筛边；图变更事务提交后按新集合重查，同一集合重现必同选。空集合无可选支，沿途无下一非运输终点仍`unresolved(damping.no_terminal)`；选中有向环也不虚构终点。完整表可包含当前失活子集的行，装载不因那一行的边当前断开拒收。每次查询只数所选支，不相加。（据：规则L16、L27、L31、L64；受限转移§3.1、§3.4）

整段锁定出支是v2的部分子族：包含固定支的集合都选该支；不含固定支的集合必须由输入补全其它选择，不能自动补。v1的`(channel,fork_unit)`表若同一fork在不同查询起点选不同支，不能直接迁为该子族，应报告未覆盖；否则先核一致再显式扩表。采用主席建议的局部表未与L27“只数其中一条”或约束·分叉分支冲突，但**只覆盖出支集合可观察的局部确定性无记忆策略**。它未覆盖依赖查询起点、图的其它部分或历史的确定性策略；“全部确定性无记忆策略”只有限定到此函数定义域才成立。规则没要求整场固定，故这仍是工程分期，不是游戏唯一机制。（据：规则L27、约束·分叉分支；函数定义域的逻辑区分）

### 5.4 全字段赋值与执行范围

运行例所有登记轴都有非空的 specified/derived 值；“有值”分为机制选值、具体输入历史、以及义务处置，不等于所有未决都已证明。对受限模型声明标为“超出覆盖即停”的轴，停止处置编码原样复制共享[内核配置-v1.json](内核配置-v1.json)的 `{policy:stop,trigger:中文触发条件}`；一旦访问该机制立即输出 unsupported/unresolved，不能返回默认物理后效。无箱相位采用 `{kind:explicit_residuals,values:[]}`，零箱这一前件必须机械核对；空映射不是 null。`warehouse.periodic_lift`保留字段名作证明义务入口；stop只在具体反向复原或全称覆盖缺证时触发。生产抽象准入与新键见受限转移§6.1—6.4，完整周期对应见§6.5，依所用支持条件复核后执行。其它未识别字符串也必须拒绝。

`warehouse.external_supply` 的 specified.value 使用两种互斥形状：`{kind:"sufficient"}`，或 `{kind:"explicit_ore_history",through:Time,events:[{event,time:Time,item,quantity:Quantity}]}`。后者event引用timeline.events中同刻runtime，item仅两矿，quantity为正整数，补后≤80000；through是包含上界。数组按非递减时刻，同刻显式序须与统一时间线合图相容；超过through停止，缺矿/耗尽前invalid。sufficient要求种子两矿各有正数、唯一且≤80000的库存格，每个成功出矿事务扣减并立即补回同量，不产生空格瞬间，不释放身份；补回量单列环境账。显式事件不与sufficient混填。矿石返回仓库仍依真实余量判容量，不能从L7推出无穷接收；两模式差分在矿未耗尽、无回矿入库的区间比较非仓库、事件物流及交付账，仓库矿量和补给账按已知关系比较。（据：任务L7；规则L13/L41；转移§2.1；KQ-01）

原 91 项始终全填；共享登记增加字段后，以指纹锁定的当前表为准并显式迁移。逐轴实际选值、来源、覆盖损失保存在[运行样例参数赋值](../数据/样例/kernel_profile_v1参数赋值.json)，它是受限模型声明与机器配置的序列化投影，不是第二份规则或另一 profile。profile-assignment-v2 分别锁定声明、内核配置及轴表原始字节；消费前核全部源哈希、轴名全集、Decision、处置和 coverage_loss，失配先拒收，不能给旧投影配新声明指纹。声明尚无精确选值的字段应在该文件标待对接，并在黄金轨迹中列为条件，不能把“待对接”包装成已通过。

## 6. 初态、运行上下文与玩家动作

`initial_state={anchor,warehouse,nonwarehouse,reachability}`。anchor 是 Decision；specified.value 为 `{event,side}`，对应任务初始锚点，未定用 unresolved。`warehouse={slots,unlisted}`，`slots[]={slot,item,quantity,empty_identity}`。slot 是不带物种含义的唯一格标签；item 为当前实际内容物种或 null（数量零），quantity 为非负整数 Quantity；empty_identity 是 Decision，specified.value 为历史物种字符串或 null，只有它可用 specified/null 表示已知无保留身份，非空格必须 not_applicable。retain_history成功赋种时item承载物种、empty_identity改为not_applicable/value=null；清空时将清空前item复制到empty_identity的specified.value，再置item=null、quantity=0；同种重入反向转换。逻辑身份没有额外隐藏字段，其与当前空格序的同步提交见受限转移定义§4.1。此处特许 nullable-value，不改其他 Decision 的非空规则。空格历史物种须有历史与 warehouse.empty_slot_identity 解释依据，不能借初始零件数预绑成品物种。据：物品格、仓库、协议核心。

在任务初始锚点，六类满额物品分别一格 80000，其他为空；unlisted=empty 是“其他物品为空”的符号规则，不截断仓库格数/物品域。多个 item=null 的空格不算同种重复；非空同物种不能占两仓库格。空格数量与容量仍核目录。settings.warehouse_assignments 只把端口连到格标签，不改变其中物品。以后出现的新格在状态仓库表登记，不能当新增物品操作。样例只列六种初始满格，不预设空成品格。据：任务仓库物品；规则 L13–14、L41、L73。

`nonwarehouse` 为 Decision；specified.value=`StateSeed={layout_snapshot,settings_anchor,warehouse,inventory,progress,logistics,environment,semantic_context}`。虽沿用字段名 nonwarehouse，完整种子必须带当前 warehouse（同上编码）；initial_state.warehouse 是任务锚点条件，两者在不同时刻不能强制相等。reachability 为 Decision，登记从任务条件经历史产生该状态域的证据，不能只填“合法”。据：运行语义 §2/§5、仓库物品、调试期。

|---|---|
| `layout_snapshot`、`settings_anchor` | 前者引 §2 快照 id；后者 `{event,side}` 必须能从 settings.anchor 和已记录操作重建当时设定，未定义的后效拒绝运行。据：设定、蓝图、重建 |

### 6.1 有限调试程序

`debug_operations[]={event,action,target,payload,when,effects}`，event 指 debug_operation，全数组有限且其相邻操作有 occurs_before 关系。当前已编码的action包括set_switch（§4 switch 记录）、assign_warehouse_slot（恰 `{port,slot}`）、set_gate（§4 gate 记录）、rotate/rebuild（§3.2 payload）、withdraw_product（下节 WithdrawalAction）。target 为所操作单位，拿取时为核心；端口寻址在 payload 内，调试清理和手工放料可改变格中实际内容，必须记录实际收支和容量检查。when 见 §3.1；effects 为 Decision，derived.value=`{axes:[轴名]}` 或已审机制引用 `{schema,path,sha256}`。调试阶段的任意操作权限已由任务L12给出；后效不完整或工具未实现时报告unsupported，零干预玩家动作按L8—9限制。据：重建、旋转、设定、开关、准入口、核心、调试期。

调试的动作权限覆盖增建、拆除、清理、手工放料和改设定；当前v3动作枚举尚未包含每一种动作。此类程序先用带路径/指纹的Markdown或JSON机制证据表示操作对象、非精确触发条件、物品出入、前后快照和全部可能后置状态，经任务5/6推导后由任务8扩展编码。既有解析器遇未实现动作应报告unsupported；本次seed样例不执行调试动作。

默认起法为“关机、填满、开机、末级最后”（任务书7 §0.1、主会话三审 §6），填的是带子和存货格，上游每台完成一批停在缓存；调试后StateSeed须按实际程序生成，有限合成全空样例另标用途。任务5负责该程序留下的状态集合与放开后的过程。

### 6.2 零干预期成品拿取

`environment={ore_supply,offline,product_withdrawal,debug_end_event,zero_intervention_after_debug}`；ore_supply=task_continuous_sufficient，debug_end_event 指 debug_end，且不早于蓝图完成和所有调试操作/其后效完成；zero_intervention_after_debug=true。`product_withdrawal={policy,selected_events}`，不能以裸 Decision 替代。policy 是 Decision，specified.value 为下面策略结构；selected_events[]=`{event,rule,action}`，event 指 withdraw_product，rule 为策略规则 id 或 null（仅历史见证），action 为实测/候选发生的具体拿取。其与离线、建成、调试、运行判定的先后/同刻交织均进 timeline.relations。每次零干预拿取须在 debug_end 之后；调试拿取则进入 debug_operations，二者不可重复记账。据：任务 L7–9、L12–14。

`WithdrawalAction={item,slot,quantity}`：item 仅高容谷地电池/精选荞愈胶囊，slot 是实际仓库格，quantity 是非负整数 Quantity，不超过动作前该格现存对应物品；零件数可对空格作空动作，不赋物种。后效为仓库减少该数，玩家外取账增加该数，目标实际入库账不变；不走物流端口，不生成 PC。据：零干预运行、仓库、物品格、目标。

策略编码 `WithdrawalPolicy={schema,rules,selection,timing_family,admissibility}`，schema=withdrawal-policy-v1。rules[]=`{id,condition,action,repeat}`，id 唯一；repeat 为 once/while_enabled，表示可能重复触发，不表示即时自动循环。action=`{item,slot_selector,amount}`：slot_selector=`{kind:containing_item,item}`；amount=`{kind,value}`，kind 为 fixed（整数 Quantity）、up_to（上限 Quantity）、all_available（value=null）。action.item 必须与 slot_selector.item 相等；fixed/up_to 的数值必须为非负整数。fixed 仅在库存足额时可执行；up_to 选 0 到 min(上限,库存) 的整数；all_available 取动作执行前的实际库存，均记录具体件数。selection 为 Decision，specified.value=`{kind,rule_order}`，kind=listed_order 或 nondeterministic，前者给全部规则 id 的优先序，后者 rule_order=[]；这是策略内冲突处理，不替代判定排序。

谓词采用结构化 AST：`{op:"always"}`；`{op:"inventory_at_least",item,quantity}`；`{op:"event_occurred",event}`；`{op:"all"|"any",args:[谓词]}`；`{op:"not",arg:谓词}`。inventory_at_least 的 quantity 为非负整数 Quantity。库存只能是可观察的仓库成品库存；event_occurred 指已发生全局事件，玩家是否知道离线/机器事件另需依据。`timing_family={kind:imprecise,after:[事件],before:[事件],response:Decision,interleaving:Decision}`；response 的 specified.value=`{earliest,latest,lower_closed,upper_closed}`，两个界为非负时长 Time 或 null（未给该侧数值界），有限下界不得大于有限上界，必须描述非单点的响应集合；不能用区间伪装已保证的响应界。interleaving 的 specified.value 为 §3.1 关系数组，约束具体发生实例而非规则 id；admissibility 是证明义务 Decision，已给时引用 `{schema,path,sha256}` 说明观测、响应族及联合规则审查，不能填 true。空 rules 且无 selected_events 的无动作策略允许 admissibility.specified.value={kind:no_actions}，仅表示本有限区间没有动作，不证明一般响应策略。语法支持以上片段，不宣称囊括所有玩家策略；未覆盖策略须增版，不可随意字符串冒充程序。据：操作精度、判定、零干预运行。

policy unresolved和空selected_events表示未提供拿取方案；任务L9仍要求定期拿取。有限无拿取区间可作工程前缀，不能把无限不拿作为现行目标的反证。每种成品库存账为I−O−P，最终厂内口仅取原矿时O=0；只有仓庫状态复原的完整周期才把该净变置0。生产投影与任务L10基地状态周期的对应由任务2/6补证明，接口见受限转移§6.5。（据：任务L2、L8—10、L13；规则L14、L36、L41、L73；约束L34、L40）

### 6.3 轮询记忆 PollMemory

`PollMemory={schema,sides}`，schema=`poll-memory-v1`。sides 对每个非供电单位的 input/output 两侧各一条（即使无通道），每条为 `{unit,side,graded,current_level,levels}`；levels[]=`{id,members,next_channel}`。成员是该侧现存 PC 的不重不漏分区；members 顺序按接通关系及显式平局值导出，id 为 `L|<unit>|<side>|other`、`L|<unit>|<side>|direct:<PC>` 或运输取货侧的 `L|<unit>|output|ungraded` 稳定成员类别编码，分级更新按成员身份映射不能借编号永久冻结优先级。graded 对所有 input 为 true，对非运输 output 为 true，对运输 output 为 false（规则 L29–32）。无通道时 levels=[]、current_level=null；未分级有通道时仅有一级；级非空时 next_channel 必为本级成员，记录下一获权位置，每级各有一份，不能只保存当前级的游标。

current_level 为当前最高可移动级 id 或 null（无可移动级）；未分级非空侧为唯一一级 id。级定义、排序、最高级守卫由运行语义和本版 profile 计算，输入不得伪造更高/更低权。初态在新时刻扫描前也须按实际仓库指派、库存、目标格容量/物种、运输年龄和端口额度计算当前级，不能按单位 id 预填样例答案。指向无货空格的源口及其目标分级侧均无可动级；历史身份不计库存。失败前移、重入级、删边投影和离线后效必须分别服从对应轴；本结构只提供无损存取位置，不裁定未选后效。桥接器按 unit 只有两条侧记录，禁止按轴重复四套。（据：轮询、优先级、取货/存货优先级、桥接器；受限模型声明 per_level/保留级内位置）

v3 的 StateSeed 必须逐格列 inventory（含空格）、逐制造/储存箱列 progress、列所有准入口计数；不适用集合显式 []。所有活动 StateSeed Decision 必须先核 §1.1 的 status/value/basis 封套，再核字段允许的已解状态；unresolved、非法 status 或空依据均不得继续执行。当前参数列表恰覆盖参数向量且值/生命周期一致。无待事件是已核的空列表，不能作为“尚未知”的替代。working 必须有 recipe/locked_recipe/remaining，缓存原料按在制用量保留到完成转换；completed 保存已制产物、remaining=Time(0)，整批转出后回 idle。恢复数据与结构、种类容量、计时、端口预算、接通/轮询关系冲突时拒收。（据：运行语义 §2；规则物品格、缓存格、制造、滞留）

### 6.4 种子派生与检查点恢复

`Input::canonicalize_seed`或`kernel seed`是已有字段的派生/校验接口，不是从库存反演任意运行史的函数。调用方必须给完整布局、设定、历史、库存/进度及已选参数；其中`semantic_context.arbitration.level_order`由调用方显式选择全体几何可能级标签的严格全序，缺标签、重复或额外标签均报invalid。该序只在正式级键相等时仲裁，不能从connection.tie、单位id、标签排序或布局推为唯一；新增布局可以枚举该序的具体输入，是否全称覆盖仍由认证器另证，不新增轴或未定义字段。（据：规则L29–32；受限转移§1、§3.1；polling.level_tie=fixed_arbitration；KQ-07）

- `before_boundary`作为**新调度起点**时，按已选起轮规则从图及显式接通/仲裁序派生环、游标和当前级，并从实际门原因、库存/进度派生现存边、待办及边界上下文；99轴当前值须与输入参数一致。若该起点只是合成试验，reachability必须继续标明可达性未证；不能因派生自洽就宣称来自蓝图/调试历史。若要恢复历史运行在边界前的续接状态，必须保存或从已核历史重放得到游标、预算及活动事件，不能调用新起轮覆盖它们；尚不支持该恢复时返回unsupported并写明位置。
- `after_closure`检查点保留原已执行游标、参数、台账、活动事件身份与时间锚点，校验其与当前布局/设定/参数一致；缺失或冲突即拒收，不重置起轮或反推缺失记忆。由此起跑首刻为t+1，见输出§2。库存和图相同不推出游标相同，因为成功、失败与图维护历史会改变游标。
- `in_boundary/in_closure`按§5.2保存continuation；格式能表示不等于本版派生器已支持。不得把未知扫描位置强制改为新before_boundary来继续原运行。

验收应核现有可派生样例`run(seed(x))=run(x)`逐字段相等，并核两种显式仲裁序各自被保留、缺/重复仲裁拒收、after_closure游标和账未重置。此处是K线实现要求；规格自查不代替该运行回归。既有仲裁域、轮询记忆和可达性字段足够表达，无需为KQ-07新增状态字段或改变schema。（据：规则L25/L29–32、任务L13；受限转移§1、§3.2–3.4；第五轮任务书K1）

## 7. 与送料契约的映射

`contract_binding=null` 表示无外部契约；非空为 `{schema,path,sha256,at_snapshot,machine_map,source_map,core_map,port_map,feed_map}`，schema 必须 `feeding-v2`，path 相对样例，sha256 锁定读取字节；at_snapshot 指本输入几何快照，映射结论仅对该快照成立。据：送料契约版本与来源追踪约定。

| 字段 | 对齐规则与核验 |
|---|---|
| `machine_map[]` | `{machine,unit}`；machine 引契约 machines.id，unit 引布局实例；完整绑定覆盖全部机器且单射，kind 相同、计划 recipe 均属该机型。可用此表映 M000 到任意本地实例名，但不能把多台机器映一台。依据：送料契约机器表；规则制造单位、配方 |
| `source_map[]` | `{source,port}`；source 引 sources.id，每个来源恰有一行且不得多行、漏行；port 是实际核心/仓库取货口 output 端口；source_domain.all_different=true 时逐个互异，边界与序号按 §4，在绑定锚点从 warehouse_assignments 和实际仓库状态推出所出物品，与 sources.item 相符；状态未解则此项 unresolved。不能只绑定核心实例而省掉六口身份。依据：契约来源身份；规则 L41、L73 |
| `core_map` | `{core,unit}`；契约 core.id 对唯一协议核心；不得复制核心。规则 L41 |
| `port_map[]` | `{logical_port,physical_port}`；把 `M:out:n` / `M:in:n` 等逻辑端口映到对应实例规范口，角色、端点须匹配；同一逻辑端口重复物品记录共享一份映射，不把逻辑序号当坐标。依据：送料契约 logical_feeds |
| `feed_map[]` | `{logical_feed,paths,status}`；logical_feed 引真实 LF id；paths 是 PC id 有向序列的数组，status=`geometry_only` 或 `unresolved`，后者 paths=[]。路径的首尾口对应 port_map，中途只能经过运输单位，逐相邻 PC 在同一个运输单位内衔接；桥接器必须同轴穿越。多分支可列多个路径，但不能据选择一条路径认定实际物品必走该路。依据：通道、桥接器、送料契约逻辑送料定义 |

完整绑定还须核以下一致性：从实际端口机型、边界位置及 §4 的排序得到 `{kind,side,index}`；逐项落在 source_domain.left/bottom/core 中，已指定的 sources[].identity 三项必须完全相等，待求者由映射给见证值，不回写契约冒充已求证。候选 B 的 52 个 source 必须覆盖全部左 23、下 23、核心 6 个 output 口，双射覆盖来自“总性＋互异＋同样大小的域”，不能仅检查互异。几何少口/多口/重复身份一律不算完整绑定。据：出库上限、取货口配置；送料契约来源身份。

port_map 的定义域恰为全部 LF 两端不同逻辑端口并集，并包括每个 source 的 out:1，重复使用的逻辑端口只有一份映射。`ORE*:out:1` 的 physical_port 必须等于对应 source_map.port；机器端口须属于 machine_map 对应单位并按同一逻辑端口共享映射；`CORE:in:n` 须属于 core_map 的 input 口，不与矿源 output 混淆，CORE 输出若由 ORE 变量绑定仍走 source_map。不同逻辑端口不得无依据合并成一个物理端口。feed_map 对全部 LF 恰一行，首尾严格等于 port_map，桥只走同轴，路径在 at_snapshot 的 PC 中完整可达。这里只规定未来完整加载器判据，当前样例检查器对非空绑定报 unsupported。据：通道、桥接器、协议核心；送料契约 logical_feeds。

映射不复制 planned_rate/proven_actual_rate；前者仍是计划，后者仍需运行证据，geometry_only 无权升级认证。配方匹配与分流器路由也不由 feed_map 控制。储存箱必须分成独立非运输端点的两段 LF；feeding-v2 目前不支持这类完整契约，加载该绑定须报 unsupported，不能恢复 via.storage。布局格式本身可以表示箱体和其 PC；无线入库独立于 PC/BC/LF。依据：送料契约“三种边与储存箱分段”；规则 L36、L72；约束运输端口收支。

本次最小检查器只支持 contract_binding=null；非空明确拒收为不支持，不能输出“映射通过”。完整映射检查是未来加载器职责。本节字段已给出机械核验条件，不以示例伪造候选 B 的物理映射。
