## 1. 运行记录顶层契约（RunRecord）

所有字段必填，明确标为可空的字段也不可省略，未知键拒收。装载前失败而无法形成合法参数、历史、种子或验证范围时，parameter_assignment/input_history/trace/validation_scope可为null，并在open_items给停止位置；completed时这四项均必须非空，不能伪造未发生的状态。物理数字沿用 Quantity，时刻沿用有理 Time；本版 schema 只接有理轨迹，非有理事件输入输出为 unsupported，不用浮点近似替代。Decision 的 value 形状由轴/状态所属接口继续校验，单靠 JSON Schema 不证明它可执行。

| 字段 | 类型与语义 |
|---|---|
| schema、run_id | kernel-output-v4、唯一运行标识。 |
| evidence_scope | §5.1公共证据范围；运行记录kind=diagnostic、direction=diagnostic，有限轨迹按实际范围报告。 |
| execution_mode | finite_concrete或production_abstraction；后者仅按受限转移§6代表化，不能报为玩家真实运行。 |
| port_meeting | 已定shared_edge_opposite，须等于参数点；角点接触不成通道。旧角点输入只作为非法输入诊断或史料。 |
| profile_id | 必须等于输入与 parameter_assignment.profile_id，例如 kernel_profile_v1；不能仅凭此名字认定相同解释，仍核源指纹及逐字段值。 |
| producer | `{kind,path,claim}`；kind=kernel、bounded_reference_checker 或 manual_expected，明确产物由内核、有限重算还是手算产生。工具路径也入指纹。手算期望不能标成实际内核输出。 |
| status | completed（所请求有限前缀完成）、invalid_input、unsupported（实现不支持）、unresolved（规格或输入义务未解）、inconclusive（资源不足）。任何状态都不自动表示达标或全题无解。 |
| fingerprints[] | `{role,path,sha256}`；至少含 input、catalog、axis_registry、profile、三份 formal_source、实现 checker/kernel 对应 checker 角色，实际读取的 parameter_projection 及其声明/配置/轴表来源，以及本记录使用的 semantics、schema；若比较黄金结果，另有 golden。依赖清单由校验器重建后与记录严格比较，禁止删掉某个依赖以绕过核验；Python 实现包括 check_golden_trace、runtime_example、check_examples、runtime_record、event_order 和运行回归入口。参数投影在消费前还要核其内部来源哈希、逐轴决定、处置及覆盖说明。哈希针对原始字节，path 绝对路径或相对记录文件；指纹不匹配需重新核验，不允许刷新后沿用旧结论。 |
| parameter_assignment | 原样保存完整 Parameters 的三个生命周期对象和轴表引用；字段集合严格等于被锁定轴表，禁止漏轴、重复轴或悄悄默认。输入历史产生的当前值也存入每个 StateSeed.semantic_context。 |
| input_history | `{timeline,construction,debug_operations,environment,reachability}`，完整保留输入的事件、关系、接通、建成、调试、离线、补矿、拿取历史/策略及初態可达性证据；结构分别按内核输入 §3、§6 校验，不以文件名代替内容。 |
| uncovered_axes[] | `{axis,reason,disposition,coverage_status,evidence,other_values}`，恰覆盖本次全部轴。reason 是配置的通用损失，disposition 是配置处置；coverage_status 单独记录 exercised（实际执行）、input_checked（仅输入/结构检查）、not_exercised（未触发）、stop_not_triggered（停止条件未触及）、proof_pending（证明未完成）。evidence 为事件 id 或结构/未触发原因，other_values 明记其它值及联合组合未覆盖。填了本版值不等于已验证该机制。 |

## 2. 逐事件、逐时刻内容

`ticks[]={time,events,state,summary,closure,warehouse_ledger}`；time严格递增，state为该时刻闭包后的完整StateSeed。首项起于本次执行产生的第一个时刻：before_boundary种子为t，after_closure种子为t+1。start_state及其phase原样保留；after_closure起点不补一条未由本次执行产生的t记录，也不重放t的事件。空前缀的end_time为start_state.environment.time。（据：受限转移§1；KQ-02；同一事件不可重放）summary 只是可读投影，以完整状态为准，校验器必须核两者一致。每个 state 的参数、物品格、在制、轮询记忆、待事件、端口额度都保存，不用状态哈希代替内容。据：运行语义 §2；内核输入 §6。

`events[]={event,operation,target,outcome,detail?,basis}`。operation 分 move/internal_move/manufacture/transfer、非判定制造完成、gate_window_expiry窗口到期、gate_identity_maintenance身份维护、时间推进、补矿、离线、玩家动作；判定与非判定不能互相冒名。event 是实际实例 id；判定扫描机会由 EventOrder 规则生成，no_request 只是未获授权的扫描观测，不是已经发生的判定，不能以观测数统计规则判定数。失败须记录原因和真实权限后效，成功有库存增减；具体成功物流和端口计量保存在 state.semantic_context.tick_context，同步核对 event 引用。据：规则 L18、L23–25、L29、L35–36；约束端口速率。

closure 给出压缩依据及扫描轮数。全状态重复指会影响后继的物理及调度状态相等；单调增长的诊断事件序号不得混入闭包判等。资源上限不能充当闭包证明；无法核验归约时返回 inconclusive/unresolved，不推进时间。zero-time 的失败循环也须保留被压缩前后相同的轮询状态。据：受限模型声明 time.instant_end、运行语义 §4。

`pending_events`可有manufacture_complete与gate_window_expiry，分别表示工作量完成和窗口到期的非判定事件；输出事件登记表同时为这些运行时 id 提供统一引用域，恢复时并入原 timeline。输入不能事先穷举无限新事件，因此 EventOrder 与完成事件生成式提供运行中扩展注册；每个新实例 id 唯一且不重用。`I|`、`J|`、`C|`、`W|`的历史前缀保留规则见内核输入§3.1；完成事件在开工时注册，窗口事件在首件收货时注册，之后pending、实际完成和账本中的同名项是同一实例的引用。manufacture_complete以remaining归零执行，初始预计trigger是审计预计值，暂停可使实际时刻较晚；验收按逐段功能工作量核，不要求实际时刻等于旧预计时刻。窗口事件仍按5tick真实截止核。验收须建立跨全部ticks的全局执行集合，与input_history.timeline及初态/逐刻pending注册对照：拒绝历史别名、跨tick重复、已办又待办、同id的操作/目标/触发改变；同一未办事件在相邻状态重复出现允许，消费只许一次。JSON Schema只核局部形状，跨集合唯一性必须由语义验收器独立核，不能仅靠重算相等。边界未完成的活动事件保留 waiting/ready，不会被“未列即空”抹去。

### 2.0 逐刻逐物种仓库台账

`warehouse_ledger={core_inbound,wireless_inbound,port_outbound,external_supply,player_withdrawal,representative_adjustment,totals}`，所有数组必填，零量用空数组，totals按物种名排序，恰覆盖本刻有任何收支/调整的物种并另保留两成品零项。件数为非负整数Quantity，逐事务明细只存正数；不能把无线传输只写whole_box而省件数。（据：约束·入库途径、目标；规则L36/L41/L72/L73）

- core_inbound每项`{event,channel,port,item,quantity}`，event是成功move，port必须是核心存货端口，channel实际PC，quantity=1。
- wireless_inbound每项`{event,unit,item,quantity}`，有实际入库的transfer按本次送出各物种分别一条，包含部分接收量，unit为实际协议储存箱；空箱/拒收无入库明细，transfer事件仍记录本次尝试和冷却重起5 tick。
- port_outbound每项`{event,channel,port,slot,item,quantity}`，port必须为核心或仓库取货口的实际取货端口，slot按当时指派，quantity=1；即使sufficient矿量不变也须记出库。
- external_supply每项`{event,mode,item,quantity}`；explicit_ore_history引用ore_supply事件；sufficient的event引用触发同一原子补回的成功move，不伪造玩家事件。两者只准两矿，合计补回/补给数按实际事务核。
- player_withdrawal每项`{event,slot,item,quantity}`，只准两成品、引用已授权环境事件。普通执行器未实现该动作时返回unsupported；抽象执行无拿取事件时数组为[]。具体完整周期按真实拿取填账，数学代表调整单列。
- representative_adjustment每项`{item,quantity,reason}`，reason固定production_representative；仅production_abstraction可非空，表示G在本次边界前将上个代表成品数归零的扣量，是数学表示账，不是实际入库/玩家外取。
- totals每项`{item,core_inbound,wireless_inbound,port_outbound,external_supply,player_withdrawal,representative_adjustment,actual_inbound}`，各项Quantity；actual_inbound=core_inbound+wireless_inbound，只把前两路计交付。

逐物种必须满足`W_after−W_before=actual_inbound+external_supply−port_outbound−player_withdrawal−representative_adjustment`；第一刻before取start_state，后续取上一重建完整state。还须与每个实际事件和库存变化交叉核，不能只通过总和。按口核出库及核心入库≤1/tick，无线无端口额度。实际入库0件时无无线入库明细；部分接收时逐物种核实际送出、箱内残留、仓库增量，某种拒收仍允许其它可收物种入库。（据：规则L13/L36，约束·入库途径/端口速率；受限转移§4.3、§6.1）

身份维护事件`operation=gate_identity_maintenance`的detail保存`{gates,removed_channels,restored_channels,reason_changes}`；reason_changes逐门给before/after原因集合。恢复判断读取原几何对接候选，前后图及指针完整后态从事件与StateSeed交叉核。event沿用全局唯一身份，属于非判定维护，不计通道成功额度。字符串detail须可解析成上述封闭对象；schema只验证封套，内容由语义验收核。旧仅有removed_channels的记录按其旧模型保留。（规则L16、L22、L64；受限转移§2.2、§3.4。）

### 2.1 checkpoint_delta 编码与验收

`full_state_each_instant` 保留。`checkpoint_delta` 的trace另带正整数`checkpoint_interval=k`及`delta_encoding=object_replace_v1`。ticks从0编号，i=0,k,2k,…的项保留完整`state`；其它项以`delta`替代state，字段互斥且不可缺。每项仍有time/events/summary/closure/warehouse_ledger，不能省略无变化时刻、失败事件或扫描观测。k计记录时刻数，不计物理tick时长；末尾不足k的段也必须逐项验收，不能丢弃。start_state仍是本次原始完整种子，允许before_boundary或after_closure；检查点分叉按上段首项规则，不重记前一刻事件。

`delta=[{op:"replace",path:[对象键,…],value:任意JSON值}]`。路径非空、每级必须为已有对象键，不穿越数组；数组整体替换，带新键或删键的对象也整体替换其父字段。对象同键时递归到实际改变处，按键UTF-8字节升序深度优先输出；禁止根替换、无变化替换、重复路径及祖先/后代冲突。空delta只表示完整状态无差异，物理时间仍须一致。前态是上一项重建的状态，不能每项重新以start_state为底。编码不增加游戏事件或丢弃StateSeed字段。

验收依次核schema、检查点位置、操作路径与规范增量；由上一完整状态连续应用增量，逐项核StateSeed、时间、事件身份、守恒与摘要。再从输入和已验证检查点按事件语义重算至下一检查点，重建状态、事件、闭包必须逐字段和JSON类型相等；检查点本身也必须与前段的重算后态相等，不能借新检查点覆盖累计错误。本参考验收器从初态重算全前缀（更强但尚未优化），解码后与完整参考逐字段比较；最后残段同样比较。单有哈希或一次解压成功不构成运行验收；unknown/inconclusive不得改报completed。

schema只能检查局部形状；k的整段位置、操作可应用性、规范差分及状态关联由[checkpoint_delta.py](../数据/样例/checkpoint_delta.py)、[runtime_record.py](../数据/样例/runtime_record.py)和本轮回归共同核验。两格式共享kernel-output-v4及全部来源/范围义务；新增台账属于必填升级，旧v2记录保留历史身份，须重算并生成kernel-output-v4，不能只改版本或刷新指纹。

## 4. 版本与引用边界

schema根oneOf区分RunRecord、CycleResult和ProofCertificate。当前版本分别为kernel-output-v4、kernel-cycle-v3、kernel-proof-v1；生产键为phase-cycle-key-v1、归一化为cycle-normalization-v2。新字段、状态含义及参数生命周期共同升版，旧输出须重核后重生。StateSeed完整原状态仍用于恢复，规范键用于判等。

引用对象`{path,sha256,producer,format}`四项必填，sha256为原始字节64位小写摘要，path相对证书目录或为绝对路径。先核摘要再解析，嵌套引用相对所属文件目录解析；producer身份与被引对象及实际工具相符。run_record_ref.format为kernel-output-v4/full_state_each_instant或kernel-output-v4/checkpoint_delta，replay_input_ref.format为kernel-input-v3。

record_mode=referenced时保存独立运行记录；none时从引用输入独立重建前缀及周期。两模式均锁全部依赖、起点、固定参数和预算。无周期的已装载结果保留last_state；装载前失败的replay_input_ref/seed/parameter_point/last_state可空，completed_ticks=0，并保存实际停止原因。指纹不符须重新验收。

### 5.2 CycleResult与D域

顶层必填schema、result_id、status、level、execution_mode、port_meeting、seed、parameter_point、reading、support_domain、domain_report、fingerprints、record_mode、replay_input_ref、run_record_ref、last_state、cycle、stop、budget、open_items、evidence_scope、environment_assumption。未知键拒收。seed保存reachability及source_event；parameter_point保留完整assignment与15输入轴的实际值；指纹包括实际读取输入、目录、三份正式源、轴表、配置、语义、schema、实现及所有引用依赖。

status=cycle_found表示指定起点/参数的已核达标周期，kind随level取production_cycle或concrete_full_cycle，direction=conditional_witness；全族结论单列。指定工程运行找到正时长重复键，但正式前向对应、真实反向复原或其他必要证据未齐时，status=diagnostic_cycle、kind/direction=diagnostic、level=production_part；实际率lt/eq/gt单独保存。当前Rust在PC-06未结清期间统一生成诊断周期，数值达标也适用。counterexample要求合法可达的完整低产周期，level/kind=concrete_full_cycle、direction=counterexample、stop.kind=low_rate，至少一个实际率低于目标且反向复原全部通过。

level只取production_part、concrete_full_cycle或null。生产部分execution_mode=production_abstraction、support_domain.name=phase_production_v1、reading.cycle_interpretation=production_projection；完整周期execution_mode=finite_concrete、解释为concrete_base_with_withdrawal。每种成品分别记ΔW=I−O−P；全矿指派给O=0；仓库确实复原时才令ΔW=0。实际入库I只来自核心与无线实际送出，代表调整单列。

domain_report仍按D.1—D.5恰五项保存condition/status/scope/locations/evidence，status=pass/fail/unresolved，scope=static/executed_prefix/cycle/not_checked。not_checked为unresolved。周期材料五项均pass/cycle；具体完整周期的D.1、D.5按保留真实外部过程和真实容量的模式核，代表化特有部分写明不采用的原因。D.2任何候选容量读点在读取前检查，D.3标签非干扰及D.4有效字段全程核，D.5只限定代表编码的工程容量安全。静态检查仅报告其实际范围，后续动态读点另验。

stopped对应unsupported/unresolved；inconclusive对应resource；invalid_input对应invalid_input。这三种cycle/level为null，保留已装载末态或装载前失败外壳。零传输冷却和判定固定性已有规则值，停止只报告尚缺实现/推导的具体后效。stop.partial_events只作未完成段审计。

### 5.3 cycle字段、键和对应义务

cycle必填period、start_time、end_time、start_state、end_state、start_key、end_key、normalization、ledger、totals、rates、acceptance、reception_scope、correspondence。period为真实正时长，两端完整状态和规范键均保存。normalization含schema=cycle-normalization-v2、definition、basis、domain_checks及mapping_proof，后者锁定所用逐字段映射、未来读取和后继/耗时保持证明。当前phase_production_v1仍只接已核整数D域；连续时域的通用字段可表示精确有理时长，实际执行支持另核。

ledger记录(a,b]内各实际推进段的warehouse_ledger，整数P tick执行恰P项；起点旧事件不重计。rates恰含电池和胶囊各一次，inbound取actual_inbound合计，average=inbound/period，目标为3/5与11/20，comparison精确取lt/eq/gt。acceptance保存观测，完整区间接收由reception_scope证明。

correspondence将以下三组义务分别保存status、proof_sources、checks。status取proved/unresolved/not_claimed；proved须有指纹证明且所有固定次序检查pass。结构校验约束列表齐全，语义验收逐项验证材料。

### 5.5 独立语义验收

1. 按相对目录解析引用，先核原始字节指纹，再核format、producer及全部依赖。重建99轴恰集及生命周期；同一运行、端点和回放中固定排序不得改变。旧版本重核后生成新记录。
