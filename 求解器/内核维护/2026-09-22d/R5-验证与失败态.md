## 3. 出错后的回滚与 halted 语义

结论：**重现了。** `crates/kernel/src/transition.rs:654–672` 的控制流是：

1. 已有 `halted` 时直接返回保存的 Stop 克隆，不进入 `step_inner`。
2. 否则清理 `active_event` 后调用 `step_inner`。
3. `step_inner` 返回错误时，可将当前保存的事件 ID 加到错误位置，然后保存 `halted=Some(stop.clone())` 并返回错误。

该包装器没有恢复旧状态的分支，也没有先克隆整个引擎。`step_inner` 的注释明确写着“失败后实例封存，不可把部分阶段当新种子续跑”（`transition.rs:674`）。

失败前可能发生的修改包括：清空本刻 records/ledger/movements/passages（`676–683`）；生产代表转换及边界动作（`691–697`）；时间和剩余工作量推进（`412–428`）；逐模板提交动作（`710–759`）。扫描预算检查位于 `702–708`，因此可以在一轮已经提交之后失败。成功闭包后才同步 `poll_memory`、`judgment_context`、`pending_events`、`tick_context`（`767–794`）。

### 3.1 正常样例上的复现

输入为未修改的 `数据/样例/生产循环环带.json`；`Engine::new_production` 装载成功后设置公开运行预算 `max_sweeps=1`。分别调用 `step(true)`、`step(false)`、`step_compact()`，三者均得到：

```text
status = inconclusive
axis = resource.sweeps
location = J|0|0|4: instant=0 sweep=1
state_changed_before_error = true
inventory_changed_before_error = true
```

失败前后具体变化：`a:transport:0` 内的 1 件高容谷地电池已移入 `b:transport:0`，`a` 格变空；该移动没有因最终返回错误而撤销。完整前后状态保存在 [probe-results.json](R5-验证与失败态/probe-results.json) 的 `failure_probes[].before/after_error`。

随后将预算提高到 1000，再调用同一入口：

```text
repeat_stop_identical = true
repeat_entire_engine_debug_unchanged = true
```

比较使用完整 Engine 的 Debug 表示，包含非公开字段；比较起点在手动提高预算之后。因此证明的是再调用没有继续修改实例，而不是声称人工预算修改没有发生。`halted` 自身是 `pub(crate) Option<Stop>`（`engine.rs:59`），外部探针没有直接改写它。

另一个探针先完成一刻，再将预算降到 1：失败时 `environment.time` 从 0 变为 1，库存也已经推进；`judgment_context.phase` 仍是上一完整边界的 `after_closure`，其 `instant` 仍为 0。**失败实例的 phase 字符串不能单独当成可恢复性证明。**

### 3.2 必须保留的限定

- “不整刻回滚”不等于每次错误都必然改变物理状态。`check_external_stops` 在边界动作前检查（`transition.rs:691`、`341–409`）；具体保留到哪一步取决于错误位置。
- `halted` 保证适用于进入 `step_with_snapshot` 后返回的 `Err(Stop)`；它不是 panic 捕获器，也不是所有 Engine 公共方法的统一守卫。
- `step_instant/step_tick` 在调用 `step()` 前先检查锚点（`transition.rs:631–644`）。探针在初始 `before_boundary` 上调用 `step_tick(true)` 得到 `invalid_input @ step_tick`，随后普通 `step(true)` 仍成功：这个入口前置错误没有封存实例。已有 halted 的实例也可能先被这些锚点检查拒绝，不能概括成“任何入口一律返回同一个 Stop”。
- 本次四个失败态重新送入 `checkpoint_input` 与 `Engine::new_production` 均被拒绝：前三个在 `poll_memory` 处，完成一刻后再失败的案例在 `J|0|0|0` 的事件账本校验处。相对地，保存上一次成功返回的完整 state 后重建引擎，其下一刻 `time/events/state/warehouse_ledger/closure` 全部与连续运行相等。这是对这些案例的验证，不是对所有失败态拒收的穷举证明。

当前输出层已有部分边界区分：`run_record` 只把成功 tick 放入 rows，失败时保存 Stop 并结束（`output.rs:405–437`）；周期搜索单独保存最近成功的 `last`，失败时记录 `stop.partial_events`（`cycle.rs:664–696`、`868`）。预算 1 的周期探针输出 `completed_ticks=0`、`partial_events` 长度 5。不能把 GPT Pro 的进一步封装建议读成“现有产物完全没有完整前缀/部分审计的区分”。

### 4.3 独立性结论的边界

复用同一转移实现会限制“通过重跑发现共同实现错误”的能力，但不能据此断言验证无效。当前还有独立的事件身份和守恒检查：普通记录在 `output.rs:529–548` 调用 `ledger::verify_tick`、`validate_event_identity`；周期前缀和 P 刻重放在 `cycle_io.rs:285–288`、`312–315` 调用 `EventValidator` 和台账检查。由这些代码能够支持“复现一致性与部分不变量核验”，不能推出全部转移规则语义正确，也不能反向推出已有错误证书。
