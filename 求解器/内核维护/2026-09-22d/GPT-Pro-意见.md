# GPT Pro 对《代码体检方案》的意见（2026-09-22，owner 转来，原文照录）

我的判断是：**这份方案作为“保守的结构维护方案”是合格的，但作为“内核代码体检方案”还不够。主要问题不是拆分方法写错，而是优先级偏向长函数、测试命名和证据归档，遗漏了更值得先处理的状态边界、构建来源绑定和长期运行资源问题。**

我不建议推倒重写，也不建议马上按表把那 30 个长函数依次拆掉。更合适的顺序是：**先固定安全、可重复的测试基线，修清楚已确认的接口和来源问题，再围绕状态不变量做结构调整，最后处理纯整理工作。**

这次我读了方案、维护记录，以及输入装载、状态、转移、缓存、周期键、周期搜索、记录验证和相关测试。实际运行了 **134 项测试，全部通过**，包括 101 项库测试、3 项参考差分测试和 30 项 topology 集成测试；Clippy 全 targets 检查也通过，未输出告警。另外做了公开接口和运行资源探针。没有修改生产源码、方案、黄金或历史证据。

下面的路径均相对于 `求解器/`。

## 一、应优先修的实际问题：公开可变状态破坏了校验边界

这不是纯粹的代码风格问题，我已经复现了一个具体的不一致。

用 `数据/样例/生产循环环带.json` 创建生产引擎并成功推进一步，然后通过公开的 `state` 字段，把 `b:transport:0` 格内一条存货的数量改为 `0`。这个状态按内核自己的校验规则是不合法的，但三个接口给出不同结果：

```text
engine.validate_inventory()               → invalid_input
engine.cycle_key()                        → Ok
cycle::cycle_key(&state, &input)           → invalid_input
```

也就是说，**同一个非法状态，独立的周期键入口拒绝，Engine 上的方法却接受。**

原因在代码里很明确：

`Engine` 将 `input`、`state`、`memory`、`production_abstraction` 等字段公开；`Input` 的原始 JSON、几何、模板和各种派生表也全部公开。与此同时，引擎还维护着库存索引、进度索引、活动边集合、待办事件和缓存。这些东西在构造时建立一致性，却允许调用方随后只修改其中一份。定位：`crates/kernel/src/engine.rs:19–60`、`crates/kernel/src/input.rs:9–24`。

`Engine::cycle_key()` 只检查生产域然后编码；独立的 `cycle_key(state, input)` 则重新构造并验证引擎。尤其 D.4 的实现直接沿用“完整 Engine 装载已核静态义务”的假设，而公开字段使这个假设可以失效。定位：`crates/kernel/src/cycle.rs:271`、`:304–320`。

需要限定一下这个结论：**这是已经复现的公共 API 一致性缺陷，不等于我已经发现正常 CLI 能生成错误周期证书。**正常装载和后续验证仍有其他检查。

### 我建议怎么改

把“可编辑的输入/种子”和“已验证、可运行的引擎”分开。

外部可以编辑输入构造器或种子副本，但进入 `Engine` 后，模型、状态及索引不应再允许任意独立修改。对外提供只读状态访问，以及经过完整校验、重建索引和缓存的恢复入口。周期键的快速入口则只能消费引擎内部保证合法的完整边界状态。

**不要用“每一步都重新校验全部状态”来补这个洞。**那会把封装问题转化成持续的运行成本。

公开字段收口可能影响现有调用方，因此它应当是单独的 API 加固批次，不能混进“纯搬函数、行为完全不变”的批次。测试里直接改状态的部分，也需要迁到明确的测试构造器，而不是因此继续保持整个引擎可任意改写。

## 二、来源指纹没有真正绑定编译产物，这会直接影响重构差分的可信度

我认为这一点比拆 `main::run` 更优先。

当前 `output::fingerprints()` 的做法是：根据编译时的 `CARGO_MANIFEST_DIR` 找到源码目录，**在运行时读取磁盘上的源码文件并计算哈希**。源码文件清单也是手工列举的。定位：`crates/kernel/src/output.rs:152–219`。

这里存在两个问题。

**第一，运行时源码哈希，不等于当前二进制的构建源码哈希。**

从这段实现可以直接推出：保留一个旧二进制，再修改它指向的源码目录；旧二进制运行时，仍可能把目录里的新源码哈希写入自己的输出。它证明的是“这些文件现在是什么内容”，不是“执行这些转移的二进制由这些内容编译”。

方案第 5 节允许把基线和候选二进制分别保存在共享 target 的不同位置。但**仅仅改二进制文件名或保存位置，不会改变它们编译时绑定的源码目录**。所以，不能只靠当前 `fingerprints()` 就认为双版本的实现来源已经分别闭合。

**第二，拆新模块时可能漏掉来源清单。**

例如把逻辑提取到一个新的 `validation/seed.rs`，Cargo 可以正常编译、运行测试也可以通过，但这个新文件不会自动进入当前的指纹枚举。验证器重新运行时沿用同一份枚举，也不能靠重算自然发现这个遗漏。

### 我建议怎么改

近期先在差分执行器外层，明确保存并绑定：

> 基线源码清单及哈希、基线二进制哈希、构建命令与工具链信息、基线原始输出。

基线输出应在修改前生成，或者从独立冻结的源码上下文中生成，而不是事后让旧二进制替当前工作树“签来源”。

之后再做正式的构建身份改造：生成构建期清单或 build ID，让记录绑定实际实现产物，同时检查新增模块和嵌入文件没有漏出来源覆盖范围。运行时输入、配置、规则来源的哈希继续保留，但应与实现构建身份分开。

这类输出协议变化也应该单独登记，不宜伪装成结构搬迁中的合法哈希噪声。

## 三、方案的“行为完全相同”验收规则，目前有一处会让它无法执行

方案第 1 节要求比较 CLI 的退出码、stdout/stderr，而且允许映射的字段主要限定为源码位置和哈希。

但当前 `run --no-output` 会在 stdout 中输出真实计时：

```json
{
  "elapsed_ns": "..."
}
```

定位：`crates/kernel/src/main.rs:252–271`。

我对**同一个二进制、同一个输入、同一组参数**连续运行两次，结果是：

```text
退出码：均为 0
其他字段：完全相同
elapsed_ns：9124353 与 8866522
```

因此，按方案现有文字执行逐字节比较，**连“基线和基线”都过不了，更不用说比较重构前后。**

### 这里应该怎样修订方案

应当明确区分三类比较对象：

| 对象                             | 比较方式                 |
| ------------------------------ | -------------------- |
| 状态、事件、物料账、Stop、basis、证据等级等语义字段 | 严格相等                 |
| 已登记的路径和来源绑定字段                  | 先分别验证来源，再按显式映射比较     |
| `elapsed_ns` 等测量字段             | 保留原始值，检查字段结构，单独做性能比较 |

不能扩大成“输出不一样就挑字段过滤”。豁免必须是一份**精确到字段路径的白名单**，而且完整原始输出仍要保留。

我还建议把 **A/A 自比较**加入第一道验收：同一版本先重复运行，确认哪些字段真的稳定，再开始 A/B 重构差分。

方案对事件、错误和证据字段不许随意过滤的要求是正确的；需要补的是测量数据的独立处理方式，而不是降低语义比较标准。

## 四、测试输出隔离应该成为“第零批”，不能只是测试迁移中的一个细节

方案其实已经意识到了测试会覆盖历史证据，第 4 节也要求重定向输出。这一点不是没写，而是**位置还不够靠前**。

目前仍有测试默认向历史目录写文件。例如 `round5_cli.rs` 在没有设置 `KERNEL_TEST_EVIDENCE_DIR` 时，默认写入：

```text
crates/kernel/evidence/round5/round5_cli
```

定位：`crates/kernel/tests/round5_cli.rs:11–15`。

维护记录还明确记载，之前的测试已经覆盖过三份旧输出，后来才按哈希恢复。定位：`内核维护/2026-09-22/记录.md:80`。

所以，“先做一点重构，然后跑完整工作区测试”在这里并不是天然安全的操作。测试环境本身就是需要先修好的基础设施。

### 我建议把第一批工作改成

统一测试输出入口，每个测试、每次执行使用独立的运行目录；黄金、历史证据和输入夹具只读。测试完成后检查允许写入范围之外有没有变化。缺少证据输出配置时，使用临时目录或明确拒绝运行，不再默认回落到历史证据目录。

然后才建立唯一的回归入口，明确列出 fixture 集、命令、比较器、字段映射和失败报告格式。

这次我没有把所有会调用固定目录写入脚本的 CLI 集成测试直接全跑；前面提到的 **134 项通过，是本次实际选择执行的测试范围，不是把历史记录中的 141 项结果冒充成重新全量通过。**

## 五、方案基本没有做性能体检，而内核已经存在值得量化的长期内存增长

目前的“代码体检”主要看告警、死代码和函数行数，但对求解器来说，长时间运行成本同样重要。

内核每次模板判断都会生成 `J|time|round|index` 这样的事件身份，然后加入：

```rust
allocated: BTreeSet<String>
executed: BTreeSet<String>
```

这两套集合会持续保留事件。关闭输出只是不把事件加入 `records`，并没有停止事件身份的注册和保存。定位：`crates/kernel/src/transition.rs::step_inner`、`crates/kernel/src/engine.rs::allocate`、`execute`、`record`。

我用 release 内核，对 `生产循环环带.json` 运行无输出模式，做了两次进程峰值 RSS 测量：

|       请求运行量 | 结果        |     峰值 RSS |
| ----------: | --------- | ---------: |
|  1,000 tick | completed | 12,548 KiB |
| 10,000 tick | completed | 22,520 KiB |

这是小规模、单次测量，不能替代完整性能分析，也不能把增长全部归因于某一个集合。但它与代码中长期保留事件身份的行为一致，已经足以说明：**`--no-output` 不意味着引擎的长期内存近似不增长。**

此外，周期搜索虽然没有保存每一步的完整键，但仍保存摘要位置及周期性完整检查点；`run_record()` 最终也会把所有 tick 记录积存在结果里。这里需要区分“减少快照开销”和“真正流式输出”。定位：`crates/kernel/src/cycle.rs::search`、`crates/kernel/src/output.rs:405–430`。

### 我建议怎么改

先补资源基线，再优化实现。至少测清不同布局规模、不同 tick 数、不同扫描轮数，以及有无缓存、有无输出、不同检查点间隔下的耗时和峰值内存。

事件身份可以进一步区分为“外部历史身份”“待办身份”“按严格时序生成的内部身份”。对内部判断事件，研究是否能用结构化 ID、时间/轮次边界或水位信息完成唯一性检查，避免永久保存每一个字符串。

**但不能直接每 tick 清空集合。**现有的重复执行、历史别名和 pending 冲突检查都必须保持。

周期搜索自身允许随搜索范围增加存储，这与无输出引擎的历史集合增长不是同一件事。前者应有明确资源预算；后者应证明保留哪些历史信息确实必要。

## 六、真正有价值的结构调整，是围绕状态不变量拆分，而不是围绕 80 行拆分

方案关于小步抽函数、保留错误优先级、不同时换算法的要求，我赞成。

但如果只是把一个大函数拆成很多仍然接收 `&mut self` 的小函数，**文件和函数变短了，读写关系未必变清楚**。现在多个文件都在为同一个大 `Engine` 实现方法，核心耦合仍然存在。

我更倾向于逐步形成下面的责任划分：

```text
Engine
├── PreparedModel    已验证且不可变的目录、几何、模板、参数和静态索引
├── RuntimeState     真正影响后继的动态状态
├── DerivedCaches    可重建的缓存和依赖失效信息
├── TickAudit        本刻事件、移动、台账和解释信息
└── RunStatus        运行中 / 已停止，以及最后完整边界
```

这不是要求一次性改成五个模块，而是要求每次提取函数时回答清楚：

> 它读取哪部分状态？修改哪部分状态？修改后哪些缓存必须失效？可能失败的位置在提交前还是提交后？

### 1. 把运行状态和序列化结构逐步分开

目前 `Progress` 使用字符串 `phase`，同时搭配多个可选字段：

```rust
phase: String
recipe: Option<String>
locked_recipe: Option<String>
remaining: Option<Time>
```

大量非法组合只能依靠运行时校验排除。定位：`crates/kernel/src/model.rs:40–47`。

更合理的方向是内部使用受约束的阶段类型，输入输出边界保留现有 JSON 协议。同时逐步把热路径反复读取的数字、操作类型和触发类型转成内部类型，而不是到处重新解释 `Value` 和字符串。

这里必须保留原有 `basis`、数字类别、输入顺序和错误定位信息。**“内部类型化”不等于删除审计信息，也不等于顺便修改接受域。**

### 2. 明确失败后状态的含义，而不是简单要求整个 tick 回滚

当前 `step_with_snapshot()` 遇到错误后设置 `halted`，阻止继续执行，但并不把本刻已做的修改全部回滚。`step_inner()` 的注释也明确采用失败后封存的策略。定位：`crates/kernel/src/transition.rs:653–675`。

这种设计不一定错误。一个 tick 中可能已经完成多个合法动作，最后在某个动作或闭包预算处停止，保留部分执行信息可以有诊断价值。

问题是，现在公开的 `state` 容易被误解为“始终可以拿来续跑的完整状态”。

我建议把两者明确区分：

> 最后一个完整、可恢复的边界状态；停止时的内部工作态及部分审计信息。

前者才能走正常 checkpoint/resume 路径，后者只能用于诊断。这样比“任何错误都整刻回滚”更符合当前实现，也避免为回滚每 tick 克隆整个引擎。

### 3. 长函数清单继续保留，但降低它的决策权重

`Config::name` 这种纯映射保留长函数没有问题。`validate_seed`、`move_channel`、`step_inner` 值得优先审查，也不是因为它们超过 80 行，而是因为它们分别承担着**装载信任边界、提交原子性和闭包/停止边界**。

方案应当按这些责任排序，而不是把行数当主要工作队列。

## 七、现有“独立重放”很有价值，但还不能替代独立语义验证

当前验证器做了不少正确的工作：来源校验、完整前缀检查、事件身份校验、物料守恒以及从周期起点重跑。这些应该保留。

但要分清两种“独立”：

**重新创建引擎、独立重跑一次**，可以检查记录是否与当前实现一致；
**使用另一套规则实现或独立不变量检查**，才能进一步发现生产器和验证器共同遵循了同一个错误。

目前 `verify_record_at()` 最终调用同一个 `run_record()`；`verify_cycle_at()` 会再次调用 `cycle::search()`，后续重放也使用同一个 `Engine`。定位：`crates/kernel/src/output.rs:607–618`、`crates/kernel/src/cycle_io.rs:231–232`、`:278–315`。

而现场 Python 完整轨迹差分，目前覆盖的是粉碎机和分流器两个场景。定位：`crates/kernel/tests/reference.rs:68–101`。

这并不意味着现有验证无效，而是意味着：**它对产物篡改和复现一致性的保证，强于对所有转移规则都实现正确的保证。**

我建议在方案中增加一张“机制 × 不变量 × 独立检查方式”的覆盖表，重点补三组性质：

| 测试方向  | 应检查的内容                                          |
| ----- | ----------------------------------------------- |
| 表示与恢复 | full/delta 往返；从完整边界恢复后的后续事件、状态和台账一致；明确累计摘要的计数起点 |
| 优化等价  | 缓存开关在逐 tick 层面一致，覆盖断边、恢复、失败尝试和容量变化，不只比较最终库存     |
| 周期投影  | 相同固定上下文中的合法同键状态，经过可执行后继后，键及声明保留的实际入库增量保持一致      |

最后一组尤其重要。**“两种状态的键相同”还不够，必须检查它们后面会不会走出不同的相关行为。**先对小规模合法状态做枚举或生成式测试，比单纯增加几个“能找到周期”的例子更有价值。

同时，当前明确保留 `diagnostic_cycle`、不把一般真实调度对应和全称覆盖冒充为已证明，这个界限应继续保留。不要借结构重构或者性能优化顺手提高证据等级。

## 我会怎样调整这份方案的实施顺序

我建议保留原方案的大部分安全约束，但把执行批次改成下面这样：

| 批次    | 主要工作                       | 通过标准                   |
| ----- | -------------------------- | ---------------------- |
| 第 0 批 | 测试输出隔离、冻结基线、A/A 自比较、明确字段映射 | 测试不污染历史；基线自身可重复        |
| 第 1 批 | 公共状态/API 校验一致性、构建来源绑定      | 已复现问题有回归测试；接口和协议变化单独登记 |
| 第 2 批 | 按只读模型、动态状态、缓存、审计划分责任       | 读写边界和缓存失效关系可审查         |
| 第 3 批 | 提取长函数、按行为搬测试、清理已证明无入口的代码   | 原方案的严格语义差分通过           |
| 第 4 批 | 长时间运行资源预算、针对实测瓶颈优化         | 正确性差分和资源基线同时通过         |
| 独立整理批 | 索引排除、证据快照归档                | 不影响活动依赖，历史内容及来源仍可校验    |

还需要在文档里明确分成两条线：

**结构等价线**：搬函数、搬测试、缩小内部职责，严格不改变行为。

**缺陷修复/API 加固线**：例如这次复现的周期键入口不一致，应该改变错误行为，不能为了通过旧版本差分继续保留问题。

这两条线可以共享测试设施，但验收标准不能混为一谈。

**归根结底，我最想先改的不是“521 行函数太长”，而是三个边界：已验证状态不能被悄悄破坏，运行结果必须绑定实际执行的实现，停止后的状态必须明确哪些可恢复、哪些只供诊断。**这三个边界立住以后，再按原方案小步拆函数，才会真正降低后续维护风险，而不只是让代码看起来更整齐。
