## 1. 实测结果

### 1.1 无输出：生产循环环带

输入为 `数据/样例/生产循环环带.json`，7 个单位、5 个判断模板。每个规模独立启动进程三次，全部退出 0、`status=completed`，完成请求的全部 tick。下表时间和峰值均取三次中位数；RSS 是 GNU time 的进程峰值，单位 KiB，不是堆内存估计。

| 请求及完成 tick | 进程墙钟秒 | CLI `elapsed_ns` 换算秒 | 峰值 RSS KiB | 三次 RSS 范围 KiB |
|---:|---:|---:|---:|---:|
| 1,000 | 0.04 | 0.037847222 | 8,392 | 8,364–8,440 |
| 10,000 | 0.39 | 0.387424260 | 22,868 | 22,864–23,004 |
| 100,000 | 4.01 | 3.955849033 | 167,716 | 167,656–168,096 |

100,000 tick 的峰值约 **163.79 MiB**。10,000→100,000 tick 的峰值增量为 144,848 KiB，即约 **1.609 KiB/tick**。循环本身约 38–40 微秒/tick；测量范围内墙钟基本随 tick 数增加，不能据此宣称已出现明显的超线性耗时退化。集合大小增长则十分明确。

三次原始结果：

| tick | 第 1 次：墙钟秒 / RSS KiB | 第 2 次 | 第 3 次 |
|---:|---:|---:|---:|
| 1,000 | 0.04 / 8,392 | 0.04 / 8,440 | 0.04 / 8,364 |
| 10,000 | 0.40 / 22,864 | 0.39 / 22,868 | 0.39 / 23,004 |
| 100,000 | 4.01 / 167,656 | 4.01 / 167,716 | 4.00 / 168,096 |

GPT Pro 的 12,548 / 22,520 KiB 两个绝对值未逐数复现；不同运行环境、工具链或分配器状态会影响绝对 RSS。本次复现的是其明确主张的长期增长，不能把两次调查的数值差异直接解释为优化或回归。

证据：[批次结果](R4-资源/main-results.json)、[全部摘要](R4-资源/summary.json)、[100,000 tick 第二次原始 time 输出](R4-资源/ring-none-100000-r2.time.log)、[同次 CLI 输出](R4-资源/ring-none-100000-r2.stdout.log)。

## 2. 集合保留方式与增长来源

代码问题先通过 CodeGraph 查询当前活动实现，`projectPath=/home/zhuran24/zmd-research-fresh/求解器`；对未返回的局部范围补读。下列行号对应本次工作树，摘录与全集合引用检索保存在 [code-audit.log](R4-资源/code-audit.log)。

### 2.1 `allocated` / `executed`：整个 Engine 生命周期保留

- `crates/kernel/src/engine.rs:47–48`：两者均为 `BTreeSet<String>`。
- `engine.rs:244–252`：`executed` 从种子已消费身份重建；`allocated` 初始并入时间线事件、pending 身份、已执行身份。
- `transition.rs:712–733`：每轮对每个模板生成 `J|time|round|index`，无条件调用 `allocate` 和 `execute`；即使模板尝试失败、没有物品移动，判断身份也已经登记。身份维护还可生成 `I|...`。
- `engine.rs:1222–1233`：`allocate` 向 allocated 插入一个字符串；`execute` 检查注册并向 executed 再插入一个字符串。正常推进路径没有删除或清空这两套集合的操作。
- `engine.rs:1236–1240`：`record` 仅由 capture 控制 `records.push`，不控制身份登记。
- `main.rs:252–274`：`--no-output` 调用 `engine.step(false)`；普通有输出运行走 `run_record`。两条 CLI run 路径使用 `Engine::new`，周期搜索才用 `Engine::new_production`，因此不能把两类模式的差异全部归因于记录开关。

若模板数为 M、每 tick 扫描轮数为 r(t)，仅判断事件数就是 `J(N)=M × Σ r(t)`。两套集合各保留这些身份，外加历史、维护及到期事件。在输入规模固定且轮数稳定时，历史项数随 N 线性增加；时间字符串长度也会缓慢增加。查重本身还要负担越来越大的树上的查询和插入。

### 2.2 读取内部大小的探针

探针用 `#[path]` 引用**未修改的生产 Rust 模块**，另加只读统计入口，未复制仓库、未改变转移函数。输出二进制为共享 target 下的 `target/release/r4-resource-probe`；它是单独编译的探针，不冒充主表中的原版 CLI。其打印和集合遍历开销也不纳入主表的性能数据。

同一环带，开启与 CLI 相同的缓存，调用 `step(false)`：

| 完成 tick | allocated | executed | allocated 内 J 身份 | records 长度 / 容量 | 普通库存内容条数 | 物理缓存项数 |
|---:|---:|---:|---:|---:|---:|---:|
| 0 | 13 | 0 | 0 | 0 / 0 | 2 | 0 |
| 1,000 | 10,013 | 10,000 | 10,000 | 0 / 0 | 1 | 4 |
| 10,000 | 100,013 | 100,000 | 100,000 | 0 / 0 | 1 | 4 |
| 100,000 | 1,000,013 | 1,000,000 | 1,000,000 | 0 / 0 | 1 | 4 |

该样例 5 个模板，1,000 tick 的有输出记录证实每 tick 2 轮，计 10 个判断身份；大规模探针总数亦符合这一增长。各测点 `pending=0`、`passages=0`，推进后 `movements=1`，最后一刻扫描轮数为 2，`executed` 中的 J 身份数等于 executed 总数。

100,000 tick 时，两个集合的字符串缓冲区 capacity 合计 **21,777,912 字节**；已占用项的 `String` 对象体积合计 **48,000,312 字节**（此平台 `size_of::<String>()=24`），合计至少 **69,778,224 字节，约 66.546 MiB**。这只计字符串缓冲区与已占用项对象，不包含 BTree 节点空余槽、节点元数据、分配器取整/管理开销及引擎其他内容。

探针此时 `/proc/self/status` 的 VmRSS / VmHWM 为 167,396 KiB，与原版 CLI 的约 167,716 KiB 同量级。集合已被直接观察到保留百万级身份，足以支持其为主要增长来源之一；未做堆分配剖析或删除历史集合的对照实验，不能给出其占 RSS 的精确比例，也不能把下界以外的差额全部记到 BTree 上。

证据：[构建脚本](R4-资源/build_probe.py)、[统计源码](R4-资源/probe_body.rs)、[构建命令、模块哈希和二进制哈希](R4-资源/probe-build.json)、[逐测点原始输出](R4-资源/probe.stdout.log)、[time 日志](R4-资源/probe.time.log)。

### 2.3 `records`、逐刻审计与完整运行记录不同

`transition.rs:675–683` 每 tick 清空 `records`、`movements`、`passages` 并新建 ledger；`cache.rs:10–12` 清空物理缓存。`records.clear()` 一般可以保留 Vec 的容量，但它不保留所有旧事件；本次从 capture=false 启动的探针连容量也一直是 0。

`transition.rs:695–699、761–765` 的闭包 `seen` 是单次 `step_inner` 的局部集合，保存当前 tick 的完整扫描边界键，函数结束后释放。它可随本刻扫描轮数增大，不能误写为跨 tick 的周期搜索 seen，也不是本次环带长期保留全部 tick 的容器。

相反，`output.rs:405–430` 的 `run_record` 建立 `rows`、`acceptance`、`manufacturing` 等整个运行的集合：每 tick 把完整记录或 delta 记录加入 rows；acceptance 每 tick 留一个字符串，manufacturing 按相关事件保存取证身份。`output.rs:467–475、502–521` 在结束时组织覆盖证据和完整 trace；`main.rs:319–324` 再把整个结果序列化为 pretty JSON 字符串并一次写文件。因而输出开销除轨迹保留外还有封套、覆盖证据、序列化临时分配等；此次没有给这些部分逐一归因。

### 2.4 周期搜索：摘要位置、State 检查点和命中后重放

`cycle.rs:661–735` 中主引擎一直存在，并保留其事件身份；此外：

| 对象 | 保留方式 | 随运行增长的条件 |
|---|---|---|
| `seen: BTreeMap<String, Vec<usize>>` | 摘要 → 所有候选位置；只在重复候选出现时恢复并比较完整键 | 没有停止/命中时继续插入摘要及位置 |
| `checkpoints: BTreeMap<usize, State>` | 初始 State，之后每 K 次完成推进克隆一个 State | 检查点随搜索前缀积累，无逐出机制 |
| `key` / `candidate` | 当前完整键、恢复候选键；命中时保存端点键 | 不把每 tick 完整键都放进 seen |
| `seed` / `last` | 起点与最近完整状态 | 固定数量；State 本身大小依布局和状态而定 |

检查点是 **State，不是 Engine**，不会每次再克隆主引擎累计的两套身份集合，不能据此推断平方级历史集合复制。

`cycle.rs:576–607` 从不晚于候选位置的最近检查点构造新引擎，重放到位置后精确比较。`cycle.rs:745–758` 命中周期后，另建周期段的 ledger、accept、combined；这部分可以随周期长度增加。`cycle.rs:822–832` 若启用 record_path，还会从 seed 重跑前缀并调用 `run_record` 保存全部记录。本次所有周期组均为 `--no-record`，没有执行这一额外完整记录分支。

未命中、固定布局时，可用以下形式估计保留量：

`主引擎历史事件身份 + O(完成 tick 数) 的摘要/位置 + O(完成 tick 数 / K × 单个 State 大小) 的检查点`。

这解释了间隔 K 对峰值的影响；也说明增大 K 不能消除主引擎的历史身份增长，且会改变候选重放距离。现有 CLI 有 ticks/sweeps 和检查点间隔控制，但这些并非直接的内存字节预算。

## 4. 额外发现、结论边界与交付清单

**额外发现（extra_issues）：**

1. 原样例集合并非都能支持长时间基准：分流器在第 12 tick 停止，需要按实际 completed_ticks 解读资源表。
2. 有输出的内存放大非常显著：环带 1,000 tick 的 full 输出约 976 MiB；delta 仍约 216 MiB。此处既包括长期记录保留，也包括结束时组织结果与序列化的峰值，未作更细分配归因。
