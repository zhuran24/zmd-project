## 2. 原因与结论边界

1. `engine.rs:31–38,58` 将模型、状态、轮询记忆、统计、生产模式和预算直接公开。外部获得 `&mut Engine` 后，可以绕过任何引擎方法修改嵌套状态。本探针是 crate 外的独立二进制，未使用库内部权限。
2. `engine.rs:904–923` 的库存校验明确拒绝 `n <= 0`。普通构造路径在 `engine.rs:357` 先调用该校验，随后还执行种子等检查。
3. `cycle.rs:307–309` 的引擎方法只调用 `production_domain()` 后进入 `encode_key`；该路径不调用完整库存校验。`cycle.rs:271` 的 D.4 分支明确依赖“完整 Engine 装载已核静态义务”。编码器会做自身的局部检查，但不拒绝本例零库存。
4. `cycle.rs:314–319` 的独立函数克隆 `Input`，将所给 `State` 写入克隆的 `raw.initial_state.nonwarehouse.value`，再调用 `Engine::new_production`。因此它重新走到了库存拒绝分支。
5. 引擎另有 `inv/progress/warehouse/active/side_index/gate_index/pending` 等派生结构和缓存；构造中的部分建表在 `engine.rs:209–244`。公开 `State/Input` 与这些结构可以被分别修改，在代码上确实缺少统一更新边界。**本实验仅重现零库存的校验差异，没有分别重现每种索引或缓存失配的运行后果。**

| 判断对象 | 结论 | 证据范围 |
|---|---|---|
| 第一节指定的三个入口差异 | 重现了 | 指定样例、生产构造、一步、单叶修改、恢复对照 |
| 其他公开字段可绕开统一更新、使冗余表示失去一致性 | 代码上成立但没重现 | 定义、建表和真实改写调用方；未逐类做运行反例 |
| 本例足以证明正常 CLI 生成错误周期证书 | 不成立 | 这个推断超出实验；正常 CLI 仍走装载／验证路径。不是对 CLI 全局正确性的证明 |
