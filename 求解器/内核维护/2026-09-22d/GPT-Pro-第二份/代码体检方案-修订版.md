# 求解器代码体检与增量维护方案

日期：2026-09-22。状态：待实施的修订方案；本文件不代表任何源码重构、测试迁移、证据搬迁或新一轮回归已经完成。

适用项目：`/home/zhuran24/zmd-research-fresh/`。主要实施范围是 `求解器/crates/kernel` 与 `求解器/crates/topology`。几何研究代码采用接口隔离，不以完成内核全面重构为开工条件。

## 1. 维护目标和边界

目标是降低一次规则修正、一次输入变更和一次几何候选接入所需理解与修改的范围，同时保持已经明确的运行行为和证据等级。函数长度、文件数量和重复哈希数量只是定位线索，不是交付目标。

当前内核应继续定位为固定布局、显式参数和受限整数运行语义下的执行、回放与诊断工具。`diagnostic_cycle` 不因重构变成正式游戏循环证明，更不变成所有参数、所有可达循环均达标的认证。

本方案不改写三份正式源、候选约束、历史证据、手工黄金或研究结论，不升级规则解释，不切换集合类型、调度算法或周期等价关系。公开 API、输入接受域、序列化格式、首错次序和停止后的行为都属于兼容性范围。源码可见性收紧、类型替换或事务语义改进如果改变上述范围，必须另立兼容性或行为变更批次，不能混入纯搬移。

不默认推倒重写，不默认新增通用框架，不把整棵证据归档作为研究工作的前置条件。没有直接收益的清理可暂缓。

## 2. 当前已识别的维护风险

### 2.1 测试输出与历史证据尚未彻底隔离

`crates/kernel/tests/revision_cli.py:12–13`、`revision_r3_cli.py:12`、`revision_r4_cli.py:11`、`revision_r5_cli.py:18`、`round6_cli.py:7` 等入口包含固定证据输出路径。`round5_cli.rs:11–14` 虽接受 `KERNEL_TEST_EVIDENCE_DIR`，默认仍写入历史目录。已有维护记录 `内核维护/2026-09-22/记录.md:80` 记载了测试覆盖旧产物后的恢复过程。

因此，“先直接跑全量测试”不是当前安全的第一步。必须先核对每个测试入口的写入范围，再在独立输出目录中建立回归基线。

### 2.2 旧二进制不等于完整旧基线

`crates/kernel/src/output.rs:157–214` 的 `fingerprints` 根据编译时的 `CARGO_MANIFEST_DIR` 找到源码目录，但在运行时读取文件并计算 SHA-256。把旧二进制复制到另一文件名，不会改变其中的源码根路径。源码原地修改之后，旧二进制可能登记新源码的哈希。

同一函数还手写列出了当前 Rust 源文件；新增模块不会自动进入这份名单。重构若搬入新文件而未同步来源清单，会留下证据覆盖缺口。

必须分别解决“实际执行的二进制来自哪一份源码”和“实现所依赖的全部文件是否纳入清单”。仅验证当前磁盘文件的哈希彼此一致，不足以解决这两件事。

### 2.3 内核的共享可变状态边界较宽

`Engine` 在 `engine.rs:19–60` 集中了输入、完整状态、轮询记忆、台账、索引、缓存、调度和停止状态；`input`、`state`、`memory` 等字段公开可变。`memory` 与 `state.logistics.poll_memory` 等还存在运行表示与封存表示的对应关系。

把长方法拆成多个仍可任意读写整个 `Engine` 的 helper，能改善导航，但未必减少耦合。需要明确每个阶段的读集、写集、缓存失效责任与封存时机。公开字段的兼容性处理应独立登记。

### 2.4 停止并不自动意味着整刻回滚

`transition.rs:654–672` 在错误后封存实例；`step_inner` 内部有多个已经发生的阶段和子动作。当前机制不是通用的“整刻事务失败则全部回滚”。重构不得把部分推进状态包装为完整可恢复种子，也不得在没有另立行为变更的情况下改成新的提交顺序。

## 3. 第一批：先让体检本身安全、可复跑

这一批优先于拆函数、搬测试和删代码。

### 3.1 固定读取集和写入集

登记活动 Cargo 成员与 targets、工具链、Cargo.lock、配置、目录、正式源、样例与测试入口。对源码、输入、黄金和历史证据保存实施前指纹。工作区存在其他并行研究产物时，记录其路径，不修改、不回退、不将它们混入维护差异。

所有 Cargo 命令从 `求解器/` 执行，显式使用已有共享 `target/`。先核对现有 Cargo 环境；环境具备离线依赖时优先使用 `--locked --offline`。不创建临时工作区内的第二个 target，不把二进制放入审阅或证据文档目录。

### 3.2 统一测试输出策略

活动测试使用统一的输出根设置，例如保留并推广现有 `KERNEL_TEST_EVIDENCE_DIR`。每次运行再分配唯一运行目录，每个测试或子进程获得独立子目录。默认无配置时使用临时目录，不能回落到历史证据目录；失败时按明确策略保留诊断产物。

Rust 和 Python 使用同一约定。测试 helper 不能在 import 时向历史目录建目录或写文件。相对来源引用以实际输入文件所在目录解析，不能依赖测试 cwd。测试仍必须调用公开 CLI 读回实际产物，不降级成 mock。

已有维护启动器可以作为暂时建立基线的隔离手段，但要记录它实际改写了哪些输出常量；不能把源码文本替换启动器当作长期测试框架。永久方案应是显式路径注入，并对“未设置环境变量”“并发执行”“不同 cwd”“路径含中文和空格”建立测试。

验收：连续两轮测试，黄金和历史证据文件的内容哈希保持；允许的写入只出现在声明的测试输出根和共享 target。不能仅凭测试退出码为零宣告安全。

### 3.3 建立来源正确的行为基线

对固定回归语料采用最小实施方式：在源码尚未修改、二进制来源已核对时，一次性生成基线输出，封存输入、输出、来源清单、工具链、命令和二进制哈希。随后再编辑源码、编译候选、与封存输出比较。后续批次以最近一次通过验收的版本重新生成并封存基线。

需要修改后仍能执行旧版本时，必须另行提供只读、最小完整的来源与运行资源目录，并核对编译路径和运行时来源解析确实落在该目录；共享 target 仍保持唯一。禁止采用“同一源码根的两个二进制文件名”来冒充来源隔离。固定语料之外补充新差分用例，需要先在真正旧环境上补基线，不能用候选自行生成旧预期。

建立实际活动源码的闭包清单：从 Cargo targets 和模块/include 关系核对，不对整个 `src` 无差别纳入测试或遗漏生成输入。每次新增、拆分、移动模块，自动检测来源清单的漏项与过期项。必要时单列来源记录格式的升级批次，保存格式变更前后的映射和证据；不偷偷改变输出契约。

### 3.4 这一批的退出条件

安全测试入口可复跑；历史证据无非预期写入；基线具备源码—二进制—输入—输出关联；新增一个参与执行的源模块时，来源完整性检查能够发现遗漏。满足后才进入结构抽取。

## 4. 行为等价的验收契约

对同一输入、配置、预算和起点，比较下列内容：

| 观察层 | 必须相同的内容 |
|---|---|
| 装载与拒收 | 接受/拒绝结果、首个 Stop 的种类、轴、位置及原因；多错误输入也不能改变首错优先级。 |
| 逐刻运行 | 事件及顺序、完整 StateSeed、物料台账、库存、进度、待办身份、轮询、门计数、冷却和缓存开关差分。 |
| 编码与恢复 | full_state 和 checkpoint_delta 解码后的全部记录、检查点导出、after_closure 续跑、最后有效前缀。 |
| 周期与证据 | 精确键、摘要碰撞处理、回放完整终态、实际入库率、预算停止、诊断范围和未完成义务。 |
| CLI 与公开接口 | 参数解析、退出码、stdout/stderr、输出文件、路径解析及公开 API 的约定。 |

JSON 对象按键集合和字段值比较，数组顺序、类型和数值全部参与比较。不能仅比较最终库存、产率或摘要。

来源路径及哈希等合法版本差异使用逐字段白名单映射，并保留原始输出。事件、basis、Stop 文本、接受域和证书等级不能当“噪声”删除。若确有计时等非确定字段，先核实实际字段路径，单独登记验收方式，不允许按名称模糊过滤所有类似字段。

有限语料差分不是对所有状态的等价证明。每次抽取还要附简短的读写顺序对照：分支顺序、短路求值、提交时点、可能失败的调用和缓存失效位置保持对应。已发现的旧 bug 另立行为批次；结构批次不顺手修复。

## 5. 按风险和责任拆分，而不是按 80 行拆分

原盘点 `内核维护/2026-09-22/functions.json` 与 `health_inventory.py` 可继续作为导航资料。超过 80 行是审查触发条件，不是强制重写条件；`Config::name` 一类封闭枚举映射可以保留。

### 5.1 优先抽取的边界

| 顺序 | 入口 | 抽取目标 | 核心安全网 |
|---|---|---|---|
| 先做 | `main.rs::run` | 命令解析与各子命令执行分开；共用显式路径和输出契约。 | CLI 全链路、退出码、不同 cwd、相对来源。 |
| 先做 | `input.rs::parse`、`interfaces.rs`、`engine.rs::validate_seed` | 按原次序分成具名验证阶段；阶段只接收必需上下文。 | 每类负例与跨阶段双错误负例。 |
| 随后 | `catalog.rs::load/build`、`topology::validate` | 分开字节/来源核对、静态数据投影、几何与必要条件报告。 | 首错、完整报告、端口与覆盖边界、独立期望值。 |
| 有需求再做 | `output.rs`、`cycle_io.rs` | 分开来源封套、编码、回放和证据范围装配。 | 来源篡改、full/delta、暂停恢复、诊断等级。 |
| 最后考虑 | `polling.rs`、`transition.rs`、`cycle.rs` | 围绕明确读写集抽取，不改变调度、提交或规范化算法。 | 失败前移、批次、门恢复、事件别名、碰撞、预算、精确终态。 |

每批只做一种主要改变。不要同时搬文件、改类型、改算法、缩小公开可见性、调整错误文案和合并测试。

### 5.2 有用的内部责任划分

在现有 crate 内逐步区分：静态已校验布局/参数、物理运行状态、调度与缓存、轨迹与证据编码。允许先只是清晰的函数参数与模块责任，不要求立刻重组全部字段，更不要求立即拆成多个 crate。

`Engine` 保留统一执行入口。对外逐步提供只读状态视图、受校验的装载和检查点恢复；对外直接改库存、几何、轮询或生产模式的调用先盘点。收紧字段可见性属于可能的 API 兼容性变更，必须明确迁移调用者，不冒充零接口变化。

JSON、`Decision`、时间与数量的无损外部表示继续保留。仅在最容易写错的运行分支考虑局部枚举或经过校验的内部值；拒收顺序和外部序列化保持。禁止一次性将全部协议模型、状态和参数轴重写为另一套类型系统。

不因为两个 crate 都读取目录，就把核验逻辑全部合并。可以共享正式字节来源及纯数据表示，但独立验证器和参考测试应保留独立判断路径，避免同一个错误同时生成结果和预期。

## 6. 测试组织和新增安全网

### 6.1 区分内部机制测试与外部集成测试

内部机制测试使用 `crates/kernel/src/tests/mod.rs` 及其子模块，按库存、制造、桥、门、轮询、仓库、事件身份、恢复、周期键和停止行为组织。转换时移走原 `src/tests.rs`，避免两个模块入口并存。

公开 CLI 与文件协议测试继续位于 `crates/kernel/tests/`，按 CLI 路径、运行记录、周期、schema 篡改和独立参考组织；共享 helper 放在不被 Cargo 当作独立测试 crate 的子目录。不要为了把私有测试搬到集成测试目录而扩大生产接口可见性。

轮次号可保留在追溯注释或测试映射中，不再作为主要导航。

### 6.2 迁移与增强分开

纯迁移批次保存旧测试全名到新全名的双射、测试清单、ignored 数、fixture 清单和原断言块。先不合并相近断言，不把计算预期改为调用被测实现。测试数保持适用于纯迁移；后续新增和有理由去重另行记录，不能把总数当作覆盖率。

### 6.3 优先补充的性质与负例

1. **首错优先级**：同一输入同时破坏前后两个验证阶段，仍返回原来的首个错误。
2. **恢复与表示等价**：连续运行和合法检查点恢复、full/delta、缓存开关、记录开关产生一致的相应观察结果。
3. **状态约束与账**：整数计数非负、容量和同种规则、配方变换后的物料守恒、事件身份闭合、停止后不可继续推进。
4. **来源与测试副作用**：活动模块未登记、旧来源或篡改来源必须被发现；测试默认运行不写历史证据。

对小规模受支持布局进行可复现的属性测试或穷举，逐步扩展输入族。随机生成必须保存种子与失败输入。现有 Python 独立参考仅覆盖有限场景，不宣称其已覆盖全部机制。

手工黄金 `数据/样例/混做粉碎机两下游-黄金轨迹.json` 保持原字节。差分失败先定位首次不同字段，不更新黄金来迁就候选代码。

## 7. 性能作为单独的验收维度

正确性优先，但维护不应在无记录的情况下显著恶化研究迭代成本。建立三个等级的测点：最小机制样例、现有密排或组合试点、真实候选出现后的整厂案例。没有真实整厂输入时必须标明缺项。

分开记录装载/验证时间、每刻与每次闭包扫描成本、周期搜索及回放成本、输出/来源计算成本、峰值内存、轨迹字节、扫描次数和回放次数。`closure_key` 每轮序列化完整动态投影、周期搜索逐刻克隆状态等是待测热点，不是已经测出的瓶颈。

先固定语料、工具链、缓存/记录模式和预算，测出波动后再设回归阈值。结构抽取和性能算法优化不放在同一批；没有性能数据时只报告未测，不宣称“零性能变化”。

## 8. 死代码和证据归档按需进行

死代码依据 Cargo 实际 targets、模块可达性、trait/Serde/宏引用、CLI/API 暴露及测试作用判断。词法单引用、pub 接口的仓库内零调用和测试专用入口都不是删除证明。不批量 `cargo fix`，不以宽泛 `allow` 掩盖问题。

先改善活动代码索引，再决定是否搬历史快照。优先 allowlist 活动 `src`、`tests` 和指定工具，并排除历史探针、复核、证据、缓存和归档；分别核对 rg、IDE、rust-analyzer、CodeGraph 实际支持的配置。不得假定所有工具都服从 Git ignore。

只有历史快照确实妨碍索引、维护或存储时才做独立归档批次。先调查活动测试对旧证据的依赖，例如 `revision_r3_cli.py:128–131`。有意使用的历史负例可保留原位，或按原字节建立具备来源说明的活动 fixture；不能按目录名字直接搬走。

归档时整树处理，保存文件内容、内部布局、权限、链接、原路径和来源映射；冲突即停，不覆盖合并，不按重复文件逐个删。迁移和回滚逐树记录；整体批次并非一个自动原子事务。归档内容哈希不变只证明搬迁保真，不证明旧结论适用于新规则。

## 9. 与几何研究的接口

几何生成器不直接修改 `Engine` 内部状态。候选先输出单位位置/朝向、配方与设定、完整自动接通关系、初态或调试义务以及来源引用，再通过受校验的适配器生成内核输入。

至少区分四种结果：必要条件放松可行、具体工程运行通过、鲁棒性证明待完成、可计入正式下界的交付物。放松可行和单次诊断运行都不能直接更新 L；UNKNOWN 和 unsupported 不能变成全局排除约束。

几何代码可在内核第一批安全工作完成后并行演进。无需等待所有长函数拆完、所有历史证据搬完或全部参数扫描机制建完。

## 10. 批次交付和停止规则

每批交付改动目的、变更路径、来源与工具链指纹、测试命令及退出码、测试映射、完整差分、首错/读写顺序审查和实际测得的性能数据。无结果的检查明确记未执行或未决。

发生接受域、事件顺序、首错、状态、账、周期键、证据等级或公开接口变化时停止当前纯结构批次，先判断是抽取错误还是应另立的行为变更。出现非授权证据写入，先保存现场和差异，再依据完整指纹恢复；不能通过重生成旧证据掩盖事故。

最低完成点是：安全回归与来源基线建立，最妨碍维护的接口/验证边界得到整理，几何候选能够通过稳定接口接入。其余清理只有在实际维护收益明确时继续，不用“全部函数短于 80 行”作为退出条件。

## 11. 审阅依据与验证边界

本方案依据已读取的原体检方案、维护记录、主要内核入口与状态/转移/周期/来源代码、若干测试入口，以及项目正式文件和思路材料。并非对全部源码逐行审计。

原维护记录报告 `cargo test --workspace` 为 141 passed、0 failed、0 ignored；这是原记录的结果，不是本方案编写时的新执行结果。独立审阅期间远程执行连接失败，新增测试命令未成功启动，没有获得新的 build、Clippy 或测试回执。本方案不能作为已实施或已验收证明。

Rust 测试目录行为可对照官方《The Rust Programming Language》“Test Organization”；CP-SAT 状态含义可对照 Google OR-Tools 官方 “CP-SAT Solver”。实现以项目实际锁定版本为准。
