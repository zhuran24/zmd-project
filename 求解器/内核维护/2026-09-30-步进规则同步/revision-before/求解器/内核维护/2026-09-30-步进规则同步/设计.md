# 内核按步进规则同步：设计

日期 2026-09-30。设计席交给实现席照做的文件。任务、范围、测试安全与核对要求以同目录[任务书](任务书.md)为准；本文件只写怎么做。规则行号指现行《明日方舟：终末地》游戏规则.txt（115 行，`c8d3a17b8830baba…`），任务行号指现行求解任务.txt（15 行，`7bec7a1edf2f4664…`）。

## 0. 总览

内核从「每 tick 按模板反复扫描到状态重复」改为「每步一次按先后逐个判定」。改动的核心是一个新的一步转移（`step.rs`）和它依赖的静态结构（元件、层数、先后、收货组，`graph.rs`）；状态去掉扫描锚点、待办日程、端口预算、断边和旧轮询级，换成步时刻、两种轮询状态和惰性的准入口窗口。输入升到 `kernel-input-v4`，运行记录升到 `kernel-output-v5`，周期证书升到 `kernel-cycle-v4`，生产键升到 `phase-cycle-key-v2`，配置换成 `内核配置-v2.json`（66 轴），目录升到 `static-catalog-v3`（加 `timing`）。旧版本的文件原样留作历史，由索引文件和 `verify_all.py` 的版本分类标明。

三个顺序工作包见 §11：包一做核心步进语义（含目录重建，理由见 §11.1）和单元测试；包二做记录、周期证书、Python 核验器、样例与 fixtures、sim2 差分；包三做其余重锁、覆盖表、规格文件与修订记录。

## 1. 规则读法定案

下列各条是实现依据。凡「无法确定」的，都作为显式输入由输入全称量化，内核不猜；凡条文最简读法已能定的，直接定。

### 1.1 步与状态时刻

- 1 步 = 1/8 tick（L25）。内核时间一律用整数步。配方时长 d tick = 8d 步；滞留 1 tick = 8 步（L23）；传输冷却 5 tick = 40 步（L37）；物品准入口窗口 5 tick = 40 步（L65）。这些数从目录读（§2.2），不写死。
- 状态只在两步之间存在。`environment.time = s` 表示「第 s−1 步已算完、下一步是第 s 步」。玩家操作、外部补给、建成都记在步与步之间（L25「玩家的操作都在两步之间」）。旧的 `before_boundary`／`after_closure` 两种锚点与中途续跑全部取消：每个状态都是步边界。
- 第 s 步依次做（L25、L36）：
  1. 边界：外部停止检查；生产抽象时成品归零代表；显式补矿事件（时刻为 s 的）入库；有电且开传输的协议储存箱冷却减 1（下限 0）。
  2. 结束到时的制造：有电且开制造、在制的机器剩余减 1，减到 0 的结束，产物进缓存格；之后对所有「完成待出」的机器试一次整批入取货物品格。
  3. 所有传送带段按 §1.9 前挪。
  4. 按先后逐个判定（§1.4—§1.8）。
  5. 开始能开始的制造（§1.10）。
  6. 收尾：准入口窗口到期的清零（§1.12）；`time = s+1`。
- 由此：开工在第 s 步末、剩余 8d，第 s+8d 步开头结束（与 sim2 相同；社区文字把结束记早 1 步，外部时刻不变，见核对-模拟2 c 附记）。协议储存箱在第 s 步传输后冷却 40，第 s+40 步再次可传。

### 1.2 元件

- 元件是一个分流器、汇流器、物品准入口，桥接器的一对平行边（竖轴、横轴各一个），或一段连续的传送带（L29）。
- 一段连续的传送带 = 沿「传送带→传送带」通道首尾相接的最长一串。每条传送带只有一个存货边和一个取货边，所以一串要么是链（有入口带和头带），要么是纯带环（没有头带）。链的外部来货只进入口带，外部送货只从头带出，结构上自动成立，装载时断言。
- 元件身份（字符串，用于输入、状态、记录）：
  - 分流器、汇流器、物品准入口：`C|<单位id>`；
  - 桥接器一轴：`C|<单位id>|vertical` 或 `C|<单位id>|horizontal`；
  - 传送带链：`C|<头带单位id>`；纯带环：`C|ring|<环中字典序最小的单位id>`。
  单位 id 只含字母数字下划线（`Geometry::build` 已核），不会与 `|` 冲突。
- 非运输单位 = 协议核心、制造单位、协议储存箱、仓库取货口。供电桩没有端口、不做任何事，不进先后。

### 1.3 层数

- 元件 C 的候选 D(C) = 经 C 的送货通道送往的元件中，自身至少有一条送货通道的那些（L28「还往下送货的元件」按结构读：有送货通道就算，不看此刻能否送出；与 sim2 相同）。非运输单位不算。
- |D(C)| = 0：层数 1。|D(C)| = 1：层数 = 该元件层数 + 1。|D(C)| ≥ 2：按哪一个数「随接通先后而定，无法确定」，由输入 `step.order.layer_choices` 给出（每个这样的元件恰一条）。不只分流器会有多个候选：桥接器一轴两边都能送时也会有，按同一条处理。
- 选定后每个元件至多一条「数层边」C→choice(C)，构成函数图。图上有环时「成环数不出来，无法确定」，由输入 `step.order.cycle_layers` 给环上元件指定层数（正整数）：每个环至少给一个，只能给在环上的元件（包括因选支而在环上的）；被给定的元件用给定值，不再沿边数。缺选支或环缺给定值 → `unresolved`（轴 `step.order`）；给多了、给错位置、候选不在 D(C) → `invalid_input`。
- 相邻两个桥接器同一轴互为送货（两条相反的通道），它们常互为候选；布局工具按 §9.4 的默认规则填选支，填出环时再给环上层数。
- 层数和先后都在装载时从整张几何图算一次。运行中通道不变（物品准入口阻断不再断开通道，§1.12；离线、调试仍然停止），所以整段运行固定。

### 1.4 先后

- 每步先判定全部元件，再判定非运输单位（L27）。
- 元件按（层数，送货通道中最早接通者的接通序位）从小到大。接通序位：先按接通时刻（步），同时刻按 `connection.tie` 给的通道全序；于是任意两条通道序位不同，不同元件不会并列。传送带链的送货通道只算头带的外部送货通道，带与带之间的通道不算（它们不是把物品送出元件）。
- 没有送货通道的元件层数为 1，判定什么也不做，也不属于任何收货组（它不往任何单位送货），它的位置不可观察；统一排在层 1 的末尾，按元件身份字典序。
- 非运输单位的次序由输入 `step.order.nontransport_order` 给全排列（全部非运输单位，不含供电桩），内核核：其中有送货通道的那些单位，相对次序必须等于按「最早送货通道序位」的次序（L27）；没有送货通道的单位，条文不给位置，按输入放在任何位置都合法。它们的判定只可能有协议储存箱的传输是可观察的。

### 1.5 判定

每个元件、每个非运输单位每步恰判定一次（L26），一次判定至多送出一件。判定前先看是否已被收货组带动判定过，判定过的跳过。

- 分流器：若自身物品已停满 8 步，按自己送货侧的轮询依次试各条送货通道，第一条送成功即止；都不成就不送。分流器不参加任何收货组（L31「非分流器」），即使只接一个出口也一样（94c5e00，madSUN 24 条放置实验支持）。
- 非分流器元件（传送带链、汇流器、物品准入口、桥接器一轴）：它的判定就是触发收货组（§1.6）。
- 非运输单位：见 §1.8。
- 被送物品要「放得下、种类合规」：运输格空（上限 1）；制造单位、协议储存箱、协议核心按原有选格与容量守卫（`Engine::target`、仓库计划）；物品准入口另按 §1.12；桥接器一轴不收刚从该单位来的物品（L24「不会移回刚离开的单位」）。

### 1.6 收货组

- 收货方 R：一个非运输单位，或一个元件。桥接器按轴分收货方（L64「两对平行边互不相干」，而元件已按轴拆分；把两轴并成一个收货方会让互不相干的两条线相互带动）。
- 组 G(R) = 以送货通道接入 R 的全部非分流器元件。
- 某非分流器元件 C 轮到判定且未判定时：以 C 为起点求「一起判定的闭包」：C 所在的每个组都触发；新拉进来的成员若还属于别的组，那些组也触发（它此刻被判定，就是那些组里最先判定的一个，L31 字面）。闭包只在一个元件有两条以上送货通道时才会扩展，现有元件里只有桥接器一轴可能如此。闭包内全部成员立即标记为本步已判定。
- 执行：按收货方被发现的次序（从 C 起，按成员自己送货侧轮询次序逐条看其送往的收货方，广度优先）逐个办理。每个收货方按自己收货侧的轮询次序，逐条看来自闭包成员的存货通道：该成员有停满 8 步的头件、该物品可去往 R、R 放得下，就移过去。一直试到这个收货方的成员通道都试过为止（「收满为止」对上限 1 的运输收货方就是只进一件）。一个成员的物品送走后，它在后面的收货方里就没有可送的了。
- 没送出的成员本步也不再判定（L31、否证-定稿第 5 条）。

### 1.7 轮询

- 「一侧」按存货侧／取货侧分，桥接器每轴各有两侧。只有一条通道的侧没有轮询状态。
- 循环侧（全部元件的两侧、非运输单位的存货侧）：通道按接通序位排成环，从「上次成功」那条的下一条开始依次尝试；从未成功时，分流器送货侧、汇流器收货侧从第二条接通的开始（L32），其余从第一条开始（`polling.initial_cursor=first_connected`，本版选值：条文「从上次成功的下一条开始」在没有上次时的最简读法）。状态只存 `last_success`（通道 id 或 null）。
- 非运输单位的送货侧：先按取货优先级分级（§1.8），同一级里先试「上次成功最早的」，从未成功的按接通序位排在最前（L32）。状态存「按上次成功时刻从早到晚排列的已成功通道表」`recency`，成功一次就把该通道移到表尾；不在表里的是从未成功的。这张表不含绝对时刻，便于周期判等。
- 何时更新：只在一次移动成功时更新，失败不动。一次成功同时更新送出方的送货侧（循环侧改 `last_success`，非运输送货侧改 `recency`）和收货方的收货侧（改 `last_success`）。分流器自己送进某单位的那一件，也算该单位收货侧的一次成功（「上次成功」按侧计，不分由谁发起；与 sim2 相同）。
- 旧语义「尝试后立刻传给下一条」「失败也前移」「双端授权」「按级记忆与回级续接」全部删除。

### 1.8 非运输单位的判定与取货优先级

- 候选物品：制造单位取取货物品格的物品；协议储存箱取编号最小的非空物品格的头一件，这件去不了就不送，不跳到后面的格（L73）；协议核心与仓库取货口每条送货通道的物品是其端口所连仓库格的物品。
- 送货次序：取货优先级把送货通道分级——直接接汇流器的通道各自一级，其余合为一级；一级的层数取其中各通道所通元件的最大层数，接通序位取其中最早的；（层数，序位）小的级先试（L33）。级内按 §1.7 的 `recency` 次序。依次试，第一条成功即止。
- 协议储存箱：有电且开传输、冷却为 0 时，在它的判定里传输；在送货之前还是之后由输入 `transfer.timing` 按箱给出（L37「与它的送货先后无法确定」）。传输按原实现「能送多少送多少」（`transfer.partial_acceptance=max_receivable`），每次尝试后冷却 40（空箱、全拒收也一样，`transfer.failure_cooldown=every_attempt`）。
- 顺带的结构事实：非运输单位只从元件收货（通道至少一端是运输单位），全部收货都发生在元件判定阶段，都早于非运输单位的判定，所以协议储存箱同一步先收后送、制造单位同一步收下的原料可在本步末开工，都是条文推出。

### 1.9 传送带段内前挪

- 条文：物品一直在尝试移动；只有「送出一个元件」要等判定（L24、L26）。所以一段链里，某格物品已停满 8 步、前一格空，就挪进前一格，入格时刻记为当步，不等判定，也不算判定。
- 实现：`settle(段)` 从头带前一格往入口方向逐格检查（头在前），能挪就挪；刚挪过的物品当步入格，不会再挪。这样头件送走后，后面停满的物品在同一步里依次跟上。纯带环取最小不动点：从每个空格往回走，前一格已停满就挪进来，直到遇到未停满的物品或另一个空格；满环不动。
- 调用时机：每步第 3 阶段对所有段各一次；此后每当一段的头件被送走或入口格收进物品，立即对该段再 `settle` 一次（与 sim2 的 eager 模式逐状态相同，核对-模拟2「即时前挪」一节）。

### 1.10 制造

- 三阶段（L25、L36）：
  - 结束：第 2 阶段。剩余减到 0 的，缓存格里的在制原料换成配方产物，阶段记 `completed`。
  - 进取货物品格：缓存格里做好的一批，取货物品格放得下（同种或空、合计不超过 50、且单位内其他普通格没有这种物品，L13）就整批进入，随时发生（L18）；阶段回 `idle`。触发点：结束之后、每步第 2 阶段末对所有 `completed` 的机器、以及每次从该机器取货物品格取走一件之后。
  - 开工：第 5 阶段。条件为有电且开制造、阶段 `idle`（即上一批已全部进入取货物品格）、存货物品格里的物品符合某个配方（沿用 `manufacturing.recipe_match_scope/completeness/quantity_match/extra_items/recipe_selection/input_slot_selection` 各轴的现值）。开工时一次用量从存货物品格进缓存格，阶段 `working`、剩余 8d。机器之间互不影响，按单位 id 顺序办理。
- 缓存格通往存货物品格的闸只在开工时打开（L18），制造需电（L36），所以停电或关开关的机器既不收料进缓存、也不开工；旧的 `intake`（停用时先把原料收进缓存）阶段取消。进行中的制造在不运行时剩余不减、恢复后继续（L20）。
- 阶段只有 `idle`、`working`、`completed`；`completed` 时剩余为 null。

### 1.11 协议储存箱的格与传输

沿用现有实现：收货放进编号最小的能放它的格，送货从编号最小的非空格取（L73）；传输按仓库可收余量逐物种尽量送（部分接收时跨编号格残留的分配仍 `unsupported`，与现状同）；冷却在有电且开传输时每步减 1（`transfer.pause=pause_with_function`）。

### 1.12 物品准入口

- 阻断 ⇔ 设了放行物品而来件不是它，或累计收下已达上限，或当前窗口已达上限（L65）。阻断时不收货，仅此而已：通道不断开，层数、先后、收货组、轮询都不变。旧的阻断原因集合、断边重建、身份维护事件、窗口到期批处理全部删除。
- 计数：收下一件时累计加 1；若窗口未开，窗口从本步起算、窗口计数 1，否则窗口计数加 1。窗口起点 w 覆盖第 w 到 w+39 步；每步收尾时，若 `w + 40 ≤ s+1` 就清空窗口（起点 null、计数 0），使边界状态唯一。累计从建成起计（`gate.counter_start=since_build`）不变。
- 「身份不符」就是对当前来件判定放不下。

### 1.13 仓库、补给、玩家操作

- 仓库身份、空格序、容量 80000、`sufficient` 模式出矿即原子回补并记账、`explicit_ore_history` 的最后一件矿检查，全部沿用。显式补矿事件的时刻改用步，在第 1 阶段入库。
- 离线、玩家拿取、调试动作、拆建：与现状一样在触及时 `unsupported` 停止（对应停止轴不变）。具体为：时间线上时刻为 e 的这些事件，以及时刻 e 大于种子时刻的建成事件，在第 e 步开始前停止；时刻不大于种子时刻的建成与接通是已发生的历史，由种子承接。

### 1.14 不移回刚离开的单位

两个单位之间的一对相对端口只能形成一个方向的通道，除非两端都是双向端口，也就是两边都是桥接器；所以只有物品从一个桥接器进入另一个桥接器后才可能有回头的通道。仍只给桥接器轴格里的物品记 `last_unit`，其他运输格不记。桥接器一轴送货时跳过通往 `last_unit` 的通道。

### 1.15 端口速率不是守卫

旧实现每 tick 每端口至多 1 件的 `port_usage` 守卫删除。它是求解约束「端口速率」，由滞留 8 步和运输格上限 1 推出，不是规则；运行中不另加。

## 2. 数据表示

### 2.1 时间值

`value.rs`：`Time { kind, value: Quantity }` 的 `kind` 改为 `"step"`，`Time::at(s)` 产出 `{"kind":"step","value":{"value":"<s>","category":"候选"}}`，`Time::integer` 只接受 `"step"`，其他一律 `unsupported("time.domain", …, "只接受整数步")`。数量 `Quantity` 不变。所有时刻字段（时间线事件、入格时刻、剩余制造、冷却、窗口起点、补矿事件与 `through`）都是步。

### 2.6 一步的算法（`step.rs`，取代 `transition.rs` 与旧 `polling.rs`）

```
step():
  s = t; check_external_stops(s); if production: represent_products()
  apply_supply(s)                               // 显式补矿，事件 supply
  for box enabled: cooldown = max(0, cooldown-1)
  for machine (unit id 序) enabled & working: remaining -= 1; if 0: complete()   // 事件 complete
  for machine completed: flush()                // 能进就进，事件 flush
  for segment: settle(segment)
  judged.fill(false)
  for subject in graph.order:
     Component(c) if !judged[c]:
        if splitter: judged[c]=true; judge_splitter(c)
        else: fire(c)
     Unit(u): judge_nontransport(u)
  for machine (unit id 序): try_start()         // 事件 start
  normalize_gate_windows(s+1); t = s+1
  return StepReport
```

- `head(c)`：元件头格（带链为头带格，其余为唯一格）里 `s - entered_at ≥ residence_steps` 的物品，否则 None。
- `accept(ch, item)`：按 §1.5、§1.12；生产抽象下目标为协议核心且物品是矿石时，在读仓库容量之前 `unsupported("cycle.domain.D2")`（取代旧 `check_production_candidates`）。
- `commit(ch, item)`：从源取（元件头格／制造取货物品格／协议储存箱最小非空格／仓库格，`sufficient` 矿即回补并记 `external_supply`；显式补矿模式下取走最后一件矿先 `invalid_input`，同旧），放入目标（运输入口格、桥接器轴格并记 `last_unit`、制造存货物品格、协议储存箱格、仓库），准入口计数，台账（`core_inbound`／`port_outbound`），两侧轮询状态更新，对源段与目标段 `settle`，源是制造单位时 `flush`，把 `{channel,item}` 追加到当前事件。
- `fire(c)`、`judge_splitter(c)`、`judge_nontransport(u)`：照 §1.5—§1.8。

- 制造：阶段、配方、剩余（已是相对量）；协议储存箱冷却（相对量）。
- 准入口：累计 = 有累计上限时取 `min(累计, 上限)`，否则 null；窗口 = `idle` 或 `{active, received, remaining: w+40−time}`。

`run --steps N`、`cycle --max-steps N`；删 `--ticks`、`--max-ticks`、`--max-sweeps`、`--no-cache`。`checkpoint` 从 v5 记录或 v4 证书取末态生成 v4 输入；`seed` 只做规范化（排序、补齐缺失的 `poll_state` 侧为 null、清到期窗口）并严格装载；`check` 改为完整装载（旧的结构检查模式只为 v2 输入存在，随 v2 删除，`Input::load` 去掉 `structural` 参数）；`request`、`verify-record`、`verify-cycle`、`verify-batch` 保留。

## 9. 与 sim2 的差分接口

### 9.1 共同投影

内核 `Engine::observe(&report)` 与 `数据/工具/sim2_adapter.py` 输出同一形状，每步一条（该步算完后的状态）：

```json
{"step": 12,
 "moves": [["C|b3", "crusher", "源矿"], ["crusher", "C|o1", "源石粉末"]],
 "transport": {"b3:transport:0": ["源矿", 5]},
 "stock": {"crusher:input:0": {"源矿": 3}, "box_1:storage:0": {"源矿": 50}},
 "machines": {"crusher": ["working", 5]},
 "boxes": {"box_1": 12},
 "warehouse": {"源矿": 80000, "源石粉末": 17}}
```

- `moves`：本步经外部通道的全部移动，按执行先后；送出方与收货方用「元件身份或非运输单位 id」。
- `transport`：有物品的运输格，`[物品, 年龄]`，年龄 = `step + 1 − entered_at`。
- `stock`：非空的非运输格（含缓存格）逐物种件数。
- `machines`：`[阶段, 剩余或 null]`；`boxes`：冷却；`warehouse`：非零物种件数。

### 9.2 适配器

`数据/工具/sim2_adapter.py <v4 输入> --steps N`，只读导入 `规则修订/2026-09-30-迟滞/sim2/simulator.py`（加 `sys.path`，不改、不复制它），输出 N 条投影的 JSON 数组到标准输出。

- 结构：用 `数据/工具/step_graph.py` 从输入的 `layout.physical_channels`、端口 id 与目录端口型求元件（与 Rust 独立实现），建 sim2 节点：带链 → `Belt(元件身份, 长度)`，格序对应链上各带；分流器、汇流器 → `Splitter`／`Merger`；未设定的物品准入口 → `Gate`；设了放行物品或上限的 → 适配器内的 `ConfiguredGate(Gate)`（按 §1.12 实现 `can_accept`／`receive` 与窗口）；桥接器一轴 → `BridgeAxis`；制造单位 → `Machine`，重设 `slots` 为目录存货格数并按 `manufacturing.input_slot_selection` 排序，`recipes` 按 `manufacturing.recipe_selection` 过滤本机型、时长 8d；协议储存箱 → `Box(wireless=开关与供电, wireless_order=transfer.timing)`；协议核心 → `Warehouse`；仓库取货口 → `Source`（物品取其指派格）。
- 连接：每条外部通道 `src.connect(dst, connected=序位)`，序位按输入时间线与 `connection.tie` 自算。
- 次序：层数用 sim2 自己的 `layers_for(nodes, choices, unknown)`（选支取 `step.order.layer_choices`，`unknown` 取 `cycle_layers`）；同层按最早送货通道序位（适配器实现 6cd6529 的这一条，sim2 本身未实现）；非运输单位按 `nontransport_order` 中有送货通道或是开传输箱的那些；作为 `World(schedule={'choices','order'})` 传入，`motion='eager'`。
- 初态：运输格 `Item(物品, entered)`，`w.t = 种子时刻`；制造、箱、仓库按种子。
- 适用范围：不含两出口的桥接器轴、不含协议核心送货、不含部分接收的多格残留（sim2 断言或未实现）；差分样例避开这些构型。

每例 `scenario.differential.steps` 取 400（c 取 800），并在 `scenario.assertions` 写出预期现象，供差分席核对。

### 9.4 默认选支

`step_inputs.py`、`migrate_input_v4.py` 与 Rust 测试辅助生成输入时的缺省：选支取「结果层数最小的候选，平手取身份字典序最小」（对应游戏里分流器几支同终点时按近的数，见仓库根 不补的设定.txt）；成环时给环上字典序最小的元件层数 1；`nontransport_order` 先排有送货通道的单位（按最早送货通道序位），再按单位 id 排其余；`transfer.timing` 每箱 `before_send`。差分样例在描述里显式给这些值，不用缺省。缺省只是一个代表值，不宣称全称。
