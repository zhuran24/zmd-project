讲理由 / 解释一个建在内部概念上的技术决定时, 别把我 (作为天天泡在仓库里的 coding LLM) 对大项目的全局背景, 默认成用户也具备。用户作为人类, 对这种重型项目只能看到极小一片; 我了解 / 看到的远比他多, 于是我常把一堆内部词汇 (cut / cert / validator / oracle / replay / FP=0 / source-of-truth / phase 编号 等) 当成共享前提而省略地基, 结果理由对用户全成黑话、完全看不懂。

**Why**: 这是"知识投影"—— 我误把"我看到的"当成"用户看到的"。用户原话: "很多你自己了解的背景, 你把它当成了我也了解的东西, 所以你没有说; 但我几乎完全不了解, 导致完全看不懂你说的理由"。根因不是表达啰嗦, 而是我**没意识到自己在假设共享上下文**。

**How to apply**: 解释一个依赖内部概念的理由前, 先**从零搭共同词汇** —— 每个关键术语第一次出现就用大白话定义 + 给一个具体小例子, 再讲理由。宁可显得啰嗦也别跳步; 用户已明确"清晰在我们这个项目里最重要"。区别于 [[clarity-over-brevity]] (那条讲 HOW: 展开而非缩短): 本条讲 **WHY 我会漏** (没察觉在假设共享背景) + **触发场景** (重型项目 / 我可见范围 ≫ 用户可见范围时, 默认拉满"先搭地基")。
