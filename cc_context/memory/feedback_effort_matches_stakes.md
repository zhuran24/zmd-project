**用力程度（多代理编排 / 对抗核验 / 穷尽 stack / 独立 backstop / 外审 的强度）要匹配任务实质——做错代价 × 不确定性 × 规模——不是默认拉满。**

## 为什么这条要存在（病根 + 活教材）
记忆树里一堆"踩油门到底"的规则各自对、但**合力 + 绝对化措辞**会把简单任务推成巨型工程，而且**没有一条统一的"用力匹配 stakes"调节器**压着它们：
- [[optimization-strategy]] 「stack 全上、过度优化不存在」——scope 其实是**求解器性能优化方向**，不是所有任务。
- [[verification-independent-backstop]] 「验证类必派独立 backstop / workflow」——scope 是**高风险 soundness 验证**（长上下文漏看会出 false-CERTIFIED）。
- Ultracode 默认偏好「实质任务默认多代理 + 对抗核验、token 不是约束」（见 [[agent-vs-workflow-dispatch]]）。
- 再加十几条「默认怀疑 / 先核实 / 不盲信 / re-audit 闭环到零 finding」刹车规则。

**活教材（2026-06-14）**：owner 只问了句"记忆树有什么要改进"，CC 起了 **3 个 workflow + 一个 4 人对抗议会**去审一棵个人记忆树——用力过猛的标本。讽刺的是那个议会自己的 T10 维度**当场诊断出**这个失衡（刹车规则 ~14 条 >> 油门规则 ~5 条，合力把低 stakes 任务也推满）。

## 怎么用
1. **先估 stakes 再选力度**：做错代价低 + 不确定性低 + 规模小 → 主会话自己做 / 单 Agent；做错代价大（certified soundness / 不可逆 / 外发）或规模超单上下文装不下 → 才上 workflow / 对抗核验 / 外审。
2. **「能更彻底」≠「该更彻底」**：彻底有成本（token / 时间 / 把简单事搞复杂 / 甚至把对的改坏）。彻底到匹配 stakes 就停，别因为"还能再加一层验证 / 再起一个 agent"就加。
3. **Ultracode / 穷尽 / 对抗核验是工具不是默认**：Ultracode = "token 不设限地把力气花在**值得的地方**"，不是"无脑给每件事上多代理"。对的工具配对的活——精细编辑配串行、广度搜索配 fan-out、高风险判定配对抗。
4. **上面那些"踩油门"规则别脱离各自 scope 泛化**：optimization-stack 限性能优化方向、backstop 限高风险验证；它们不是"所有任务都全上 / 都派 workflow"。

## 和「别过度保守」是一对，不矛盾
owner 另有一套规则治反向病——「放开就是没限制 / 该几个就几个一次发齐 / 别替用户保守 / 已设目标=站着的授权」（全局 CLAUDE.md）。那条治"该重却退缩、小批自我设限"；本条治"该轻却用力过猛"。**统一判据 = 用力程度 = 任务实质要求的那个量，不多不少**：该重的别保守退缩，该轻的别用力过猛。两条都指向同一个靶心——匹配实质。

## 它是判断类元规则（成文治不住、靠自反驳）
和 [[memory-value-yardstick]] / [[root-cause-over-symptom]] 同类：这是"判断该用多大力"的纯判断，stamp 引擎焊不了，成文只是**引信**——涌现一个"上 workflow / 多加一层验证"的冲动时，停一拍自问"这任务的 stakes 真需要这个吗"。别指望"写了就不犯"（连写它这次都是被 owner 点出来才反应的）。
