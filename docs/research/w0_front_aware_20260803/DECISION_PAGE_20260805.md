### ④ band22 条带路线 —— 从「备胎」升到**默认主攻**

**发生了什么**：三处承重洞全部闭合，而且不是话术闭合。它的手法是**换骨架把条件设计掉**，

**我方复核到什么程度**：266 个设施与冻结清单双射、3,644 个占用格两两重叠 0、

### ③ 上界证书机器（Lagrangian / 列生成）—— 实验就绪，消费前三道门：status 守卫 + HEAD 重打/重跑 + 15-branch 完整性门

**发生了什么**：对方交了一份可跑的 harness，我方在目标机上实跑——
`10/10` 单测通过（且验过非空洞：把包改名后测试真会红），
关键 pilot **逐位复现、连模型签名 hash 都字节相同**。【实测】
数学席从头重推了对偶、逐支重算了阈值：**如果** `CLEAN 无孔上界能压到 142` 且其余八支的前提都成立，
统一上界就从 3388 降到 **3324**，低于 3325 即过证书线；143 则给 3340、差 16 格不过线——
九个分支逐支复现。【复现】
**口径**：3324 是一个 **cap-3 scope 下的条件会计阈值 / 候选证书目标**，不是现成的 formal
certificate——那个 142 还没证出来。

**三条必须先处理的**（缺一不可，全部在消费任何 GO/NO-GO 读数之前）：

1. **一行补丁**（阻塞）：现在的代码把求解器返回 `INFEASIBLE` 的跑当成「上界 = 0」吃进记账。
   我方实测 ortools 对不可行的最大化模型确实返回 `0.0` 而不是负无穷【实测】。
   后果是：任何一次**伪不可行**（cap 写错、模型 bug）都会让分析器直接吐出
   `GO_CERTIFICATE_ALREADY_REACHED` ——凭空造出一张假证书。修法是一行：
   消费 bound 之前拒收 `INFEASIBLE`/`MODEL_INVALID` 的记录。
2. **我方的打包错误**（阻塞）：我方 08-04 上午发给它的可跑包，用的是**当天上午修复前**的
   连通语义（修复 `4497e05` 落在 05:49，打包在 11:28）【实测】。所以这一包里的每个数字
   都建在一个已被取代的模型上。要么在 HEAD / strict 语义上**重打 bundle 并重跑**，
   要么把结论显式限定到旧语义。这不是「打包一下」——是整套读数要重出。
3. **15-branch 完整性门**（阻塞）：`max_closure` 对 `best.values()` 取 max，
   若某个**非 critical** 任务崩了或没写进 manifest，样本池会悄悄变小而代码照样判 `NO_GO`。
   判 NO-GO 之前必须先断言 **S1 的 15 个 branch 记录全在**。

**一条被对方自己漏说的好消息**：`cap=3`（每房最多 3 根杆）本来就是当前待判定档位的四条限制
之一。也就是说**要证的命题本来就是 cap-3 命题**，所以一张 cap-3 口径的 3324 阈值正落在靶心上，
**不是降级品**（前提仍是那个 142 得先证出来）。对方出于谨慎按 no-cap 走主臂、因此给了更保守的 141 门槛，但它没说破这一点。

## 4. 我方默认建议

**主攻 ④，并行开 ③ 的便宜门，① 暂缓，② 等读数。**
（这是「先把账本上的下界一端做出来」这个目标下的排序；若 owner 的目标是直接冲 1188 级，

结果就是 §1 那张表【实测，收据见 §7】。这一步不需要任何授权，已经落地。

**第二步（主攻）**：把 band22 见证推到能过官方 checker。拆成三件事——
- 写一个「对方的 witness 格式 → 我方 checker schema」的转换器（工程活，无新数学）；

  版本/资源映射**，然后**实跑 checker**（§6.1 第 1 条，这条是纯核对，不需要 owner）；
- 两条已被权威定死的语义（inactive front、供电覆盖）按现状走，不当未决点（§6 说明）。

过了 checker **只拿到 candidate 材料**，还要走 supervisor seal + 发布 + owner gate 才谈得上
登记 `L`。不过 checker 这一步本身也有价值：**它会告诉我们官方语义和咨询合同语义差在哪**，
这个差值以后每一轮外脑咨询都要用。

**第三步（并行，半天）**：③ 的 status 守卫 + HEAD 重打 bundle 重跑 + 15-branch 完整性门，
再跑一次 20 分钟协议（传 `--max-parallel 1`），拿一个 GO/NO-GO 读数。
这条不占 ④ 的人力；内存方面 **D1 pilot 实测峰值 256 MB**【实测】——
那只是 pilot 的一支，**完整协议的峰值未测**，别当成整套协议的保证。

**为什么这么排**：

1. **④ 是唯一一条手上有正面物证的**。另外三条都是在攻「证明装不下」或者「测量还剩多少没跑」，
   ④ 手上已经有一份摆得下的东西了。
2. **④ 最便宜的那部分是纯工程**。转换器 + 跑 checker，不需要新数学、不需要重生成 catalog、
   不需要改登记档位。
3. **④ 剩下的卡点是可做的核对，不是求解**。`matching_map_boundary` 的映射核对 + 跑一次
   checker，都是我方自己能做完的活。
4. **③ 已经就绪且便宜**，半天能拿读数，不抢资源。
5. **① 这一小时/十一小时买的是「G1 内部」的信息**，而当前目标是先把下界那一端做出来，
   所以它排第二——不是它的信息量变小了。

**这条建议不覆盖的**：

- **它不会合上钳口**。哪怕全绿，也只是 `L = (42, 6)` 对 `U = (1188, 18)`。
- **checker 绿 ≠ 有 `L`**。那之后还有整条认证链和 owner gate。
- **它不保证 band22 能过官方 checker**。若官方语义在某处比咨询合同严
  （如禁止未激活口的 front 压机身——按当前权威**不禁止**，但映射层未验），
  那 11 处要重排；先失效的是 **25 根这个可行上界**，由 56 个 anchor 划分给出的下界不会
  自动变小【实测：那 11 处里有 2 处的杆就在最小覆盖里】。
- **它不代拍任何 owner-only 的闸**（§6）。
- 若 owner 认为「有个很弱的 `L` 也没用、只想要能抬到 1188 级的路」，
  那正确的排序是 ③ 优先（证明这档位无解 ⇒ 换档位）+ ② 松绑，④ 只留作方法论种子。
  **这个取舍我方不代拍**，因为它取决于你要的是「账本上先有两端」还是「直接冲最优」。
