# 翻案文书：(b) → (a)-修正 —— 模型的门口排他是对游戏语义的正确保守编码

2026-08-06 晚。前序：`COUPLING_VERDICT.md`（原判 (b)）及其批注一/二/三。
触发：owner 补足游戏语义定谳（机器入口无选择权＋缓存格类型锁＋耗尽照单全收），
并指出主线此前已获答过一次、在上下文压缩中遗失。

## 一、原判与翻案点

原判 (b)：官方 routing 模型「终端 front 格对外商品排他」比 canonical
`mixed_commodity_flow`（混流无例外合法）更严 = 模型保真缺口。

翻案依据——把 owner 定谳的输入口机制放进最坏情况分析：

1. 裸机器口**不拒收**：错货到口前只是**等待**（区别于限制口的瞬时拒收+回退）；
2. 缓存格一格一种货，机器持续消耗 → 空窗必然出现 → 空窗期错货**照单全收**；
3. 吞入后：能加工 → 产物污染下游；不能加工 → 槽位中毒、机器饿死。

⇒ 混流到达任何机器口，在无限时间线上**必然**发生吞错货事件。认证要求最坏情况
安全，故「混流经过门口格」在游戏真语义下不是合法布局性质。**模型禁它禁对了**；
写宽的是 canonical 的混流条款（缺终端/门口例外），以及主线昨日「混流可路过门口、
机器只吸自己要的货」的推理（吸取式机制是走私进来的假语义）。

## 二、三颗钉子（终裁前置证据，全部到位）

1. **分流器对「堵住但非拒收」的出口会回退吗？** 模拟器语义收据（08-05 兄弟线
   准入口案）：有下一条出边就走、没有才队头卡死 ⇒ 支持「会回退」。注意回退
   **不改变**结论 1-3：回退只保护走廊流动性，空窗吞入照样发生。
2. **空缓存格照单全收错货吗？** owner 逐步推导定谳：会（机制见上）。
3. **限制口在 canonical 设施宇宙里吗？** 不在，且是**记录在案的刻意省略**：
   canonical 原文（rules_audit_20260718/00 §3.7 交叉核对条目）——"The 1x1 item
   admission port (straight pass-through with item filtering) exists in game v1.1
   but is deliberately NOT modeled: geometrically … equivalent to a straight belt
   …, and its filtering function is throughput-scope (OUT-OF-SCOPE). Omitting it
   cannot exclude [solutions]." 该省略理由在「混流无例外合法」的旧读法下成立；
   在修正语义下需要重述（见 §四.3）。

## 三、终裁

**(a)-修正**：官方 routing 模型的 front 排他 = 游戏语义的正确保守静态抽象；
不存在需要修模型的保真缺口。需要修的是文档与规则文本：

- canonical `mixed_commodity_flow` 应补终端条款（混流仅限非门口格；门口格/
  终止段必须纯流——除非未来把限制口建模进来）；
- band22 三见证（R1/R2/R3）**真死**：其路网依赖「分流器筛货/机器挑货」假语义，
  官方门两次 5.67h 拒收是模型正确行使职责。④路对它们的登记结论从「模型语义下
  不可注册、canonical 语义下未裁决」收紧为「双语义下均不可注册（canonical 按
  修正后读法）」；
- 严格 (42,6) 的 L 侧问题实质变难：门口格纯流=末段专线，1 宽走廊网络中代价
  极高。三份独立设计全部绕不开门口混流，构成「无混流则难/不可行」的负面信号
  （非证明）。

2. **昨日对 owner 的口头汇报勘误**：「模型比规则严=地基裂缝」的定性作废；
   「可行性/下界安全、上界/不可行性带条件」的方向分析在 (a)-修正下**不再需要**

3. **新挂账——限制口省略理由的重述**：原「省略不排除任何解」在修正语义下不再

   作用域声明；(ii) 远期把限制口建模（新设施类型+筛选语义，与 P2.0 流量层

4. **纪律记账**：本案从 (b) 到 (a)-修正 的反转根因 = 主线遗失 owner 已给答案
   （压缩事故）+ 用限制口行为走私裸机器口行为。已立卡

## 附录：速率引理（2026-08-06 晚，owner 提问「纯流是否可从规则推出」的分析产物）

**数据源**：`src/preprocess/demand_solver.solve_demands_exact`（Fraction 精确账）＋
`PreprocessContext.belt_capacity_per_tick=1, tick_interval_seconds=2`（=0.5 件/s，
与 owner 实测 2s 头距及 IP `log_admission=30/min` 三方一致）。

**引理（中间产物纯流强制）**：满产状态下，除两种终端成品外，每条最小分配下的
运输道残余速率 ∈ {5/6, 11/12, 19/22, 21/22, 10/11, 1(满)}，任意两条残道速率之和
> 1 ⇒ **任何两种中间产物（含种子回路）不可能共乘一条道**——纯流不是风格选择，
是皮带帽算术的强制结论。混流仅存的速率合法域：qiaoyu_capsule（11/60/机）与
valley_battery（1/5/机）——两种终端成品去 protocol_core 的运输段（六台产机各自
sub-lane 可并流，如全部胶囊 11/20 并一道、胶囊+单台电池 3/4 并一道等）。

**推论**：①模型的 front 排他对中间产物是 **WLOG 无损**（真实最优布局本就必须
纯流）；②限制口建模的必要性从「肯定要建」缩水为「仅核心前混流分拣一个场景」，
且若 protocol_core 输入缓存为多槽分型（能直接混吃），则连这个场景也不需要；
③唯一新定谳点：**核心口的吞取语义**（多槽混吃 or 单槽同污染机制）——owner
游戏实测或模拟器判例可裁。混流省道上限量化：胶囊/电池 6 条 sub-lane 并至 2 条，
省约 2-4 条走廊道，仅影响核心邻域几何。

**边界诚实**：全局消耗账与 flows 在循环商品（buckwheat/sandleaf 族）上采用不同
簿记（cycle 内部流单列），本引理只依赖单机残道速率（已逐配方抽验），不依赖全局
totals；认证谓词本身不含速率——引理属「真实运行层」论证，若要在认证叙事中引用
（如把 front 排他从保守升格为 WLOG），需把速率语义作为 scope 声明写入 canonical
修正批。

## 附录补遗（owner 终定谳，2026-08-06 晚）

核心口吞取语义已闭：owner 定谳「**所有连着仓库的输入口都吃**（混流）」——协议核心
与协议箱（箱→仓库无线段）均为仓库系口，逐类型开槽混吃安全（与 IP warehouse-submit
`slot:${itemType}` 判例一致）。口岸语义终版二分：机器口=单槽污染机制（混流不安全，
模型 front 排他=正确编码）；仓库系口=逐型分槽（混流安全）。

**残余保真注记（新，被速率引理钉死上界）**：官方模型 binding 槽位为单商品制，
不能表达「单个核心/箱口同时吃两种成品」；由速率引理，该表达力缺口仅影响
胶囊+电池终端段的 2-4 条道。处置选项：(i) canonical 批中作 scope 声明（推荐——
认证作用域=每仓库口单商品的游戏片段）；(ii) 远期 generic 槽位扩展为商品集合
（与 P2.0 相邻）。限制口建模必要性终裁=**零**（中间产物算术禁混、仓库口天然混吃、
无需分拣装置）。

## 附录补遗二（owner 精度修正，2026-08-06 晚）

「仓库系口」准确范围=**有线连接仓库的存货口**（边界仓储口、核心）。协议储存箱
**除外**：无连接、仅无线传送缓存入仓库，本体走机器机制——6 缓存格动态定型
（一格一种），占满 6 种后第 7 种堵门 ⇒ 箱=有界混吃（≤6 并发类型）。前文把箱归入
「逐类型开槽混吃安全」系笔误，以本条为准。胶囊+电池→核心结论不变（核心属有线
仓储口；即按机器机制读 2 型亦安全）；限制口终裁=零不变；canonical scope 声明
措辞按三分法修正：有线仓储口=无限混吃 / 协议箱=6 槽有界 / 机器口=配方槽污染。
