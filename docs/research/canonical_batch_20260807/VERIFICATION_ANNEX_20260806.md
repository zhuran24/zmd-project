# 一、反例席裁定书（原文）

# 反例席裁定书：对《游戏语义最小公理系》的逐条驳斥

**本轮我实读了上游源码四处**（`/home/zhuran24/upstream/IndustrialPlanner`，HEAD `7b946c16`）与 zmd 侧 `src/models/routing_subproblem.py` 两处，用来把三条最重的反驳从「证据清单转述」升到「一手实读」。以下每条标了证据等级：**[实读]**＝本轮亲自打开源码核对；**[清单]**＝仅依据提案附的证据清单。

## 摘要：三条 kill shot

1. **A2「内容盲」是假的**——模拟器的接收端仲裁 `selectAcceptedSourceForEdge` 逐个上游槽试、跳过自己容不下的那些，**这正是「机器只吸自己要的货」**，即 band22 被判死刑的那条「假语义」。**[实读]**
2. **A3 与 A4 直接互斥**——A3 说「类型锁唯一的永久钉法是人工 slot.lock」，A4 说仓库槽「预锁定」。两句不能同真；根因是 A3 把模拟器的两个字段（动态 `itemType` / 静态 `lock`）揉成了一个「类型锁」。**[实读]**
3. **推导 #2「箱 ≤6 并发类型安全」推不出来**——协议箱是 **6 个独立槽位组**，A3 的组内互斥**不跨组**，同一种货可以占掉多个槽，5 种货就能占满 6 格。**[实读，附源码逐字]**

另有 **A4「行为只作用于自己的缓存格」被它自己引的四条证据推翻**、**推导 #8 只证了 sink 侧而模型对 source front 同样排他（未登记的过严面）** 两条重伤。

## A1 守恒·单向公理

**驳 1.1（措辞过强）「不生不灭」在设备内即为假，而 #1 的推导恰恰要用到它为假。**
- 反例：加工行为消灭输入、创造输出（A4 自己把「加工」写进设备行为）。推导 #1 的结论分支「能加工 → 产物污染下游」直接依赖「错货被消灭、新物品被创造」。
- 另一反例：`ignoreStock` 链视为无限来源、搬出不扣库存＝**凭空生**（SIM-M16，`runtime-slot-access.ts:126-131/442`）。提案以「调试开关」排除，但 SIM-P08 把它写成**取货口的正式功能**（`entity-definition.ts:945-953`「ignoreStock 可设为 true 实现无限取货」）；而 zmd 的边界仓储口正是按这类取货口建模的——模型里矿石本来就是**无中生有的源**。
- 建议措辞：A1 只对**设备间搬运边**成立，改为「跨设备搬运不生不灭、不逆行；生/灭只发生在两处：设备内配方转化，与网络边界（源/汇）」，并把「配方转化」单列为缺失的 A9（见文末）。

**驳 1.2（措辞过强）「搬运失败的唯一表现＝该边本 tick 不动」不唯一。**
- 反例：① 堵塞自动清理直接销毁（SIM-M29）；② 产物放不下时进 `waiting-output`、设备被标 block，物品既不在上游槽也没动边（SIM-M27，`stage-1-advance-devices.ts:135-146`）；③ 部分提交（SIM-M15）＝同一条「边」半动。
- 建议措辞：删「唯一」，改为「失败的**缺省**表现是…；已知例外三处（清理销毁／waiting-output 滞留／部分提交）」。

**驳 1.3（权威序倒置）用模拟器改写了 owner 的原话。**
- 冲突：owner 定谳 OWN-M01 与 OWN-M06② 都用了「**回退**」一词（「限制口的瞬时拒收**+回退**」「偏好方向不通时瞬时回退、零耗时」）。A2 的反证检查用 SIM-M11 把「回退」重新定义成「不放行、留在上游」。
- 但 W-SOP-01/OWN-U09 定的权威序是 **owner 游戏定谳 > 模拟器规则层**。用低阶证据改写高阶证据的措辞，方向反了。
- 建议措辞：A1 不要断言「不存在退回通路」，改为「模拟器扫描范围内无反向搬运（SIM-U05 自标非穷举）；owner 措辞中的『回退』语义未经澄清，列入残余待 owner 一句话定谳」。这是一个 5 秒就能问掉的问题，不该在公理里替 owner 定死。

## A2 内容盲调度·入口唯一筛点公理

**驳 2.1（kill shot，公理直接为假）接收端仲裁按物品内容挑上游槽。[实读]**
- 反例源码逐字（`src/simulation/runtime/stage-3-layered-reverse-solve.ts:457-495`）：
  ```ts
  for (const sourceSlotId of getReadableSourceSlotIds(options.sourceNode)) {
      ... const targetSlotId = findInputSlotForItem({...});
      if (targetSlotId !== null) { return { sourceSlotId, targetSlotId, itemType }; }
  }
  return null;
  ```
  上游节点有多个可读槽时，接收端**逐个试、跳过自己容不下的**，取第一个能落位的。若上游槽 1 是错货、槽 2 是正货，接收端**直接拿走正货、把错货留下**——这就是「机器只吸自己要的货」。
- 提案引 SIM-M09 作为「零选择权」的证据是**错位的**：`findInputSlotForItem` 签名没有配方参数，只证明**单次落位测试**与配方无关，不证明**仲裁不挑**。挑选发生在它的调用者那一层。
- 与 0 节 ① 裁定的冲突：裁定说「推/吸在可观测层面不可分辨」。**可分辨**——pull 有可观测签名，即上述「多槽源上的择货」；push 语义下发货方不知道收货方能不能收。
- **不翻案的诚实边界**：合法布局里机器输入边的上游必是物流件（A5 禁直连），而物流件全是 `share-cap` 1 槽（SIM-P03/P04/P05/P06/P07），单槽无从可选——所以 #1 的**结论**仍站得住，band22 仍死。
- 建议措辞：A2 改为「**在单槽物流件构成的输入链上**，调度无从按内容选择；一般情形下接收端仲裁按『能否落位』择上游槽，因而**在多槽源节点上事实上具有选择性**」。同时 #1 必须显式补进两个真前提：**A5（禁零格直连）+ 物流件单槽（参数）**——错货必被吞的真正原因是「门口那一格只能装一件」，不是「调度盲」。

**驳 2.2（枚举不全）「全网只有三个按内容判定的点」少了第四个。[实读]**
- 反例源码逐字（`runtime-slot-access.ts:247-254`，位于 `findInputSlotForItem` 最开头）：
  ```ts
  // 运输组件域锁检查：若该节点所属组件已锁定为其他物品类型，拒绝接受。
  const componentId = device?.transportComponentId ?? null;
  if (componentId !== null) { const domain = ...; if (domain !== null && domain !== options.itemType) return null; }
  ```
  这是**跨多格连通分量级**的物品类型锁（SIM-M19），既不是槽级类型锁（A3），也不是域位标志（Solid/Liquid/Gas 是物质相，不是具体 itemId），更不是人工锁或准入规则。
- 次要遗漏：`excludedItemTypes` 是**节点级**快照（`stage-2-build-solve-graph.ts:32-45`，本轮 grep 确认 `for (const slotId of node.slotIds)`），与槽级锁是两个机制。
- 提案可辩「本项目 19 商品全固体、不走管道」——但公理写的是「**全网**只有三个」。
- 建议措辞：「四个点：准入规则／缓存格类型锁／运输组件域锁（管道族，本项目不适用）／域位标志与人工槽锁」，并把「本项目不适用」写成 scope 而不是删掉。

**驳 2.3（措辞过强）「域匹配且有落位槽就必收」。**
- 反例：还要过组内互斥快照与剩余容量（`slotState.count === 0 && slotState.itemType === null && !excluded.has(...)` 且 `getRemainingCapacity(...) > 0`）。有空槽但该类型已被组内另一槽持有时，**整节点拒收**（SIM-M07）。
- 建议措辞：「有**可容纳该类型的**落位槽就必收」。

## A3 缓存格公理

**驳 3.1（kill shot，与 A4 硬冲突 + 字段混淆）「类型锁唯一的永久钉法是人工 slot.lock」为假。[实读]**
- 反例：仓库槽出厂即 `lock: item.id`（SIM-M13，`topology-compiler.ts:468-481`），是**编译期预锁定**，无人工参与。A4 自己也写「每槽**预锁定**该类型」。两条不能同真。
- 更深的根因：模拟器有**两个字段**——动态 `itemType`（`count===0` 时置 null，`runtime-slot-access.ts:443-447`）与静态 `lock`（`slotCanHold` 里 `slot.lock !== null && slot.lock !== itemType → false`，`:1336-1349`，**从不因清空而复位**）。A3 把两者合称「类型锁」，于是「空格类型锁自动清空」这句在仓库槽上直接是假的（仓库槽 count=0 时 `lock` 仍钉死）。
- 建议措辞：拆成两条——「**动态定型**：空槽被首件钉住 `itemType`，count→0 自动清空」与「**静态锁 `lock`**：三个来源（出厂预锁定＝仓库槽／人工配置／—），永不因清空而释放」。

**驳 3.2（句内自相矛盾）「空格…来者不拒」与同句「组内两格不得同持同一类型」互斥。**
- 反例：组内已有 A 且满容 → 空格存在，A 仍被整节点拒收（SIM-M07 逐字：「匹配成功但满容 → 立即返回 null（不另找空槽）」）。
- 建议措辞：「空格对**域匹配、且该类型未被本组其它槽占用**的物品来者不拒」。

**驳 3.3（范围过窄）组内互斥的「组」边界未定义，而下游推导全押在这个边界上。**
- 见下 #2 的驳斥：模拟器的「组」＝一个 `storageSlotGroup`＝一个求解节点，协议箱有 6 个。公理不写清「组」是什么，#2 就无从推。

## A4 设备构成公理

**驳 4.1（公理被自己的支持证据推翻）「行为只作用于自己的缓存格」为假。[实读]**
- 四个反例，全部出自 A4 自己列的支持证据：
  1. `WarehouseSink` 把落位目标改写到**仓库设备的槽**（SIM-M14，`runtime-slot-access.ts:256-265/342-353`，本轮实读确认它在遍历本设备槽位**之前**执行）；
  2. `r_warehouse_submit` 把箱的本地槽搬进**仓库的槽**（SIM-M15，`warehouse-submit.ts:47-55`）；
  3. `share-all` 代理链把本地槽映到**别的设备的槽**（SIM-M16）；
  4. 暗管 loader/unloader 跨距共享一个槽（SIM-M30）。
- 建议措辞：删掉这半句，或改为「行为作用于**其绑定的槽位集合**（可经 share-all/WarehouseSink 代理到其它设备，含仓库）」。

**驳 4.2（措辞过强）「容量无限」「结构上永不拒收」两处都是有限/有条件的。[实读]**
- 反例①：容量是 `Number.MAX_SAFE_INTEGER`＝有限；SIM-M15 里明写着「仓库容量不足时移动可容纳数量」的分支——**代码里存在拒收路径**，只是实践不可达。
- 反例②：`findWarehouseSinkTargetSlotForItem` 在 `topology.slots[warehouseSlotId] === undefined` 时返回 null（SIM-M14 逐字），随后回落到**本地 1 槽 × 1 容量**缓存。即协议核心「永不拒收」的前提是「该物品在仓库已开槽」，不是结构性无条件。
- 建议措辞：「容量 2^53−1（实践不可达）；对**已在仓库注册开槽**的物品结构上不拒收」。推导 #3/#12 同步加这个前件。

**驳 4.3（错误归类）把边界仓储口并进「有线仓储口＝无限混吃」是空转，且与模拟器实现不符。**
- 反例①：边界仓储口 `generic_input_slots = 0 / generic_output_slots = 1`（P-UTIL-01，`preprocess_plan.json`）——**它没有输入口**，「混吃安全」对它没有内容。
- 反例②：模拟器同类 unloader 的仓库连接是**玩家在 warehouse-item-link 面板逐槽配的单条 share-all 链**（SIM-P08 `entity-definition.ts:945-953`，本轮实读见注释「通过 warehouse-item-link 面板将槽位连接到仓库」），一个口对应一种物品，不是「按类型自动开槽」。
- 连带后果：**残余 5.2#3 与 U-01 的范围被夸大了**——「front 排他对有线仓储口过严」只可能对**协议核心 14 进**成立；边界口本就是单商品口，模型对它 front 排他不过严。
- 建议措辞：三分法的「有线仓储口」在**输入侧**只剩协议核心一家；边界仓储口单列为「仓库取货口＝单链单商品输出」。

**驳 4.4（措辞过强）「设备 = 端口 + 缓存格组 + 行为规则」不是定义。**
- 反例：供电桩无口、无槽、无物品行为；仓库无口。公理描述的是「物流设备」的模板，不是「设备」的定义。
- 建议措辞：把 A4 限定为「**参与物流的**设备」，供电桩/仓库各作显式退化条款。

## A5 接口公理

**驳 5.1（措辞过强，「唯一」为假）跨设备物流有三条不经口/front 格的通路。**
- 反例：① 协议箱→仓库的无线提交（SIM-M15，owner 亦定谳 OWN-M19「无线只在箱→仓库这一段」）；② `WarehouseSink` 落位改写（SIM-M14）；③ 暗管 `share-all` 跨距直连（SIM-M30）。三者都不经「口 → front 格」几何。
- 建议措辞：「**经端口的**跨设备物流，其唯一接口是口 → front 格；无线提交、仓库代理、暗管为显式例外，各自的几何/合法性单独定谳」。

**驳 5.2（误引证据）用 SIM-M18 支持「口坐标就是 front 格」是反向的。**
- 反例：SIM-M18 逐字判据是 `sourcePort.outsideGridPoint == targetPort.insideGridPoint && sourcePort.insideGridPoint == targetPort.outsideGridPoint`——模拟器的口是 **inside/outside 两点模型**（口在机身边缘格、另存一个体外格），恰恰是 zmd 07-18 事故里被判错的那种「口 + 偏移」形态。identity 语义是 **zmd 候选池的存储约定**（OWN-M14/R-14），不是模拟器的。
- 建议措辞：identity 只引 OWN-M14 + R-14；SIM-M18 改引为「口对口的**对接判据**」，并注明两侧坐标约定不同、换算时必须走 `_port_front_cell` 唯一 helper。

**驳 5.3（非最小）A5 捆了六条彼此独立的断言，掩盖了 #10 是谁推出来的。**
- 「零格交接不可」其实**可从「接口必须落在一个能放带的自由 front 格上」直接推出**（两机身相贴时不存在这样的格）。推导矩阵 #10 却写「公理本身」。一个自称最小的公理系里，能推的东西不该当公理。
- 建议措辞：A5 拆为 A5a（front 格 identity 与口对口判据）+ A5b（闲置口不占格）+ A5c（边圈/出界），零格交接降级为 A5a 的定理。

## A6 形态公理

**驳 6.1（夹带私货）「带是单通道 FIFO、无超车」不在 owner 的口述公理里。**

**驳 6.2（推论越层）「垂直各自满速」是速率断言，形态公理推不出。**

**驳 6.3（与 canonical 字面冲突）「一格带上不能再放另一条带」vs `can_overlap_straight_belt: true`。**
- 反例：P-BRIDGE-01 逐字允许桥压直带（canonical:37-43），R-04 的模型实现也允许 L1 bridge 与 L0 直带同格。按 A6 字面，这是「带上叠带」，应当禁止。

## A7 速率公理

**驳 7.1（措辞过强）「此后模型中不再存在速率变量」在仓库代码里为假。**

**驳 7.2（措辞过强）「准入规则只能削减速率」掩盖了突发。**
- 反例：R-ADM-01——相邻两个 10s 窗可背靠背，短时最多 `2×floor(r/6)` 件；窗界硬清零、`limit` 跨 tick 永久累计不自愈。「削减速率」这个朴素读法在**任何有限时间窗**上都不成立，只在长期均值上成立。

**驳 7.3（措辞过强）「设备节拍 = 配方 duration」忽略阻塞与相位门禁。**
- 反例：`waiting-output` 时设备被 block、节拍拉长（SIM-M27）；配方启动被挪到 Stage 5、用的是本 tick 物流结算后的库存（SIM-M25/M26）；管道族受整数秒相位门禁（SIM-M22）。

**驳 7.4（证据等级）「1 件/格」的「每格」半边没有游戏证据。**

**驳 D-8（重伤）#8 只证了 sink front，模型对 source front 同样排他。[实读]**
- 反例（`src/models/routing_subproblem.py:1233 / 1244-1246 / 1271 / 1282`，本轮实读）：终端豁免与置零对 `_sink_port_fronts` 与 `_source_port_fronts` **完全对称**。两个索引都在 `:837/:840` 按 commodity 记账，因此**生产者输出口的 front 格对外商品同样是实心障碍**。

**驳 D-1（隐藏前件）#1 的推导链缺两个前件、并且越了 A7 自己划的层。**
- 缺件①：**上游必为单槽物流件**——真正逼出「错货必被吞」的是门口那一格只装一件（A5 禁直连 + 物流件 share-cap 1 槽），不是 A2 的内容盲（见驳 2.1）。

**驳 D-3 / D-12：见驳 4.2**（「永不拒收/永不堵」须加「已在仓库注册开槽」前件，并把 `MAX_SAFE_INTEGER` 写成有限）。

**驳 D-7（未声明前提）速率引理的「最小分配」是一个选择，不是定律。**
- 反例：残道速率集合 `{5/6, 11/12, 19/22, 21/22, 10/11, 1}` 是**在最小车道数分配下**算出来的。布局者完全可以用**更多车道**把流摊薄（例如 2.833 车道的流摊到 4 条），使两条残道之和 ≤ 1，从而合法混流。

## ① 证据里有、公理系推不出、也没进参数表/残余清单

### A 组：硬伤级（承重推导已经在用，但没有条款）

**①-1　配方约束缺席（最高优先）**

推导矩阵 #1 的完整链条是「错货必被吞 ⇒ 能加工→污染下游，不能加工→槽位死锁饿死」。**第二个分支需要一条公理系里根本没有的前提：设备的加工行为只消耗配方声明的原料集、只产出声明的产物集**。没有它，「不能加工」这个状态在公理系内无定义。

- 提案把它塞进 #1 的「参数（机器配方槽有限、持续消耗）」，但参数表制造机行只写「加工（配方节拍）」，从未声明「非配方物品进了槽就永久占位」。
- 证据齐全：SIM-M09（`findInputSlotForItem` 签名无配方参数——**收货不看配方**）、SIM-M28（配方选择在设备内部、不外溢为口的选择性）、M-PORT-01。
- 建议：立 A4a「加工公理」——设备行为由配方定义（原料集→产物集+节拍），收货不看配方、开工只看配方；两者的落差就是污染/中毒的全部来源。

**①-2　设备产出侧阻塞语义缺席**

SIM-M27 给了确定答案：产物放不下 ⇒ 配方停在 `waiting-output`、设备被标 `block`、**不丢产物**、落产用 overlay 全成功才提交（原子事务）。

- 残余 5.2#9 只登记了「机器输出阻塞 D5 游戏未定谳」，**没记模拟器已有的确定答案**——而 owner 08-06 已裁「canonical 对账以模拟器为第一参照」（OWN-U09），模拟器答案本应作为工作默认值入册。
- 这条同时是 A1「守恒」在设备侧闭合的唯一依据，也是 #1「污染下游」分支的隐含前提（产物出得去）。

**①-3　来源侧商品身份的产生机制缺席**

公理系完整回答了「一个口为什么会吃到错货」，但**完全没有回答「一个边界仓储口为什么只出蓝铁矿」**。

- 真实机制：取货口/核心出口的「出什么货」= 玩家配置 `warehouseItemLink`，用 share-all 链把设备本地槽代理到仓库 `slot:<itemId>`（该槽 lock=该类型）。证据：SIM-M16、SIM-P08、SIM-P02（核心 6 出各配 warehouseItemLink inspector）、OWN-M20（6 出=各一个独立仓库取货口）。
- 在 A2 的三个内容判定点里它归入 (iii) 人工槽锁，但公理系没写出这层还原，参数表边界口行的「定型方式=仓库类型槽代理」也没点明**是玩家选的**。
- 承重性：binding 模型的 `generic_output` 槽（B-01/P-01：boundary_io 0进1出）正是这条的镜像。公理系少了它，就解释不了模型为什么要给每个边界口分配一个商品。

**①-4　A7↔A5 的接缝无条款：同商品多口并联供货是否可加**

A7 说速率经 `slots = ceil(rate / belt_cap)` 唯一换算点固化为整数口数（P-SLOT-01/RT-02），**而这就是认证谓词 (4) 端口精确计数所比对的 `required` 来源**。但公理系里没有任何条款保证「一台机器的 n 个口能为同一商品并行满速供货」。

- 反向风险就在 A3 自己身上：组内互斥规定「同一槽位组内两格不得同持同一类型，同型槽满容即**整节点拒收**、不找空格溢出」（SIM-M07，有专门回归测试）。若制造机的一族原料槽同属一个 node，同商品的第 2 条带在第 1 个槽满容时会被整节点拒收。
- 缺的参数恰恰是证据自陈的最大空白：制造机槽数/容量「未系统抽取」（SIM 覆盖缺口 3），提案参数表也照写「（槽数按配方，未系统抽取）」。
- 结论：**谓词 (4) 的换算在公理系内是悬空的**。见 ③ 表-c 的判别实验。

### C 组：公理系内部自洽（不是证据缺口，是条款缺口）

## ③ 预测力检查：3 个可推的未定谳新场景

### P1　高架桥跨越机器门口 front 格（外商品借 L1 过境）

**问题**：一条载 B 货的干线能不能从 A 货某台机器的门口格**上方**直穿过去？

**推导**：
1. A6：一切物流器件 = 具特殊功能的直传送带；十字 = 两条互不接触的垂直直通道；桥不可压弯道/分流/合流。
2. A4：行为只作用于自己的缓存格；参数表十字行 = 每通道各 1 槽 ⇒ **两条通道的缓存格互不相同**。
3. 由 2 + A3（类型锁作用于缓存格）⇒ 地面通道的类型锁对高架通道零作用；两通道可同时载不同货、互不定型污染（**这就是任务举例「桥上物品与地面槽交互」的答案：零交互，除 A6 的共格几何约束外**）。
4. A5：跨设备物流的唯一接口是「口 → front 格」，只有**对准该口方向**的通道能向口投料。B 在 L1 上垂直直穿，其 flow_in/flow_out 都不指向机身 ⇒ **B 永不进入 A 的口**。
5. 由 4 ⇒ #1 的污染前提（错货到达机器口）不触发 ⇒ **合法且安全**。
6. 由 A6（`can_overlap_curved_belt=false`，P-BRIDGE-01）⇒ **附带条件：该 front 格上 A 的终端带必须是直进直入（来向与口方向共线）；若 A 在门口格转弯，桥不能压，排他恢复。**

**与在案裁决对照**：与 OWN-M23（07-18 owner）逐字一致——「口前格被他商品带占 ≠ 堵，可借十字交叉通过（但弯带不兼容 cross，仅限双方直穿）」。所以这条**不是新规则，是被公理系独立重推出来、却在提案里失踪的旧裁决**。

**模型侧核实（我亲手读的）**：`routing_subproblem.py:1233` 与 `:1271` 的终端豁免带 `layer == GROUND_LAYER` 守卫；`:1238/:1276`（邻格不在活跃域）与 `:1244/:1282`（邻格是对家口 front）只把**该方向**的 use 变量置零，不封整格；`:1124-1143` 允许 L1 bridge 与 L0 **直** belt 垂直共格。⇒ **模型也允许外商品在终端 front 格的 L1 过境**（条件同 6）。

**结论与影响**：
- 提案 #8 与 §4 里「front 格 = 外商品的实心障碍」的表述**过强，应改为「地面层排他」**。原文出自 COUPLING_VERDICT（已被翻案的那份），措辞被 REVERDICT 继承下来。
- **这可能是 band22 的关键遗漏**：U-BAND22-01 记「三份独立设计全部绕不开门口混流」「门口格纯流 = 末段专线，1 宽走廊网络中代价极高」。但「混流干线从门口格**上方**过境 + 门口格下方留纯流末段」是模型与游戏都允许的自由度，被「实心障碍」的措辞遮住了。建议 L 侧重开时把这条列为首选构造模式。
- **置信度**：游戏侧 0.9（OWN-M23 已定谳）；模型侧 0.85（我读了守卫但**没跑 probe**）。**建议 15 分钟内做一次三格 probe**（A 直进机器口 + B 在同格 L1 垂直穿）落实，与 U-02 的 probe 同法同脚本。

### P2　同一种货能否占协议箱的多个槽

**问题**：#2 的「箱 = 有界混吃（≤6 并发类型安全）」隐含「每种货只占 1 格」。这条成立吗？

**推导**：
1. A3 的组内互斥条款是「**同一槽位组内**两格不得同持同一类型」。
2. 参数表协议箱行写的是「**6 组 × 1 槽 × 50**」——即 6 个**独立**槽位组，每组只有 1 个槽。
3. 由 1+2 ⇒ 组内互斥在协议箱上**恒真空**（每组只有一格，组内根本没有第二格）；组与组之间公理系没有任何互斥条款。
4. 由 3 + A3 第二条（空格对域匹配的任意物品来者不拒）⇒ **公理系预测：同一种货可以占满箱的多个槽，极端情况下一种货吃掉全部 6 格。**
5. 由 4 ⇒ #2 的结论应收紧为：「**箱在 6 格被占满时堵门，与占用它的类型数无关**」。「≤6 并发类型安全」只在「每种货恰好占 1 格」的额外假设下成立，而那个假设无来源。

**模拟器侧一致性**：SIM-M08 的 `excludedItemTypes` 快照是 **per-node** 建的（Stage 2 遍历 `node.slotIds`）。箱编译成 12 个节点（6 input-view + 6 output-view，SIM-P01），每节点 1 槽 ⇒ 快照里只有自己那一格的类型 ⇒ 不阻止另一组接同类型。**模拟器实现与公理系预测一致。**

**owner 侧**：OWN-M04 只断言了「6 格被 **6 种不同物品**占满后第 7 种堵门」，从未排除同种占多格。**该分支从未定谳。**

**影响**：#2「箱 = 有界混吃 ≤6 并发类型」是 M-PORT-02 三分法的一条腿，也是 canonical 修正批四件套里「协议箱 = 6 槽有界」措辞的依据。若预测成立，措辞要改成**槽数口径而非类型数口径**，否则 canonical 会再写宽一次（同一个病：类型数 ≥ 槽占用数）。

**置信度**：0.8（模拟器源码结构支持；游戏侧零证据）。**判别实验 ~10 分钟**：模拟器里给箱单喂一种货、关掉 warehouse_submit（或看提交周期内的瞬时占用），数它占了几个槽；或直接游戏内单货种灌箱看第 2 格是否被占。

### P3　分拣结构的终端条件：错货侧枝必须终止于「永不拒收」终端

**问题**：#4 结论是「限制口拒收不堵干线、零堵塞」。这个「零」是无条件的吗？

**推导**：
1. A1：物品不生不灭、不逆行；搬运失败 = 该边不动、物品留在上游等待。
2. A3 + 参数表：分流器只有 1 槽 × 1 容量（share-cap）。
3. 由 1+2 ⇒ 分流器**全部**出边都不可搬运时，那一格卡死 ⇒ 队头阻塞传播到上游干线（SIM-M31 的「全堵才卡」半句同结论）。
4. #4 之所以成立，是因为 owner 实测装置里被拒的紫晶矿**还有另一条出边**（主带继续走），且主带下游有吸收能力。
5. 由 1（不消灭）⇒ 网络里任何一股「没有任何下游愿意吃」的货流，只能被**吸收**或**堵死**，没有第三条路（唯一例外 = 显式配置的堵塞清理销毁 SIM-M29，游戏对应未定谳、且未配置完全不生效）。
6. ⇒ **定理：任何含限制口分拣的结构，其每一支的终端都必须能吸收该支实际到达的全部货；错货支必须终止于一个结构上永不拒收的终端**（由 #3/#12：有线仓储口 = 核心 14 进 / 边界口；箱只是**有界**吸收，见 P2）。否则分拣只是把堵塞推迟到侧枝饱和那一刻。

**为什么是新的**：#4 现在写的是「⇒ 错货沿干线继续、零堵塞」，**无任何前提标注**。owner 的实测装置恰好把侧枝终点接到了协议储存箱（OWN-M08），所以前提被自动满足、从未暴露。把同一装置的侧枝终点换成一台不吃该货的机器，干线会在侧枝饱和后堵死——这是 #4 的反例，且完全在公理系内可推。

**置信度**：0.9（纯 A1+A3 推论，不依赖任何未定参数；模拟器侧 SIM-M31 的结构结论同向）。**判别实验**：owner 原装置侧枝终点换成一台不消耗该货的机器，跑到饱和看主带是否停。

**影响**：这条应当作为**设计守则**进 P2.0：混流干线的末端必须挂一个永不拒收终端（核心 14 进是天然的最后垃圾桶）。它也给 W-ADM-03「限制口必要性 = 零」补上了一条独立支撑——不是「不需要分拣」，而是「有了永不拒收终端，分拣就不必要」。

## 给综合席的三条处置建议

1. **补两条公理**：A4a 加工公理（配方是设备行为的定义域，收货不看配方、开工只看配方，落差 = 污染/中毒的全部来源）与 A2a 商品身份公理（来源侧商品身份来自玩家配置的仓库物品链接，还原为 A2(iii) 人工槽锁）。这两条一补，#1 与 binding generic 槽就都有根了。
2. **给 §4 加一行「连通性」轴**，把 OWN-M29/W-CONN-01 与 ①-13（模型多两条严）一起登记。矩阵按公理分行的做法会系统性丢掉「没有对应公理的语义轴」——连通性是第一个受害者，也是最贵的一个（它是谓词 5 本体）。
3. **把 #8 的措辞从「front 格 = 外商品的实心障碍」改成「front 格的**地面层**对外商品排他；高架层可垂直过境，条件 = 该格终端带为直」**，并在矩阵里补一行 OWN-M23。这一处措辞已经遮住了一个可能对 L 侧有实质价值的自由度。改之前建议先跑一次 15 分钟的 L1 过境 probe 把模型侧钉死。
