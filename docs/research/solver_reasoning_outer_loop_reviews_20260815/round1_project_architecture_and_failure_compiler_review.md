# 总判

我把当前仓库、主求解链、规则系统重设计、最新求解器设计稿，以及正在落地的文档系统都拆开看了一遍。

一句话总判：

**这是一个“求真能力已经接近安全关键系统，但求解能力仍停留在研究原型”的项目。**

它最牛逼的地方，是已经非常清楚地知道：

* 什么才算证明；
* 什么不能冒充证明；
* 谁有资格铸造 `CERTIFIED`；
* 规则、数据、代码、证据一旦变化，旧结论应该怎样失效；
* 预算耗尽为什么只能叫 `UNKNOWN`；
* 模型过松和模型过严分别会制造什么假结论。

它最傻逼的地方，是：

**法院已经有三审制、证据保全、司法解释和档案馆了，但生产线上至今没有第一件验收合格的产品。**

当前下界账本仍是 `L=absent`。这不是“已经证明无解”，而是目前还没有一个完整布局被当前六谓词完整接纳，成为正式下界见证。上界 `U=(1188,18)` 也只是带前提的条件式上界，上下界根本还没有合口。

# 先把你仓库里三个“新架构”分清

你现在其实有三个容易被混叫成“新架构”的东西。

**第一套是 8 月 7 日的规则系统重设计。**

它解决的是：游戏事实、owner 裁决、派生定理、生成视图应该分别放在哪里；一条规则成立所依赖的前提怎样登记；怎样审计模型过松、过严和“某个限制在现实参数下根本触发不了”。

这条线已经被 owner 允许立项，但不等于所有设计细节都批准了。决策摘要里仍有多项待裁，主体也还没有完整落到运行代码。

**第二套是 8 月 8 日的“推理外环 + CP-SAT 内层”。**

这才是最新的求解器架构构想。当前状态写得很明确：

> 概念收敛、未立线。

它仍在本地 `.artifacts/solver_rethink_20260808/`，属于设计与审查材料，不是当前生产架构。

**第三套是 8 月 15 日正在落地的文档与知识系统。**

当前 checkout 正在 `document-system-consolidated-landing` 分支，HEAD 是 `8c25aaf`。相对 `main`，这一批改了 236 个文件，增加约 57,818 行、删除约 5,066 行。

它解决的是：当前真相在哪里、历史材料是什么身份、claim、decision、dossier、generated view 如何关联，以及代理进入仓库后该从哪里读。

所以三者的关系是：

```text
文档系统：告诉你“真相和历史放在哪里”
规则系统：告诉你“事实怎样成为公理和定理”
推理外环：告诉你“定理怎样真正减少求解空间”
```

目前最关键的断桥，正是最后一条：

**仓库越来越会保存和审查定理，但还没有证明自己能稳定地产出真正减少 binding/routing 成本的定理。**

# 这个项目真正牛逼的地方

## 1. 它不是“找到一个解”，而是在认真做 exact certification

普通布局求解器的终点是：“我找到了一个看起来不错的布局。”

这个项目的终点是：“我给出一个固定布局，并证明它满足规定的全部谓词，同时证明所有字典序更好的候选都不可行。”

当前认证范围被明确限定为六个谓词：

1. 空矩形严格无任何占用物；
2. 266 个 mandatory 实例不重叠；
3. 摆放姿态合规；
4. 端口绑定满足精确需求；
5. 传送带连通可行；
6. 供电覆盖可行。

再加 lex 最优性。

更难得的是，它把没有证明的东西明确排除掉了。比如：

* 离散物料吞吐；
* 传送带容量；
* 完整的离散流可行性；
* 电力吞吐配平。

`flow_subproblem` 明确是 diagnostic-only，不能偷偷参与认证。

这点非常牛逼，因为很多“形式化项目”最后都会把自己实际没证明的东西含糊地包进宣传口径。这个项目至少知道自己的定理到底有多大。

## 2. 它的 fail-closed 做得非常彻底

这个项目很少把“不知道”冒充“不可能”。

例如：

* 子问题超时返回 `UNKNOWN`；
* alternative cap 用尽返回 `UNKNOWN`；
* cut 复验不完整就不允许落 cut；
* 当前 binding/routing 没有终态，就不能说该布局不可行；
* 预算删失的实验不能被解释成“没有效果”；
* `main.py` 自己不能铸造 `CERTIFIED`；
* 普通 producer 最多只能提交 `CANDIDATE_PROPOSED`；
* 必须由独立 supervisor 重新固定 witness、复验并 seal；
* 只有中央 publisher 能写 canonical 发布面。

这已经不是普通防御式编程了，而是一套“结论权限系统”。

## 3. 它终于认识到了模型过严也会制造假证书

这是很多求解器项目最容易犯、也最隐蔽的错误。

模型过松时，会产生游戏里不合法的假见证，这很直观。

但模型过严时，虽然找到的见证通常仍合法，却可能把真正的最优布局排除掉。于是你最后证明的只是：

> 在我这个缩水后的模型里，没有更好的解。

而不是：

> 在真实游戏里，没有更好的解。

这个项目的规则重设计已经把它明确成“双向保真”：

```text
模型过松：主要伤见证
模型过严：主要伤 UNSAT、上界与最优性证明
```

而且不是停留在口号上，它已经登记了一批现实中的 stricter faces，例如：

* 某些 1×1 admission port 没有进入模型；
* warehouse bridge 的排除只在特定目标下成立；
* binding 的单商品端口模型表达不了某些多商品吸收能力；
* 某些连通性附加限制可能比游戏真实规则更严；
* candidate discovery 的完整性与 candidate validation 是两回事。

能走到这里，说明项目已经从“代码正确性”进入了“所证明命题是否正确”的层级。

## 4. 它很会把事故沉淀成不变量

这个仓库里很多复杂结构不是凭空设计出来的，而是被真实事故逼出来的：

* 严格空矩形语义曾经错过；
* 同一裁决在多个副本中有一处没同步，后来读到了陈旧副本；
* checkpoint、marker、seal、publisher 之间出现过竞态；
* 某些 heuristic 限制曾经被误当成硬语义；
* budget-censored 的实验曾差点被解释成负面结果；
* 同一个层号在两份设计里含义相反；
* 自产文书自我评审时把“相互独立”说得过头。

最可贵的不是“从没犯错”，而是它经常把犯过的错误变成：

* schema；
* gate；
* immutable event；
* provenance；
* status algebra；
* regression test；
* authority boundary。

这种项目长期做下去，抗胡说能力会非常强。

## 5. 最新 v2 的 Judgment 设计在逻辑上确实高级

v1 把一个结论写成：

```text
Lemma(type, P)
```

但同一句“所有可行解都满足 P”，可能是在不同空间里说的：

* 原始六谓词问题；
* 已经经过一轮 WLOG 裁剪的问题；
* scope 被缩小的问题；
* 加了流量语义的问题；
* 某个固定候选矩形的问题。

v2 改成：

```text
Judgment(
    problemHash,
    objectiveHash,
    contextHash,
    binders,
    Γ ⊢ φ
)
```

这一步非常正确。

它意识到“命题是什么”不能只看文字，还必须看：

* 在证明哪个问题；
* 优化目标是什么；
* 当前已经施加了哪些裁剪；
* 前提是什么；
* 量词绑定了谁；
* scope 到底是什么。

这避免了一类很危险的问题：在缩小后的空间里证明的全称命题，被错误提升成原问题的全称命题。

从形式逻辑角度看，这不是花架子，而是一个真正承重的修正。

# 这个项目最傻逼的地方

我这里说“傻逼”，不是说谁傻，而是说系统在哪些地方把聪明用错了方向。

## 1. 它严重倒置了“求出东西”和“证明东西”的投入比例

当前状态最扎眼的事实是：

```text
下界 L = absent
```

没有完整见证。

但与此同时，仓库已经有：

* 复杂的 producer / supervisor / publisher 三权分立；
* 冻结工件体系；
* typed cut 平台；
* owner gate；
* proof obligation；
* release surface；
* 文档 authority；
* claim ledger；
* decision ledger；
* validity ledger；
* dossier registry；
* generated projection；
* 20 份 ADR；
* 5599 行的 `docctl.py`；
* 3608 行的知识文档生成器。

这些东西大部分都有价值，但资源顺序明显倒过来了。

更直白地说：

**项目现在很擅长证明自己没有乱说，却还不擅长说出一个有用答案。**

一旦长期处于这个状态，项目会形成一种危险的自我奖励机制：

* 多加一道 gate，立刻能看到“更严谨了”；
* 多加一份 ledger，立刻能看到“知识结构更完整了”；
* 多加一层 hash，立刻能看到“证据更可靠了”；
* 但真正让一个完整布局穿过 binding 和 routing，可能连续几周都没有正反馈。

于是人会自然地继续做那些容易得到“完成感”的治理工作，而最难的求解瓶颈继续躺着。

## 2. 它可能精确证明了一个比游戏更小的问题

当前认证目标本身就不包含吞吐，这已经意味着它证明的是“结构性可行布局”，不一定是完整可运转工厂。

更严重的是，六谓词模型内部仍有多处已知的 model-stricter debt。

所以即使未来得到一个完美的 `CERTIFIED`，你仍要问两层问题：

```text
第一层：它是否是当前六谓词模型的全局最优？
第二层：当前六谓词模型是否与真实游戏目标足够一致？
```

第一层可以形式化证明得滴水不漏。

第二层如果没闭合，最后仍可能是“错误问题的正确答案”。

这也是为什么 `TARGET_CLAIM` 和 `PROVED_CLAIM` 必须分开。不能因为目前只能证明一个缩水命题，就把缩水后的命题悄悄改成项目原目标。

## 3. 当前分解方式把最昂贵的信息发现得太晚

现有求解流程可以用一句很普通的话解释：

```text
master 先把整座城市画完
binding 再检查所有插座怎么接
routing 再检查所有道路能不能铺
某处失败后，常常只告诉 master：这一整张城市图不行
```

这就像建筑师画完整栋楼后，水电工程师才说某个房间管道塞不进去。然后系统不给建筑师总结“这种户型的管井必然不够”，只是说：

> 这张完整图不要再画了。

于是下一次 master 可能画出一张本质相同、只挪了几块砖的图，再把整个昂贵流程走一遍。

代码里这个问题非常具象：

* `benders_loop.py` 超过 10,000 行；
* `exact_coordinate_master.py` 超过 8,600 行；
* `master_model.py` 超过 12,000 行；
* `src/search/` 一项就约 15.1 万行；
* `src/` 总计约 47.8 万行，其中测试约 25.1 万行，非测试表面仍约 22.7 万行。

当前 binding 到 routing 的循环会枚举 binding selection：

```text
binding feasible
→ routing precheck / routing solve
→ 当前 binding 不行
→ 给 binding 加 selection nogood
→ 解下一个 binding
→ 再跑 routing
```

生产规模复验已经展示了后果：

* master 能找到候选；
* binding 与 routing 无帽枚举超过 33 小时仍无终态；
* CPU 累计约 1 天 8 小时 46 分；
* 内存峰值约 29.4 GB；
* swap 约 17.1 GB；
* 热点长期落在 binding；
* 同一基准在严格语义修正前只需 649 秒；
* 墙至少加深了 183 倍。

这不是“再给 CP-SAT 一点时间”能解决的问题，而是反馈粒度不对。

## 4. Cut 系统先修好了消费端，却没有证明生产端存在

typed cut 平台做得很漂亮：

```text
registry
→ resolver
→ checker
→ lowering
→ master attach
→ receipt
```

但问题是：谁来稳定地产出真正有用的 family-level cut？

现状是：

* certified 路径仍默认禁用；
* 16 臂实验全部被预算截断；
* 没有可归因的运行时改善；
* 有机触发为零；
* 当前已知触发点在 cap 口径下甚至结构性到不了；
* typed pipeline 能检查已有 cut，却不会发现新 cut。

这像修了一条路面、排水、红绿灯都极其规范的高速公路，但还没证明有车能从入口开进来。

真正缺的不是另一层 cut lifecycle，而是：

```text
下游失败
→ 提取可复用的最小原因
→ 归纳为一类失败
→ 证明这类失败可以安全地前推
→ 编译成 master 或 binding 域限制
```

也就是一个**失败编译器**。

## 5. 仓库已经形成严重的“地层堆积”

现在的核心代码不是一套清晰架构，而是很多代架构叠在一起：

* 旧 master；
* exact coordinate master；
* phase3b 遗留路径；
* 各种 env-gated 实验；
* fallback ladder；
* diagnostic path；
* certified path；
* typed cut；
* legacy cut；
* shadow-only family；
* 不同阶段的 precheck；
* 旧语义修复留下的守卫；
* 研究代码和生产代码之间的桥。

每一个局部看起来可能都有历史理由，但合起来以后，维护者很难回答：

> 一个当前候选到底经过了哪几层约束，哪些层是正式语义，哪些层只是历史实验，哪些层失败后会返回 UNKNOWN，哪些层能向上反馈？

这也是为什么项目不断需要新增导航图、authority 表和文档系统。文档负担不是偶然的，它是代码结构失去可直接理解性的外部症状。

## 6. 现在有形成“三套真理账本”的风险

最新三套设计里，类似的命题可能同时存在于：

* 文档系统的 `claim`；
* 规则系统的 `DERIVED_THEOREM`；
* 推理求解器的 `Judgment`。

owner 裁决又可能同时存在于：

* `decisions.jsonl`；
* canonical semantics；
* 历史事件记录；
* 当前状态投影。

如果它们各自有独立 ID、状态、hash 和失效逻辑，同一条命题就会被表示三到四次。

这正是项目过去最怕的 C-53 型事故，只不过被放大到了架构级：

> 一份更新了，另一份没更新，后来某个机器流程恰好读到陈旧的那份。

正确方向不应该是三套 ledger 互相同步，而应该是：

```text
一个规范化命题身份
一个 evidence / authority root
一个结构化 context
多种只读投影
```

文档 claim、规则 theorem、solver judgment 应该共享同一个 proposition AST/hash，只是拥有不同的用途视图。

否则新架构还没开始推理，就先陷入跨账本一致性工程。

# 最新“推理外环”架构到底好不好

方向是对的，而且很可能是当前最值得继续研究的方向。

它想做的是：

```text
游戏公理与冻结数据
→ 推理机组合前提
→ 产出带上下文的 Judgment
→ checker 决定这条 Judgment 能怎么用
→ 把安全判断编译成域限制
→ 在缩小后的残余空间上运行 CP-SAT
```

它解决的核心问题也判断对了：

**不要等完整布局死在 binding/routing 深处后只回传一个点状 nogood，要尽量提前推出“整类布局为什么必死”。**

但它现在有一个根本问题：

> 它已经把“一个判断应该长什么样、怎样登记、怎样检查、怎样失效”设计得很精细，却还没证明项目能稳定发现有用判断。

换句话说，它已经设计好了大学的学籍、课程编号、考试规范、论文引用和学位授予制度，但尚未证明这里能培养出会解决二维 binding/routing 问题的学生。

## 最危险的几个问题

### 第一，X1 的成功不能证明二维推理外环可行

X1 存货口的三行排除非常漂亮：

```text
边界条带 139 格
46 个取货口占 138 格
存货口还需 3 格
因此放不下
```

但这是一个接近一维的容量账。

真正卡住项目的是：

* 内部二维几何；
* 多设施端口关系；
* binding 组合；
* routing 拓扑；
* 局部选择对全局连通性的影响。

从“一维边界条带能推出排除定理”，跳到“系统能够自动推出有用的二维 binding/routing 定理”，中间还有一条很宽的河。

新架构最大的设计假设，正是这条河能被跨过去。目前没有实证。

### 第二，真正缺的是 producer，不是更完整的 Judgment 类型

`Judgment(problemHash, objectiveHash, contextHash, Γ ⊢ φ)` 很正确。

但一个完全正确的容器，不能自动产生内容。

核心待证问题不是：

> 我怎样存储一条 family-level judgment？

而是：

> binding/routing 的失败里，到底有没有可重复、可归纳、可 sound 前推的 family-level 原因？

如果大多数失败高度依赖整局身份，最后只能生成点状 nogood，那么通用推理机不会带来数量级提升。

### 第三，context 可能爆炸

每加一条活动裁剪，`contextHash` 都可能变化。

如果不同上下文之间只靠 hash 判同一，那么同一个结论在稍有差异的上下文中就无法复用，需要重新证明或提供 transport theorem。

最后可能出现：

* 判断很多；
* context 更多；
* cache 命中率很低；
* 依赖 DAG 巨大；
* 每次 campaign 都要冻结新根；
* 证明管理本身成为新瓶颈。

所以 context 不能只是一个不透明 hash。它必须是结构化的 assumption set，并支持：

* 子集关系；
* 单调提升；
* 可行域包含；
* 已证等价；
* context transport。

hash 只应用来确认字节身份，不能替代上下文代数。

### 第四，抽象定理到实际约束之间还有三道翻译缝

即使一条数学判断是真的，也不等于实际加进 CP-SAT 的约束是对的。

至少有三层可能错：

```text
游戏语义 → 形式命题
形式命题 → runtime checker
checker 许可 → master/binding 具体约束
```

现在的 typed cut 主要能防“类型放错”，不一定能防“lowering 后比原命题更严”。

所以每一种可执行判断都必须有独立的 lowering correctness contract。否则会出现：

> 定理本身正确，编译器把它编译错了，最后仍然砍掉合法最优解。

### 第五，开放世界问题没有真正消失

系统只能在已知公理和已知能力上推理。

如果游戏里存在一个三份 inventory 都没登记的能力，那么三个表互相对得上，也只能证明：

> 我们共同漏掉了同一件事。

模型完整性不能仅靠多个仓内清单互相做差得到。它仍需要：

* owner 实测；
* 上游数据差分；
* 模拟器判例；
* 独立构造反例；
* model correspondence；
* runtime canary。

新架构能管理“已知知识”，但不能机械证明自己没有未知知识。

### 第六，它仍然偏向上界和排除，下界问题没有得到同等投资

项目当前最醒目的事实不是上界不够紧，而是：

```text
L = absent
```

通用推理外环天然更擅长：

* 排除元素；
* 推出不可达；
* 缩小域；
* 证明上界；
* 证明某类候选不可能。

但项目现在同样急需一条完全不同的路线：

```text
不可信的外部构造器
→ 提交完整布局
→ 独立 fixed-witness verifier
→ 合法就成为下界
```

寻找见证不需要生产者本身可信。生产者可以是：

* 局部搜索；
* 大邻域搜索；
* 手工布局；
* 启发式 CP-SAT；
* 其他求解器；
* 非 certified 的实验模型。

只要最终 witness 能由独立 verifier 验收，就可以进入下界。

你仓库其实已经把这种 proof-carrying producer 架构的大半安全壳造好了，缺的是一个稳定的“外部完整布局入口”，以及确认它能绕开当前同一个无帽 binding↔routing 死循环。

# 我认为正确的下一步架构

不是直接开工完整的“通用推理外环”。

应该先把它收缩成一个：

# 失败驱动的域编译器

初始形态只需要这一条链：

```text
FailureReceipt
→ NormalizedSupportCore
→ DeathCauseFamily
→ FamilyCandidate
→ SoundChecker
→ DomainCompiler
→ Master / Binding domain
→ Holdout A/B
```

这里每一格都回答一个非常具体的问题：

* 这个布局为什么死？
* 最小原因是什么？
* 这个原因在多少个独立布局里重复？
* 它能否被归纳成一族，而不是一个点？
* 这族规则是否真的 sound？
* 它能否在昂贵子问题之前收紧域？
* 在没参与归纳的布局上，昂贵调用是否真正下降？

你自己的最新收束文书已经给出了非常合理的 Phase -1，应该把它当真正的架构闸，而不是直接上 Level 2。

## 先做五个动作

**D1：收集真正的无删失死因谱。**

取 30 至 50 个固定布局，绕过 master，单跑 binding/routing。不能使用那个会先撞 `ALT_CAP→UNKNOWN` 的 cap 口径，否则得到的仍是删失谱。

记录：

* 死因；
* 最小 sound 支撑核；
* binding proposal 数；
* routing 往返；
* censorStatus；
* seed、worker、timeout。

关键问题是：有没有某类死因在多个独立布局中重复。

**D2：验证 producer 到 consumer 的链真的通。**

既做注入式触发，也做自然触发，逐边区分：

```text
NOT_REACHED
REACHED_NO_EFFECT
EFFECT_NO_TERMINAL
```

不能再用“代码路径存在”代替“生产上真的能到达”。

**D3 至 D4：只编译一个死因家族。**

选重复最多的一族，把它 sound 地编译成上游端口域或 binding 域限制。

然后必须在没有参与归纳的 holdout 布局上做 paired A/B。

真正的成功不是“新增了一条 Judgment”，而是：

* 昂贵提案明显减少；
* 域确实变小；
* 没有错误排除；
* 热点没有只是从 binding 搬到 routing 或 verifier。

你设计稿给出的“至少减少约 10% 昂贵提案”可以作为第一道工程门，不必神化这个具体数字，但必须有预注册的量化门槛。

**D5a：打通外部完整布局的终验 canary。**

拿一个外部构造的完整布局，尝试走到现有六谓词终验链。

要实测清楚：

* terminal fixed-witness 链能不能直接吃外部布局；
* 缺不缺 adapter；
* binding/routing 能否独立重导；
* 是否仍被迫重新进入同一个无帽循环。

这一步直接决定下界路线有没有活路。

**D5b：真正做 go/no-go。**

只有同时满足下面两件事，才值得继续投资通用推理外环：

1. 至少一个重复死因可以 sound 地编译成 family/domain 级反馈，并在 holdout 上显著减负；
2. 外部 witness 路线能够独立进入终验，或者所缺适配层清晰且可控。

没有这两个信号，就应该停止建设通用知识机，转向：

* 更强的联合模型；
* binding/routing 一体化；
* 专用传播器；
* 更好的分解；
* PB/SAT 侧证书；
* 大邻域见证构造。

停止并不亏，因为死因语料、feedback compiler、外部 verifier、基准和薄 ledger 都能保留。

# 对三个新系统的具体取舍

## 规则系统重设计

应该保留，但先只落最小骨架：

* 单一规范命题身份；
* 前提 DAG；
* 自动 stale；
* owner ruling event；
* derived theorem 非冻结层；
* model correspondence；
* 消费侧闸。

不要一开始就把八步流程、三种审计、所有视图、完整 closure scanner 和大量人工字段全部建完。

凡是机器能推出来的字段，都不要让人手填：

* consumers 自动生成；
* status 自动计算；
* hash 自动计算；
* stale 自动传播；
* generated view 自动生成；
* 方向与 applicability 尽量由 checker 判。

否则这会变成“用表格模拟类型系统”，人最后仍会填错。

## 推理外环

先以离线批次工作，不要在 campaign 中实时激活规则。

比较稳妥的形态是：

```text
离线推导
→ 冻结 reasoning snapshot
→ 启动一次 campaign
→ 全部 worker 使用同一个 snapshot
→ 收集反馈
→ 下一轮再更新 snapshot
```

这样不会让并行 worker、cache、cut 和 checkpoint 在一场 campaign 中跨版本污染。

Lean 也应只承担少数 schema/meta-theorem，不要给每条 runtime judgment 生成 Lean 源码。实际 judgment 用轻量独立 checker 更合适。

## 文档系统

设计思想有价值，尤其是：

* policy 不自我授权；
* authority 与 representation 分开；
* generated projection 不能反向成为真源；
* 历史快照与当前命题分开；
* inventory coverage 不冒充 semantic review。

但当前 landing 还不能叫完成。

我实际运行当前分支的门禁后，得到的是：

* `docctl doctor` 阻断；
* `docs/AGENT_OPERATIONS.md` 为 247 行，超过 240 行预算；
* convergence projection 过期；
* 8 份生成知识页漂移，包括 `CURRENT`、`CATALOG`、`REASONING_LEDGER`、`VALIDITY_LEDGER`、`OPEN_QUESTIONS` 等；
* document-system regressions 为 59 过、3 败；
* knowledge regressions 为 22 过、2 败；
* 某个测试还硬编码期待出现 `204`，而当前生成页已不满足；
* 更严重的是，治理 gate 在运行期间修改了 5 个 tracked 文件，然后由自己的“工作树不可变检查”把自己判红。

最后这个很有意思，也很说明问题：

**它成功发现了自己不该修改工作树，但它还是先把工作树修改了。**

我已经把本次检查造成的 5 个 tracked 文件变化恢复到 HEAD，原来就存在的大量 untracked 实验工件没有碰。

文档系统下一步不应该再加功能，而应该先做到：

1. 所有 gate 在临时 worktree 或临时目录运行；
2. read-only 检查路径绝不能调用任何 write-through 生成逻辑；
3. 不用“247 行大于 240 行”这种容易刷指标的粗门作为主要质量标准；
4. 测试验证结构不变量，不硬编码 `204` 之类会随合法数据变化的快照数字；
5. 人类只保留一个真正的当前入口，其余索引按需生成；
6. 165 个 dossier 已被 inventory triage，不等于 165 个都做过语义审查，这个边界继续保持醒目；
7. 在求解面出现下一次实质进展前，冻结文档框架功能扩张。

# 最后给项目下一个非常明确的结论

这个项目不是烂，甚至可以说它的某些部分非常罕见。

**认证宪法、结论权限、fail-closed、证据边界、双向保真，这几块是真正牛逼的。**

真正的问题是，项目把最强的工程能力优先投到了“如何确保答案不骗人”，而不是“如何更快地产生答案”。

所以接下来最该保留的是：

```text
现有认证核
独立 fixed-witness verifier
状态与 authority 边界
最小前提 DAG
```

最该暂缓的是：

```text
完整通用推理机
更多知识视图
更多文档治理功能
未经实证的大型规则 DSL
```

最该立刻补的是：

```text
无删失死因谱
失败家族 → 上游域的 sound compiler
外部完整 witness 入口
holdout A/B
```

一句最狠、但也最准确的话是：

**这个项目已经造出了极其可靠的“真理海关”，现在缺的不是再扩建海关大楼，而是先证明真的有货能运过来。**
