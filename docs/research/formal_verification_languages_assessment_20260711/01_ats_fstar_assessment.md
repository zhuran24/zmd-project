# ATS / F\* 形式化验证语言对本项目的适用性评估

- 日期:2026-07-11
- 缘起:owner 了解到 ATS 与 F\*(F-star)两门语言后问询「对我们这个项目有没有帮助」。
- 结论先行:**概念上与项目的信任结构同源(verified checker / De Bruijn 准则),工程上当下引入不划算;两语言均不解决项目信任链的真瓶颈。远期若做验证器形式化,以 Lean 生态优先(与既有 `formal/` Lean 侧、roadmap「PBLean 自研验证器(轴 B Phase 6,远期)」同向),ATS 直接排除。**
- 状态:评估已向 owner 口头汇报(2026-07-11 对话),owner 要求记入文档。不改变任何现行排期。

## 1. 两门语言是什么

- **ATS**:ML 系语法的系统编程语言,依赖类型+线性类型,可在类型层证明数组越界/内存安全/终止性等性质,编译到 C。学习曲线极陡,社区极小,定位是系统编程(指针/内存),与本项目问题域基本不搭。
- **F\***(F-star):微软研究院的验证导向函数式语言,依赖类型+effect 系统+SMT(Z3)自动化,可提取 OCaml/F#/C 代码。工业案例:HACL\*(验证过的加密库)、Project Everest(TLS 栈)。生态大于 ATS,但仍属研究性生态。

## 2. 它们能解什么:与项目的概念连接点

这类语言的看家本领是把「程序本身正确」变成机器可查的定理——典型用法不是验证求解器,而是验证**检查器**(De Bruijn 准则:求解器大而不可信,检查器小而可信)。

本项目的认证架构正是该准则的工程版:

- CP-SAT+外层搜索(大、不可信)只产生 `CANDIDATE_PROPOSED` 候选材料;
- L0 verifier(`pr2_l0_true_verifier_child`,隔离子进程 `-I -S -B`)+独立复验器(I1)是「小而可信」端,由 close-kernel hash-pin+三权分立+双审流程在工程层面维持其可信性。

用 F\* 重写 L0 verifier 等于把「小而可信」从工程纪律升级为数学证明——这是概念上成立的升级方向。

## 3. 为什么当下不划算:真瓶颈不在 verifier 实现语言

项目信任链的三个环节:

1. **CP-SAT 黑盒判定(真瓶颈,形式化语言无解)**:lex 最优性论证依赖 OR-Tools 的 INFEASIBLE/OPTIMAL 判定。SAT 侧有成熟证书生态(DRAT/LRAT:求解器出证明、独立小工具复查),**CP-SAT 没有工业级 proof log**。这是证明链里最大的「信任而非验证」块;verifier 换任何语言都改变不了。
2. **模型编码忠实性(真瓶颈,形式化语言只能部分帮)**:「CP-SAT 模型忠实表达 70×70 游戏规则」是 specification 问题。验证语言能把 spec 写得更精确,但「spec 是否等于真实游戏规则」只能靠人对照(现行手段:canonical_rules 冻结+placement_rule 谓词复验)。
3. **代码漂移(已被工程手段覆盖)**:close-kernel sealed+hash floor+obligations checker+慢 soundness lane+双审流程。此处边际收益已很小——恰是 F\*/ATS 唯一能直接强化的环节。

即:**它们能解的环节我们已解到边际收益很小;它们解不了的环节恰是剩下的大头。**

成本侧:F\* 与 Python 生态(45MB JSON 工件、strict JSON、CP-SAT 绑定)的接口成本高;研究性语言代码的长期维护负担大(单 owner+AI 团队);ATS 另加「生态极小+问题域错配」两条,直接排除。

另注:项目当下的实际痛点(慢 lane 时长、uv 解释器间歇 segfault、CI 2 核 runner 超时)全部是工程运维问题,与验证语言无关。

## 4. 重看条件与既有布局的关系

- 触发重看的条件(任一):①项目进入发布后/学术化阶段,想把证明强度再推一档;②OR-Tools 侧出现可消费的 proof log/证书机制(那会改变瓶颈 1 的性质,值得单独评估);③owner 出于学习目的想投入。
- 若重看,现实路径是**只把 L0 verifier 的少数纯算法谓词**(矩形不重叠、连通性等)用验证语言写第二独立实现并提取,不是重写任何主链。
- 语言选型届时以 **Lean 4** 优先:社区/数学库(mathlib)/AI 辅助证明资料均比 F\* 成熟一个量级,且项目已有 Lean 资产(`formal/` 的覆盖链+Finset 工作、TNS 证书链数学侧)与既有远期登记(roadmap §3「PBLean 自研验证器(轴 B Phase 6,远期)」)。本评估不改变该登记的「圈外/远期」定位。
