### 2. 数学断言与 cert payload

**断言（一句话）**：对 free-cells 图上一个**封闭**（无逃逸边）的 patch 划分 (A,B)，若跨划分自由边数 `cut_size` 小于所有「路线跨该划分」的 contributing commodities 的 demand 总和，则该 blocked-cell 配置下 belt 路由不可行（Menger min-cut 论证；spec `docs/research/p3_b_design_v2_20260521/cut_family_specs/02_cutset.md` §1a/§2a）。

**cert payload 字段表**（`src/cuts/cert_schema.py:39-47`；注意 `CERT_PAYLOAD_REQUIRED_FIELDS` 就是 allowed 全集（:113-116），**全部字段必填**，多一个少一个都 `CertPayloadSchemaError`）：

|---|---|---|
| `cert_kind` | str | 必须 == `"menger_min_cut"` |
| `side_a_bitset_b64` | str(base64) | A 侧 cell 集，70×70 bitset（613 字节，`idx = x*70+y`；解码器 `_decode_bitset` cutset.py:63-81，带 padding-bit 越界检查） |

### 3. step_8 master 翻译候选形态

现状：`step_8_apply_to_master`（`src/cuts/lifecycle.py:1133-1189`）只有 `region_capacity` 分支；其余族在 :1186-1189 `raise NotImplementedError`。`MasterModelLike` Protocol（:1115-1130）目前只声明 `add_region_capacity_cut`。

**F2 不能是 F1 式恒真容量不等式**：F1 的 RHS（cap_R）是静态几何量（区域非 blocked 格数），LHS 是 presence 加权和，对任何可行布局恒真（exact_coordinate_master.py:7137-7159 注释同此论证）。F2 的 RHS `cut_size` 是 **free_cells 的函数**（= f(ghost, exterior, cell_owner)，即依赖哪些 pose 被放置），不是静态量；master 里也没有任何 routing 变量可以直接表达「跨划分流」。所以 F2 的 master 翻译只能是**对放置构型的条件禁止**（nogood 形态）：「(封住走廊的 poses 全在) ∧ (钉住 src/sink 的 poses 在) ∧ (该 ghost 被选) ⇒ 禁止」。最接近的现有 API 是 `add_benders_cut(conflict_set: Mapping[str,int], *, condition_lits: Sequence[IntVar] = ())`（exact_coordinate_master.py:7084，presence nogood `sum ≤ N-1`，全有或全无 fail-closed，经 `_conflict_pose_entries` :7017 归一化）；`add_region_capacity_cut` 完全不可复用（形状不同）。

**soundness 依据不是「恒真」**，而且比 F4 多两道未解决的语义门：
1. **demand 量纲 = 吞吐**：`commodity_demand` 是流量需求量纲。PROJECT_LOCK.md §1A B-1（:113-118）把带 demand 量纲的 flow 锁成 diagnostic-only 绝不 gate；B-2（:119-123）明说 F1-F9 是「面积/空间密度 packing cut、**非吞吐 cut**」、「无 cut family 表达『离散容量流够不够』」，进 certified 需**新范式**。生产 demand 源 `data/preprocessed/commodity_demands.json`（17 个 commodity）的值是**速率浮点数**（如 `buckwheat: 5.5`）——F2 oracle 的 `_is_strict_positive_int`（cutset_oracle.py:78-79, 145-148）会静默跳过非 int demand。所以 demand 加权版 F2 的 master attach 实质上属于 P2.0 吞吐认证轴（roadmap 00_master_roadmap.md §1e，owner 2026-07-04 已改判必做），不属于命题 P 六谓词。
2. **图抽象保真度**：F2 用单层 4-邻接、edge_capacity=1、cell_capacity=∞（`_INF_CAP=10**9`，Phase 1.2 edge-only mode）的图；而 certified routing 模型（routing_subproblem）是**双层**（ground + elevated bridge），bridge 允许同 cell 第二条流。未见任何仓内文档 reconcile 这两个模型——一个只数 ground 邻接的 Menger 上界可能对 bridge 可绕行的布局**过切**。即使弱化成「跨划分 commodity 个数 > cut_size」的连通版，也仍需过 bridge 语义审查。

结论：F2 的 step_8 翻译是「依赖 cert 门禁 + 额外语义裁定」型，不是物理恒真型；master 需要条件 nogood 能力（复用 `add_benders_cut` 的 `condition_lits` 或新 API），且在 owner 对 demand 语义/桥语义拍板前**没有已知 sound 的翻译**。

### 3. step_8 master 翻译候选形态

不是 F1 式恒真不等式，是**条件 nogood**，且有两个候选子形态（对应 family docstring 预告的 "ghost-cause vs cell_owner-cause sub-kinds (类 F7 causation split)"，component_reach.py:17）：

- **(a) ghost-cause**（恰是生产 cell_owner={} 下唯一可能的形态：separator ⊆ ghost_cells）：cert 证明「选这个 ghost anchor 时，c 的 src/sink 在空场上就不连通」→ 对**该 ghost anchor** 的禁止。几何论证是布局无关的（src_component 的 4-邻接边界全被 ghost 封死 → 任何布局只会减少 free 格，不可能重连）——但**前提 src/sink cell 本身布局无关**才成立；生产里端点是设施端口格、随布局移动 → 严格恒真版还要把「钉住端点的 poses」并进条件。master 侧现无「禁 ghost anchor」公开 API（ghost 选择 literal `u_var` 在 `_selected_ghost_context` 里有，benders_loop.py:7558）→ 需新 API 或扩 `add_benders_cut` 的 `condition_lits` 用法。
- **(b) cell_owner-cause**（Phase 1.5+）：对 `blocking_facilities` 的 presence literals（∪ 端点钉住 poses）做 nogood——形状正好是 `add_benders_cut(conflict_set, condition_lits=...)`（exact_coordinate_master.py:7084，`sum(present) <= N-1`，all-or-nothing，literal 走 `_pose_present_literal` 三层 content-addressed 缓存 :6983-7015）。**当前被双重卡死**：cert 里 `blocking_facilities=[]`，且 v1.1 validator 拒绝为 pose ID 背书 → 翻译若信 cert 的 ID 就是「依赖 cert 门禁但 cert 又没被验证该字段」，不 sound。要走 (b) 必须先做 causation split + validator 升级（相当于 F9 解封所需的「cert 加 proof-carrying 字段 + replay 校验」同类升级）。

soundness 定性：几何蕴含本身（封闭前沿 ⇒ 分量隔离）可从 cert bitset **replay 重算**（validator 已做），不需信 oracle 标量——这点比 F2 干净；但作为 master 约束它仍是「条件成立才禁止」的 implication，不是 F1 那种无条件恒真不等式。`add_region_capacity_cut` 不可复用。

## RISKS

- F2 master 翻译没有『恒真』出路：cut_size 依赖 free_cells（即布局），demand 量纲是吞吐（PROJECT_LOCK B-1/B-2 明锁 out-of-scope）——把 F2 做成 F1 式不等式或直接 nogood 都会引入命题 P 六谓词之外的语义；接线前必须 owner 裁定（连通弱化版 or 等 P2.0 吞吐轴），不要试图绕过 B 块
- F2 的单层 edge_capacity=1 抽象 vs certified routing 的 elevated-bridge 双层语义未 reconcile：任何基于 F2 min-cut 的 master 剪枝都可能过切桥可绕行的合法布局——这是 soundness 级风险，不是性能问题
- F4 的 (b) cell_owner-cause 翻译看似能直接复用 add_benders_cut，但 cert.blocking_facilities 恒为 [] 且 v1.1 validator 刻意不为 pose ID 背书——若翻译端自己从 state.cell_owner 反推 blocking poses，等于信任了一个 replay 从未验证的映射，正是 F9 tight-K 被 quarantine 的同型错误（『信任无法重算的 cert 标量』）
- F4 ghost-cause nogood 的『恒真性』依赖 src/sink cell 布局无关——生产里端点是设施端口格、随布局移动；漏掉『钉住端点的 poses』条件会把仅对某 incumbent 成立的 disconnect 泛化成对所有布局的禁止 → 过切
- 生产 BState 材料三缺口（commodity registries 未注入、oracle 版本未登记、cell_owner={}）互为纵深：补任何一个都不等于通路；且 route schema（单 src/sink cell vs 真实多端口）是 roadmap 明写的 P1.5+ owner 拍板项，抢跑等于替 owner 拍板
- commodity_routes/commodity_demands 进 source digest（demands 还挂在 generic_io_requirements 键下）：按迭代注入 incumbent 端口会让 digest 每轮变化、cut 全部 QUARANTINE/失效；实现时要先设计 registry 的稳定性口径，且别被键名误导
- 写实现时的封印连锁：families/*.py、lifecycle.py、cert_schema.py、replay.py、benders_loop.py、exact_coordinate_master.py 全是 sha-pin 封印文件，动任何一个都要走完整 reseal 仪式（LF 字节 sha、checker 自钉最后算）；只有 oracle 与 dinic helper 在封印外
- 测试盲区会掩护回归：两族 generator 正向路径零测试（现有 'stub returns empty' 测试用空 free_cells/空 registry 构造，换了实现也照样绿）；接线时若不先补 F2-narrow-corridor / F4-disconnected 正向用例（08 plan :144-145 计划过但从未落地），validator/oracle 的漂移不会被抓
- commodity_demands.json 的 float 值（5.5 等）被 _is_strict_positive_int 静默跳过：直接拿该文件当 F2 registry 会让部分 commodity 无声消失，且『静默跳过』本身可能掩盖 schema 错配
- F4 evaluator 的 O(|Grid|) BFS 是已登记的 P1.21 必修项：接 CP-SAT propagator 热路径前不改增量算法会数量级退化
- 多处过时叙述别当真：test 文件 docstring 仍称 generator 为 stub、PROJECT_LOCK B-2 仍写 step_8 全 NotImplementedError（F1 已通电）、08 plan banner 未记 F2/F4 generator 落地——以源码为准
