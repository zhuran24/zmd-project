# DOC-ADR-020｜阶段性重构收口与常态维护交接

状态：Accepted
日期：2026-08-15

## 问题

知识脊柱、继承式 policy、事件 intake、周期审计、统一治理门与真实仓库 landing 已经形成闭环。如果收尾只存在于补丁包说明或一次聊天记录中，后续 agent 虽然能够继续操作普通文档，却不知道何时应当停止继续编号大型整理批次、怎样判断框架需要重新开启，以及外部前置条件缺失时为何必须继续阻断。

另一种风险是增加一份新的手写“系统完成状态页”。这种页面会复制版本、测试数量和环境结果，很快成为下一套易漂移真相。

## 决定

1. 在 framework core 中建立 manifest-owned 的 `STEADY_STATE.md`，只保存耐久维护合同，不复制当前 gate、测试数量、hash、研究账本或 owner 状态。
2. manifest 通过 `steady_state_guide` 提供固定坐标；`docctl guide`、doctor、section registry、架构和恢复说明共同保证它可发现、可读取、受 policy 管理。
3. 阶段性重构收口后，普通变化回到事件驱动 intake；周期审计只负责发现长期遗漏，所有修复仍写回原真源。
4. 普通积压、文档数量增长或一次较大的内容整理，不自动产生新的 Phase 或 Batch。只有改变核心 invariant、schema、resolver、authority/landing 语义或 owner 权威档案面时，才以新的独立框架迁移重新开启，并同时提供 ADR、版本、迁移和红测。
5. 历史 Git 对象、外部档案根或 owner authority 缺席时继续 fail closed。收口不能通过跳过检查、改写冻结摘要、降低 authority 或复制状态页来制造完成感。
6. 完成报告和测试收据属于交付物，不成为仓内 current truth source。仓内只保留可长期执行的维护合同和机器约束。

## 后果

- 后续 agent 能从固定入口找到“系统如何继续活下去”，而不必重新阅读整个补丁历史。
- 文档系统不会因常规维护自然长出 Batch 6、Batch 7；需要重新开启时，边界由语义变化而不是编号决定。
- 收尾没有增加新的手写状态面，当前事实仍由结构化源和生成投影负责。
- 外部环境无法复验的检查仍会诚实阻断，但阻断条件和恢复路径可被稳定发现。
